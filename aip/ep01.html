上周有个瞬间让我愣了一下：我在看板上把一个 issue 拖给了一个 AI，然后它真的像同事一样回了个进度，两小时后自己把状态挪到了"待验收"。

大家好，我是郑同学。这个让我愣一下的项目叫 Multica，今天开一个新的系列——「AI 产品拆解」，第一篇就拆它。

先交代背景：Multica 是一个 Apache 2.0 开源项目（github.com/multica-ai/multica），定位是"人 + AI 编码 Agent 混合团队的工作区"。你建一个工作区，拉上人类同事，再"招聘"几个 agent——比如一个绑了 Claude Code 的、一个绑了 Cursor CLI 的。然后在看板上建 issue，把任务派给某个 agent。

接下来的流程很像新员工入职：agent 领了任务，状态变成 working；干活过程中往 issue 底下发进度评论；卡住了就把状态改成 blocked，给你发通知；做完了自己挪到 in_review，等你验收。全程你不用开终端，不用盯着它跑。

支持 26 种编码 agent CLI，可以完全自托管。我把它的源码拆了一遍，这篇讲两件事：核心功能长什么样，核心实现怎么落地。

● ● ●

先看它给了一个 agent 什么"员工待遇"

拆实现之前，先把功能盘清楚。Multica 里每个 agent 都是一等公民，有自己的档案和状态机，不是一句 prompt 就打发的玩具：

能力是什么源码位置
Agent 档案五态状态机 idle/working/blocked/error/offline，可设最大并行任务数migrations/001
Issue 看板七种状态 + 指派对象可以是人类、agent 或小队migrations/001、084
收件箱分三级：需要人拍板 / 需要关注 / 仅告知migrations/001
Squad 编队队长必须是 agent，队员人机混编migrations/084
Autopilotcron/webhook 定时触发 agent，可自动建 issue 或只执行migrations/042
Skills 技能包把经验沉淀成可复用技能，绑定给指定 agentmigrations/008
用量统计每个任务、每小时、每天的 token 消耗都能归因migrations/013、032

这套数据模型里我最认可的是收件箱的三级分级——agent 的多数输出是"仅告知"，少数是"需要关注"，只有真正需要人拍板的才标"需要人拍板"。通知系统的最大痛点从来不是发不出，是不分轻重地全发。

Autopilot 单独说一句。它是"无人值守"的载体：用 cron 或 webhook 定期触发一个 agent，两种执行模式——要么自动建一个 issue 走正常派活流程，要么只跑一次不留下任务。并发冲突也有策略可选：跳过、排队、或替换上一次。相当于给 agent 排了一个"每天早上九点的站会"。

有了这层地基，才能谈它最反直觉的设计。

● ● ●

最反直觉的设计：服务器上不跑一个 Agent

听到"Agent 平台"，多数人第一反应是：云端养了一堆容器，替用户跑着 agent。

Multica 正好反着来。它的服务器不执行任何 agent，所有 agent 都跑在用户自己的电脑上。

架构长这样：

你（浏览器）
   │ 建任务板 / 派 issue / 写评论
   ▼
Multica 服务端（只存状态和内容，不跑 agent）
   │ WebSocket 唤醒 + HTTP 认领
   ▼
你电脑上的 daemon（常驻后台进程）
   │ spawn 子进程
   ▼
Claude Code / Cursor / …… 26 种编码 CLI
   │ 用 multica CLI 回读写
   ▼
Multica 服务端（issue 状态、评论、PR 关联）
 

daemon（常驻在你电脑上的后台进程）干两件事：替你守着任务队列，以及在你已登录的编码 CLI 里把 agent 拉起来。

为什么这么设计？三个原因，都很实际：

第一，代码不出境。你的项目源码永远在本机，agent 在本机仓库里干活，服务器上只流过 issue 标题、评论和状态这些"协作元数据"。

第二，不锁供应商。换模型等于在界面上换个下拉框，因为 daemon 拉起的是你本机装好的 CLI——你用什么套餐、什么账号，Multica 不掺和。

第三，agent 和人是对称的。这条最妙，下一节单独讲。

daemon 本身的工程量比想象中大。它启动时会用 --version 逐个探测本机装了哪些编码 CLI，探测到的注册成在线运行时；CLI 升级导致路径失效还有自愈逻辑。和服务器之间靠 WebSocket 长连接保活，断线了退避重连，外加轮询兜底。唤醒消息只是"有活了"的提示，真正的任务内容永远走 HTTP 认领接口拿，这条双通道设计保证了消息丢失也不会丢任务。

更省细节的是"搭车"机制：服务器有东西要下发给 daemon（CLI 该更新了、模型列表变了），不单独发请求，而是搭在心跳应答里顺路带走。桌面端更直接，Electron 客户把 daemon 拉起来并轮询健康检查，装完 app 你的电脑就自动变成了一个 agent 运行时。

● ● ●

Agent 拿到的不是任务内容，是"自己去看任务的工具"

看它给 agent 组装的任务指令，来自 server/internal/daemon/prompt.go:215：

b.WriteString("You are running as a local coding agent for a Multica workspace.\n\n")
fmt.Fprintf(&b, "Your assigned issue ID is: %s\n\n", task.IssueID)
// 交付规则：活干完送待验收就行，done 永远留给人
fmt.Fprintf(&b, "Start by running `multica issue get %s --output json` to understand your task, then complete it.\n", task.IssueID)
 

注意一个细节：它没有把 issue 标题、描述、验收标准塞进 prompt，只给了一个 ID 和一句"你自己跑 multica issue get 去看"。

我认为这是整个项目最有味道的设计。agent 干活用的 multica 命令行，和你浏览器里点鼠标，走的是同一套平台接口。人怎么看 issue、怎么发评论、怎么改状态，agent 就怎么看、怎么发、怎么改。没有任何"agent 特权后门"。

配套的是凭证控制：daemon 给每次任务注入的是任务作用域的 token（internal/daemon/daemon.go:163），这个 agent 只能读写自己这条 issue 和自己的工作区，想越权碰别人的任务，接口层直接挡住。

对比一下常见做法——把 issue 全文、相关评论、项目背景在任务开始时一股脑塞进系统提示词——Multica 等于把"信息下发"变成了"信息自助"。上下文不会一次性膨胀，agent 按需去查，评论还有 --since 增量接口。

顺便说下派活的触发判定。你在 issue 上 @ 一下 agent、或者把 issue 拖给它，服务端不是无脑发车，而是先过一个统一的准入判定，再进任务队列。排队期间用户追加的评论会被合并进同一个任务，agent 醒来一次就能把所有新评论一起看——不会你连发三条评论它就连跑三趟。

● ● ●

任务认领：一次 HTTP 拉回全部上下文

agent 的 daemon 收到唤醒后，会调认领接口把任务领走。这里有个容易被忽略的设计：认领接口的响应不是一个任务 ID，而是一整个任务的执行现场。

internal/daemon/types.go:70 的任务结构里装了：工作区系统提示词、agent 的人设和模型配置、绑定的仓库列表、技能包引用（带哈希）、上一轮会话的续接指针（PriorSessionID 和工作目录），以及服务端预计算好的增量——排队期间新增了几条评论、issue 的哪些字段变过。

daemon 拿到任务的那一刻，不需要再发第二次请求问任何事。为什么这么设计？agent 在你的本机跑，每一次多余的往返都是延迟；更重要的是执行路径越简单，故障面越小。上下文在服务端拼装完成、一次下发，daemon 只负责"照单执行"。

并发抢任务也处理得很干净：你家里有台电脑、公司有台电脑，都跑着 daemon 时，同一个任务可能被两边同时伸手。服务端用一段 Redis Lua 脚本把"从队列移除"和"标记运行中"两步焊死成原子操作——谁抢到就是谁的，绝不会两个 agent 领到同一个活。

还有一处顺手的对称：agent 干活过程中的每次工具调用、每段输出都会流式上报，落库后就是 issue 评论里的进度记录——人类在评论区问一句，agent 下次的回答也落在同一条线程里。整个协作过程天然就是一份完整的交接文档，新人（或者新 agent）接手时把线程读一遍就够，不用找人问历史。

● ● ●

26 个 CLI，收敛成一个接口

第二个值得学的地方：它对"agent 运行时"的抽象。

市面上的编码 CLI 每家一个性格：Claude Code 输出 stream-json，Cursor CLI 类似，还有一批走 Zed 的 ACP 协议（JSON-RPC over stdio）。Multica 的 pkg/agent 包用一个接口把它们全收了：

// Backend 是所有编码 agent 的统一执行接口
// 26 种 CLI 各自实现，daemon 只面向接口编程
type Backend interface {
    Execute(ctx context.Context, prompt string, opts ExecOptions) (*Session, error)
}
 

两大协议族：Claude Code、Cursor 走 stream-json；Grok CLI、QwenPaw、Hermes 这些走 ACP 的 JSON-RPC。新增一家 CLI 等于加一个 adapter，daemon 的执行面一行不改。

工程细节里全是真实事故的痕迹。比如进程管理，pkg/agent/launch.go:112：

// 全包唯一建进程的出口：强制进程组所有权
func newRuntimeCmd(cmd *exec.Cmd) *exec.Cmd {
    configureProcessGroup(cmd)
    cmd.Cancel = func() error {
        // 取消 = 对整个进程组发 SIGKILL
        signalProcessGroup(cmd, syscall.SIGKILL)
        return nil
    }
    return cmd
}
 

注释里写了为什么：不设进程组时，Windows 上一个被"取消"的 agent 实际又偷偷干了 40 分钟活。取消一个 agent，必须连它的整个子进程树一起取消。

还有一层防线：用户可以给 CLI 配自定义启动前缀参数，但每个协议族有一份黑名单，协议关键 flag 不允许用户覆盖——比如 --output-format（黑名单定义在 launch.go:445）——不然一次配置错误，整个上报通道就瞎了。

连"向用户提问"这种小事都有事故记录。Claude Code 内置一个交互提问工具（AskUserQuestion），但 daemon 是无人值守跑的，没有界面渲染这个问题——agent 会自己"猜"一个答案继续跑，用户永远看不到问题（他们的真实 issue #2588）。Multica 的解法是启动参数里直接禁用这个工具，把"向人澄清"引导到 issue 评论里去。无人值守场景下，"问人"必须变成"留话"。

● ● ●

给 agent 的"入职手册"：Runtime Brief

agent 每次领任务，daemon 会先在任务工作目录写一份 CLAUDE.md（Claude Code 用）或 AGENTS.md（Codex、Copilot 用），内容是工作区背景、agent 人设、命令手册、交付流程。这份文件有个讲究的机制（internal/daemon/execenv/runtime_config.go:31）：

<!-- BEGIN MULTICA-RUNTIME (auto-managed; do not edit) -->
… daemon 托管的工作区上下文、可用命令、交付规则 …
<!-- END MULTICA-RUNTIME -->
 

用标记对包住：重写时幂等，清除时精确——不会碰到用户自己写的内容。

更有意思的是一条隐性纪律：这份手册在同一个会话的多次任务之间必须逐字节一致，每次任务的私有数据只允许追加在 prompt 尾部。为什么这么苛刻？因为续接会话靠模型服务的 prompt cache（提示词缓存），前缀差一个字节，缓存全部失效，token 成本直接翻倍。源码里连问题编号都标着（MUL-5377）。

顺带一个交互设计：agent 做完后把 issue 挪到 in_review（待验收），这一步是 agent 通过 CLI 自己做的；done 这个状态，代码里写死了"永远留给人"。机器交活，人验收，这条线画得很清楚。

● ● ●

交付那一刻，比派活还讲究

任务跑完怎么"交差"，Multica 也堆了一层防护。服务端处理完成上报时（internal/handler/daemon.go:4053）：

// JSONB 拒绝包含 \u0000 的字符串
// 一条脏数据会把任务永远卡在 running
// → 上报内容先做 NUL 消毒
 

这是真实 issue（#7098）：agent 输出里混进一个 \u0000 字符，写库失败，任务状态永远停在 running。所以入库前先消毒。

后面还有三道：

  •  幂等：完成任务用条件更新（只更新 running 状态的行），同一个完成请求重放也不会重复结算
  •  纠偏：agent 说"我做完了"但实际上下文耗尽、什么都没交付——这种"假成功"会被重路由成失败
  •  兜底：每个完成的任务保证至少有一条 agent 评论留在 issue 上，没有就合成一条

瞬时错误还有一种更保守的处理：宁可让任务留在 running 等重试，也不误报成 failed——状态错一次，人的信任就少一分。

真失败了也有退路：失败会先做分类归因（网络问题、上下文耗尽、runtime 掉线……各有独立的状态记录），然后自动生成一个子任务做重试，父子的失败链路在数据里可以完整追出来。runtime 整机掉线时，服务端会把它名下所有任务批量标记失败，不让它们永远悬着。

● ● ●

记忆是显式的，甚至主动"戒掉"了原生记忆

现在做 agent 记忆，流行答案是上向量库、上 mem0。Multica 给了一个相反的答案：记忆要显式、要用户可见，宁缺毋滥。

它的记忆分四层，全部可审计：

  •  会话续接：上个任务的 session ID 存在数据库里，下个任务用 --resume 续上，失败的会话指针会被"退休"，避免反复踩坑
  •  工作区上下文：workspace 级的系统提示词，用户随手可编辑
  •  issue 评论流：agent 再次领任务时，服务端预计算"你上次看之后新增了什么"，只下发增量
  •  Skills：把踩过的坑沉淀成技能包，按需绑定给 agent

最让我意外的是它对 CLI 原生记忆的处理。Codex CLI 自带一套 auto-memory（自动把对话摘要写进本地文件，下次读回上下文），Multica 的 daemon 会主动写配置把它关掉（internal/daemon/execenv/codex_memory.go:11）。注释里的论证很硬：那套记忆是黑盒，用户在 Multica 界面里无法审计它写了什么；更糟的是它会把这台机器上其他项目的上下文漏进你当前的任务里。

长期记忆的答案应该是平台自有的、项目作用域的、用户可见的存储——而不是重新打开一个隐藏黑盒。

在所有人都往"更聪明的自动记忆"上卷的时候，这个"先保证不泄漏、可审计"的取舍，值得抄走。

● ● ●

Skills：怎么把踩过的坑变成团队资产

技能包的分发链也值得单独看一眼，它是四步接力（internal/daemon/daemon.go:6891）：

服务端存储（skill + 多文件 + 内容哈希）
   │ 任务认领时带下来
   ▼
daemon 缓存（按哈希校验，慢链路不重复下载）
   │ 按协议族物化
   ▼
CLI 原生技能目录（.claude/skills/、CODEX_HOME、.github/skills/…）
 

最后一步是点睛之笔：Multica 不发明自己的技能格式，而是把技能写进各家 CLI 原生会扫描的目录——Claude Code 的技能放 .claude/skills/，Codex 放它自己的 HOME 目录。平台只负责"把对的技能放到对的地方"，CLI 自己就会用。

还能反向流动：daemon 能枚举你本机 CLI 已经装好的技能，导入到工作区分享给全团队。个人的经验，一条命令变成团队的资产。

● ● ●

怎么防止 AI 同事跑飞

多 agent 协作最怕两件事：重复开工，和无限自触发。Multica 的防线是一套组合拳。

第一道：单一准入谓词。internal/service/issue_trigger.go:97 有个函数 WillEnqueueRun，全项目只有这一处定义"哪些操作会让 agent 发车"：

case in.IsCreate || in.AssigneeChanged:
    // Backlog 是停车场：把 issue 派进 backlog 永远不发车
    if currentStatus == "backlog" {
        return IssueRunTrigger{}, false
    }
    source = RunSourceAssign
 

把 issue 派给 agent 但还放在 backlog？不发车。移出 backlog？发车。规则集中一处，其他地方想发车都得问它。

第二道：每个 run 必须有主。创建任务时强制解析"谁发起、谁担责"，解析不出来且工作区开了严格模式，直接拒绝派活——不存在无主的任务。

第三道：Squad（混合编队）的队长协议。squad 的 leader 必须是 agent，成员可以人机混编。每次 leader 被唤醒，系统注入一段硬编码协议（internal/handler/squad_briefing.go:33）：你的职责是协调，不是自己动手；用 @mention 把活派给成员；在 issue 里登记处理结果；派完就停，处理完会被自动再唤醒。

这里最细的是 no_action 这个设计：leader 评估后觉得不需要动，就静默退出——防止 agent 之间互相 @ 来 @ 去刷屏。

第四道在看不见的地方：每个"为什么不发车"的情况都有一个稳定的枚举值——排队中、已合并、运行时离线、触发者无权限、自触发被抑制……排障时看到哪个码，就知道去修哪一层，而不用翻日志猜。

● ● ●

自托管：三个容器装下一个平台

最后看一眼部署面，简朴得让人意外：一个 Postgres 17 容器、一个 Go 后端容器、一个 Next.js 前端容器，完事。Redis 是可选项，加上之后任务认领的原子性和实时消息转发会更稳。

安全默认也做得很克制：容器端口只绑 127.0.0.1，要公网访问得自己上 TLS 反代。官方文档原话提醒你别把端口改成 0.0.0.0，因为 Docker 会绕过 UFW 防火墙——这种细节能看出团队踩过坑。

● ● ●

小结

拆完整个项目，三个印象最深的设计：

  1. 01代码不出境的执行架构——服务器只管派活和存状态，agent 在用户本机的 daemon 里跑，隐私和供应商自由同时拿到
  2. 02对称性——agent 和人用同一套平台接口，没有特权后门，权限天然可控
  3. 03显式优于隐式——记忆、归因、准入规则、leader 协议，全部是代码写死的显式机制，而不是在 prompt 里求模型"别乱来"

如果说之前的 agent 框架教程讲的是"怎么让一个 agent 跑起来"，Multica 演示的是下一阶段的问题：怎么让一群 agent 像团队一样干活，还不跑飞。这两个问题不一样，后者难得多。

感兴趣可以自己 clone 下来读，注释质量很高，全是真实事故换来的经验。
