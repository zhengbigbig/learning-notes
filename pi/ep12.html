大家好我是郑同学。前十一篇拆完了 Pi 的全部核心模块和测试工具。最后一个问题：你怎么知道 AI Agent 真的做对了任务？

程序跑完——Agent Loop 正常退出，没有报错——不代表任务做对。模型可能调了错误的工具，文件可能没改成预期内容，工具结果可能没正确配对。「没崩」和「做对」是两件事。

独立评测层是纯测试工具，不是运行时组件。它放在 test-support/eval.ts 目录下，只在测试文件里被调用，实际运行时不存在。它做的事是在代码测试时，跑完一个任务后独立检查结果对不对——不是运行态的前置检验，而是测试态的后置判定。

● ● ●

评测的三层分离

评测层把一次 eval run 分成三个独立阶段，每个阶段有自己的失败类型：

// eval.ts:54-58

export type EvalStatus =

  | "passed"           // 任务通过

  | "task_failed"      // 任务没做对（judge 拒绝）

  | "protocol_failed"  // 消息协议违反

  | "infra_failed";    // 基础设施错误（prepare/execute/dispose 挂了）

 

四态而非两态。不是简单的 pass/fail——protocol 挂了和 task 挂了是完全不同的问题。protocol_failed 说明 Agent 的消息结构本身有问题（工具调用没配对、缺少用户消息），task_failed 说明消息结构没问题但任务结果不对。

● ● ●

EvalCase：每个测试用例的契约

每个评测用例是一个 EvalCase，定义三个回调：

// eval.ts:46-52

export interface EvalCase {

  id: string;

  prompt: string;

  files: readonly string[];       // 要检查的文件列表

  prepare(): Awaitable<PreparedEval>;  // 准备环境（创建 Runtime）

  judge(observation: EvalObservation): Awaitable<TaskVerdict>;  // 判定结果

}

 

prepare 负责搭环境——创建 Runtime、写入初始文件、返回一个 readFile 函数让评测层读取结果。judge 负责判定——拿到观察数据后返回通过或失败。

两个回调完全隔离。prepare 不知道 judge 会检查什么，judge 拿到的是冻结的观察数据（deepFreeze），不能修改。

● ● ●

runEvalCase：一条流水线

评测的核心是 runEvalCase，一条严格的流水线：

// eval.ts:359-380（核心骨架）

export async function runEvalCase(evalCase: EvalCase): Promise<EvalReport> {

  // 1. 校验 case 本身合法性

  if (!caseIsValid(evalCase)) {

    return reportWith(evalCase, evidence, "infra_failed",

      failure("prepare", "invalid_case"));

  }

 

  // 2. prepare：搭建环境

  prepared = await evalCase.prepare();

  runtime = prepared.runtime;

 

  // 3. execute：执行 prompt

  result = await runtime.prompt(evalCase.prompt);

  await runtime.flush();

 

  // 4. collect：收集 session entries

  allEntries = await runtime.session.entries();

 

  // 5. protocol：检查消息协议

  activeEntries = pathTo(allEntries, leafId);

  assertProtocol(activeEntries);

 

  // 6. judge：判定任务结果

  const observation = frozenObservation(result, activeEntries, files);

  verdict = await evalCase.judge(observation);

 

  // 7. dispose + cleanup

  await runtime.dispose();

  await prepared.cleanup();

 

  return report;

}

 

每一步都有 try-catch，失败立即返回对应类型的 EvalReport。prepare 挂了报 infra_failed，execute 挂了也报 infra_failed，protocol 检查不过报 protocol_failed，judge 拒绝报 task_failed。后一步的错误不能覆盖前一步的事实。

● ● ●

assertProtocol：消息协议检查

这是评测层最核心的检查。Agent 跑完后，评测层遍历整条消息链，验证每一条消息的合法性：

// eval.ts:190-260（核心骨架）

function assertProtocol(entries: readonly SessionEntry[]): void {

  const calls = new Map<string, { name: string; matched: boolean }>();

  let sawUser = false;

 

  for (const message of messages) {

    if (message.role === "user") {

      // 检查：上一个 interaction 的工具调用是否都已配对

      if ([...calls.values()].some(c => !c.matched))

        throw new ProtocolViolation("unpaired_tool_call");

      sawUser = true;

      continue;

    }

    if (message.role === "assistant") {

      // 助手消息前必须有用户消息

      if (!sawUser)

        throw new ProtocolViolation("assistant_without_user");

      // 记录工具调用

      for (const call of toolCalls(message)) {

        if (calls.has(call.id))

          throw new ProtocolViolation("duplicate_tool_call");

        calls.set(call.id, { name: call.name, matched: false });

      }

      continue;

    }

    // toolResult：必须匹配一个已有的 toolCall

    const call = calls.get(message.toolCallId);

    if (!call) throw new ProtocolViolation("orphan_tool_result");

    if (call.matched) throw new ProtocolViolation("duplicate_tool_result");

    if (call.name !== message.toolName)

      throw new ProtocolViolation("tool_name_mismatch");

    call.matched = true;

  }

}

 

十种协议违规，覆盖所有可能的消息结构问题：

  •  assistant_without_user——助手消息前面没有用户消息
  •  tool_call_without_user——工具调用前面没有用户消息
  •  duplicate_tool_call——同一个 callId 出现两次
  •  orphan_tool_result——工具结果找不到对应的工具调用
  •  duplicate_tool_result——一个工具调用有两个结果
  •  tool_name_mismatch——工具调用和结果的工具名不一致
  •  unpaired_tool_call——交互结束时还有未配对的工具调用
  •  missing_user_interaction——整条链没有用户消息
  •  incomplete_user_interaction——交互没有助手回复

这些检查不是测试 Agent 的业务逻辑，是测试消息结构本身。EP03 讲的消息类型系统（user/assistant/toolResult）在这里被严格验证。

● ● ●

SafeEvidence：只暴露安全的统计数据

评测报告里不包含原始消息内容，只暴露计数统计：

// eval.ts:102-121

export interface SafeEvidence {

  messages: { user: number; assistant: number; toolResult: number };

  tools: { calls: number; results: number; errors: number };

  files: { requested: number; read: number };

  checks: { passed: number; failed: number };

}

 

外部 Error 的 message、cause、stack 不能越过评测边界。评测层只保留自己定义的固定枚举（EvalFailureCode）。这防止敏感信息泄露到报告里。

● ● ●

冻结观察数据

judge 拿到的 EvalObservation 是深度冻结的：

// eval.ts:320-326

function frozenObservation(result, entries, files): EvalObservation {

  return deepFreeze(structuredClone({ result, entries, files }));

}

 

deepFreeze + structuredClone——先深拷贝（切断引用），再递归冻结（不能修改）。judge 函数不能篡改观察数据来伪造通过。

● ● ●

held-out capstone：防作弊设计

评测的最后一层是held-out capstone——Lab 14.4 的三项测试只存在于 target 和最终 full gate，practice 14 不会复制它们。

这些测试会更换 case id、prompt、路径、callId 和故障参数。陪练 agent 只能根据公开契约解释失败，不能读取或转述 held-out 测试内容。

这是防作弊设计——如果练习环境里有全部测试，学习者可以对着测试写代码。held-out 测试确保学习者真正理解了原理，而不是背答案。

● ● ●

对比真实 CC 的测试

CC 的测试在 test/suite/ 目录下。

① 测试架构

Pi 用独立的 runEvalCase 流水线，四态报告（passed/task_failed/protocol_failed/infra_failed）。CC 用 vitest + harness.ts——每个测试文件独立运行，harness 提供 faux provider 和 session 断言。

② 协议检查

Pi 的 assertProtocol 遍历整条消息链检查十种违规。CC 也有类似检查，但分散在各个测试用例里——没有集中的协议验证函数。

③ 评测 vs 单测

Pi 的 eval 层是独立于单元测试的——它不测某个函数的行为，测的是整个 Runtime 的端到端表现。CC 的 test/suite 也是端到端测试，但 CC 没有 Pi 这种四态报告 + SafeEvidence 的结构化评测框架。

两边目标一致：程序跑完不等于任务做对。Pi 用更结构化的方式把两者分开。

● ● ●

小结

设计决策选择为什么
评测四态passed/task_failed/protocol_failed/infra_failed区分任务错和结构错
case 契约prepare + judge 分离搭环境和判定结果隔离
协议检查assertProtocol 十种违规验证消息结构合法性
证据安全SafeEvidence 只暴露计数防敏感信息泄露
观察冻结deepFreeze + structuredClonejudge 不能篡改数据
held-out隐藏测试换参数防背答案

口诀：四态分错误，prepare搭judge判，十种协议查结构，证据只留数，观察冻住不让改，held-out防作弊。
