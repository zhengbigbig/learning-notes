Agent 框架要真正有用，光有循环和工具还不够。你得让用户能往里塞东西——项目规范、技能包、自定义工具、拦截器。这些东西怎么进系统？进来之后谁先谁后？万一代码本身有恶意怎么办？

这一节拆 Pi 的资源与扩展系统，全在 src/resources.ts 里，862 行。课程 Checkpoint 12 把它分成两块：资源发现（skills、instructions、templates 怎么被扫描和去重）和扩展加载（第三方代码怎么安全地注册工具和拦截器）。

两者共享同一个信任模型——先校验身份，再决定放不放进来。

● ● ●

skill discovery：先看身份证，再看正文

Agent 启动时要扫描多个 root 目录，把里面的 skills、instructions、templates 收集成一个 catalog。但这里有个关键取舍：skill 的正文很长，全读进来浪费内存；只在需要时才读，又得先知道它叫什么、干什么用。

Pi 的答案是分两遍读。第一遍只读 frontmatter（YAML 头），第二遍激活时才读全文。

readFrontmatterOnly（第 146-162 行）是第一遍的实现：

async function readFrontmatterOnly(file: string): Promise<Frontmatter> {
  const handle = await open(file, "r");
  try {
    // 只读前 64KB，绝大多数 frontmatter 都在这个范围内
    const buffer = Buffer.alloc(64 * 1024);
    const { bytesRead } = await handle.read(
      buffer,
      0,
      buffer.length,
      0,
    );
    const prefix = buffer.subarray(0, bytesRead).toString("utf8");
    const parsed = parseFrontmatter(prefix, file);
    // body 主动置空，不返回正文
    return { attributes: parsed.attributes, body: "" };
  } finally {
    await handle.close();
  }
}
 

注意它分配了固定 64KB 的 buffer，从文件开头读一次就停。绝大多数 skill 的 frontmatter 不会超过这个大小，但正文可能有好几 KB 甚至几十 KB。discovery 阶段只需要 name 和 description，所以 body 直接置空返回。

这带来一个直接好处：扫描 100 个 skill 时，磁盘 IO 和内存占用只有全量读取的几十分之一。而且因为是固定 buffer，文件再大也不会读到尾部——读取时间可预测，不会被超大 skill 卡住。

等到真正要用某个 skill 时，才走 activateSkill（第 353-390 行）读全文：

export async function activateSkill(
  catalog: ResourceCatalog,
  name: string,
  options: ActivateSkillOptions = {},
): Promise<ActivatedSkill> {
  const skill = catalog.skills.find((candidate) => candidate.name === name);
  if (!skill) throw new Error(skill 不存在：${name});
 
  const source = await realpath(skill.source);
  // 校验路径没逃出 skill 自己的 root
  assertWithin(skill.root, source, skill ${name});
  const parsed = parseFrontmatter(await readFile(source, "utf8"), source);
  // 二次校验：激活时的 name 必须和 discovery 时一致
  const currentName =
    parsed.attributes.name ?? path.basename(skill.root);
  if (currentName !== skill.name) {
    throw new Error(
      skill ${name} 激活时身份变成了 ${currentName},
    );
  }
  // ...读取附加 resources
}
 

这里有个细节值得停一下。discovery 时读的是 frontmatter 里的 name，激活时又读了一次全文重新解析 name，两次必须一致。为什么要查两遍？因为文件可能在这段时间被改过。如果在 discovery 之后、激活之前，有人把 skill 的 name 改了，catalog 里登记的还是旧名字——激活时就会报错「身份变成了 XXX」。

这是防御性编程的典型场景：discovery 的结果不能当永恒真相，跨时间点用到的数据要重新校验。

注意激活时还会校验路径——assertWithin(skill.root, source, ...) 确保 realpath 之后路径没有逃出 skill 自己的 root。这是防符号链接逃逸攻击的硬约束：如果有人在 skill 目录里放了个软链指向 /etc/passwd，realpath 会解析出真实路径，assertWithin 一看不在 root 内就直接抛错。

● ● ●

资源优先级：先来后到，kind:name 判冲突

多个 root 目录可能有同名资源——两个 root 都叫 AGENTS 的 instructions，或者都叫 git-helper 的 skill。谁赢？

discoverResources（第 305-334 行）的策略是先出现者获胜：

export async function discoverResources(
  roots: readonly string[],
): Promise<ResourceCatalog> {
  const winners = new Map<string, Candidate>();
  for (const [rootOrder, root] of roots.entries()) {
    for (const candidate of await discoverRoot(root, rootOrder)) {
      const key = resourceKey(candidate.resource);
      // 只有 Map 里还没有这个 key 才写入
      if (!winners.has(key)) winners.set(key, candidate);
    }
  }
  // ...
}
 

resourceKey（第 182-184 行）决定什么叫「冲突」：

function resourceKey(resource: CatalogResource): string {
  return ${resource.kind}:${resource.name};
}
 

冲突判断只看 kind 和 name，不看路径。也就是说，skill:git-helper 在 root A 和 root B 里都存在，就视为冲突；但 template:git-helper 和 skill:git-helper 不冲突，因为 kind 不同。这种设计让不同类型的资源可以共享同一个简短名字，不会互相踩踏。

注意一个细节：同一个 root 内部如果出现重复，会直接抛错（第 287-297 行）；但跨 root 的重复是「先来后到」的覆盖，不报错。内部冲突是 bug，外部冲突是配置——这是两种完全不同的处理态度。内部的 bug 应该立即暴露给开发者去修，跨 root 的覆盖则是用户有意识的选择。

roots 数组的顺序就是优先级，文档注释（第 301-304 行）写得很直白：「roots 的输入顺序就是 precedence。冲突按 kind+name 判断，先出现的 root 获胜。」这让「哪个 root 优先」变成了显式的配置项，而不是隐式的文件系统顺序。

● ● ●

resourceOrder：instructions 在前，templates 垫底

去重之后，catalog 里的资源要排个序。排序不仅影响展示，也影响 system prompt 里知识出现的先后——靠前的知识模型会更早「看到」。

sortResources（第 192-200 行）调用 resourceOrder（第 186-190 行）做排序：

function resourceOrder(resource: CatalogResource): number {
  if (resource.kind === "instructions") return 0;
  if (resource.kind === "skill") return 1;
  return 2;
}
 
function sortResources(
  resources: readonly CatalogResource[],
): CatalogResource[] {
  return [...resources].sort(
    (left, right) =>
      // 先按 kind 的固定顺序排
      resourceOrder(left) - resourceOrder(right) ||
      // 同 kind 内按 name 字母序排
      compareText(left.name, right.name),
  );
}
 

排序规则是两层：先按 kind 的固定优先级——instructions（0）→ skill（1）→ template（2），同 kind 内再按 name 字母序。

为什么是 instructions 在最前？因为它是项目级的硬性规范。AGENTS.md 这类文件定义的是「这个项目必须怎么做」，优先级最高；skill 是「需要时才用的能力」，中等；template 是「填充模板」，最后。这个顺序符合「规则先于能力，能力先于格式」的认知优先级。

同 kind 内按 name 字母序排序，保证了「相同输入永远得到相同输出」——排序结果不依赖文件系统返回的顺序，也不依赖扫描时的随机时序。确定性排序让 catalog 可复现、可测试。如果同 kind 资源乱序，每次启动 system prompt 里知识的排布都不同，模型行为就不稳定了。

● ● ●

扩展原子注册：factory 抛错，一个 tool 都别想漏进去

资源系统讲完了，下面是更危险的部分——加载第三方代码。

用户可能写了个扩展模块，里面注册了 3 个工具和 2 个拦截器。如果加载到一半失败了——比如注册第 2 个工具时发现重名——怎么办？最糟的情况是「注册了 1 个就半死不活」，系统里残留一个不完整的扩展。

Pi 用 staging + commit 两阶段来保证原子性。stage 方法（第 633-711 行）创建一个临时上下文，所有注册操作先写进临时数组：

stage(extensionId: string): StagedRegistration {
  if (
    extensionId.trim() === "" ||
    this.extensionIds.has(extensionId)
  ) {
    throw new Error(extension id 无效或重复：${extensionId});
  }
  // 全是临时数组，还没碰真正的 registry
  const tools: StagedTool[] = [];
  const toolNames = new Set<string>();
  const beforeHooks: BeforeToolCallHook[] = [];
  const afterHooks: AfterToolResultHook[] = [];
  let committed = false;
 
  const context: ExtensionContext = {
    registerTool: <TParameters, TDetails>(
      source: Tool<TParameters, TDetails>,
    ): void => {
      const name = source.name;
      if (name.trim() === "" || toolNames.has(name)) {
        throw new Error(Tool 已存在：${name});
      }
      toolNames.add(name);
      // 包装一层 execute，再 push 到临时数组
      const tool: Tool = {
        name,
        description: source.description,
        schema: source.schema,
        execute: (parameters, toolContext) =>
          source.execute(parameters as TParameters, toolContext),
      };
      tools.push({ name, tool });
    },
    on: (hook, listener): void => {
      // hook 也先进临时数组
      if (hook === "beforeToolCall") {
        beforeHooks.push(listener as BeforeToolCallHook);
      } else if (hook === "afterToolResult") {
        afterHooks.push(listener as AfterToolResultHook);
      } else {
        throw new Error(extension hook 不存在：${String(hook)});
      }
    },
  };
 
  return { context, commit: (): void => { /* ... */ } };
}
 

context.registerTool 往 tools 临时数组里 push，context.on 往 beforeHooks/afterHooks 里 push——这些操作完全不碰真正的 registry 和 host 的 hook 列表。factory 看到的 context 是个隔离沙箱，它注册的任何东西都还没生效。

真正的提交在 commit 方法（第 680-709 行）里，一次性完成：

commit: (): void => {
  if (committed) {
    throw new Error(extension ${extensionId} 已提交);
  }
  if (this.extensionIds.has(extensionId)) {
    throw new Error(extension id 重复：${extensionId});
  }
  // 提交前再查一遍重名，防止并发提交撞车
  for (const staged of tools) {
    if (this.registry.get(staged.name)) {
      throw new Error(Tool 已存在：${staged.name});
    }
  }
  // 全部校验通过，一次性注册
  for (const staged of tools) {
    this.registry.register(staged.tool);
  }
  this.beforeHooks.push(
    ...beforeHooks.map((listener) => ({ extensionId, listener })),
  );
  this.afterHooks.push(
    ...afterHooks.map((listener) => ({ extensionId, listener })),
  );
  this.extensionIds.add(extensionId);
  committed = true;
},
 

commit 分两段：先循环检查所有 tool 名字在 registry 里都没冲突，再循环一次性注册全部。如果第一段循环里发现重名就抛错，第二段循环根本不会执行——registry 一个 tool 都没多。

这个「先全查再全注册」的顺序很关键。如果改成「边查边注册」，第一个注册成功、第二个发现重名抛错，第一个就漏在 registry 里了。原子性的本质就是：要么全进，要么一个不进。这就是数据库事务的 commit 语义在内存里的翻版。

loadExtension（第 829-861 行）把信任门和这两阶段串起来：

export async function loadExtension(
  source: ExtensionSource,
  options: LoadExtensionOptions,
): Promise<LoadExtensionResult> {
  if (source.id.trim() === "" || source.path.trim() === "") {
    throw new Error("extension source 缺少 id 或 path");
  }
  // 信任门：先问 isTrusted，不信任直接跳过
  const trusted = await options.isTrusted(frozenClone(source));
  if (!trusted) {
    return structuredClone({
      id: source.id,
      status: "skipped_untrusted" as const,
    });
  }
 
  const imported = await options.importModule(frozenClone(source));
  // ...校验 default factory 存在
  const factory = imported.default as ExtensionModule["default"];
  // 拿到 staging context
  const staged = hostImplementation(options.host).stage(source.id);
  // 执行 factory：所有注册都进临时数组
  await factory(staged.context);
  // factory 没抛错才 commit
  staged.commit();
  return structuredClone({ id: source.id, status: "active" as const });
}
 

顺序是：先 isTrusted 把关 → 通过才 importModule → 拿到 factory → 在 staging context 上跑 factory → factory 全程没抛错才 commit。如果 factory 里任何一步抛错（重名 tool、参数非法、第三方代码 bug），commit 永远不会执行，registry 干干净净。不信任的代码连 import 都不会触发，更别说执行。

注释（第 825-828 行）一句话点题：「trust gate 先于 import。factory 只接触 staging context；成功返回后才把 tools/hooks 一次提交到 host。」

● ● ●

hook 故障隔离：拒绝、抛错、超时走同一条出口

扩展可以注册 beforeToolCall hook 来拦截工具调用——比如禁止某些危险操作，或强制加参数。但 hook 是第三方代码，它可能出 bug：可能抛异常，可能卡死不返回。

Pi 的态度是：hook 出问题不能把整个 Agent 拖死。所有故障情况都要被捕获，统一转化成「这个工具被拦截了」的结果。

before 方法（第 721-767 行）就是这套故障隔离的核心：

private async before(
  call: ToolCall,
): Promise<ToolResultMessage | undefined> {
  for (const hook of this.beforeHooks) {
    let decision: void | BeforeToolDecision;
    try {
      // 用 withTimeout 包住 hook 调用
      decision = await withTimeout(
        Promise.resolve().then(() =>
          hook.listener(frozenClone(call))
        ),
        this.options.hookTimeoutMs,
        beforeToolCall:${hook.extensionId},
      );
      // 返回值只能是 allow / deny / undefined
      if (
        decision !== undefined &&
        decision.decision !== "allow" &&
        decision.decision !== "deny"
      ) {
        throw new Error("beforeToolCall 返回了未知 decision");
      }
    } catch (error) {
      const timeout = error instanceof HookTimeoutError;
      const message = errorMessage(error);
      // 报告诊断信息（但不停机）
      this.diagnostic({
        extensionId: hook.extensionId,
        hook: "beforeToolCall",
        kind: timeout ? "timeout" : "error",
        message,
      });
      // 统一返回 blockedResult
      return blockedResult(
        call,
        hook.extensionId,
        timeout ? "timeout" : "error",
        message,
      );
    }
    if (decision?.decision === "deny") {
      return blockedResult(
        call,
        hook.extensionId,
        "deny",
        decision.reason,
      );
    }
  }
  return undefined;
}
 

三种故障情况被同一个 try/catch 兜住：

第一种，hook 主动 deny（返回 { decision: "deny", reason: ... }）——走 blockedResult(... "deny" ...)。

第二种，hook 抛异常——被 catch 捕获，标记 kind: "error"，走 blockedResult(... "error" ...)。

第三种，hook 超时——withTimeout 用 Promise.race 抛出 HookTimeoutError，同样被 catch 捕获，标记 kind: "timeout"，走 blockedResult(... "timeout" ...)。

三种情况全部返回 blockedResult（第 598-621 行），它构造一条带 isError: true 的 tool result，把拦截原因写进 content 和 details：

function blockedResult(
  call: ToolCall,
  extensionId: string,
  kind: "deny" | "error" | "timeout",
  reason: string,
): ToolResultMessage {
  return {
    role: "toolResult",
    toolCallId: call.id,
    toolName: call.name,
    content: [
      text(
        Tool ${call.name} blocked by ${extensionId}: ${reason},
      ),
    ],
    details: {
      blockedByExtension: extensionId,
      kind,
      reason,
    },
    isError: true,
    timestamp: Date.now(),
  };
}
 

模型看到的是一条结构化的错误结果，和工具本身执行失败长得一样。hook 故障和工具故障在模型眼里没区别，都是「这个工具调用没成功，原因写在 result 里」。这避免了模型被底层异常信息搞糊涂，模型只需要根据 isError 和 content 决定下一步，不需要区分「hook 挂了」和「工具自己挂了」。

diagnostic 方法（第 713-719 行）额外把故障报告给宿主的 onDiagnostic 回调，但用 try/catch 包住——「诊断观察者不能改变工具事实」。诊断是旁路，不能影响主流程。诊断回调本身抛错了也被静默吞掉，绝不让观察者拖垮核心循环。

● ● ●

wrapExecutor：把拦截包在核心执行器外层

前面几块讲完了「资源怎么发现」「扩展怎么注册」「hook 怎么隔离」，最后要把它们串起来——让每次工具调用都自动经过 hook 层。

wrapExecutor（第 790-802 行）就是串联的胶水：

wrapExecutor(coreExecutor: ToolExecutor): ToolExecutor {
  return async (sourceCall, context = {}) => {
    // 深拷贝入参，防止 hook 改原对象
    const call = structuredClone(sourceCall);
    // 先跑所有 beforeToolCall hook
    const blocked = await this.before(call);
    // 被拦截就直接返回 blockedResult，不碰 coreExecutor
    if (blocked) return structuredClone(blocked);
 
    // 没被拦截，跑真正的工具
    const coreResult = structuredClone(
      await coreExecutor(structuredClone(call), context),
    );
    // 跑所有 afterToolResult hook（只观察，不拦截）
    await this.after(coreResult);
    // 返回前再深拷贝，防止 hook 留下引用
    return structuredClone(coreResult);
  };
}
 

这个返回的新 executor 包装在 coreExecutor 外面，调用顺序是：before hook → core executor → after hook。

wrapExecutor 是装饰器模式的典型应用——它不改 core executor 的任何代码，只是在外面套了一层拦截逻辑。对调用方来说，拿到的还是一个 ToolExecutor，接口完全一样，但行为已经被增强了。调用方完全感知不到中间有 hook 层，它只知道调用工具拿到结果。

注意里面频繁出现的 structuredClone——入参 clone 一次给 before hook，clone 一次给 core executor，结果 clone 一次给 after hook，最后再 clone 一次返回。hook 拿到的永远是副本，改了也不影响原始数据。这是把「不可变数据」原则强制施加给第三方代码，你不信任它，就不给它修改的权力。

frozenClone（第 573-575 行）更进一步，把副本也冻住——Object.freeze 递归作用到所有子对象。hook 拿到一个冻结的对象，想改属性直接报错。从「拿到副本改了没用」升级到「想改就崩」，把防御等级又提了一档。

● ● ●

串联：一次完整的工具调用经过什么

把上面几块拼起来，看一次工具调用从触发到返回的全过程：

模型发起 tool call
    ↓
wrapExecutor 接到 sourceCall
    ↓
structuredClone(call) → before(call)
    ↓
before 遍历所有 beforeToolCall hook：
  - hook A：allow（放行）
  - hook B：deny（拦截）→ blockedResult → 直接返回
    ↓ （全部 allow 才继续）
coreExecutor(call) → 真正执行工具，拿 coreResult
    ↓
structuredClone(coreResult) → after(coreResult)
    ↓
after 遍历所有 afterToolResult hook（只观察，故障被 catch 吞掉）
    ↓
structuredClone(coreResult) → 返回给调用方
 

整个链条里，任何一环出问题都不会让数据错乱：before hook 拦截了就不碰 core，core 抛错了 after 就不跑，after hook 出故障了 coreResult 照样返回。每一层都有隔离，每一层都有副本。

这背后是一个清晰的设计原则：信任边界划清楚，不可信代码只能在沙箱里动副本。资源发现时校验身份和路径，扩展加载时走 trust gate + 原子提交，hook 执行时包超时 + 故障兜底——三道关，层层递进。每一道关都假设上一道可能失守，自己再加一层防线。
