整个 Pi 系列拆完，回头看，TypeScript 的类型系统不只是在「防 bug」——它在做一件更大的事：把 Agent 的不变量直接写进类型定义，让类型本身成为可执行的文档。

这篇把 Pi 里最有代表性的四个类型设计拎出来，看它们各自守住了什么不变量。

● ● ●

一、tagged union：事件类型不串台

Pi 的事件系统用 tagged union——每种事件带一个 type 标签：

export type DemoEvent =
  | { type: "started"; requestId: string }
  | { type: "delta"; requestId: string; text: string }
  | { type: "finished"; requestId: string; reason: "stop" | "length" }
  | { type: "aborted"; requestId: string };
 

标签做了两件事：

第一，类型缩小。写 case "delta" 时，TypeScript 自动知道 event.text 存在。不需要运行时检查，不需要 as any。

第二，字段隔离。delta 有 text，finished 有 reason。拿 finished 的事件去读 text？编译不过。

对比 CC 的 Python 版：

# CC 用 dict，没有类型约束
event = {"type": "delta", "requestId": "r1", "text": "hello"}
# 如果 event["type"] 是 "finished"，event["text"] 会 KeyError
# 但你只在运行时才知道
 

类型在编译期守住的不变量，运行期就不用再查。

● ● ●

二、never 穷尽检查：少写一个 case 编译就不过

formatEvent 函数用 switch 处理四种事件。default 分支里有一个看似无用的赋值：

export function formatEvent(event: DemoEvent): string {
  switch (event.type) {
    case "started": return start ${event.requestId};
    case "delta": return delta ${event.requestId} ${event.text};
    case "finished": return finish ${event.requestId} ${event.reason};
    case "aborted": return abort ${event.requestId};
    default: {
      const unreachable: never = event;
      return unreachable;
    }
  }
}
 

const unreachable: never = event 看起来什么都没做。但它的威力在于：如果将来 DemoEvent 新增了第五种事件 paused，而这行 switch 没补 case，event 在 default 里就不再是 never 类型——编译器立刻报错。

这就是穷尽性检查（exhaustiveness check）。CC 的 Python 版完全做不到——新增一种事件类型，Python 不会提醒你 switch 漏了。

● ● ●

三、unknown 收窄：外部数据默认不可信

Pi 的 readDelta 函数从外部 JSON 构造 DemoEvent。输入类型是 unknown——不是 any，不是 DemoEvent，是 unknown。

export function readDelta(value: unknown): DemoEvent {
  if (
    typeof value === "object" &&
    value !== null &&
    !Array.isArray(value) &&
    "type" in value &&
    value.type === "delta" &&
    "requestId" in value &&
    typeof value.requestId === "string" &&
    "text" in value &&
    typeof value.text === "string"
  ) {
    return {
      type: "delta",
      requestId: value.requestId,
      text: value.text,
    };
  }
  throw new Error("invalid delta event");
}
 

八层检查，一层都不能少。过了所有检查，value 的类型才从 unknown 收窄成可以安全使用的形状。

为什么不用 any？any 等于放弃了类型系统的保护——你可以写 value.anything.anything，编译器不管，运行时炸。

为什么不用 DemoEvent 直接接收？因为你不确定外部数据真的符合 DemoEvent 的形状。网络传来的 JSON 可能缺字段、多字段、类型不对。

外部数据默认不可信，必须一项一项验明正身，才放它进系统。这是类型系统在边界处做安检。

● ● ●

四、call id 配对：类型强制因果链

回到 EP01 讲过的 call id 配对。Prologue 的验证函数用两个 Set 做登记簿：

const calls = new Set<string>();
const results = new Set<string>();
 
events.forEach((event, index) => {
  if (event.type === "assistant_message" && event.toolCallId) {
    calls.add(event.toolCallId);
  }
  if (event.type === "tool_result") {
    if (!event.toolCallId || !calls.has(event.toolCallId)) {
      throw new Error("tool result 先于对应的 tool call");
    }
    results.add(event.toolCallId);
  }
});
 
for (const callId of calls) {
  if (!results.has(callId)) {
    throw new Error(tool call ${callId} 缺少配对结果);
  }
}
 

这段代码守住的不变量是：每个 tool call 必须有配对的 tool result，不能悬空。

类型系统在这里的角色：toolCallId?: string 的可选标记——只有工具相关的事件才带这个字段。非工具事件根本无法伪装成工具调用。

● ● ●

类型即文档

回头看这四个设计，它们做的事情有一个共同点：把不变量写在类型里，让编译器替你守。

  •  tagged union 守的是「事件类型不串台」
  •  never 穷尽检查守的是「分支必须全覆盖」
  •  unknown 收窄守的是「外部数据先验证」
  •  call id 配对守的是「因果链不能断」

CC 的 Python 版做不到这些——动态类型的好处在灵活，代价在「不变量只能靠人记」。Pi 用 TypeScript 把不变量写进类型，代码本身就是文档，编译器就是审查员。

学完 Pi 的类型系统，你回头看任何 TypeScript 项目，都会自动寻找这些不变量。这就是「类型即文档」的真正含义。
