写到这里，Pi 系列的 12 篇正文全部拆完了。从 Checkpoint 00 的七步轨迹到 Checkpoint 14 的独立评测，我们沿着 Pi 的源码一路读下来。

这篇衍生文章做一个横向对比：Pi（TypeScript）和 learn-claude-code（Python，CC 系列）——同样是教学版 Agent Harness，两者在设计哲学上有什么不同？

● ● ●

语言：动态 vs 静态

最根本的差异是语言。

CC 用 Python——动态类型，写起来快，30 行就能跑一个 Agent Loop。但类型错误只在运行时暴露：你忘了处理 stop_reason 的一种值，程序不会报错，只会默默走错分支。

Pi 用 TypeScript——静态类型，tagged union + never 穷尽检查在编译期就抓住遗漏。代价是每个事件、每条消息都要定义类型，代码量更大。

// Pi 的 DemoEvent：编译器帮你检查穷尽性
export type DemoEvent =
  | { type: "started"; requestId: string }
  | { type: "delta"; requestId: string; text: string }
  | { type: "finished"; requestId: string; reason: "stop" | "length" }
  | { type: "aborted"; requestId: string };
 

CC 胜在简洁，Pi 胜在安全。对于教学，CC 的简洁更容易理解概念；对于生产，Pi 的类型安全能省下大量调试时间。

● ● ●

模型接入：单家 vs 多家

CC 直接调 Anthropic SDK，锁死 Claude 一家。简单，但没有选择权。

Pi 有完整的 Provider 适配器层——同一个 Model 接口，底下接 OpenAI、Anthropic、Google、DeepSeek、Ollama 等 15+ Provider。三层翻译把 API 格式差异全部吃掉。

维度CC (Python)Pi (TypeScript)
Provider 数量1（Anthropic）15+
适配器层无ProviderAdapter
SSE 流式无（同步）有
API key 安全基础Authorization only

● ● ●

流式：同步 vs 异步

CC 的 s01-s20 全部用同步调用——等模型一次性返回完整响应再继续。用户体验是「等几秒，突然蹦出一大段文字」。

Pi 有 EventStream——同一个对象同时提供 AsyncIterable（过程）和 result()（结果）。模型边吐 token，UI 边渲染。

// Pi 的 EventStream：过程和结果分离
class EventStream<T, R> implements AsyncIterable<T> {
  // queue: 事件先到，先存着
  // waiting: 消费者先等，先排着
  // done: 终态到达，闸门关闭
  result(): Promise<R> { ... }
}
 

CC 没有 EventStream 这层抽象，因为 CC 不需要处理流式。

● ● ●

会话存储：内存 vs JSONL 会话树

CC 无持久化——每次运行从零开始，状态全在内存里，进程结束就没了。

Pi 有 JSONL 会话树——每条消息是一行 JSON，带父指针，支持分支。换行是 commit marker：半行 JSON 在崩溃恢复时被丢弃。

维度CCPi
存储内存JSONL 文件
分支不支持会话树
崩溃恢复无pathTo + commit marker
审计无每行一条事实

Pi 的 JSONL 会话树是生产级的，CC 完全没有这层。

● ● ●

上下文管理：四层压缩 vs 预算投影

CC 的 s08-s09 用四层压缩：系统提示词 → 工具定义 → 历史摘要 → 最近对话。每层有独立策略。

Pi 的 Checkpoint 11 用预算投影：历史不动，给模型看的上下文按 token 预算重建。compaction 是追加到 session 的新事实，不删旧 entry。

// Pi 的 compaction：追加不删除
// 从最新 group 向前累加，先扣 system 和安全余量
// 恢复时只读最新摘要，再从 firstKeptEntryId 投影后缀
 

CC 的做法更直观（分层），Pi 的做法更精确（预算投影 + compaction entry）。

● ● ●

工具系统：dispatch map vs Registry

CC 用一个 Python dict 做 dispatch——工具名映射到处理函数。简单但无类型约束。

Pi 有完整的工具契约管线：validator（验参数）→ Registry（注册查找）→ executor（执行）→ 结构化 ToolResult。

// Pi 的工具执行管线
validator(input)  // JSON Schema 验证
  → Registry.lookup(name)  // 查找已注册工具
  → executor(args)  // 执行
  → { content, details, isError }  // 结构化结果
 

● ● ●

测试：无 vs held-out capstone

CC 没有独立测试——s01-s20 是学习笔记，跑通 demo 就行。

Pi 有完整的测试体系：每个 checkpoint 有聚焦测试，最后还有 held-out capstone——三项测试只存在于 target 和最终 full gate，practice 不复制。「跑完了」不等于「做对了」。

● ● ●

扩展机制：Hook vs 原子注册

CC 有 Hook 注册表——beforeToolCall / afterToolCall 钩子，但注册不是原子的。

Pi 有原子注册：factory 注册了一个 tool 后如果抛错，这个 tool 不能留下。hook 故障隔离——beforeToolCall 拒绝/抛错/超时都阻止 core executor。

● ● ●

总结：一张表看完

维度CC (Python)Pi (TypeScript)
语言Python（教学友好）TypeScript（生产级类型安全）
模型接入直接调 Anthropic SDK多 Provider 适配器层
流式无（同步）SSE 流式 + EventStream
会话存储无（内存）JSONL 会话树 + 磁盘持久化
上下文管理四层压缩预算投影 + compaction entry
工具系统dispatch mapRegistry + validator + executor
测试无每章聚焦测试 + held-out eval
扩展Hook 注册表原子注册 + 信任门

两套代码教的是同一件事：Agent Loop 怎么从零搭起来。但工程取舍完全不同：CC 追求最短路径让你理解概念，Pi 追求每个细节都经得起生产考验。

对照着看，概念更扎实。
