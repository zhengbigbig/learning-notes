你在终端敲下 pi "帮我重构这个函数"，回车。几秒后模型开始读你的代码、调工具、给出建议，整个过程行云流水。

但你有没有想过——这一秒背后，Pi 是怎么把模型、工具、会话历史、资源、扩展这些零件，在一瞬间拼成一台能跑的机器的？

前面 10 章我们拆完了每一个零件：会话怎么存成树、上下文怎么压缩、工具怎么执行、Agent Loop 怎么转。每一章都是孤立的零件。

这一章是 Checkpoint 13——所有零件在这里第一次接到一起。源码只有一个文件：src/composition.ts，390 行。它的名字叫 composition root（组装根）。

● ● ●

一、你敲下 pi 的时候，createRuntime 做了什么

整个 Pi 的启动，本质上就是调一次 createRuntime。这个函数不做任何业务逻辑，只负责把零件接好。第 317 行：

// composition.ts:317-353
export async function createRuntime(
  config: RuntimeConfig,
  deps: RuntimeDeps,
): Promise<Runtime> {
  // 第①步：从 session 存储读出所有历史条目（JSONL 文件里的每一行）
  const entries = await deps.session.entries();
 
  // 第②步：根据 activeLeafId 从历史里恢复"当前这条对话路径"
  // resume 旧会话时，这里会沿着 parentId 往上追溯到根
  const initialPath = validateSessionSelection(entries, config.activeLeafId);
  const initialMessages = messagesIn(initialPath);
 
  // 第③步：拼 system prompt——把你配置的 prompt 和资源描述接成一段
  const systemPrompt = combinedSystemPrompt(config.systemPrompt, deps.resources);
 
  // 第④步：把原始 model 包一层"上下文投影"，每次调模型前自动压缩历史
  let runtime!: RuntimeImpl;
  const model = createContextProjectingModel(
    deps.model,
    { systemPrompt, context: config.context },
    () => runtime.contextSnapshot(),  // 闭包：运行时实时取当前快照
  );
 
  // 第⑤步：组装工具执行器——没扩展就裸调，有扩展就包一层 hook
  const coreExecutor: ToolExecutor = (call, context) =>
    executeToolCall(call, deps.tools, context);
  const toolExecutor = deps.extensionHost
    ? deps.extensionHost.wrapExecutor(coreExecutor)  // 扩展可拦截/改写工具调用
    : coreExecutor;
 
  // 第⑥步：把所有零件喂给 Agent，造一个有状态的 Agent 实例
  const agent = new Agent({
    model, tools: deps.tools, toolExecutor,
    initialMessages, systemPrompt, maxSteps: config.maxSteps,
  });
 
  // 最后把 Agent 和 deps 一起塞进 RuntimeImpl，返回给调用方
  runtime = new RuntimeImpl(agent, initialPath, deps);
  return runtime;
}
 

六步，每一步对应前面某章拆过的零件：①②是 session、③是 resources、④是 context、⑤是 tool、⑥是 agent。

你下次启动 Pi 卡顿一两秒，多半就是在等第①步读 session 文件；如果 resume 一个很长的旧会话，第②步的路径恢复也要花点时间。理解了这六步，排启动问题就有了抓手。

createRuntime 不发明任何东西，它只是个装配工。装配顺序也很讲究：必须先有 system prompt 才能包 model，必须先有 model 和 toolExecutor 才能造 Agent，必须先造好 Agent 才能造 RuntimeImpl。

整个 Pi 的对象图，就在这 30 行里一次性建好。建完之后，runtime.prompt() 就能用了。

● ● ●

二、RuntimeDeps：六个接口，决定 Pi 能换什么零件

createRuntime 接两个参数：config（配置）和 deps（依赖）。deps 是六个接口，第 45 行：

// composition.ts:45-53
export interface RuntimeDeps {
  model: Model;              // 模型——真 Provider 或测试用的 ScriptedModel
  tools: ToolRegistry;       // 已注册的工具集合，agent-loop 调工具时查这里
  session: SessionStore;     // 会话存储——内存版或 JSONL 落盘版，append-only
  resources: ResourceCatalog;// 资源目录——文件、文档等上下文素材
  extensionHost?: ExtensionHost; // 扩展宿主（可选）——hook 工具调用、注入上下文
  createId(): string;        // ID 生成器——每条消息一个唯一 id
  now(): number;             // 时间戳——写进 session 的 timestamp 字段
}
 

六个全是接口，没有一个是具体类。这是依赖注入的标准写法：上层定义需要什么，下层传什么实现。

这个设计直接影响你怎么定制 Pi。想换个模型？实现 Model 接口传进去。想自己存会话（比如存数据库）？实现 SessionStore 接口。createRuntime 的参数表就是 Pi 的扩展点清单。

测试时传 ScriptedModel 和内存 SessionStore，能精确控制每一步。createId 和 now 也被抽出来，是为了测试时让 id 和时间戳确定——否则断言没法写。生产环境换成真实现，代码一行不改。

● ● ●

三、createContextProjectingModel：模型看到的，永远是被压缩过的

这是整个 composition 里最巧妙的一层。问题在于：Agent 内部保留的是完整的 canonical transcript——从第一句到最新一句，一条不删。但模型上下文窗口有限，不能全塞。怎么办？

答案：在 Agent 和真模型之间插一个"投影"层。第 148 行：

// composition.ts:148-177
export function createContextProjectingModel(
  inner: Model,                                              // 真模型
  config: Pick<RuntimeConfig, "systemPrompt" | "context">,
  getSnapshot: () => ContextProjectionSnapshot,              // 取当前会话快照的闭包
): Model {
  return {
    stream(context, options = {}) {
      // 每次模型请求前，先取当前 runtime 的快照
      const snapshot = getSnapshot();
 
      // buildContext 做"投影"：按 token 预算裁剪，超出的旧消息压成摘要
      const projected = buildContext(
        temporaryEntries(snapshot, context.messages),        // 临时拼接：已落盘+未落盘
        {
          maxTokens: config.context.total,                   // 总预算
          reservedOutput: config.context.reservedOutput,     // 给输出留的额度
          safetyMargin: config.context.safetyMargin,         // 安全余量
          systemPrompt: config.systemPrompt,
          estimateTokens: config.context.estimateTokens,     // token 估算函数
        },
      );
 
      // 拼出发给模型的请求——用的是投影后的、裁剪过的消息
      const request: AgentContext = {
        systemPrompt: projected.systemPrompt,
        messages: structuredClone(projected.messages),
        tools: context.tools === undefined
          ? undefined
          : structuredClone(context.tools),
      };
 
      // 最终调真模型
      return inner.stream(request, { signal: options.signal });
    },
  };
}
 

Agent 记的是全量，模型看的是投影。这两个状态是分离的。

为什么不能让 Agent 直接记压缩后的？因为压缩是破坏性的——旧消息压成摘要就回不来了，万一你想回看完整历史、或者换个大窗口模型重跑，全量 transcript 还在。这层投影就是为此存在的缓冲。

temporaryEntries 很关键：它把"已落盘的消息"和"这一轮还没落盘的新消息"临时拼成一条完整路径，再交给 buildContext 裁剪。Agent 不用关心落盘状态，模型不用关心会话树结构，中间这层全包了。structuredClone 出现了三次，每次传给下层的数据都是深拷贝，防止任何一层意外改了上层状态。

● ● ●

四、RuntimeImpl.prompt：一条消息从进来到落盘

你调 runtime.prompt("帮我重构") 之后发生了什么？第 248 行：

// composition.ts:248-271
prompt(value: string): Promise<AgentRunResult> {
  // 入口检查：dispose 了或 poison 了，直接拒绝
  if (this.disposed) return Promise.reject(new Error("Runtime 已 dispose"));
  if (this.poisoned) return Promise.reject(this.poisonCause);
 
  // 关键：所有 prompt 操作串在 operationTail 后面，保证不并发
  const operation = this.operationTail.then(async () => {
    this.assertHealthy();
    // 记住调用前 Agent 里有多少条消息
    const beforeCount = this.agent.getState().messages.length;
 
    // 真正触发 Agent Loop——模型流式输出、工具调用、多轮都在这里
    const result = await this.agent.prompt(value);
 
    // 取出这一轮新增的消息（suffix）——beforeCount 之后的所有消息
    const suffix = result.messages.slice(beforeCount);
 
    // 把新增消息逐条落盘到 session
    await this.persist(suffix);
 
    // 返回深拷贝，防止调用方改到内部状态
    return structuredClone(result);
  });
 
  // 无论成功失败，都把 operationTail 推进到这次操作之后
  this.operationTail = operation.then(() => undefined, () => undefined);
  return operation;
}
 

四步：触发 Loop → 取 suffix → 落盘 → 返回拷贝。

operationTail 是串行化的关键。连续调两次 prompt，第二次会等第一次完全落盘后才开始。这不是性能优化，是正确性保证——并发写 session 树会乱套。

beforeCount 这个设计很干净：Agent 的 messages 是权威源，prompt 只需知道"这次多了几条"，把这几条追加进 session。Agent 和 Runtime 各管各的状态，边界清晰。

● ● ●

五、persist：一条一条往会话树上挂

第 222 行，persist 把每一轮的新消息逐条 append：

// composition.ts:222-246
private async persist(messages: readonly AgentMessage[]): Promise<void> {
  let parentId = this.activeLeafId;   // 从当前叶子节点开始挂
 
  for (const message of messages) {
    try {
      // 每条消息造一个 session entry，parentId 指向上一条
      const entry: MessageSessionEntry = {
        id: this.deps.createId(),     // 新 id
        parentId,                      // 链向上一条——构成树
        timestamp: this.deps.now(),
        type: "message",
        message: structuredClone(message),
      };
 
      await this.session.append(entry);              // 写进存储
      this.activePath.push(structuredClone(entry));  // 更新内存里的路径
      this.persistedMessageCount += 1;               // 计数器+1
      this.activeLeafId = entry.id;                  // 叶子推进
      parentId = entry.id;                           // 下一条挂在这条后面
 
    } catch (error) {
      // 任何一条失败，整个 Runtime 进入 poison 状态
      this.poisoned = true;
      this.poisonCause = error;
      throw error;
    }
  }
}
 

逐条 append，每条带 parentId，这就是会话树的结构。

为什么逐条而不是批量？因为 append 是幂等的——中途崩了，已写入的条目还在，下次 resume 能接着挂。poison 机制是"一旦坏了就别再用"：写入失败意味着 session 和内存状态不一致，继续用会污染数据，直接锁死。activeLeafId 和 activePath 是 Runtime 自己维护的"当前游标"——resume 旧会话时游标停在某个叶子，新消息从这个叶子往下长。

● ● ●

六、三种 mode：输出编码不同，内核完全一样

最后是 runMode，第 365 行。Pi 有三种运行模式：interactive（终端交互）、print（一次性打印）、json（结构化输出给程序消费）。

// composition.ts:365-389
export async function runMode(
  runtime: Runtime,
  mode: RuntimeMode,   // "interactive" | "print" | "json"
  prompt: string,
  io: ModeIO,          // 输出接口——终端传 stdout，测试传 buffer
): Promise<AgentRunResult> {
  // 三个 mode 调的是同一个 runtime.prompt，没有任何分支
  const result = await runtime.prompt(prompt);
 
  // 区别只在最后怎么编码输出
  const output =
    mode === "json"
      ? `${JSON.stringify({
          reason: result.reason,     // 结束原因（完成/中止/超步数）
          steps: result.steps,       // 执行了多少步
          messages: result.messages, // 完整消息列表
        })}\n`
      : finalAssistantText(result);  // interactive 和 print 都取最后一条 assistant 文本
 
  await io.write(output);
  return structuredClone(result);
}
 

mode 不拥有 Agent，不碰 persistence，只负责调 prompt 和选输出格式。

interactive 和 print 走同一条路径——都是 finalAssistantText，取最后一条 assistant 消息的纯文本。唯一不同的是 json mode，它把整个结构化结果序列化出去，给别的程序消费——你可以用 json mode 把 Pi 当后端，自己写前端。io: ModeIO 又是一层抽象：runMode 不直接 console.log，而是写到 io 接口，测试时传内存 buffer 就能断言输出。

● ● ●

收尾：composition root 的意义

这一章是整个系列的收口。前面 10 章拆零件，这一章讲怎么装。

createRuntime 六步：session 恢复 → system prompt → context 投影 → 工具执行器 → Agent → RuntimeImpl。每一步都对应一个独立模块，模块之间只通过接口说话。

composition root 的本质是：把"用什么实现"这个决定，推迟到最后一刻。Agent 不知道 model 是真的还是脚本，不知道 session 是内存还是文件，不知道 tools 里注册了什么——所有具体选择都在 createRuntime 调用时由调用方传入。

这种结构的直接好处是可测性：测试里 model 是 ScriptedModel，session 是内存版，createId 和 now 返回固定值，整条链路完全确定。生产环境换成真实现，代码一行不改。

Pi 用 390 行 composition.ts 证明了一件事：一个能跑的 AI Agent，不需要全局单例、不需要隐式依赖、不需要启动时副作用——只要把零件按顺序接好，剩下的交给接口。
