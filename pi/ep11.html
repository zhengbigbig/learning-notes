大家好我是郑同学。前十篇拆了 Pi 的所有核心模块。但你有没有想过一个问题：这些模块怎么测试？

Agent 的核心是 model → tool → model 的循环。如果你用真实模型跑测试，每次返回不一样——你没法写一个断言说「模型第三轮一定会调 read 工具」。用真实模型测试 Agent 代码，结果不可复现，今天过明天挂。

ScriptedModel 是纯测试工具，不是运行时组件。它只在 test 文件里出现，不在实际运行时使用。实际运行时，Pi 用的是 EP05 讲的 provider adapter 接真实模型。两者实现同一个 Model 接口，但用途完全不同：provider adapter 连真实模型，ScriptedModel 连预设脚本。

ScriptedModel 做的事是在代码测试时替代真实模型。你把模型每一回合的行为写成脚本，Agent Loop 跑的时候不连真实模型，而是按脚本走。这样测试就成了确定性的——同一个脚本跑十遍，结果一模一样。

● ● ●

不是 mock，是规格

ScriptedModel 的源码注释写得很明确：

ScriptedModel 不是 mock 掉设计问题，而是把预期的多轮行为写成可执行规格。

mock 是糊弄过去，规格是定义清楚。区别在于：mock 不关心行为对不对，只让测试跑过；规格则精确描述「第 N 次调用应该返回什么」，如果实际行为和规格不符，测试就挂。

用法很简单——构造时传一个 ScriptedTurn 数组，每个元素描述一次模型响应：

// scripted-model.ts:11-17

export type ScriptedTurn =

  | AssistantMessage           // 正常的助手消息（文本+工具调用）

  | {

      stopReason: "error" | "aborted";

      errorMessage: string;

      partialText?: string;    // 中断前的部分文本

    };

 

两种 turn：正常的 AssistantMessage（包含 text 和 toolCall），和异常终止（error 或 aborted，可选带部分文本）。

● ● ●

怎么用：一个完整测试场景

假设要测试 Agent 能不能正确执行「模型调 read → 工具返回内容 → 模型总结」这个循环：

const model = new ScriptedModel([

  // 第一回合：模型调用 read 工具

  assistantMessage([

    { type: "text", text: "让我读取文件" },

    { type: "toolCall", callId: "c1", name: "read",

      arguments: { path: "hello.txt" } },

  ], "tool_use"),

  // 第二回合：模型拿到工具结果后总结

  assistantMessage([

    { type: "text", text: "文件内容是 hello" },

  ], "stop"),

]);

 

const agent = new Agent({ model, tools, ... });

const result = await agent.prompt("读取 hello.txt 并告诉我内容");

 

每一回合的模型行为都是预定义的。如果 Agent Loop 的逻辑有 bug——比如漏传工具结果、或者多调了一次模型——ScriptedModel 的 cursor 会不匹配，要么报「没有更多响应」，要么 requests 数组里记录的请求数和预期不一致。

● ● ●

核心机制：cursor + queueMicrotask

ScriptedModel 实现了 Model 接口。每次 Agent Loop 调 model.stream()，ScriptedModel 做三件事：

// scripted-model.ts:39-51（核心骨架）

export class ScriptedModel implements Model {

  readonly requests: AgentContext[] = [];

  private cursor = 0;

 

  constructor(private readonly turns: ScriptedTurn[]) {}

 

  stream(context: AgentContext, options): AssistantMessageEventStream {

    const stream = new AssistantMessageEventStream();

    // 1. 记录请求（测试可以检查 Agent 传了什么）

    this.requests.push(structuredClone(context));

    // 2. 取出下一个预设回合

    const turn = this.turns[this.cursor++];

    // 3. 异步推送事件（模拟真实流式）

    queueMicrotask(() => { /* 推送 start/delta/end 事件 */ });

    return stream;

  }

}

 

cursor 是关键。每次 stream() 被调，cursor 前进一位。如果 Agent Loop 多调了一次模型，cursor 会越界——this.turns[this.cursor++] 返回 undefined，ScriptedModel 报错「没有更多响应」。

requests 数组是测试的眼睛。每次 stream() 被调时，Agent 传入的完整 context（messages + tools + systemPrompt）被深拷贝保存。测试可以检查「第二轮模型收到了哪些消息」「工具结果是否正确配对」。

● ● ●

为什么用 queueMicrotask

ScriptedModel 用 queueMicrotask 异步推送事件，不是同步返回。这是为了模拟真实模型的行为——真实模型的 stream 是异步的，事件分批到达。

// scripted-model.ts:53-60

queueMicrotask(() => {

  if (options.signal?.aborted) {

    // 预取消：还没开始就被 abort

    const aborted = assistantMessage([], "aborted", { ... });

    stream.push({ type: "error", reason: "aborted", error: aborted });

    stream.end(aborted);

    return;

  }

  // ... 正常推送事件

});

 

如果 Agent 的取消逻辑有 bug——比如 abort 信号没传下去——测试就能抓到。同步返回的话，abort 信号永远不会在正确时机被检查。

● ● ●

事件投影：final message → event trace

ScriptedModel 的核心技巧是从最终消息反推事件流。真实模型是流式的——text 一段一段来，toolCall 参数一个个字累积。ScriptedModel 需要模拟这个过程。

// scripted-model.ts:72-116（核心骨架）

const message = terminalMessage(turn);

const partial = partialFrom(message);  // 空内容的 partial

stream.push({ type: "start", partial });

 

message.content.forEach((block, contentIndex) => {

  if (block.type === "text") {

    // text 块：一次性推送完整文本

    partial.content = [...partial.content, block];

    stream.push({ type: "text_delta", contentIndex,

      delta: block.text, partial });

  } else {

    // toolCall 块：先推 rawArguments 增量，再推完整 toolCall

    const toolCall = structuredClone(block);

    stream.push({ type: "toolcall_delta", contentIndex,

      delta: rawArguments, partial });

    stream.push({ type: "toolcall_end", contentIndex,

      toolCall, partial });

  }

});

 

stream.push({ type: "done", reason: message.stopReason, message });

stream.end(message);

 

先发 start，再逐个 content block 发 delta/end，最后发 done。这和真实模型的 SSE 流完全对应——EP02 讲的 EventStream 就是在接收这些事件。

● ● ●

对比真实 CC 的测试

CC 的测试在 test/suite/harness.ts 里。

① 测试模型

Pi 用 ScriptedModel——把预设回合写成数组，精确控制每一轮。CC 用faux provider——一个假的 HTTP provider，返回预设的 SSE 流。思路一样：用确定性的假模型替代真实模型。

② 测试覆盖

Pi 的 ScriptedModel 覆盖单 Agent 单线程场景。CC 的 faux provider 覆盖更复杂——子 Agent 并发、压缩恢复、extension 钩子等。Pi 的测试更聚焦在核心反馈回路。

③ 断言方式

Pi 通过 requests 数组检查 Agent 传给模型的内容。CC 通过session transcript 断言——检查 JSONL 文件里记录的完整对话历史。两边都能验证「模型收到了正确的消息」。

两边思路一致：确定性假模型 + 精确事件序列 + 可检查的请求记录。

● ● ●

小结

设计决策选择为什么
测试模型ScriptedModel（预设回合数组）确定性可复现
cursor 机制每次调用前进一位越界即报错，抓多调
requests 记录深拷贝每次请求测试可检查 Agent 传了什么
异步推送queueMicrotask模拟真实流式 + 测 abort
事件投影final message → event trace从结果反推过程

口诀：预设回合排队走，cursor 前进一格收，requests 留证据，异步推事件测取消。
