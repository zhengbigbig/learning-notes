大家好，我是郑同学。

上篇拆了 EventStream——流式数据怎么在 Pi 内部缓冲和兜底。但有个东西我们一直没问：你发的那句话，Pi 内部到底存成什么样？

用一条真实的对话追到底。你发「帮我查天气」，模型回了一句「我来查」加一个 read 工具调用，工具执行完返回结果。这句话从头到尾经过了几次变形——每一步 Pi 都用不同的数据结构来存。

● ● ●

第一步：你的话存成 UserMessage

你敲的那句话，Pi 不是存成纯字符串。它包了一层：

// types.ts:36-41
interface UserMessage {
  role: "user";              // 标记：这是用户说的
  content: TextContent[];    // 内容块数组（不是 string）
  timestamp: number;         // 什么时候说的
}
 

为什么 content 是数组而不是 string？因为将来可能加图片、音频等非文字内容。现在只有 TextContent（{ type: "text", text: "..." }），但结构上留了扩展口。

● ● ●

第二步：模型回复存成 AssistantMessage，内容是块数组

模型回复也不只是文字。它可能一边说话一边调工具，这些混在同一条消息里：

// types.ts:43-52
interface AssistantMessage {
  role: "assistant";
  content: AssistantContent[];  // TextContent 和 ToolCall 混排
  provider: string;             // 哪家模型
  model: string;
  stopReason: StopReason;       // 为什么停了（见第四步）
  timestamp: number;
}
 

content 是内容块数组，每个块有自己的 type：

// types.ts:1-8
interface TextContent { type: "text"; text: string; }
 
interface ToolCall {
  type: "toolCall";
  id: string;            // 唯一编号，第三步配对用
  name: string;
  arguments: unknown;
}
 
type AssistantContent = TextContent | ToolCall;
 

模型说「我来查一下，同时调 read 工具」，存出来长这样：

content: [
  { type: "text", text: "我来查一下" },
  { type: "toolCall", id: "call-01", name: "read", arguments: {...} },
]
 

按数组顺序就是说话的顺序。先说话再调工具，或者反过来，都靠数组顺序表达。

● ● ●

第三步：工具结果存成 ToolResultMessage，带 callId 配对

工具执行完，结果怎么存？不是塞回 user 或 assistant，是独立的第三种角色：

// types.ts:54-62
interface ToolResultMessage {
  role: "toolResult";        // 不是 user，不是 assistant
  toolCallId: string;        // 指向第二步的 ToolCall.id
  toolName: string;
  content: TextContent[];
  isError: boolean;          // 工具出错也是正常结果
  timestamp: number;
}
 

关键在 toolCallId——它指向第二步那个 { id: "call-01" } 的工具调用。模型可能一次调三个工具，三个结果混着回来，靠这个 id 才知道哪个结果对应哪次调用。

为什么不让工具结果伪装成 role: "user"？因为用户消息是「人说的话」，工具结果是「机器执行的输出」。混在一起模型分不清谁是谁。Pi 选了更严格的路线。

● ● ●

到这里，一条完整的对话长这样

把三步拼起来，你发的那句话在 Pi 内部完整存成了一条消息链：

messages: [
  { role: "user", content: [{ type: "text", text: "帮我查天气" }] },
  { role: "assistant", content: [
    { type: "text", text: "我来查一下" },
    { type: "toolCall", id: "call-01", name: "read", arguments: {...} },
  ]},
  { role: "toolResult", toolCallId: "call-01", content: [...], isError: false },
]
 

三种角色，一条链，每个工具调用和结果靠 id 锁死。这就是 types.ts 的全部核心——定义这条链上每个节点的形状。

● ● ●

第四步：模型回复的五种结局

上面的 assistant 消息有个 stopReason 字段。模型回复不是只有「说完了」一种结局：

// types.ts:15-20
type StopReason =
  | "stop"      // 正常说完
  | "length"    // 被 max_tokens 截断
  | "toolUse"   // 要调工具
  | "error"     // 出错了
  | "aborted";  // 被用户取消
 

这个字段是 Agent Loop 唯一的控制信号（后面 EP05 讲）。toolUse 就去执行工具然后继续循环，stop 就结束对话。上一篇 EventStream 的终态检测也靠它。

● ● ●

第五步：流式过程中，每个块拆成事件

上面说的是最终存进对话链的完整消息。但流式过程中模型还在一个字一个字吐，这时候每一步都用事件来表达：

// types.ts:69-92（简化）
type ModelEvent =
  | { type: "start"; partial: AssistantMessage }
  | { type: "text_delta"; delta: string; partial: AssistantMessage }
  | { type: "toolcall_delta"; delta: string; partial: AssistantMessage }
  | { type: "toolcall_end"; toolCall: ToolCall; partial: AssistantMessage }
  | { type: "done"; reason: "stop" | "length" | "toolUse"; message: AssistantMessage }
  | { type: "error"; reason: "error" | "aborted"; error: AssistantMessage };
 

每个 delta 事件都带了 partial——当前已累积的部分消息。UI 可以直接用它渲染，不用自己拼。流结束后，done 事件里的 message 就是完整的 AssistantMessage，存进第三步的消息链。

事件是流式过程中的临时形态，消息是最终形态。一个从 model 出来经过事件流变成消息存进链。

● ● ●

第六步：怎么测试这条链对不对

消息结构定义清楚了，但你怎么验证 Agent 的行为对不对？真实模型每次回复不一样，你没法断言「第三轮一定调 read」。

Pi 的答案是 ScriptedModel——不调真模型，把预期行为写成可执行规格。先看一张图：

你提前写好一串预期回复（turns），每次 Agent Loop 调 stream()，ScriptedModel 按顺序吐下一个 turn。看核心代码：

// scripted-model.ts:40-46（简化）
class ScriptedModel implements Model {
  readonly requests: AgentContext[] = [];   // 每次调用收到的输入，存下来
  private cursor = 0;
  constructor(private readonly turns: ScriptedTurn[]) {}
 

每次 stream() 被调用时发生两件事：

// scripted-model.ts:48-94（简化）
  stream(context, options) {
    const stream = new AssistantMessageEventStream();
    this.requests.push(structuredClone(context));  // ① 存输入，测试可断言
    const turn = this.turns[this.cursor++];        // ② 取下一个预设回复
 
    queueMicrotask(() => {
      // turns 用完了？吐 error + end
      if (!turn) { stream.push({ type: "error", ... }); stream.end(...); return; }
      // 否则：先 push start，再逐个内容块 push delta，最后 push done
      stream.push({ type: "done", reason: message.stopReason, message });
      stream.end(message);
    });
    return stream;
  }
 

每次调用的输入存进 requests，测试结束你可以断言「第二轮收到的 messages 里有第一轮的 toolResult」。turns 用完了直接报错——告诉你「预设不够，Agent 多跑了一轮」。

ScriptedModel 不是 mock，是可执行规格——把模型契约固化成可断言的数据，Agent 测试从「大概对」变成「精确对」。
