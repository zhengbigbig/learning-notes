大家好，我是郑同学。

上篇拆了 EventStream——流式数据怎么在 Pi 内部缓冲和兜底。但有个东西我们一直没问：你发的那句话，Pi 内部到底存成什么样？

你敲一句「帮我查天气」，模型回了一段话加一个 read 工具调用，工具跑完把结果塞回对话。如果你只看 UI，这些都是气泡框里的文字。但如果你要给 Pi 加一个工具、改一下 Agent Loop、或者写个测试验证「模型调工具时 Agent 会正确执行」——你就绕不开消息结构。

这一篇拆 types.ts 和 scripted-model.ts，两个文件加起来不到三百行，定义了 Pi 跟模型之间所有数据流动的形状。

● ● ●

三种角色，不能混

先看最基础的。Pi 里只有三种消息：

// types.ts:36-58（简化）
interface UserMessage {
  role: "user";
  content: TextContent[];
  timestamp: number;
}
 
interface AssistantMessage {
  role: "assistant";
  content: AssistantContent[];   // 可以同时含文字和工具调用
  provider: string;
  model: string;
  stopReason: StopReason;
  timestamp: number;
}
 
interface ToolResultMessage {
  role: "toolResult";
  toolCallId: string;            // 必须带，配对用
  toolName: string;
  content: TextContent[];
  isError: boolean;              // 工具出错也是正常结果
  timestamp: number;
}
 

有人可能问：工具结果不也是一种「消息」吗？为什么不能塞进 role: "user" 里，像 ChatGPT API 那样？

因为语义不同。用户消息是「人说的话」，工具结果是「机器执行的结果」。如果混在一个 role 里，模型分不清哪些是你说的、哪些是工具返回的。Pi 选了一条更严格的路线：toolResult 独立成第三种角色，还必须带 toolCallId 指向哪次调用。

● ● ●

一条回复拆成块

模型回复不是一个大字符串。它是内容块数组，可以同时有文字和工具调用：

// types.ts:1-8
interface TextContent {
  type: "text";
  text: string;
}
 
interface ToolCall {
  type: "toolCall";
  id: string;            // 唯一编号，结果配对用
  name: string;          // 工具名
  arguments: unknown;    // 参数
  rawArguments?: string; // 原始 JSON 字符串
}
 
type AssistantContent = TextContent | ToolCall;
 

一条 assistant 消息的 content 长这样：

content: [
  { type: "text", text: "我来查一下" },
  { type: "toolCall", id: "call-01", name: "read", arguments: {...} },
]
 

按数组顺序表达「先说话，再调工具」这种自然节奏。也可以反过来——先调工具拿到结果，再说一句话总结。

● ● ●

五种结局

模型回复不是只有「说完了」一种结局。types.ts 定义了五种：

// types.ts:15-20
type StopReason =
  | "stop"      // 正常说完
  | "length"    // 被 max_tokens 截断了
  | "toolUse"   // 要调工具
  | "error"     // 出错了
  | "aborted";  // 被用户取消
 

每种决定 Agent Loop 走不同分支。toolUse 就去执行工具，stop 就结束循环，length 就告诉用户回复被截断了。这个字段是循环唯一的控制信号——上一篇 EventStream 的终态检测就靠它。

● ● ●

流式过程拆成事件

上面说的是「最终消息」的结构。但流式过程中，模型吐的不是完整消息，而是一个个增量事件：

// types.ts:69-92（简化）
type ModelEvent =
  | { type: "start"; partial: AssistantMessage }
  | { type: "text_delta"; contentIndex: number; delta: string; partial: AssistantMessage }
  | { type: "toolcall_delta"; contentIndex: number; delta: string; partial: AssistantMessage }
  | { type: "toolcall_end"; contentIndex: number; toolCall: ToolCall; partial: AssistantMessage }
  | { type: "done"; reason: "stop" | "length" | "toolUse"; message: AssistantMessage }
  | { type: "error"; reason: "error" | "aborted"; error: AssistantMessage };
 

六个分支，每个都有明确的 type 字段。tagged union 的好处是编译器帮你穷举——你写 switch(event.type) 时漏掉一个分支，TypeScript 直接报错。

注意每个 delta 事件都带了一个 partial——当前已累积的部分消息。消费者可以直接用它渲染，不用自己拼。

● ● ●

textOf：有损投影

有时候你只想要消息里的文字，不关心工具调用。textOf 做这件事：

// types.ts:113-119
function textOf(message: AgentMessage): string {
  const blocks = message.content;
  return blocks.flatMap((block) =>
    block.type === "text" ? [block.text] : []
  ).join("\n");
}
 

遍历所有内容块，只挑出 text 类型的，拼成字符串。工具调用块被丢掉——这是有损的，但对于「给用户展示纯文字」足够了。

● ● ●

Agent 怎么测才可靠

到这里 Checkpoint 03 讲完了——消息结构定义清楚，数据的形状就定了。但还有个问题：你怎么测试 Agent 的行为对不对？

真实模型每次回复都不一样，你没法断言「模型第三轮一定会调 read 工具」。跑一遍测试今天过明天不过，这种测试没意义。

Pi 的答案是 ScriptedModel——不调真模型，把预期行为写成可执行规格：

// scripted-model.ts:40-46（简化）
class ScriptedModel implements Model {
  readonly requests: AgentContext[] = [];   // 记录每次调用收到的输入
  private cursor = 0;
  constructor(private readonly turns: ScriptedTurn[]) {}
 

你给一串预期的回复（turns），每次 stream() 被调用，它按顺序吐出下一个 turn：

// scripted-model.ts:48-94（简化）
  stream(context, options) {
    const stream = new AssistantMessageEventStream();
    this.requests.push(structuredClone(context));  // 存下来，测试可以断言
    const turn = this.turns[this.cursor++];
 
    queueMicrotask(() => {
      // ① 被取消？吐 error + end
      if (options.signal?.aborted) {
        stream.push({ type: "error", reason: "aborted", error: aborted });
        stream.end(aborted);
        return;
      }
      // ② 没有更多 turn 了？吐 error + end
      if (!turn) {
        stream.push({ type: "error", reason: "error", error: exhausted });
        stream.end(exhausted);
        return;
      }
      // ③ 正常：先 push start，再逐个内容块 push delta
      stream.push({ type: "start", partial });
      message.content.forEach((block, i) => {
        if (block.type === "text") {
          stream.push({ type: "text_delta", contentIndex: i, delta: block.text });
        } else {
          stream.push({ type: "toolcall_delta", contentIndex: i, ... });
          stream.push({ type: "toolcall_end", contentIndex: i, toolCall: block });
        }
      });
      // ④ 最后 push done + end
      stream.push({ type: "done", reason: message.stopReason, message });
      stream.end(message);
    });
 
    return stream;
  }
 

注意③——ScriptedModel 忠实模拟了真 Provider 的流式行为：文字块吐 text_delta，工具调用块先吐 toolcall_delta 再吐 toolcall_end。不是一次性返回，是一条一条 push。

而且它每次 stream() 被调用时会把收到的 context 存进 requests 数组。测试结束你可以断言「第二轮调用收到的 messages 里有第一轮的 toolResult」。

ScriptedModel 不是 mock，是可执行规格。它把模型契约固化成可断言的数据。Agent 测试从「大概对」变成「精确对」。

● ● ●

小结

概念解法
消息怎么存三种角色：user / assistant / toolResult
模型回复结构内容块数组：TextContent + ToolCall 混排
工具结果怎么存独立角色 toolResult + toolCallId 配对
模型回复有几种结局StopReason 五种：stop/length/toolUse/error/aborted
流式过程怎么表达ModelEvent 六种事件，每个带 partial
Agent 怎么测ScriptedModel 写成可执行规格，确定性回放

两个文件定义了 Pi 所有数据流动的形状。下一篇 Checkpoint 05——Pi 怎么接不同的模型。
