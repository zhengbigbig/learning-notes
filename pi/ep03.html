这是《动手学 Pi》系列第 3 篇。

你打开 Pi，敲一句「帮我查一下今天的天气」。Pi 收到这句话，内部会怎么存它？过几秒模型回了一段话加一个工具调用，这个回复长什么样？工具执行完把结果塞回对话，那条结果消息又是什么结构？

如果你只看 UI，这些都不重要——框里显示什么就看什么。但如果你想给 Pi 加一个工具、改一下 Agent loop、或者写个测试验证「模型调工具时 Agent 会正确执行」，你就绕不开一个问题：消息在 Pi 内部到底长什么样。

这一篇拆 Checkpoint 03（消息 IR）和 Checkpoint 04（ScriptedModel），对应 src/types.ts 和 src/scripted-model.ts。两个文件加起来不到三百行，但定义了 Pi 跟模型之间所有数据流动的形状。

● ● ●

一条消息拆成块：TextContent 与 ToolCall

先看最底层。你在 Pi 里看到的「模型说了一段话，然后调了个工具」，在源码里是两个不同的内容块。

types.ts:1-12

// 文字块：一段纯文本，用 type:"text" 做判别
export interface TextContent {
  type: "text";
  text: string;
}
 
// 工具调用块：模型决定调一个工具
export interface ToolCall {
  type: "toolCall";
  id: string;          // 这次调用的唯一标识，工具结果靠它回指
  name: string;        // 工具名
  arguments: unknown;  // 参数类型故意是 unknown：从 JSON 来，先不信，由工具自己验
  rawArguments?: string; // 流式阶段还没拼完整的半截 JSON 字符串
}
 

两个块都有一个 type 字段做判别，这是上一讲 tagged union 的延续。arguments 的类型是 unknown 而不是 any——边界处先不信，是 Pi 一以贯之的线。rawArguments 是给流式用的：模型一个字符一个字符吐 JSON，在 JSON 还没拼完整时你拿不到 arguments，只能拿到半截字符串。

两个块合起来叫 AssistantContent：

types.ts:14

// 助手消息的内容是数组：文字和工具调用可以按顺序混排
export type AssistantContent = TextContent | ToolCall;
 

一行代码，但含义重。一次回复里可以同时有文字和工具调用，而且按数组顺序表达「先说一段话，再调一个工具」这种自然节奏。这跟「文字一个字段、工具调用另一个字段」的做法刻意不同。

● ● ●

三种消息角色：toolResult 为什么不能伪装成 user

内容块只描述「一段话或一个调用」，完整的消息还要带角色。Pi 定义三种角色：

types.ts:29-54

// 用户消息：只有文字
export interface UserMessage {
  role: "user";
  content: TextContent[];
  timestamp: number;
}
 
// 助手消息：字段最多，承载模型的所有元信息
export interface AssistantMessage {
  role: "assistant";
  content: AssistantContent[];
  provider: string;       // 哪家 provider
  model: string;          // 哪个 model
  usage: Usage;           // token 用量
  stopReason: StopReason; // 为什么停
  errorMessage?: string;  // 出错时的信息
  timestamp: number;
}
 
// 工具结果消息：独立成一种 role，不伪装成 user
export interface ToolResultMessage<TDetails = unknown> {
  role: "toolResult";
  toolCallId: string;   // 回指是哪次工具调用
  toolName: string;     // 调了哪个工具
  content: TextContent[];
  details?: TDetails;   // 工具可挂自定义结构化数据，泛型默认 unknown
  isError: boolean;     // 这次调用有没有失败
  timestamp: number;
}
 

UserMessage 最简单，只有文字和时间戳。AssistantMessage 字段最多，因为它要把模型的元信息全记下来——你哪天想统计「这个 provider 平均消耗多少 token」，直接遍历 usage 字段就行，不用额外埋点。

重点看 ToolResultMessage。如果你用过 Anthropic 的原始 API，会发现它把工具结果塞进 user 角色里。Pi 偏要把 toolResult 独立成一种 role。看字段就懂了：toolCallId 回指哪次调用、toolName 记录调了谁、isError 标记成败。用户消息天生是「人说的话」，工具结果是「机器执行的结果」，两者的语义边界不该混在一个 role 里。独立成 role 后，Agent 回放历史时能一眼分清「这是用户输入」还是「这是工具返回」，断言和调试都干净得多。

三种消息用一个联合收口：

types.ts:56-59

// 整个对话历史就是 AgentMessage[]
export type AgentMessage =
  | UserMessage
  | AssistantMessage
  | ToolResultMessage;
 

上游 provider 不管怎么返回——OpenAI、Anthropic、Bedrock——进了 Pi 都被归一化成这三种消息。这就是 canonical IR 的意义。

● ● ●

StopReason：模型回复的五种结局

模型每次回复都有一个「为什么停了」的理由。Pi 枚举了五种：

types.ts:22-27

// 模型回复的五种结局，覆盖 Agent loop 所有分支决策点
export type StopReason =
  | "stop"     // 自然说完，遇到 stop token
  | "length"   // 撞到 max_tokens，被截断
  | "toolUse"  // 决定调工具，主动让出控制权
  | "error"    // provider 报错（限流、鉴权失败、内容违规）
  | "aborted"; // 被调用方主动中断（用户点了停止）
 

Agent loop 看到这五种值就走不同分支：toolUse 去执行工具，error / aborted 终止，stop / length 把控制权交回用户。少一种，loop 就有一个分支没法表达。你在调试时如果发现 Agent 行为诡异，第一步就是看上一轮的 stopReason——它几乎就是 loop 的转辙器。

● ● ●

ModelEvent：流式过程的六种事件

StopReason 描述结局，ModelEvent 描述过程。模型一边吐 token 一边发事件，Pi 把事件分成六种：

types.ts:73-102

export type ModelEvent =
  // 流开始，给一个空壳 partial
  | { type: "start"; partial: AssistantMessage }
  // 文字增量，contentIndex 指明是第几个内容块
  | {
      type: "text_delta";
      contentIndex: number;
      delta: string;
      partial: AssistantMessage;
    }
  // 工具调用参数的增量（半截 JSON 字符串）
  | {
      type: "toolcall_delta";
      contentIndex: number;
      delta: string;
      partial: AssistantMessage;
    }
  // 一个工具调用收尾，给出完整的 ToolCall
  | {
      type: "toolcall_end";
      contentIndex: number;
      toolCall: ToolCall;
      partial: AssistantMessage;
    }
  // 正常结束：reason 只能是三种"非错误"StopReason
  | {
      type: "done";
      reason: Extract<StopReason, "stop" | "length" | "toolUse">;
      message: AssistantMessage;
    }
  // 异常结束：reason 只能是两种"错误"StopReason
  | {
      type: "error";
      reason: Extract<StopReason, "error" | "aborted">;
      error: AssistantMessage;
    };
 

这里有个精妙的类型约束：done 的 reason 用 Extract 收窄，error 的 reason 用 Extract 收窄。你永远构造不出一个 done 事件却带 error reason——编译器直接拦下。这种「用类型编码业务不变量」的做法，是 TypeScript 相比动态语言的硬收益。

contentIndex 字段也要注意。前面说 AssistantContent 是数组、文字和工具调用按顺序混排，contentIndex 就是告诉消费者「这个 delta 属于第几个块」，有了它增量能精确拼回正确的位置。

textOf()：有损投影

types.ts:133-138

// 从任意消息里把所有文字块抽出来拼成字符串
// 有损投影：工具调用块被丢弃，只剩文字
export function textOf(message: AgentMessage): string {
  const blocks: readonly AssistantContent[] = message.content;
  return blocks.flatMap((block) =>
    block.type === "text" ? [block.text] : []
  ).join("\n");
}
 

textOf() 看着不起眼，但写测试时天天用。它让断言写成 assert(textOf(msg) === "hello")，而不是手动遍历 content 数组。注意它是「有损投影」——工具调用块被丢弃，只剩文字。所以它只适合做「这条消息的文字部分对不对」的断言，不能拿它验证工具调用是否正确。

types.ts:140-155

// 构造助手消息的工厂，默认 provider:"scripted" 泄露了主要用途：给 ScriptedModel 造消息
export function assistantMessage(
  content: AssistantContent[],
  stopReason: StopReason = "stop",
  overrides: Partial<AssistantMessage> = {},
): AssistantMessage {
  return {
    role: "assistant",
    content,
    provider: "scripted",
    model: "scripted-v1",
    usage: EMPTY_USAGE,
    stopReason,
    timestamp: Date.now(),
    ...overrides, // 先填默认值再 spread 覆盖，Pi 构造复杂对象的惯用法
  };
}
 

text()、userMessage() 同理，把字符串包成对应的消息对象，让测试里写 userMessage("hi") 就行，不用手搓一坨对象字面量。

使用者问题：Agent 怎么测才可靠

到这里 CP03 讲完了，IR 定义清楚了。但有个现实问题：你想测 Agent 的行为，比如「模型调工具时 Agent 会正确执行并回传结果」，怎么测？

真去打 OpenAI 的 API 有三个毛病：慢、贵、不可复现——今天模型这么回，明天换个说法，断言就挂了。少测一种结局，就有一个 loop 分支没被验证过。

CP04 的答案是 ScriptedModel——你给它一张「剧本表」，它就按表逐字吐出来。源码在 src/scripted-model.ts。

scripted-model.ts:11-17

// 剧本的一条：要么直接给完整的 AssistantMessage，要么给一个简化结构模拟出错/中断
// 这种联合让写测试的人能一句话描述「这一轮模型该怎么反应」
export type ScriptedTurn =
  | AssistantMessage
  | {
      stopReason: "error" | "aborted";
      errorMessage: string;
      partialText?: string;
    };
 

类上面有一条注释，直接点明设计意图：

scripted-model.ts:36-38

/**
 * ScriptedModel 不是 mock 掉设计问题，
 * 而是把预期的多轮行为写成可执行规格。
 */
 

这句话是 CP04 的题眼。Mock 的潜台词是「绕过设计」，scripted 的潜台词是「固化设计」。你声称模型会先调工具再总结，那就把这条轨迹喂给 ScriptedModel，跑一遍，断言每一步都对得上。

● ● ●

ScriptedModel：requests 与 cursor

scripted-model.ts:39-43

// implements Model 意味着它跟真 provider adapter 实现同一个接口
// Agent 代码对它俩完全无感——依赖倒置，后面所有 provider 能插拔的基础
export class ScriptedModel implements Model {
  readonly requests: AgentContext[] = []; // 公开 readonly，记录每次 stream() 收到的上下文
  private cursor = 0;                      // 游标，指向下一次该吐第几条 turn
 
  constructor(private readonly turns: ScriptedTurn[]) {} // 剧本，不可替换
}
 

三个成员撑起整个类。requests 是关键钩子——测试结束后可以断言「Agent 第二轮发来的 messages 长这样」，这是验证 Agent 行为的核心。

● ● ●

stream()：queueMicrotask 模拟异步

scripted-model.ts:45-52

stream(
  context: AgentContext,
  options: { signal?: AbortSignal } = {},
): AssistantMessageEventStream {
  const stream = new AssistantMessageEventStream();
  // structuredClone 深拷贝：防止调用方事后修改 context 污染记录
  this.requests.push(structuredClone(context));
  const turn = this.turns[this.cursor++]; // 取出当前 turn 并自增游标
 
  queueMicrotask(() => {
    // ... 所有事件都在这里 push
  });
 
  return stream;
}
 

为什么用 queueMicrotask 而不直接同步 push？因为真模型是异步的。如果 ScriptedModel 同步 push，消费者还没 for await 起来，事件就全堆在 queue 里，时序跟真实场景完全不一样。用 microtask 把 push 推迟到当前同步代码结束之后，消费者才有机会先挂起 iterator 再接收事件。这是忠实模拟异步时序的关键。

microtask 内部三条路径，按顺序看。

路径一：abort 检查。

scripted-model.ts:54-61

// 进来先看 AbortSignal：已 abort 就直接吐 error 事件
// 这让"测试中断"成为零成本用例——构造一个已 aborted 的 signal 传进去就行
if (options.signal?.aborted) {
  const aborted = assistantMessage([], "aborted", {
    errorMessage: "Request was aborted",
  });
  stream.push({ type: "error", reason: "aborted", error: aborted });
  stream.end(aborted);
  return;
}
 

路径二：turns 耗尽。

scripted-model.ts:63-70

// cursor 超过 turns.length：剧本写少了，Agent 多问了一轮但测试没准备
// 不假装、不沉默，直接报明确的 error——fail fast，错误信息能定位是第几轮缺 turn
if (!turn) {
  const exhausted = assistantMessage([], "error", {
    errorMessage: "ScriptedModel 没有更多响应",
  });
  stream.push({ type: "error", reason: "error", error: exhausted });
  stream.end(exhausted);
  return;
}
 

路径三：正常播放一条 turn。

scripted-model.ts:72-74

const message = terminalMessage(turn); // turn 联合 → AssistantMessage
const partial = partialFrom(message);  // 造一个空壳 partial
stream.push({ type: "start", partial: structuredClone(partial) });
// 每个 partial 都 structuredClone：同一个 partial 后续会被修改，不 clone 消费者拿到的引用会跟着变
 

然后遍历 message 的每个内容块。文字块：

scripted-model.ts:76-87

message.content.forEach((block, contentIndex) => {
  if (block.type === "text") {
    partial.content = [
      ...partial.content,
      structuredClone(block),
    ];
    stream.push({
      type: "text_delta",
      contentIndex,
      delta: block.text, // 整段吐，不做字符级切片，测试用不着那么细
      partial: structuredClone(partial),
    });
  }
 

工具调用块分两步：

scripted-model.ts:88-115

  } else {
    const toolCall = structuredClone(block) as ToolCall;
    // rawArguments 是半截字符串的形式，先于完整解析
    const rawArguments =
      toolCall.rawArguments ??
      JSON.stringify(toolCall.arguments) ??
      "null";
    // 第一步：toolcall_delta，partial 里这一块 arguments 还是空对象
    partial.content = [
      ...partial.content,
      {
        ...toolCall,
        arguments: {},
        rawArguments,
      },
    ];
    stream.push({
      type: "toolcall_delta",
      contentIndex,
      delta: rawArguments,
      partial: structuredClone(partial),
    });
    // 第二步：toolcall_end，partial 里这一块替换成完整 ToolCall
    partial.content[contentIndex] = toolCall;
    stream.push({
      type: "toolcall_end",
      contentIndex,
      toolCall,
      partial: structuredClone(partial),
    });
  }
});
 

这两步忠实模拟真 provider 的流式行为：参数先以半截字符串到达，最后才解析成完整对象。如果你写的消费者只处理 toolcall_end 不处理 toolcall_delta，在真 provider 下会丢半截渲染——ScriptedModel 能提前暴露这个问题。

最后是终态：

scripted-model.ts:118-131

// stopReason 决定 push done 还是 error
// 编译器保证不会 push 一个 reason 不匹配的事件
const terminal: ModelEvent =
  message.stopReason === "error" || message.stopReason === "aborted"
    ? {
        type: "error",
        reason: message.stopReason,
        error: message,
      }
    : {
        type: "done",
        reason: message.stopReason,
        message,
      };
stream.push(terminal);
stream.end(message); // 收口
 

这里的类型分支跟 CP03 的 ModelEvent 定义严丝合缝。

● ● ●

小结

CP03（消息 IR）回答「消息在 Pi 内部长什么样」：

  •  TextContent / ToolCall 两个内容块，AssistantContent 是它们的联合——文字和工具调用能在一个回复里按顺序混排
  •  UserMessage / AssistantMessage / ToolResultMessage 三种角色，toolResult 独立是为了语义边界清晰
  •  StopReason 五种值覆盖 Agent loop 所有分支决策点
  •  ModelEvent 六种事件描述流式过程，done / error 的 reason 用 Extract 收窄，编译期杜绝非法组合
  •  textOf() 是有损投影，让断言简短

CP04（ScriptedModel）回答「Agent 怎么测才可靠」：

  •  ScriptedTurn 联合让「这一轮模型该怎么反应」一句话可描述
  •  requests 深拷贝记录每次上下文，cursor 游标推进剧本
  •  queueMicrotask 把 push 推迟到同步代码之后，忠实模拟异步时序
  •  abort → turns 耗尽 → 正常播放，三条路径都 fail fast
  •  工具调用分 toolcall_delta + toolcall_end 两步，模拟半截参数到达
  •  ScriptedModel 不是 mock，是可执行规格——它把模型契约固化成可断言的数据
