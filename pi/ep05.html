Pi怎么把模型和工具串成循环：Agent Loop｜动手学Pi EP05

你在 Pi 里输入「帮我读一下 README」。接下来发生的事，拆开看是这样一串动作：

1. Pi 把你的话和一份工具清单打包，发给模型；

2. 模型回了一句话，里面夹着「我要调 read 工具，参数是 path=README」；

3. Pi 把这句话拆出来，真的去执行 read；

4. 读到的内容塞回对话，再发给模型；

5. 模型这次看到文件内容了，回你一句人话：「这个项目是……」。

这五步来回转，就是 Agent 的核心——一个循环。问题是，这个循环在源码里到底怎么写的？谁在转它？转到什么时候停？工具报错了怎么办？

EP04 拆完适配器，模型能说话了；这一篇拆两个文件：src/tool.ts（188 行，定义工具长什么样）和 src/agent-loop.ts（297 行，把模型和工具串成循环）。对应课程的 Checkpoint 06（工具契约）和 Checkpoint 07（Agent Loop）。

Checkpoint 06：一个工具由什么组成

先回答最朴素的问题：模型嘴里说的「工具」，在代码里是什么形状？答案在 tool.ts 第 103-111 行：

// src/tool.ts 第 103-111 行
export interface Tool<TParameters = unknown, TDetails = unknown> {
  name: string;            // 工具叫什么，模型靠它喊人
  description: string;     // 工具能干什么，模型靠它判断该不该用
  schema: Schema<TParameters>;  // 参数长什么样（菜单 + 验参一体）
  execute(                 // 真正干活的函数
    parameters: TParameters,
    context: ToolContext,
  ): Promise<ToolOutput<TDetails>>;
}

四个字段拆成两组：name + description + schema 是给模型看的「菜单」（对外声明），execute 是「厨房」（对内执行）。菜单和厨房写在同一个接口里，但职责分得清清楚楚——schema 负责验参，execute 负责干活，两步分开，这是后面健壮性的根。

Schema：菜单和验参必须同源

schema 字段的类型是 Schema<T>，定义在第 9-12 行：

// src/tool.ts 第 9-12 行
export interface Schema<T> {
  parse(value: unknown): T;              // 运行时验参：unknown 收窄成 T
  jsonSchema?: Record<string, unknown>;  // 给模型看的 JSON Schema 菜单
}

两件事：parse 给运行时用，jsonSchema 给模型看。一份参数描述，同时服务编译器和模型，必须同源。Pi 用积木拼装它们，核心是 objectSchema，第 50-84 行：

// src/tool.ts 第 50-84 行（节选）
export function objectSchema<
  TShape extends Record<string, Validator<unknown>>,
>(shape: TShape): Schema<{ /* ... */ }> {
  return {
    jsonSchema: {
      type: "object",
      properties: Object.fromEntries(
        Object.entries(shape).map(([key, validator]) => [
          key,
          validator.jsonSchema ?? {},  // 每个积木自带 jsonSchema 片段
        ]),
      ),
      required: Object.entries(shape)
        .filter(([, v]) => !v.optional)  // 非可选字段才进 required
        .map(([key]) => key),
      additionalProperties: false,        // 模型多塞字段直接拒
    },
    parse(value) {
      if (!value || typeof value !== "object" || Array.isArray(value)) {
        throw new Error("参数必须是 object");  // 不是对象直接拒
      }
      // 逐字段调每个积木的 validator，任一失败就抛
      const result = {} as { /* ... */ };
      for (const [key, validator] of Object.entries(shape)) {
        result[key as keyof TShape] = validator(
          (value as Record<string, unknown>)[key],
        ) as ReturnType<TShape[keyof TShape]>;
      }
      return result;
    },
  };
}

一个函数同时产出 jsonSchema（给模型）和 parse（给运行时）。改一处积木，两边同步更新，不会出现菜单说要有 path、代码却忘了验这种裂缝。

ToolRegistry：重名注册直接炸

工具多了得集中管。ToolRegistry（第 113-144 行）底层就是一个 Map：

// src/tool.ts 第 113-144 行（节选）
export class ToolRegistry {
  private readonly tools = new Map<string, Tool<unknown, unknown>>();
 
  register<TParameters, TDetails>(tool: Tool<TParameters, TDetails>): void {
    if (this.tools.has(tool.name)) {
      throw new Error(`Tool 已存在：${tool.name}`);  // 重名直接抛，不静默覆盖
    }
    this.tools.set(tool.name, tool as Tool<unknown, unknown>);
  }
 
  definitions(): ToolDefinition[] {
    // 把所有工具的菜单抽出来，就是每次调模型塞进 tools 字段的那份清单
    return this.list().map((tool) => ({
      name: tool.name,
      description: tool.description,
      parameters: tool.schema.jsonSchema ?? { type: "object" },
    }));
  }
}

重名注册直接抛错，不是覆盖。两个工具撞名，模型调的时候 registry 返回哪个就成了玄学，不如启动时就炸掉。definitions() 把菜单转成数组——这就是每次发给模型的那份工具清单。

executeToolCall：四步管线，绝不把异常抛出去

Checkpoint 06 最核心的函数是 executeToolCall（第 162-188 行），它把零件串成一条管线：

// src/tool.ts 第 162-188 行
export async function executeToolCall(
  call: ToolCall,
  registry: ToolRegistry,
  context: Omit<ToolContext, "callId"> = {},
): Promise<ToolResultMessage> {
  const tool = registry.get(call.name);          // 第一步：按名字查工具
  if (!tool) return failedResult(call, new Error("未知工具"));  // 查不到，返回失败结果
 
  try {
    const parameters = tool.schema.parse(call.arguments);  // 第二步：schema 验参
    const output = await tool.execute(parameters, {        // 第三步：执行
      ...context,
      callId: call.id,
    });
    return {                                  // 第四步：组装成结构化结果
      role: "toolResult",
      toolCallId: call.id,
      toolName: call.name,
      content: output.content,
      details: output.details,
      isError: output.isError ?? false,
      timestamp: Date.now(),
    };
  } catch (error) {
    return failedResult(call, error);         // 验参或执行抛错，统统归一化
  }
}

四步：查找、验参、执行、组装。每一步都可能失败，但没有任何一步会把异常抛出这条函数。catch 把所有错误兜住，转成 failedResult：

// src/tool.ts 第 146-160 行
function failedResult(call: ToolCall, error: unknown): ToolResultMessage {
  const message = error instanceof Error ? error.message : String(error);
  return {
    role: "toolResult",
    toolCallId: call.id,
    toolName: call.name,
    content: [text(`Tool ${call.name} failed: ${message}`)],  // 失败原因写进正文
    details: { error: message },
    isError: true,                          // 用标志位区分成败，不靠抛异常
    timestamp: Date.now(),
  };
}

工具失败不抛异常，而是返回一个带 isError 标志的正常结果。为什么这么做？因为 Agent Loop 是个循环——工具一抛异常整个 loop 就崩，一个工具抽风就拖死整段对话。用 isError 标志，失败的真相原样送回模型，让模型自己决定怎么办：换个工具、放弃、或老实告诉用户。这比异常被吞掉或直接崩掉都健康得多。

到这里 Checkpoint 06 闭环了：ToolDefinition 是菜单，Tool 是菜单加厨房，ToolRegistry 管一堆 Tool，executeToolCall 把「模型说要调工具」变成「真的调了并拿到结果」。但这些都是零件——谁在调用它们？这就是 Checkpoint 07 的事。

Checkpoint 07：Agent Loop 不是 while True

最朴素的写法是 while True 调模型、看有没有工具调用、有就执行、把结果塞回去、再调模型。Pi 没这么写。先看 runAgentLoop 的骨架（第 146-167 行）：

// src/agent-loop.ts 第 146-167 行
export async function runAgentLoop(options: AgentLoopOptions): Promise<AgentRunResult> {
  const messages = structuredClone(options.context.messages);  // 深拷贝，循环内的修改不影响调用方
  const maxSteps = options.maxSteps ?? 32;                     // 有上限，不是 while True
  const executeToolCall: ToolExecutor =
    options.executeToolCall ??
    ((call, context) => executeCoreToolCall(call, options.tools, context));
  let ended = false;                          // 保证 turn_end 事件只发一次
  const finish = (reason, steps): AgentRunResult => {
    if (!ended) {
      ended = true;
      emit(options, { type: "turn_end", reason });
    }
    return { reason, messages, steps };
  };
 
  for (let steps = 1; steps <= maxSteps; steps += 1) {  // for 循环，不是 while

三个细节值得停一下。第一，messages 是 structuredClone 出来的副本——循环里不断往里 push 工具结果，但调用方手里的原数组不受影响。第二，Agent Loop 有 maxSteps 上限（默认 32），不是 while True。模型可能陷入死循环、反复调同一个工具、来回扯皮不收敛。有上限，最坏跑 32 步然后停下来。源码注释写得很直白（第 48-51 行）：这个 maxSteps 是课程增强，防止错误脚本无限循环。第三，finish 函数的 ended 标志保证 turn_end 事件只发一次——哪怕多条分支都能触发结束，也只有第一条会真的 emit。

流式调模型：边来边转发

循环体第一步是调模型（第 172-185 行）：

// src/agent-loop.ts 第 172-185 行
let assistant: AssistantMessage;
try {
  const stream = options.model.stream(
    {
      systemPrompt: options.context.systemPrompt,
      messages,                              // 当前累积的对话
      tools: options.tools.definitions(),    // 工具清单每次都带上
    },
    { signal: options.signal },              // AbortSignal，用户取消时触发
  );
  for await (const event of stream) {        // 边流边转发事件给上层（UI 实时显示）
    emit(options, { type: "model_event", event });
  }
  assistant = structuredClone(await stream.result());  // 流结束才拿完整结果
} catch (error) {
  const failed = failedModelTurn(error, options.signal?.aborted === true);
  messages.push(failed.message);
  emit(options, { type: "assistant_message", message: failed.message });
  return finish(failed.reason, steps);       // 模型调用失败，归一成 error 或 aborted
}

模型是流式调的，事件边来边转发，但最终结果要等流结束才拿。stream.result() 返回完整的 AssistantMessage，这时候文本和工具调用都攒齐了。signal 是 AbortSignal，用户点取消时它会被触发，failedModelTurn 据此区分「真的出错」还是「被用户取消」。

stopReason 分流：五种终止方式

拿到 assistant 消息后，关键来了——根据 assistant.stopReason 分流。这是整个 loop 最精密的部分。

length：响应被截断了（第 202-211 行）：

// src/agent-loop.ts 第 202-211 行
if (assistant.stopReason === "length") {
  for (const call of calls) {
    const result = skippedCall(call, "length");  // 不执行，但配一个 skipped 结果
    messages.push(result);
    emit(options, { type: "tool_skipped", result });
  }
  return finish("length", steps);
}

length 意味着 token 到上限了，模型的话被硬切。这时候工具调用的参数可能是半截 JSON——执行它就是灾难。所以 Pi 绝不执行，但给每个已经形成的 call 配一个 skippedCall 结果。为什么不能直接丢掉？因为 transcript 里 assistant 消息已经带了 toolCall，下一条必须是对应的 toolResult——少一条，下一轮模型看到「我说了要调工具，但没有结果回来」，会彻底懵掉。error 和 aborted 两个分支（第 213-224 行）逻辑一样，配 skipped 后 finish。

stop：模型说「我好了」（第 226-249 行）。这是最微妙的分支：

// src/agent-loop.ts 第 226-249 行（节选）
if (assistant.stopReason === "stop") {
  if (calls.length > 0) {
    // 模型说停却带着工具调用，这是矛盾状态，当 error 处理
    for (const call of calls) {
      const result = skippedCall(call, "unexpected-stop");
      messages.push(result);
      emit(options, { type: "tool_skipped", result });
    }
    return finish("error", steps);
  }
  const steering = options.takeSteeringMessages?.() ?? [];  // 有没有人中途纠偏
  if (steering.length > 0) {
    messages.push(...steering);
    continue;                                  // 插了消息就回循环顶部再调一次
  }
  const followUps = options.takeFollowUpMessages?.() ?? [];  // 有没有人接着追问
  if (followUps.length > 0) {
    messages.push(...followUps);
    continue;
  }
  return finish("stop", steps);                // 没人插话，才真正结束
}

模型说停却带着工具调用，这是一种矛盾状态——很多框架不做这个判断，直接执行了事，结果模型本意是停、工具却被跑了，行为和意图对不上。Pi 当 error 处理，但 calls 仍配 skipped 结果。

如果模型干干净净地停了（没有 calls），Pi 还不急着结束——它先问有没有人中途插话。那两个 takeSteeringMessages 和 takeFollowUpMessages 是给循环外留的钩子：steering 是纠偏消息（模型跑偏了，外部塞一条拽回来），followUp 是追问消息（模型答完了，外部接着问下一句）。有了它们，++一个 loop 既能跑长任务，又能响应外部干预==。注意 continue——插了消息后不是结束，而是回循环顶部再调一次模型。如果都没插话，才真正 finish stop。

toolUse 分支：并发执行，按原顺序回填

最后是默认分支——stopReason 不是上面四种，那就是 toolUse，模型要调工具（第 251-291 行）：

// src/agent-loop.ts 第 251-291 行（节选）
if (calls.length === 0) {
  return finish("error", steps);   // 说了要调工具却没给 call，错误
}
 
calls.forEach((call) => emit(options, { type: "tool_start", call }));
const results = await Promise.all(           // 并发执行所有调用
  calls.map(async (call) => {
    let result: ToolResultMessage;
    try {
      result = canonicalToolResult(
        call,
        await executeToolCall(call, {
          signal: options.signal,
          reportProgress: (content) => {     // 工具可上报进度，边跑边转发
            emit(options, { type: "tool_progress", callId: call.id, content });
          },
        }),
      );
    } catch (error) {
      result = failedExecution(call, error);  // 注入的执行器不一定归一化异常
    }
    emit(options, { type: "tool_end", result });
    return result;
  }),
);
 
for (const result of results) {              // 按原始 call 顺序追加，不按完成顺序
  messages.push(result);
}

三个设计点。第一，Promise.all 并发执行所有工具调用，但按原始 call 顺序回填结果。模型一轮可能调好几个工具——读文件、查数据库、算数学——串行执行浪费时间，并发才是正解。Promise.all 的返回值按 calls 原始顺序排，不按完成顺序，所以追加进 messages 时和 calls 一一对应。第二，每个 call 的 catch 都走 failedExecution——一个工具崩了不能拖垮同批的其他工具，这正是 Checkpoint 06 把异常归一化成 isError 的用意。第三，canonicalToolResult（第 116-128 行）做了 structuredClone 验证，工具返回必须可结构化克隆，不可克隆的直接判失败，保证 transcript 能序列化、能回放。

执行完工具，结果进 messages，循环回到顶部再调一次模型——模型这次看到的就是「我上一轮调的工具，结果回来了」。这就是「模型说、工具做、结果回」的完整闭环。如此往复，直到模型说 stop、或撞上 maxSteps、或出错。

skippedCall：给悬空的 toolCall 配对

前面好几个分支都调了 skippedCall，值得单独看它干了什么（第 67-91 行）：

// src/agent-loop.ts 第 67-91 行
function skippedCall(
  call: ToolCall,
  reason: "length" | "error" | "aborted" | "unexpected-stop",
): ToolResultMessage {
  const explanation =
    reason === "length" ? "the model response was truncated"
      : reason === "unexpected-stop" ? "the model returned stop with a tool call"
      : `the model turn ended with ${reason}`;
  return {
    role: "toolResult",            // 仍是一条正常的 toolResult
    toolCallId: call.id,           // id 和原 call 对得上
    toolName: call.name,
    content: [{ type: "text", text: `Tool call was not executed because ${explanation}.` }],
    details: { skipped: true, reason },  // 标记为 skipped
    isError: true,
    timestamp: Date.now(),
  };
}

这个函数的全部意义，是维护 transcript 的结构完整性。LLM 对话格式有个硬约束：assistant 消息里每个 toolCall，后面必须跟一条 toolCallId 对得上的 toolResult。少一条，下一轮模型的输入就是残缺的，轻则重复调用，重则直接报错。skippedCall 就是给那些不该执行但已经形成了的 call 配一个占位结果，把残缺补齐。

小结

两个文件，把 Agent 怎么干活讲透了。几个要点：

  • Tool 接口菜单和厨房合一：schema 验参，execute 干活，职责分清
  • objectSchema 一处积木同时生成 jsonSchema 和 parse，菜单和运行时永不脱节
  • executeToolCall 四步管线绝不抛异常，失败一律归一化成带 isError 的结果
  • Agent Loop 有 maxSteps 上限（默认 32），不是 while True，模型抽风最坏跑 32 步
  • stopReason 五路分流：length、error、aborted 配 skipped，stop 先查矛盾再查 steering，toolUse 并发执行
  • Promise.all 并发跑工具但按原顺序回填，一个崩不拖垮同批
  • skippedCall 的全部意义是维护 transcript 结构完整，每个 toolCall 都必须有配对的 toolResult

回到开头那个「帮我读 README」的例子，现在能完整说清了：你说完这句话进 loop，模型第一轮流式返回一个带 read 工具调用的 assistant 消息（stopReason 是 toolUse），Pi 并发执行（这批只有一个），read 读到的内容变成 toolResult 塞回 messages，循环回到顶部再调模型，模型第二轮看到文件内容、回复人话、stopReason 是 stop、没有工具调用——loop 结束。五步，全在这 297 行里。

读完这两个文件最大的感受：Agent 的健壮性，全藏在「失败时不抛异常而是归一化成结果」这个决定里。工具崩了不拖死 loop，模型截断了不留悬空 call，用户取消了能干净退出——这些都不是正常路径能体现的，全靠异常分支的设计撑着。写 Agent，百分之八十的代码在处理不正常情况，正常路径反而简单。
