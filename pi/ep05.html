大家好，我是郑同学。

上篇拆了 provider 适配器——模型怎么把话说出来。但有个问题一直没回答：你在 Pi 里输入「帮我读一下 README」，中间到底发生了什么？

模型不会直接读文件。它会先吐一句「我来读一下」，然后发起一个 read_file 的 tool call；Pi 执行这个工具，把文件内容塞回消息历史；模型拿到内容，再吐一句总结。模型说话 → 工具执行 → 结果塞回 → 模型再说话，这个来回就是 Agent Loop。

这一篇拆两个文件：tool.ts（188 行，工具怎么定义和调用）和 agent-loop.ts（297 行，循环怎么转）。两个文件加起来不到 500 行，却是整个 Pi 最核心的部分。

先记四句口诀，后面所有代码都在讲这四句话：schema 管两头，循环转模型，并发不串台，出错不穿堂。

● ● ●

先看大图：循环长什么样

先不贴代码，用一张流程图看清全局：

换成马的比喻理解：模型是马，harness 是马鞍。马有腿能跑、有脑能认路，但你不能直接骑上去——你需要一套马鞍、缰绳、马蹄铁，让骑手能控制方向、让马能驮重物。Agent Loop 就是这套 harness：模型本身只会生成 token，harness 给它套上工具（缰绳）、消息历史（鞍囊）、循环控制（马蹄铁），它才能成为一个能干活的 Agent。

具体到 Pi 的循环：模型每一步只能做一件事——看到 messages 和 tools，决定下一步调哪个工具。它自己不碰文件系统、不跑命令。工具是真正干活的人——read 真的去读文件、bash 真的去执行命令。ToolRegistry 是花名册——记录所有已注册的工具，每轮把清单递给模型。

一轮循环就是：模型看 messages 和 tools → 决定调哪个工具（tool call）→ 工具执行出结果 → 结果塞回 messages → 模型看到结果再决定下一步。如果没有 tool call 了，模型直接回复用户（stop），循环结束。

整个 runAgentLoop 就是一个 for 循环，最多转 32 圈。每一圈：调一次模型、可能执行一批工具、把结果追加进消息历史。我们从头拆。

对比真实 Claude Code 的 Agent Loop

上面的学习课程（CC s01）是一个 30 行的教学版。真实 Claude Code 的核心循环在 query.ts（1730 行），骨架长这样：

// query.ts:307 — Claude Code 的核心循环（真实源码骨架）
while (true) {
  // 调模型（流式），边收边判断有没有 tool call
  for await (const msg of callModel({...})) {  // :659
    if (msg has tool_use blocks) needsFollowUp = true
  }
  // 没调工具 → 结束
  if (!needsFollowUp) return { reason: 'completed' }  // :1357
  // 执行工具，结果追加回 messages
  for await (const update of runTools(...)) { ... }  // :1384
  state = { messages: [...old, ...assistant, ...toolResults] }
}
 

真实 CC 的骨架和 Pi 一模一样：调模型 → 检查有没有 tool call → 有就执行 → 结果塞回 → 再调。但 CC 在这骨架外面套了 1700 行的 harness（马鞍）。逐个看 Pi 和 CC 在哪些地方做了相同的选择，哪些地方走了不同的路。

① 都是 while 循环 + 退出条件

CC 和 Pi 都用 while (true) / for 循环，靠 stop reason 决定退出。但细节不同：

CC 没有 maxSteps 兜底——它用 turnCount 和 maxTurns（调用方可选传入），还有 token budget 做软限制。Pi 用硬编码 maxSteps ?? 32。

CC 的退出原因有 10 种：

// Claude Code 的 10 种退出原因
completed         // 模型自然结束
max_turns         // 达到轮次上限
aborted_streaming // 用户在模型输出时打断
aborted_tools     // 用户在工具执行时打断
prompt_too_long   // 上下文溢出，所有压缩都失败了
model_error       // API 不可恢复错误
blocking_limit    // 硬 token 上限
image_error       // 图片处理失败
stop_hook_prevented // 外部 hook 阻止继续
hook_stopped      // hook 发出硬停止信号
 

Pi 只有 5 种：stop / length / error / aborted / maxSteps。CC 多出来的都是生产环境踩坑后加的——prompt_too_long 是上下文压缩全失败、hook_stopped 是 CI/CD 集成时外部系统要叫停。

② 都是流式 + emit，但 CC 更激进

Pi 流式消费模型输出，每个 event 通过 emit 转发：

// Pi: agent-loop.ts:182-184
for await (const event of stream) {
  emit(options, { type: "model_event", event });
}
 

CC 不仅流式输出文字，还在模型还在吐的时候就开始执行工具。它有个 StreamingToolExecutor（流式工具执行器），模型吐出一个完整的 tool_use block 就立刻启动，不等整轮结束：

API 流: ┃ 文字 ┃ tool_A ┃ 文字 ┃ tool_B ┃ 结束 ┃
              │           │
     启动 A   │  启动 B   │
         ▼    ▼      ▼    ▼
工具:   ┏━━━━━━━━━━┓  ┏━━━━━━━━━━┓
        ┃ 执行 A   ┃  ┃ 执行 B   ┃
        ┗━━━━━━━━━━┛  ┗━━━━━━━━━━┛
 

Pi 是等整轮模型输出结束后才 Promise.all 并发执行。CC 更激进——边收边跑，工具执行和模型输出重叠，减少整体延迟。

③ 都并发执行工具，但 CC 做了安全分区

Pi 用 Promise.all 一股脑全并发。CC 用 partitionToolCalls（工具分区器）把工具分成两类：

  •  只读工具（Read、Glob、Grep）→ 并发执行
  •  写入工具（Edit、Write、Bash）→ 串行执行

Pi 假设所有工具都可以并发，因为 Pi 的工具都是课程级别的简单实现。CC 有 20+ 个工具，写入工具并发会导致文件冲突，所以必须分区。

④ 消息隔离：都是深拷贝

Pi 第一行就 structuredClone：

// Pi: agent-loop.ts:149
const messages = structuredClone(options.context.messages);
 

CC 用 State 对象重建——每次 continue 时构造一个全新的 State，而不是原地修改：

// Claude Code: 每次 continue 都重建 State
const next: State = {
  messages: [...messagesForQuery, ...assistant, ...toolResults],
  toolUseContext: toolUseContextWithQueryTracking,
  turnCount: nextTurnCount,
  transition: { reason: 'next_turn' },
  // ... 其他字段全量重建
};
state = next;
 

Pi 拷一份就完事，CC 每轮重建整个状态对象。CC 多出来的好处是 transition 字段记录了「为什么继续」，测试可以断言走了哪条恢复路径。

⑤ 错误恢复：Pi 三层归一，CC 七层恢复

Pi 在工具层做三层 try/catch，保证工具异常不炸循环。CC 有 7 条恢复路径（state = next; continue），按代价从低到高排序：

恢复策略触发条件做法
collapse drainprompt 太长（413）提交已暂存的上下文压缩
reactive compact413 持续现场用 LLM 做全量摘要
token escalation输出截断在 8k重试，上限提到 64k
multi-turn recovery还是被截断注入「直接继续」提示
stop hook retryhook 报告阻塞错误追加错误信息，重试
token budget continuationbudget 没用完注入「继续干」提示
normal next turn工具执行完了追加结果，正常继续

每条恢复路径都有熔断器（circuit breaker）：同一个恢复策略连续触发 3 次没进展就放弃，降级到下一条。这是踩过坑的——CC 早期版本没有熔断器，一个会话一天烧了 25 万次 API 调用。

Pi 没有这些恢复路径。教学场景不会触发 413、不会上下文溢出、不需要 token 升级。但如果 Pi 要上生产，这些路径迟早得加。

++CC 是已经上过生产的 harness，Pi 是正在长肌肉的 harness==。骨架一样，但 CC 的马鞍上多了缰绳调节器、刹车保险、疲劳检测——每一个都是真实事故的产物。

Part 1：Tool 接口——给模型看的菜单和给代码用的验参是同一份

先看一个工具长什么样：

// tool.ts:103-111
export interface Tool<TParameters = unknown, TDetails = unknown> {
  name: string;
  description: string;
  schema: Schema<TParameters>;
  execute(
    parameters: TParameters,
    context: ToolContext,
  ): Promise<ToolOutput<TDetails>>;
}
 

四个字段：名字、描述、schema、execute。前两个给模型看（模型靠 name + description 决定调不调），后两个是干活用的。

关键在 schema。它不只是类型标注，而是一份契约管两头：

// tool.ts:9-12
export interface Schema<T> {
  // 运行时验参：模型给的参数对不对
  parse(value: unknown): T;
  // 给模型看的 JSON Schema：告诉模型该工具接受什么参数
  jsonSchema?: Record<string, unknown>;
}
 

parse 是代码执行前的验参，jsonSchema 是给模型看的参数说明。同一份 schema，导出成 jsonSchema 给模型看（模型才知道怎么调），运行时又用 parse 验模型给的参数（模型可能给错）。两头同源，不会出现给模型看的说明写了「要整数」、代码里却收字符串的情况。

Pi 自己实现了几个基础 validator，然后用 objectSchema 拼装：

// tool.ts:50-84（简化）
export function objectSchema<TShape>(shape: TShape): Schema<...> {
  return {
    // 拼出给模型看的 JSON Schema
    jsonSchema: {
      type: "object",
      properties: Object.fromEntries(
        // 每个 validator 自带 jsonSchema
        Object.entries(shape).map(([key, v]) => [key, v.jsonSchema ?? {}]),
      ),
      required: Object.entries(shape)
        // 没标 optional 的都进 required
        .filter(([, v]) => !v.optional)
        .map(([key]) => key),
      additionalProperties: false,
    },
    parse(value) {
      // 运行时逐个字段验证
      ...
      for (const [key, validator] of Object.entries(shape)) {
        result[key] = validator(value[key]);
      }
      return result;
    },
  };
}
 

积木式拼装——stringValue、optionalString、optionalPositiveInteger 这些小 validator 各自带 jsonSchema 和校验逻辑，objectSchema 把它们拼成一个对象 schema。properties 和 required 从同一份 shape 算出来，菜单和验菜规则永远一致。

Part 2：ToolRegistry + executeToolCall——注册、调用、错误归一

工具定义好了，要有个地方集中管理。ToolRegistry 就是个 Map：

// tool.ts:113-118
export class ToolRegistry {
  private readonly tools = new Map<string, Tool<unknown, unknown>>();
 
  constructor(tools: Tool<never, unknown>[] | Tool[] = []) {
    tools.forEach((tool) => this.register(tool));
  }
 

register 放进去，get 拿出来，list 列全部。最关键的是 definitions()——把工具翻译成模型能看懂的格式：

// tool.ts:137-143
definitions(): ToolDefinition[] {
  return this.list().map((tool) => ({
    name: tool.name,
    description: tool.description,
    // schema 里的 jsonSchema 就是用在这儿
    parameters: tool.schema.jsonSchema ?? { type: "object" },
  }));
}
 

这个数组会塞进每轮调模型的 context.tools。模型看到的不是 Pi 内部的 Tool 对象，而是这份精简的菜单。schema.jsonSchema 在这里派上用场了——当初定义的那份契约，现在原样递给模型。

调用工具的入口是 executeToolCall，它做三件事：查注册表、验参、执行，最后把一切异常归一成 ToolResultMessage：

// tool.ts:162-188（简化）
export async function executeToolCall(call, registry, context) {
  const tool = registry.get(call.name);
  // 没注册的工具
  if (!tool) return failedResult(call, new Error("未知工具"));
 
  try {
    // 验参：模型给的参数过 schema.parse
    const parameters = tool.schema.parse(call.arguments);
    const output = await tool.execute(parameters, { ...context, callId: call.id });
    return {
      role: "toolResult",
      toolCallId: call.id,
      toolName: call.name,
      content: output.content,
      isError: output.isError ?? false,
      ...
    };
  } catch (error) {
    // 工具炸了 / 参数不合法，统一变成 failedResult
    return failedResult(call, error);
  }
}
 

注意 try/catch 的位置——它包住了 parse 和 execute 两步。参数不合法、工具内部抛错，全部被 catch 住，变成一个带 isError: true 的 ToolResultMessage。工具再怎么炸，executeToolCall 绝不抛异常出去，只会返回一个「失败结果」。这就是后面循环能稳稳转下去的前提。

failedResult 长这样：

// tool.ts:146-160
function failedResult(call, error): ToolResultMessage {
  const message = error instanceof Error ? error.message : String(error);
  return {
    role: "toolResult",
    toolCallId: call.id,
    toolName: call.name,
    content: [text(`Tool ${call.name} failed: ${message}`)],
    details: { error: message },
    isError: true,
    timestamp: Date.now(),
  };
}
 

只留 error.message，不带 stack、不带路径。这个细节后面会再强调一次。

Part 3：runAgentLoop——那个 for 循环

热身结束，正主来了。runAgentLoop 是整个 Pi 的心脏：

// agent-loop.ts:146-167（简化）
export async function runAgentLoop(options: AgentLoopOptions): Promise<AgentRunResult> {
  // 深拷贝消息历史，循环里怎么改都不污染调用方
  const messages = structuredClone(options.context.messages);
  const maxSteps = options.maxSteps ?? 32;
  const executeToolCall = options.executeToolCall ??
    ((call, context) => executeCoreToolCall(call, options.tools, context));
 
  for (let steps = 1; steps <= maxSteps; steps += 1) {
    if (options.signal?.aborted) {
      return finish("aborted", steps - 1);
    }
    ...
  }
  return finish("maxSteps", maxSteps);
}
 

三件事先记住：

  1. 01structuredClone 拷一份消息历史（JS 内置的深拷贝，递归复制所有嵌套对象）——循环内部往 messages 里 push 工具结果，但不会改到调用方传进来的 context。这是隔离。
  2. 02maxSteps 默认 32——防止模型陷入「调工具 → 再调工具」的死循环。这是兜底。
  3. 03executeToolCall 可注入——默认走 core 的 executeToolCall，但允许外部换一个。这是可测试性。

循环体里每一圈干的事：调模型（流式）→ 拿到 assistant 消息 → 看 stop reason 分支。

先说 options.model.stream 是什么。model 是 AgentLoopOptions 里传进来的，类型是 EP04 拆过的 Model 接口：

// types.ts
export interface Model {
  stream(context: AgentContext,
    options?: { signal?: AbortSignal },
  ): ModelStream;
}
 

这个接口就是上一篇讲的适配器出口——createOpenAICompatibleModel 返回的东西。它把 provider 的 SSE 字节流翻译成六种 ModelEvent，stream() 返回一个异步迭代器 + result() 方法。循环不关心你接的是 OpenAI 还是 DeepSeek，它只认这个接口。

先看怎么流式消费：

// agent-loop.ts:173-185（简化）
const stream = options.model.stream(
  {
    systemPrompt: options.context.systemPrompt,
    messages,
    // 每轮都把最新工具清单递给模型
    tools: options.tools.definitions(),
  },
  { signal: options.signal },
);
 
// 流式消费：每个 event 转发出去（UI 靠这个实时显示）
for await (const event of stream) {
  emit(options, { type: "model_event", event });
}
// 流结束，拿完整的 assistant 消息
assistant = structuredClone(await stream.result());
 

for await 把流吃干抹净，最后 result() 拿到完整消息。上一篇拆的六种 ModelEvent（模型产生的事件，如文字片段、工具调用、结束信号），在这里通过 emit（事件分发函数，把事件转发给上层监听者）转发给上层（TUI 靠这个实时打字）。stream.result() 返回组装好的 AssistantMessage（模型这一轮的完整回复），再 structuredClone 一次——防止模型实现返回的对象被后续修改。

拿到 assistant 消息后，push 进 messages，然后按 stop reason 走分支。

● ● ●

stop reason 五条岔路

模型一轮结束有五种原因，每种处理不同。这是整个循环最绕的地方，但逻辑很清晰：

// agent-loop.ts:200-248（简化）
if (assistant.stopReason === "length") {
  // 截断了，tool 参数可能是残缺的，绝不执行
  for (const call of calls) {
    const result = skippedCall(call, "length");
    messages.push(result);
  }
  return finish("length", steps);
}
 
if (assistant.stopReason === "error" || assistant.stopReason === "aborted") {
  // 模型自己出错了
  for (const call of calls) {
    const result = skippedCall(call, reason);
    messages.push(result);
  }
  return finish(reason, steps);
}
 
if (assistant.stopReason === "stop") {
  if (calls.length > 0) {
    // 模型说停了却带了 tool call，矛盾，记 error
    for (const call of calls) {
      messages.push(skippedCall(call, "unexpected-stop"));
    }
    return finish("error", steps);
  }
  // 正常结束：检查有没有 steering / followUp
  const steering = options.takeSteeringMessages?.() ?? [];
  if (steering.length > 0) { messages.push(...steering); continue; }
  return finish("stop", steps);
}
 
// 剩下的就是 toolUse：真的要调工具
 

关键设计：只要模型吐了 tool call，不管最后因为什么没执行，都必须给它补一个配对的 ToolResultMessage。

为什么？因为消息历史里，每个 toolCall 必须有对应的 toolResult。悬空的 toolCall 写进 messages（对话记录），下一轮调模型时 provider 会报错——OpenAI 要求 tool_calls 和 tool 消息一一配对。所以哪怕 length 截断了、模型出错了，也要用 skippedCall（生成一个「跳过未执行」的占位结果）补一个「这个调用没执行」的结果：

// agent-loop.ts:67-91（简化）
function skippedCall(call, reason): ToolResultMessage {
  const explanation = reason === "length"
    ? "the model response was truncated"
    : ...;
  return {
    role: "toolResult",
    toolCallId: call.id,
    toolName: call.name,
    content: [{ type: "text", text: `Tool call was not executed because ${explanation}.` }],
    details: { skipped: true, reason },
    isError: true,
    ...
  };
}
 

补配对，但不真执行。这是防御性编程——循环的每一步都保证消息历史是「合法」的，不管发生什么。

● ● ●

Part 4：并行执行工具——Promise.all 不串台

stopReason 是 toolUse 时，真正调工具。模型一轮可以同时发起多个 tool call（比如同时读两个文件），Pi 用 Promise.all（JS 的并发原语，等所有 Promise 都完成后再返回）并发执行：

// agent-loop.ts:255-282（简化）
calls.forEach((call) => emit(options, { type: "tool_start", call }));
 
const results = await Promise.all(
  calls.map(async (call) => {
    let result;
    try {
      result = canonicalToolResult(
        call,
        await executeToolCall(call, {
          signal: options.signal,
          reportProgress: (content) => {
            // 工具执行中可以回报进度
            emit(options, { type: "tool_progress", callId: call.id, content });
          },
        }),
      );
    } catch (error) {
      // 注入的执行器可能抛异常，这里兜底
      result = failedExecution(call, error);
    }
    // 哪个先完成先 emit，反映真实顺序
    emit(options, { type: "tool_end", result });
    return result;
  }),
);
 
// 但追加进 messages 必须按 call 原始顺序
for (const result of results) {
  messages.push(result);
}
 

这里有个精妙的设计：观察事件（tool_end）按真实完成顺序 emit（分发出去），但 messages 追加按 call 原始顺序。

为什么？因为 messages 里 assistant 消息的 toolCall 是有顺序的（index 0、1、2...），对应的 toolResult 必须按同样的顺序追加，否则 provider 解析会乱。Promise.all 返回的数组天然保持 map 的输入顺序，不管谁先 resolve。所以 emit 给 UI 看的是乱序的（哪个工具先干完先显示），写进历史的是有序的（和 toolCall 严格配对）。

并发执行，顺序写入。两件事分开处理，互不影响。

canonicalToolResult（规范化工具结果，确保可安全写入消息历史）还做了一道防护：

// agent-loop.ts:116-128
function canonicalToolResult(call, result): ToolResultMessage {
  try {
    return structuredClone(result);
  } catch {
    // 工具返回了不可克隆的东西（带函数、循环引用等）
    return failedExecution(
      call,
      new Error("tool result is not structured-cloneable"),
    );
  }
}
 

structuredClone 验证结果能不能安全地进 messages。工具实现要是返回了带函数、循环引用之类的对象，克隆会炸，这里兜住变成 failedExecution。

● ● ●

Part 5：出错不穿堂——错误归一化的三层防线

工具失败不该炸掉整个循环。Pi 在三个层面把异常归一：

第一层：executeToolCall（tool.ts，工具调用入口）。try/catch 包住 parse + execute，任何异常变成 failedResult（失败结果，带 isError 标记）。这一层挡住了工具内部错误。

第二层：failedExecution（agent-loop.ts，把工具异常转成错误结果）。兜住注入执行器的异常，且只留 message 不留 stack：

// agent-loop.ts:93-114（简化）
function failedExecution(call, error): ToolResultMessage {
  const message = error instanceof Error ? error.message : String(error);
  return {
    role: "toolResult",
    toolCallId: call.id,
    toolName: call.name,
    content: [{ type: "text", text: `Tool ${call.name} failed: ${message}` }],
    // 错误对象不能进 messages：可能携带 stack、路径或凭据
    details: { error: message },
    isError: true,
    ...
  };
}
 

注释写得很直白：错误对象不能进 messages，它可能携带 stack、文件路径或凭据。所以只提取 message 字符串，原始 error 对象丢掉。

第三层：Promise.all 的 catch。多个工具并发，一个炸了不能让兄弟结果丢失：

// agent-loop.ts:273-277
} catch (error) {
  // 注入的执行器不一定像 core executor 一样自行归一化异常。
  // 每个 call 都必须形成结果，且一个拒绝不能让同批兄弟结果丢失。
  result = failedExecution(call, error);
}
 

一个 reject 不能连累整批。如果不用 Promise.all + 每个 call 独立 catch，一个工具抛错会让整个 Promise.all reject，其他正常完成的工具结果全丢。这里每个 call 各自 try/catch，保证每个 call 都有结果，一个不落。

三层下来，工具再怎么出问题，循环拿到的永远是一个带 isError 标记的 ToolResultMessage。模型下一轮看到这个错误结果，自己会决定怎么办——重试、换工具、或者告诉用户「这个工具用不了」。循环本身永远不会因为工具异常而崩溃。

小结

层职责关键代码

Agent Loop 的本质是「让不确定性留在循环外」——模型可能给错参数、工具可能炸、网络可能断，但循环每一步都把这些变成一个干净的结果塞进消息历史，交给模型自己消化。

最后回到开头的口诀：schema 管两头，循环转模型，并发不串台，出错不穿堂。两个文件 485 行代码做的事，四句话讲完了。
