前几节我们让 Agent 学会了调工具，但工具箱里只有"问问题"的能力——它还不会真正动手碰你的硬盘。这一节（课程 Checkpoint 08）就是那道分水岭：Agent 要长出 read、write、edit、bash 四只手，从此它不再只是"会查资料"，而是真正能读写你硬盘文件的代码执行体。

我读完这节最大的感受是：让 Agent 碰文件系统，难的不是"怎么调 fs"，而是"怎么保证它别把你的代码改崩"。下面按工具逐个拆 Pi 的源码，文件统一在 coding-tools.ts，总共 500 行不到。这 500 行几乎全是在处理边界情况：文件写到一半断电怎么办、两个工具抢同一个文件怎么办、Agent 读了一个超大文件怎么不把上下文撑爆。真正生产级的文件操作代码，大部分篇幅都在处理"正常路径之外"的情况，这一点在我通读之后感受特别深。

● ● ●

工厂入口：createCodingTools

课程这一章先把"四个工具从哪来"讲清楚——用一个工厂函数统一生产，而不是散落四处各自 new。

来自第 482-499 行：

export function createCodingTools(
  input: CodingToolsOptions,
): ToolRegistry {
  const options: Required<CodingToolsOptions> = {
    maxReadBytes: 48_000,
    maxReadLines: 240,
    maxBashOutputBytes: 96_000,
    bashTimeoutMs: 30_000,
    ...input,
    cwd: path.resolve(input.cwd),
  };
  return new ToolRegistry([
    createReadTool(options),
    createWriteTool(options),
    createEditTool(options),
    createBashTool(options),
  ]);
}
 

options 用 Required<...> 强制所有字段非空，再配一份默认值。这样新增工具时，不用每个 create 函数里都写一遍 if-undefined 兜底——上限（字节数、行数、超时）在工厂层一次性喂满。

这套默认值值得记一下：read 最多 48000 字节/240 行，bash 输出最多 96000 字节、超时 30 秒。这些数字是"Agent 一次工具调用能塞进上下文"的经验上限，不是拍脑袋定的。大模型上下文窗口再大，单次工具结果塞太满也会挤掉前面的对话——Pi 用字节预算把单次返回卡在一个合理体积。

四个 create*Tool 都是纯函数：吃 options、吐 Tool。Pi 用工厂模式而不是类继承，好处是每个工具能独立测试、独立替换。比如你想给 read 加个缓存层，只要包一层 createReadTool 返回的 Tool 对象就行，不用动 write 和 edit。这种解耦让工具组合变得很灵活——工具是即插即用的零件，不是焊死在 Agent 类上的方法。

● ● ●

read：续读 + 字节预算双截断

课程强调：让 Agent 读文件，不能一次全塞给它——大文件会把上下文撑爆。所以 read 必须做双截断：行数截断 + 字节截断，而且要告诉 Agent"还能接着读"。

核心在 第 176-206 行：

let selected = "";
let endIndex = startIndex;
// 逐行往候选窗口里加，加到字节预算爆为止
for (
  let candidateEnd = startIndex + 1;
  candidateEnd <= requestedEndIndex;
  candidateEnd += 1
) {
  const body = sourceLines
    .slice(startIndex, candidateEnd)
    .map(
      (line, index) =>
        ${String(startIndex + index + 1).padStart(4, " ")}│ ${line},
    )
    .join("\n");
  const hasMore = candidateEnd < sourceLines.length;
  const continuation = hasMore
    ? \n\n[已显示第 ${startIndex + 1}-${candidateEnd} 行，共 ${sourceLines.length} 行；继续读取：offset=${candidateEnd + 1}]
    : "";
  const candidate = body + continuation;
  if (Buffer.byteLength(candidate) <= options.maxReadBytes) {
    selected = candidate;
    endIndex = candidateEnd;
  }
}
 

这段循环我读了两遍才反应过来：它不是先取 N 行再判断超不超字节，而是一行一行往里加，找到字节预算内能装下的最大行数。为什么这么做？因为字节数和行数不是一一对应——一行可能 10 字节也可能 200 字节，先按行切再砍字节会切到半截。

换个角度想：如果先按行数取 240 行，结果这 240 行加起来 100KB，远超 48000 字节预算，你怎么办？砍掉一半？砍到哪行？砍完 Agent 还能续读吗？Pi 逐行累加的方案直接回避了这些问题——它在循环里维护一个"已经确认能装下的 selected"和一个"正在试探的 candidate"，字节预算爆了就停，最后一次成功的 selected 就是返回值。这种贪心策略保证每行都是完整的，不会把一行从中间劈开。

continuation 那行更关键：被截断时，read 会主动告诉 Agent 下一刀从哪开始。Agent 不用猜，照着 offset 续读就行。这就是为什么 Pi 的 read 能读几千行大文件而不爆上下文——每次只回一部分，但留好了接力的钩子。模型看到"继续读取：offset=201"这种提示，下一轮自然知道传 offset=201 接着读，不需要任何额外编排逻辑。

行数上限在更上面（161-168 行）：Math.min(limit ?? maxReadLines, maxReadLines)。用户传的 limit 不能超过系统硬上限，这是个防御性兜底。如果 Agent 传了 limit=10000，系统也会强制压回 240——宁可多次读，也不一次性吐太多。

● ● ●

write：原子写 + 串行队列

write 的核心问题不是"怎么写文件"，是"写到一半挂了怎么办"。Pi 的答案是原子写：先写临时文件，再 rename。

atomicWrite 在第 132-141 行：

async function atomicWrite(file: string, value: string): Promise<void> {
  // 确保目录存在
  await mkdir(path.dirname(file), { recursive: true });
  // 临时文件名带 pid + 时间戳，防并发撞名
  const temporary = ${file}.pi-tmp-${process.pid}-${Date.now()};
  try {
    await writeFile(temporary, value, "utf8");
    // rename 是原子的：要么整个换上，要么完全没动
    await rename(temporary, file);
  } finally {
    // 兜底清理（正常路径下临时文件已 rename 走）
    await rm(temporary, { force: true }).catch(() => undefined);
  }
}
 

rename 在 POSIX 上是原子操作——要么你看到旧文件，要么看到新文件，绝不会看到写一半的中间态。这就是为什么 Pi 的 write 不会留出"半截文件"。想象一下如果直接 writeFile(file, content)：写到 80% 时断电，文件就成了 80% 的新内容加 20% 的旧内容混在一起，下次 Agent 读到的就是乱码。原子写把这个风险彻底消掉。

但原子写只解决"写到一半挂"，没解决"两个工具同时写"。于是 Pi 还有个 MutationQueue，第 61-83 行：

export class MutationQueue {
  private readonly tails = new Map<string, Promise<void>>();
 
  async run<T>(key: string, operation: () => Promise<T>): Promise<T> {
    // 取出同一个 key 上的"上一棒"
    const previous = this.tails.get(key) ?? Promise.resolve();
    let release!: () => void;
    const gate = new Promise<void>((resolve) => {
      release = resolve;
    });
    // 把当前操作的尾巴接到上一棒后面
    const tail = previous.catch(() => undefined).then(() => gate);
    this.tails.set(key, tail);
 
    await previous.catch(() => undefined);
    try {
      return await operation();
    } finally {
      release();
      if (this.tails.get(key) === tail) this.tails.delete(key);
    }
  }
}
 

这个类我一开始看懵了——一堆 Promise 绕来绕去。其实就一句话：同一个文件路径上的写操作，排队串行执行，谁也别插队。

展开解释一下 run 方法的工作原理。每次调用 run(key, operation) 时，它先从 tails Map 里取出这个 key 对应的"上一棒 Promise"（previous）。如果没人排过队，previous 就是一个已 resolved 的空 Promise。接着它创建一个新的 gate Promise，把它接到 previous 后面，存回 tails。然后 await previous——这一步是关键，当前操作会卡在这里，直到上一棒完成。上一棒完成后，当前操作才开始真正执行 operation()。finally 块里调用 release()，让 gate resolve，好让下一棒能继续走。

这套 Promise 链的妙处在于：它不需要显式的锁变量，全靠 Promise 的 then 串联来排队。每个 key（文件路径）维护一条独立的链，不同文件互不阻塞。

write 工具调用它的方式（236 行）很干净：

await mutations.run(file, () => atomicWrite(file, content));
 

key 就是文件路径。所以对同一个文件的多次 write，会被强制排成一队，前一个完成才放后一个进去。不同文件之间不互锁——这是细粒度锁，不是全局大锁。

● ● ●

edit：批量替换 + two-phase commit

edit 比 write 麻烦：write 是整个覆盖，edit 是局部改。课程把它讲成"精确匹配替换"，Pi 的实现有个两阶段提交（two-phase commit）的味道。

核心逻辑在 第 290-309 行：

return mutations.run(file, async () => {
  const current = await readFile(file, "utf8");
  let next = current;
  // 第一阶段：验证全部位置都唯一可匹配
  for (const [index, edit] of edits.entries()) {
    if (!edit.oldText) throw new Error(edits[${index}].oldText 不能为空);
    const first = next.indexOf(edit.oldText);
    if (first < 0) throw new Error(edits[${index}] 没有匹配);
    // 匹配到多个就拒绝，防止改错地方
    if (
      next.indexOf(edit.oldText, first + edit.oldText.length) >= 0
    ) {
      throw new Error(
        edits[${index}] 匹配多次；请提供更精确的上下文,
      );
    }
    // 第二阶段：在内存副本上替换
    next =
      next.slice(0, first) +
      edit.newText +
      next.slice(first + edit.oldText.length);
  }
  // 全部通过验证后才落盘
  await atomicWrite(file, next);
  ...
});
 

两个阶段是分开的：先在内存里把所有 edits 跑一遍验证，任何一个匹配不到或匹配多次，整批直接抛错，文件不动。只有全部通过，才 atomicWrite 落盘。注意循环里的 next 变量——第一个 edit 的替换结果会成为第二个 edit 的搜索目标，多个 edit 是串行叠加在一个内存副本上的。这意味着如果两个 oldText 有重叠区域，顺序会影响结果，但 Pi 不做冲突检测，交给调用方自己保证。

这就是 two-phase commit 的精髓——先验证全部位置，再统一执行。比"改一个写一个"安全得多：如果第 3 个 edit 匹配失败，前 2 个已经写到磁盘的修改就成了一半的脏状态，撤都撤不回来。先全部验证、再统一落盘，是把"部分成功"这个灾难场景从根上掐掉。

还有个细节：edit 也走 mutations.run，和 write 共用同一个模块级单例（第 83 行的 mutations）。所以对同一个文件，write 和 edit 不会打架——它们排在同一条队里。

indexOf 那个"匹配多次就报错"的设计（297-303 行）我特别想点出来：Agent 贴 oldText 时必须给够上下文，让目标在文件里唯一。这是 Pi 在逼 Agent 做精确编辑，而不是含糊地说"把那个函数改一下"。

● ● ●

bash：取消 + 超时 + 输出截断

bash 工具是四个里最危险的——它执行任意命令。课程花了不少篇幅讲怎么"驯服"它。Pi 的 runCommand（353-465 行）做了三重保护。

第一重：命令本身先过 guardrail（358-363 行）：

if (
  options.containment === "workspace" &&
  /(^|[\s;&|])(?:\/|~\/|\.\.\/)/.test(command)
) {
  throw new Error("教学 guardrail 不允许命令中显式出现绝对路径或 ../");
}
 

正则拦掉绝对路径和 ../——防止 Agent 用 bash 绕过 workspace 限制去碰外面的文件。这个正则的设计有点巧：(^|[\s;&|]) 匹配命令开头或者空白/管道符后面，这样能抓住 cat /etc/passwd 和 ls ~/secret 这种典型逃逸，又不会误伤命令中间出现的 /（比如 sed 's/a/b/'）。它是按"token 边界"来匹配的，不是简单字符串包含。

第二重：超时 + AbortSignal 取消（407-424 行）：

const terminate = () => {
  killProcessTree(child.pid, "SIGTERM");
  forceKillDone ??= new Promise<void>((resolve) => {
    // SIGTERM 后 100ms 还不死，升级 SIGKILL
    forceKill = setTimeout(() => {
      killProcessTree(child.pid, "SIGKILL");
      resolve();
    }, 100);
  });
};
const onAbort = () => {
  aborted = true;
  terminate();
};
// 外部取消（用户主动触发）
signal?.addEventListener("abort", onAbort, { once: true });
// 内部超时（自动杀）
const timeout = setTimeout(() => {
  timedOut = true;
  terminate();
}, options.bashTimeoutMs);
 

两路触发 terminate：外部 AbortSignal（用户主动取消）和内部 setTimeout（超时自动杀）。杀的时候先 SIGTERM 给程序 100ms 收尾时间，不死就 SIGKILL 强杀。killProcessTree（324-338 行）用 process.kill(-pid) 杀整个进程组——子进程自己 fork 出来的孙进程也一起带走，不留僵尸。

第三重：输出截断（392-402 行）：

const collect = (chunk: Buffer) => {
  if (bytes >= options.maxBashOutputBytes) {
    truncated = true;
    return;
  }
  const remaining = options.maxBashOutputBytes - bytes;
  // 只取这个 chunk 里预算允许的部分
  const accepted = chunk.subarray(0, remaining);
  chunks.push(accepted);
  bytes += accepted.length;
  if (accepted.length < chunk.length) truncated = true;
};
 

collect 挂在 stdout/stderr 上，来一块数据就累计字节数，超了 maxBashOutputBytes（默认 96KB）就停收。truncated 标志位会在最终输出末尾补一句"… [输出已截断]"，告诉 Agent "你看到的不是全部"。

截断后还有个收尾动作（442-452 行）值得提：如果被截断，Pi 会重新算一遍预算，把"… [输出已截断]"这个提示语也算进 96KB 里，保证最终返回的字节数不超限。连提示语自己都受预算约束，这种严谨度我一开始没注意到，回头读才发现。

三重保护叠加，bash 才能安全地交给 Agent：命令受路径限制、进程能被取消、输出有上限。没有这三道，一个失控的 find / 或者死循环脚本就能把整个 Agent 搞崩。

● ● ●

workspace containment：路径越狱的两道门

四个工具都绕不开一个问题：Agent 传进来的路径，凭什么信？Pi 的答案在 resolvedPath 函数（106-130 行）和它的帮手 isInside（85-91 行）。

第一道门——字符串前缀检查（113-119 行）：

const root = path.resolve(cwd);
const resolved = path.resolve(root, candidate);
if (
  containment === "workspace" &&
  resolved !== root &&
  !resolved.startsWith(${root}${path.sep})
) {
  throw new Error(路径越过教学 workspace：${candidate});
}
 

resolved.startsWith(root + path.sep) 这个检查看着朴素，但有个坑：必须拼上 path.sep。不拼的话，root 是 /home/pi，候选路径 /home/pi-evil/x 也会被前缀匹配通过——这是经典的路径前缀绕过。

但字符串检查还挡不住符号链接。第二道门专门防这个（120-128 行）：

if (containment === "workspace") {
  const [realRoot, realCandidateOrParent] = await Promise.all([
    realpath(root),
    nearestExistingPath(resolved),
  ]);
  if (!isInside(realRoot, realCandidateOrParent)) {
    throw new Error(符号链接越过教学 workspace：${candidate});
  }
}
 

realpath 解析符号链接到真实路径。如果 workspace 里有个软链接指向外面，realpath 一解析就露馅。nearestExistingPath（93-104 行）处理的是"目标文件还不存在"的情况——往上找最近的存在的祖先目录，对它做 realpath。因为 write 要创建的新文件本身没有 realpath，只能从它已存在的祖先目录下手。这个函数实现挺巧妙：从目标路径往上逐级 realpath，谁先成功就用谁。

这两道门叠加起来，Pi 的 workspace 模式能挡住绝大多数"手滑越界"和"低级符号链接绕过"。当然，它挡不住蓄意攻击——比如 Agent 如果能在 workspace 内编译一个 setuid 程序，就能从 bash 里提权出去。防误操作和防恶意攻击是两个完全不同级别的安全目标，Pi 清楚地选择了前者。

不过源码第 478-481 行有一段老实声明：

/**
 * workspace 模式只是课程里用于防止常见误操作的 guardrail，不是安全 sandbox。
 * 它不能替代操作系统对 shell、符号链接和子进程的隔离。
 */
 

Pi 主动声明这层防护不是真正的沙箱——它挡得住手滑和低级绕过，挡不住蓄意的 shell 提权。guardrail 不等于 security boundary，课程的态度很诚实。

● ● ●

小结

这节四个工具各自扛着不同的工程难题：

  •  read：双截断（行 + 字节）+ 续读提示，保证大文件不爆上下文
  •  write：原子写（temp + rename）+ MutationQueue，保证写到一半挂不留脏文件
  •  edit：two-phase commit，保证一批编辑要么全成要么全不动
  •  bash：guardrail + 超时 + 取消 + 输出截断，把"任意命令"关进笼子
  •  containment：字符串前缀 + 符号链接 realpath，双重挡路径越狱

这些机制不是"让 Agent 更聪明"，而是"让 Agent 碰文件时足够安全可控"。读完这节我才理解，为什么真正的 coding agent 代码里，文件读写那部分远比"调 fs.writeFile"复杂得多——复杂度全花在边界防护上了。
