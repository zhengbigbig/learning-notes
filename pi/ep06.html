上一节我们让 Agent 学会了调工具，但工具箱里还只有"问问题"——它不会真正碰你的硬盘。这一节（课程 Checkpoint 08）就是那道分水岭：Agent 要长出 read、write、edit、bash 四只手，从此不再只是"会查资料"，而是真正能读写你硬盘文件的代码执行体。

我读完最大的感受是：让 Agent 碰文件系统，难的不是"怎么调 fs"，而是"怎么保证它别把你的代码改崩"。源码统一在 coding-tools.ts，500 行不到，几乎全在处理边界情况：文件写到一半断电怎么办、两个工具抢同一个文件怎么办、Agent 读超大文件怎么不把上下文撑爆。下面按工具逐个拆。

● ● ●

工厂入口：createCodingTools

课程这一章先把"四个工具从哪来"讲清楚——一个工厂函数统一生产，而不是散落四处各自 new。

// coding-tools.ts 第 482-499 行
export function createCodingTools(
  input: CodingToolsOptions,
): ToolRegistry {
  // 用 Required 强制所有字段非空，再配默认值
  // 新增工具时就不用每个 create 函数里都写 if-undefined 兜底
  const options: Required<CodingToolsOptions> = {
    maxReadBytes: 48_000,        // 单次 read 最多 48KB，避免撑爆上下文
    maxReadLines: 240,           // 同时限制 240 行，双重兜底
    maxBashOutputBytes: 96_000,  // bash 输出最多 96KB
    bashTimeoutMs: 30_000,       // 子进程最多跑 30 秒，防止死循环卡死
    ...input,
    cwd: path.resolve(input.cwd), // 工作目录绝对化，后面路径检查依赖这个
  };
  return new ToolRegistry([
    createReadTool(options),   // 四个工具都是纯函数：吃 options、吐 Tool
    createWriteTool(options),  // 工厂模式而不是类继承——每个工具能独立测试、替换
    createEditTool(options),
    createBashTool(options),
  ]);
}
 

这些默认数字值得记一下：read 48000 字节/240 行，bash 输出 96000 字节、超时 30 秒。这些是"Agent 一次工具调用能塞进上下文"的经验上限，不是拍脑袋定的。大模型上下文窗口再大，单次工具结果塞太满也会挤掉前面的对话——Pi 用字节预算把单次返回卡在一个合理体积。

工具是即插即用的零件，不是焊死在 Agent 类上的方法。想给 read 加个缓存层，包一层 createReadTool 返回的 Tool 对象就行，不用动 write 和 edit。如果换成类继承，你想给 read 加缓存就得改基类，基类一动 write 和 edit 也跟着受影响——耦合度一下就上去了。工厂模式把四个工具彻底隔离，各自演进互不牵连，这在后续课程加新工具时格外舒服。

● ● ●

read：续读 + 字节预算双截断

让 Agent 读文件，不能一次全塞给它——大文件会把上下文撑爆。所以 read 必须做双截断：行数截断 + 字节截断，而且要告诉 Agent"还能接着读"。

// coding-tools.ts 第 176-206 行
let selected = "";           // 已经确认能装下的最大结果
let endIndex = startIndex;   // 对应的结束行
// 逐行往候选窗口里加，加到字节预算爆为止
for (
  let candidateEnd = startIndex + 1;
  candidateEnd <= requestedEndIndex;
  candidateEnd += 1
) {
  const body = sourceLines
    .slice(startIndex, candidateEnd)
    .map(
      (line, index) =>
        // 行号右对齐 4 位 + 分隔线，方便 Agent 引用具体行
        `${String(startIndex + index + 1).padStart(4, " ")}│ ${line}`,
    )
    .join("\n");
  const hasMore = candidateEnd < sourceLines.length;
  // 被截断时主动告诉 Agent 下一刀从哪开始——不用猜，照着 offset 续读
  const continuation = hasMore
    ? `\n\n[已显示第 ${startIndex + 1}-${candidateEnd} 行，共 ${sourceLines.length} 行；继续读取：offset=${candidateEnd + 1}]`
    : "";
  const candidate = body + continuation;
  if (Buffer.byteLength(candidate) <= options.maxReadBytes) {
    selected = candidate;   // 字节预算还够，更新为成功结果
    endIndex = candidateEnd;
  }
}
 

这段循环我读了两遍才反应过来：它不是先取 N 行再判断超不超字节，而是一行一行往里加，找到字节预算内能装下的最大行数。为什么？因为字节数和行数不是一一对应——一行可能 10 字节也可能 200 字节，先按行切再砍字节会切到半截。逐行累加的贪心策略保证每行都是完整的，不会把一行从中间劈开。

continuation 那行最关键：被截断时，read 会主动告诉 Agent 下一刀从哪开始。模型看到"继续读取：offset=201"这种提示，下一轮自然知道传 offset=201 接着读，不需要任何额外编排逻辑。我实际用下来，读一个 2000 行的源码文件，Agent 会自动分十几次 read 把它啃完，每次的 offset 都精确接上——整个过程我不用管，它自己接力。这就是为什么 Pi 的 read 能读几千行大文件而不爆上下文：每次只回一部分，但留好了接力的钩子。

行数上限在更上面（第 161-168 行）：Math.min(limit ?? maxReadLines, maxReadLines)。用户传的 limit 不能超过系统硬上限，这是个防御性兜底——Agent 传了 limit=10000，系统也会强制压回 240，宁可多次读，也不一次性吐太多。

● ● ●

write：原子写 + 串行队列

write 的核心问题不是"怎么写文件"，是"写到一半挂了怎么办"。Pi 的答案是原子写：先写临时文件，再 rename。

// coding-tools.ts 第 132-141 行
async function atomicWrite(file: string, value: string): Promise<void> {
  await mkdir(path.dirname(file), { recursive: true });
  // 临时文件名带 pid + 时间戳，防并发撞名
  const temporary = `${file}.pi-tmp-${process.pid}-${Date.now()}`;
  try {
    await writeFile(temporary, value, "utf8");
    await rename(temporary, file); // rename 在 POSIX 上是原子操作
    // 要么你看到旧文件，要么看到新文件，绝不会看到写一半的中间态
  } finally {
    // 兜底清理：正常路径下临时文件已被 rename 走，这里只清异常残留
    await rm(temporary, { force: true }).catch(() => undefined);
  }
}
 

想象一下如果直接 writeFile(file, content)：写到 80% 时断电，文件就成了 80% 新内容加 20% 旧内容的混合体，下次 Agent 读到的就是乱码。原子写把这个风险彻底消掉。我在本地故意 kill 进程试过，临时文件留在磁盘上，但目标文件毫发无损——要么是完整的旧内容，要么是完整的新内容，绝没有中间态。

但原子写只解决"写到一半挂"，没解决"两个工具同时写"。于是 Pi 还有个 MutationQueue：

// coding-tools.ts 第 61-83 行
export class MutationQueue {
  private readonly tails = new Map<string, Promise<void>>();
 
  async run<T>(key: string, operation: () => Promise<T>): Promise<T> {
    // 取出同一个 key（文件路径）上的"上一棒"
    const previous = this.tails.get(key) ?? Promise.resolve();
    let release!: () => void;
    const gate = new Promise<void>((resolve) => {
      release = resolve;
    });
    // 把当前操作的尾巴接到上一棒后面，存回 tails
    const tail = previous.catch(() => undefined).then(() => gate);
    this.tails.set(key, tail);
 
    await previous.catch(() => undefined); // 卡这里，直到上一棒完成
    try {
      return await operation();            // 上一棒放行后才开始真正执行
    } finally {
      release();                           // 放行下一棒
      if (this.tails.get(key) === tail) this.tails.delete(key);
    }
  }
}
const mutations = new MutationQueue(); // 模块级单例
 

这个类我一开始看懵了——一堆 Promise 绕来绕去。其实就一句话：同一个文件路径上的写操作，排队串行执行，谁也别插队。它不需要显式锁变量，全靠 Promise 的 then 串联排队；每个 key（文件路径）维护一条独立链，不同文件互不阻塞——这是细粒度锁，不是全局大锁。

write 工具调用它的方式（第 236 行）很干净：

await mutations.run(file, () => atomicWrite(file, content));
 

对同一个文件的多次 write，会被强制排成一队，前一个完成才放后一个进去。实际场景里，Agent 经常连续改同一个文件——先 write 再 edit 再 write，如果没有这个队列，三次操作的执行顺序就不可控，文件内容会乱套。MutationQueue 把这种竞态从根上堵死。

● ● ●

edit：批量替换 + two-phase commit

edit 比 write 麻烦：write 是整个覆盖，edit 是局部改。Pi 的实现有个两阶段提交（two-phase commit）的味道。

// coding-tools.ts 第 290-309 行
return mutations.run(file, async () => {
  const current = await readFile(file, "utf8");
  let next = current; // 内存副本，多个 edit 串行叠加在它上面
  // 第一阶段：验证全部位置都唯一可匹配
  for (const [index, edit] of edits.entries()) {
    if (!edit.oldText) throw new Error(`edits[${index}].oldText 不能为空`);
    const first = next.indexOf(edit.oldText);
    if (first < 0) throw new Error(`edits[${index}] 没有匹配`);
    // 匹配到多个就拒绝，防止改错地方
    if (next.indexOf(edit.oldText, first + edit.oldText.length) >= 0) {
      throw new Error(`edits[${index}] 匹配多次；请提供更精确的上下文`);
    }
    // 第二阶段：在内存副本上替换（还没落盘）
    next =
      next.slice(0, first) +
      edit.newText +
      next.slice(first + edit.oldText.length);
  }
  await atomicWrite(file, next); // 全部验证通过后才落盘
});
 

两个阶段是分开的：先在内存里把所有 edits 跑一遍验证，任何一个匹配不到或匹配多次，整批直接抛错，文件不动。只有全部通过，才 atomicWrite 落盘。

这就是 two-phase commit 的精髓——比"改一个写一个"安全得多。如果第 3 个 edit 匹配失败，前 2 个已经写到磁盘的修改就成了一半的脏状态，撤都撤不回来。先全部验证、再统一落盘，是把"部分成功"这个灾难场景从根上掐掉。

indexOf 那个"匹配多次就报错"的设计我特别想点出来：Agent 贴 oldText 时必须给够上下文，让目标在文件里唯一。这是 Pi 在逼 Agent 做精确编辑，而不是含糊地说"把那个函数改一下"。实际用下来，Agent 一开始会贴很短的 oldText 然后被报错打回来，几轮之后就学会了带够上下文——这种报错机制本身就是在调教模型行为。

edit 也走 mutations.run，和 write 共用同一个模块级单例。所以对同一个文件，write 和 edit 不会打架——它们排在同一条队里。

● ● ●

bash：取消 + 超时 + 输出截断

bash 是四个里最危险的——它执行任意命令。Pi 的 runCommand（第 353-465 行）做了三重保护。

第一重，命令本身先过 guardrail：

// coding-tools.ts 第 358-363 行
if (
  options.containment === "workspace" &&
  /(^|[\s;&|])(?:\/|~\/|\.\.\/)/.test(command)
  // 正则按 token 边界匹配：开头或空白/;&| 后面跟着 /、~/ 或 ../
  // 这样能抓住 cat /etc/passwd 和 ls ~/secret，又不会误伤 sed 's/a/b/'
) {
  throw new Error("教学 guardrail 不允许命令中显式出现绝对路径或 ../");
}
 

它是按"token 边界"来匹配的，防止 Agent 用 bash 绕过 workspace 限制去碰外面的文件。

第二重，超时 + AbortSignal 取消：

// coding-tools.ts 第 407-424 行
const terminate = () => {
  killProcessTree(child.pid, "SIGTERM"); // 先发 SIGTERM，给程序 100ms 收尾
  forceKillDone ??= new Promise<void>((resolve) => {
    forceKill = setTimeout(() => {
      killProcessTree(child.pid, "SIGKILL"); // 不死就强杀
      resolve();
    }, 100);
  });
};
const onAbort = () => { aborted = true; terminate(); }; // 外部取消（用户主动触发）
signal?.addEventListener("abort", onAbort, { once: true });
const timeout = setTimeout(() => {          // 内部超时（自动杀）
  timedOut = true;
  terminate();
}, options.bashTimeoutMs);
 

两路触发 terminate：外部 AbortSignal（用户主动取消）和内部 setTimeout（超时自动杀）。外部取消的实际触发场景是用户按了中断键——Agent 正在跑一个跑偏的命令，你不想等了，一个信号下去进程就被收掉。killProcessTree（第 324-338 行）用 process.kill(-pid) 杀整个进程组——子进程自己 fork 出来的孙进程也一起带走，不留僵尸。我在本地试过跑一个会 fork 子进程的脚本，取消后 ps 一看干干净净，没有漏网的孤儿进程。

第三重，输出截断：

// coding-tools.ts 第 392-402 行
const collect = (chunk: Buffer) => {
  if (bytes >= options.maxBashOutputBytes) { // 预算已满，直接丢
    truncated = true;
    return;
  }
  const remaining = options.maxBashOutputBytes - bytes;
  const accepted = chunk.subarray(0, remaining); // 只取预算允许的部分
  chunks.push(accepted);
  bytes += accepted.length;
  if (accepted.length < chunk.length) truncated = true;
};
 

collect 挂在 stdout/stderr 上，来一块数据就累计字节数，超了 96KB 就停收。截断后还有个收尾动作（第 442-452 行）：Pi 会重新算预算，把"… [输出已截断]"这个提示语也算进 96KB 里——连提示语自己都受预算约束，保证最终返回字节数不超限。

三重保护叠加，bash 才能安全地交给 Agent：命令受路径限制、进程能被取消、输出有上限。没有这三道，一个失控的 find / 或者死循环脚本就能把整个 Agent 搞崩。

● ● ●

workspace containment：路径越狱的两道门

四个工具都绕不开一个问题：Agent 传进来的路径，凭什么信？Pi 的答案在 resolvedPath（第 106-130 行）和帮手 isInside（第 85-91 行）。

第一道门，字符串前缀检查：

// coding-tools.ts 第 111-119 行
const root = path.resolve(cwd);
const resolved = path.resolve(root, candidate);
if (
  containment === "workspace" &&
  resolved !== root &&
  !resolved.startsWith(`${root}${path.sep}`) // 必须拼 path.sep！
) {
  throw new Error(`路径越过教学 workspace：${candidate}`);
}
 

resolved.startsWith(root + path.sep) 看着朴素，但有个坑：必须拼上 path.sep。不拼的话，root 是 /home/pi，候选路径 /home/pi-evil/x 也会被前缀匹配通过——这是经典的路径前缀绕过。

但字符串检查还挡不住符号链接。第二道门专门防这个：

// coding-tools.ts 第 120-128 行
if (containment === "workspace") {
  const [realRoot, realCandidateOrParent] = await Promise.all([
    realpath(root),              // 解析 workspace 真实路径
    nearestExistingPath(resolved), // 目标可能还不存在，往上找最近祖先
  ]);
  if (!isInside(realRoot, realCandidateOrParent)) {
    throw new Error(`符号链接越过教学 workspace：${candidate}`);
  }
}
 

realpath 解析符号链接到真实路径。如果 workspace 里有个软链接指向外面，realpath 一解析就露馅。nearestExistingPath（第 93-104 行）处理"目标文件还不存在"——往上找最近的已存在祖先目录，对它做 realpath。为什么需要这一步？因为 write 要创建的新文件本身还没有 realpath，只能从它已存在的祖先目录下手反推。这个函数实现挺巧妙：从目标路径往上逐级 realpath，谁先成功就用谁，保证不管目标存在不存在都能检查到真实的物理位置。

源码第 478-481 行有一段老实声明：

/**
 * workspace 模式只是课程里用于防止常见误操作的 guardrail，不是安全 sandbox。
 * 它不能替代操作系统对 shell、符号链接和子进程的隔离。
 */
 

Pi 主动声明这层防护不是真正的沙箱——它挡得住手滑和低级绕过，挡不住蓄意的 shell 提权。防误操作和防恶意攻击是两个完全不同级别的安全目标，课程的态度很诚实。

● ● ●

小结

这节四个工具各自扛着不同的工程难题：

  •  read：双截断（行 + 字节）+ 续读提示，保证大文件不爆上下文
  •  write：原子写（temp + rename）+ MutationQueue，保证写到一半挂不留脏文件
  •  edit：two-phase commit，保证一批编辑要么全成要么全不动
  •  bash：guardrail + 超时 + 取消 + 输出截断，把"任意命令"关进笼子
  •  containment：字符串前缀 + 符号链接 realpath，双重挡路径越狱

这些机制不是"让 Agent 更聪明"，而是"让 Agent 碰文件时足够安全可控"。读完这节我才理解，为什么真正的 coding agent 代码里，文件读写那部分远比"调 fs.writeFile"复杂得多——复杂度全花在边界防护上了。
