大家好我是郑同学。上一篇我们把 Agent Loop 拆完了——一个 for 循环驱动整个 Agent。但循环只是骨架，真正干活的是工具。

这一篇拆 Pi 的四个文件工具：read、write、edit、bash。它们全在 coding-tools.ts（499 行），是模型操作文件系统的唯一通道。

先看大图。模型说「帮我读 README」，Agent Loop 收到 tool_use block，调 executeToolCall，最终走到这四个工具里的某一个。上一篇讲的循环管调度，这一篇讲工具本身怎么干活。

● ● ●

先看大图：四个工具怎么注册

工厂函数 createCodingTools 接收一个 options 对象，设置各种上限，然后把四个工具塞进 ToolRegistry 返回。每个工具拿到同一份 options——里面是各种上限和配置。

export function createCodingTools(
  input: CodingToolsOptions,
): ToolRegistry {
  const options: Required<CodingToolsOptions> = {
    // 读文件最多 48KB，防止日志塞爆上下文
    maxReadBytes: 48_000,
    // 最多 240 行，比字节限制更直观
    maxReadLines: 240,
    // bash 输出最多 96KB
    maxBashOutputBytes: 96_000,
    // bash 命令 30 秒超时
    bashTimeoutMs: 30_000,
    ...input,
    cwd: path.resolve(input.cwd),
  };
  // 四个工具共享同一份 options，塞进 ToolRegistry
  return new ToolRegistry([
    createReadTool(options),
    createWriteTool(options),
    createEditTool(options),
    createBashTool(options),
  ]);
}
 

这些数字不是随便填的，每一个都是踩坑后的经验值。

● ● ●

Part 1：read——读文件不是 cat

最简单的工具是 read，但 Pi 的 read 比 cat 多了好几层保护。

function createReadTool(options: Required<CodingToolsOptions>): Tool {
  return {
    name: "read",
    description: "按行数和字节上限读取 UTF-8 文件",
    // 三个参数：path 必填，offset/limit 可选
    schema: objectSchema({
      path: stringValue,
      offset: optionalPositiveInteger,
      limit: optionalPositiveInteger,
    }),
 

执行逻辑的核心是边读边算字节，超了就截断。逐行累加，每次加一行就算一下总字节数。还没超就继续加，超了就停。

// 逐行累加：从 startIndex 开始，一行一行往上加
let selected = "";
let endIndex = startIndex;
for (
  let candidateEnd = startIndex + 1;
  candidateEnd <= requestedEndIndex;
  candidateEnd += 1
) {
  // 切出当前范围，每行前面加行号（左补空格到4位 + 竖线）
  const body = sourceLines
    .slice(startIndex, candidateEnd)
    .map(
      (line, index) =>
        `${String(startIndex + index + 1).padStart(4, " ")}│ ${line}`,
    )
    .join("\n");
  // 如果还有更多行，末尾附续读提示
  const hasMore = candidateEnd < sourceLines.length;
  const continuation = hasMore
    ? `\n\n[已显示第 ${startIndex + 1}-${candidateEnd} 行，共 ${sourceLines.length} 行；继续读取：offset=${candidateEnd + 1}]`
    : "";
  const candidate = body + continuation;
  // 没超 maxReadBytes 就保留，超了自然停在外层循环
  if (Buffer.byteLength(candidate) <= options.maxReadBytes) {
    selected = candidate;
    endIndex = candidateEnd;
  }
}
 

截断后结果末尾会带一句提示：

[已显示第 1-180 行，共 500 行；继续读取：offset=181]
 

模型看到这行提示就知道还有内容，会自己发第二次 read 请求。这比一次性把 500 行全塞进上下文聪明得多——模型可能只需要前 20 行就够了。

模型看到的不是原始文本，而是带行号的格式化输出：

   1│ import { read } from './tool'
   2│ 
   3│ export function main() {
 

这样模型引用某行时能说「第 3 行有 bug」，而不是自己数行。

● ● ●

Part 2：write——原子写入防损坏

write 看着简单——把内容写进文件。但 Pi 做了两层防护。

第一层：原子写入（atomicWrite）

不是直接写目标文件，而是先写临时文件，再 rename。rename 在同一个文件系统上是原子的——要么成功，要么文件还是旧内容。不会出现写到一半进程崩了、文件变成半截的情况。

async function atomicWrite(file: string, value: string): Promise<void> {
  // 确保父目录存在
  await mkdir(path.dirname(file), { recursive: true });
  // 临时文件名带 PID 和时间戳，防多 Agent 同时写撞车
  const temporary = `${file}.pi-tmp-${process.pid}-${Date.now()}`;
  try {
    // 先写临时文件
    await writeFile(temporary, value, "utf8");
    // 再 rename，这一步是原子的
    await rename(temporary, file);
  } finally {
    // 清理可能残留的临时文件
    await rm(temporary, { force: true }).catch(() => undefined);
  }
}
 

第二层：MutationQueue（写入排队）

MutationQueue 按 key（文件路径）串行化写入操作。如果两个工具调用同时 write 同一个文件，第二个会等第一个写完再开始。核心机制：每个 key 维护一个 Promise 链（tails），新操作等前一个完成才开始，完成后释放并清理。

export class MutationQueue {
  // 每个文件路径对应一条 Promise 链
  private readonly tails = new Map<string, Promise<void>>();
 
  async run<T>(key: string, operation: () => Promise<T>): Promise<T> {
    // 取出这个 key 的前一个操作（没有就是已完成的空 Promise）
    const previous = this.tails.get(key) ?? Promise.resolve();
    let release!: () => void;
    // 创建一个 gate，当前操作完成后 release
    const gate = new Promise<void>((resolve) => {
      release = resolve;
    });
    const tail = previous.catch(() => undefined).then(() => gate);
    this.tails.set(key, tail);
    // 等前一个操作完成
    await previous.catch(() => undefined);
    try {
      // 执行当前操作
      return await operation();
    } finally {
      // 释放 gate，让下一个操作能开始
      release();
      if (this.tails.get(key) === tail) this.tails.delete(key);
    }
  }
}
 

write 工具通过 mutations.run(file, ...) 走 MutationQueue，在闭包里调 atomicWrite。read 不排队，write 和 edit 排队。因为读操作并发安全，写操作并发会冲突。

// 先验证路径在 workspace 内，再排队写入
async execute({ path: inputPath, content }) {
  const file = await resolvedPath(
    options.cwd,
    inputPath,
    options.containment,
  );
  // mutations.run 保证同文件的写操作串行
  await mutations.run(file, () => atomicWrite(file, content));
 

● ● ●

Part 3：edit——精确替换，拒绝歧义

edit 是最精妙的工具。它的设计原则是宁可报错，绝不猜。

function createEditTool(options: Required<CodingToolsOptions>): Tool {
  return {
    name: "edit",
    description: "先验证一批唯一精确匹配，再一次写回文件",
    schema: { parse: parseEditParameters },
    async execute({ path: inputPath, edits }) {
      const file = await resolvedPath(
        options.cwd,
        inputPath,
        options.containment,
      );
      // 走 MutationQueue 串行化
      return mutations.run(file, async () => {
        // 读当前内容，逐个检查 edits
        const current = await readFile(file, "utf8");
        let next = current;
        for (const [index, edit] of edits.entries()) {
          // ① oldText 不能为空——防止全文匹配
          if (!edit.oldText) throw new Error(`edits[${index}].oldText 不能为空`);
          // ② indexOf 找不到——报错，不猜不试
          const first = next.indexOf(edit.oldText);
          if (first < 0) throw new Error(`edits[${index}] 没有匹配`);
          // ③ 二次搜索还找到——匹配多次，拒绝猜
          if (
            next.indexOf(edit.oldText, first + edit.oldText.length) >= 0
          ) {
            throw new Error(
              `edits[${index}] 匹配多次；请提供更精确的上下文`,
            );
          }
          // 三个检查都过了，执行替换
          next =
            next.slice(0, first) +
            edit.newText +
            next.slice(first + edit.oldText.length);
        }
        // 全部 edits 成功才写回
        await atomicWrite(file, next);
 

三个检查，层层递进：

  1. 01oldText 不能为空——防止模型传了空字符串导致全文匹配
  2. 02indexOf < 0 → 报错「没有匹配」——找不到要替换的内容，不猜不试
  3. 03indexOf 二次搜索 → 报错「匹配多次」——同一个字符串在文件里出现多次，Pi 拒绝猜你想改哪个

第三个检查是关键。如果文件里有两个 const x = 1，Pi 不会随便改第一个或全部改——它要求模型提供更多上下文，比如 const x = 1\nconst y = 2，让匹配唯一。

edit 还支持批量编辑（edits[] 数组）：模型可以一次提交多个 {oldText, newText} 对。Pi 在内存里逐个应用，全部成功才写回。中间任何一个匹配失败，整个编辑回滚——文件不变。

edit 也走 MutationQueue（mutations.run(file, async () => ...)），和 write 共享同一个排队。

Part 4：bash——最危险的工具需要最多保护

bash 是四个工具里最危险的——它能执行任何命令。Pi 做了五层防护。

第一层：containment 路径检查

workspace 模式下，命令里不能出现绝对路径（/）、home 路径（~/）、上级路径（../）。防止模型跑 rm -rf / 或读 workspace 外的文件。

// 正则匹配命令中的绝对路径、home路径、上级路径
if (
  options.containment === "workspace" &&
  /(^|[\s;&|])(?:\/|~\/|\.\.\/)/.test(command)
) {
  throw new Error("教学 guardrail 不允许命令中显式出现绝对路径或 ../");
}
 

第二层：超时 + 进程树 kill

bash 用 spawn 启动子进程，detached: true（创建新的进程组），设 30 秒超时。

// detached: true 让子进程拥有独立的进程组
const child = spawn(command, {
  cwd: options.cwd,
  shell: true,
  detached: process.platform !== "win32",
  env: process.env,
});
 

超时后不是只 kill 主进程，而是 kill 整个进程组。process.kill(-pid) 里的负号是关键——杀掉整个进程树，包括子进程的子进程。只 kill 主进程的话，子进程会变成孤儿继续跑。kill 分两步：先 SIGTERM（优雅退出），100ms 后 SIGKILL（强制）。

function killProcessTree(
  pid: number | undefined,
  signal: NodeJS.Signals = "SIGTERM",
): void {
  if (!pid) return;
  try {
    // 负 PID = kill 整个进程组，包括所有子进程
    process.kill(-pid, signal);
  } catch {
    try {
      // 退而求其次：只 kill 主进程
      process.kill(pid, signal);
    } catch {
      // 进程已经退出
    }
  }
}
 
// 先 SIGTERM 让进程优雅退出，100ms 后 SIGKILL 强制
const terminate = () => {
  killProcessTree(child.pid, "SIGTERM");
  forceKillDone ??= new Promise<void>((resolve) => {
    forceKill = setTimeout(() => {
      killProcessTree(child.pid, "SIGKILL");
      resolve();
    }, 100);
  });
};
 

第三层：输出字节限制

边收边截断。stdout 和 stderr 的每一块都检查字节数，超过 96KB 就标记 truncated 并停止收集。防止 find / 或 cat huge.log 把上下文撑爆。

const collect = (chunk: Buffer) => {
  // 已经超了，直接标记截断
  if (bytes >= options.maxBashOutputBytes) {
    truncated = true;
    return;
  }
  // 只收剩余额度内的字节
  const remaining = options.maxBashOutputBytes - bytes;
  const accepted = chunk.subarray(0, remaining);
  chunks.push(accepted);
  bytes += accepted.length;
  if (accepted.length < chunk.length) truncated = true;
};
 

第四层：UTF-8 安全截断

按字符遍历而不是按字节切。如果按字节切，一个 3 字节的中文可能被切成两半，变成乱码。utf8Prefix 确保截断点永远在字符边界上。

function utf8Prefix(value: string, maxBytes: number): string {
  if (maxBytes <= 0) return "";
  let bytes = 0;
  const prefix: string[] = [];
  // 逐字符遍历，不按字节切
  for (const character of value) {
    const characterBytes = Buffer.byteLength(character);
    // 加上这个字符会超限就不加
    if (bytes + characterBytes > maxBytes) break;
    prefix.push(character);
    bytes += characterBytes;
  }
  return prefix.join("");
}
 

第五层：用户取消

bash 工具接收 context.signal（AbortSignal，用户取消时触发）。用户按 Ctrl+C 时，bash 立刻 kill 进程树，不需要等命令跑完。

// signal.aborted 时立即终止进程树
const onAbort = () => {
  aborted = true;
  terminate();
};
signal?.addEventListener("abort", onAbort, { once: true });
 

● ● ●

路径安全：resolvedPath 五重检查

所有四个工具的第一步都是 resolvedPath——解析和验证文件路径。

async function resolvedPath(
  cwd: string,
  candidate: string,
  containment: ContainmentMode,
): Promise<string> {
  const root = path.resolve(cwd);
  const resolved = path.resolve(root, candidate);
  // ① 字符串检查：resolved 必须以 root 开头
  if (
    containment === "workspace" &&
    resolved !== root &&
    !resolved.startsWith(`${root}${path.sep}`)
  ) {
    throw new Error(`路径越过教学 workspace：${candidate}`);
  }
  if (containment === "workspace") {
    // ② realpath 解析，防符号链接逃逸
    // ③ nearestExistingPath：路径可能还不存在，向上找最近存在的祖先
    const [realRoot, realCandidateOrParent] = await Promise.all([
      realpath(root),
      nearestExistingPath(resolved),
    ]);
    // ④ isInside 检查：真实路径必须在 workspace 内
    if (!isInside(realRoot, realCandidateOrParent)) {
      throw new Error(`符号链接越过教学 workspace：${candidate}`);
    }
  }
  // ⑤ 所有检查通过，返回 resolved
  return resolved;
}
 

源码注释写得很直白：

workspace 模式只是课程里用于防止常见误操作的 guardrail，不是安全 sandbox。它不能替代操作系统对 shell、符号链接和子进程的隔离。

● ● ●

对比真实 CC 的工具实现

CC 的工具系统在 Tool.ts + tools.ts。从反编译源码看，CC 的 Tool 接口有约 45 个成员，但理解工具系统只需要 5 个：

// CC Tool 接口核心 5 个成员
interface Tool<Input, Output, P> {
  call(input): Promise<ToolResult<Output>>;  // 执行工具
  inputSchema: ZodSchema<Input>;             // 参数校验 + 生成 JSON Schema
  isConcurrencySafe(input): boolean;          // 能不能并发跑
  checkPermissions(input): PermissionResult;  // 需不需要用户确认
  validateInput(input): void;                 // 语义校验（比 schema 更细）
}
 

对比 Pi 的 Tool 接口（EP05 拆过）：Pi 只有 name、description、schema、execute 四个字段。CC 多出来的 isConcurrencySafe、checkPermissions、validateInput 是生产级工具系统才需要的。

CC 的每个工具都过 buildTool() 工厂，注入 fail-closed 默认值：

// CC buildTool: 新工具忘了标安全属性 → 默认走最安全路径
const SAFE_DEFAULTS = {
  isParallelSafe: () => false,   // 忘了标 → 串行执行
  isReadOnly: () => false,        // 忘了标 → 当写操作对待
  isDestructive: () => false,
  checkPermissions: (input) => ({ behavior: 'allow', updatedInput: input }),
};
function buildTool(definition) {
  return { ...SAFE_DEFAULTS, ...definition };
}
 

Pi 没有这层——Pi 的工具直接返回对象，不经过工厂函数注入默认值。

逐个工具对比：

① read：行号 + 截断两边都做

CC 的 Read 也格式化行号、也有截断。差别：CC 的 Read 工具能直接读图片文件——检测 magic bytes 后 base64 编码送给多模态模型。Pi 教学版的 read 工具用 readFile(file, "utf8") 只读文本，没有这层。但 Pi 平台本身完全支持图片：用户在终端粘贴图片会走 TUI 的 ImageContent 类型直接送给模型，工具结果也能返回图片（ToolOutput.content 支持 ImageContent）。CC 还有文件状态缓存（LRU cache），同一文件多次读不重复 IO。

Pi 的优势是续读提示——截断后明确告诉模型「继续读取：offset=181」。CC 没有这个提示，模型得自己猜还有多少行。

② write：原子写入两边都做

CC 的 Write 也先写临时文件再 rename，和 Pi 一样。但 CC 多了一层 diff 预览——写入前生成 diff，显示给用户确认。Pi 直接写，不预览。

③ edit：批量 vs 单次

这是最大的差异。Pi 的 edit 原生支持批量编辑（edits[] 数组），一次提交多对 {oldText, newText}，内存里逐个检查全部通过才写回。CC 要批量编辑得用单独的 MultiEdit 工具，Edit 本身只做单次替换。

两边的匹配逻辑都要求精确字符串匹配，匹配不到就报错。Pi 多了一层唯一性检查——同一个 oldText 在文件里出现多次时拒绝执行，要求加更多上下文。CC 的 Edit 没有这个检查。

// CC Edit 的 isConcurrencySafe 是 input-dependent
// 同一个工具，不同输入有不同安全等级
isConcurrencySafe(input) {
  // ls -la → true（只读，可并发）
  // rm -rf → false（写入，串行）
}
 

Pi 选择加唯一性检查是因为教学场景要让学生理解「编辑 = 精确替换」。CC 拆成两个工具（Edit + MultiEdit）是因为生产环境需要更细的工具分类。

④ bash：进程管理两边都做

CC 的 Bash 也有超时、输出截断、进程组 kill。CC 多了后台进程支持——bg 命令让长任务在后台跑，Agent 可以继续干别的。Pi 没有后台支持，所有命令都是前台阻塞。

CC 还有权限系统——14 步执行管线，每个 bash 命令要过 checkPermissions，根据命令分类（只读 / 写入 / 危险）决定是否需要用户确认：

// CC 工具执行管线 14 步（简化）
// 1-4: 查找工具 → abort检查 → Zod校验 → 语义校验
// 5-6: 权限准备 → checkPermissions
