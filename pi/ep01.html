这系列跟着 Pi 课程走——课程每一章教一个概念，我们就打开对应的 Pi 源码，看这个概念在真实代码里长什么样。

课程第一章（Checkpoint 00）只教一件事：一条完整的 Agent 回路是什么形状的。为了让你看清形状，课程把模型、网络、真工具全抹掉了，只留一条写死的七步轨迹。

源码在 src/demo/prologue.ts，100 行。我们逐行读。

● ● ●

四个角色：谁在干活

课程第一节建立了一个认知：Agent 回路里有四种角色。

// prologue.ts:1
export type PrologueOwner = "user" | "model" | "loop" | "tool";
 

四种，没有第五个。每一步都有明确的主人：

  •  user：提需求的人
  •  model：思考、决定调什么工具
  •  loop：调度，把 model 要的工具派出去执行
  •  tool：真正干活，读文件、跑命令

为什么要分这么细？因为后面要做并发工具和状态管理——loop 和 tool 是两个独立的角色，loop 派活、tool 干活，不是一回事。先在这里把角色定义好，后面每一层都建立在这个基础上。

● ● ●

五种事件：回路被拆成五步

课程接着把一轮 Agent 回路拆成五种事件——每种是独立的数据结构：

// prologue.ts:3-8
export type PrologueTraceType =
  | "user_message"
  | "model_start"
  | "assistant_message"
  | "tool_start"
  | "tool_result";
 

五种事件，对应回路里的五个动作：

  •  user_message：用户输入
  •  model_start：开始调模型
  •  assistant_message：模型回复
  •  tool_start：开始执行工具
  •  tool_result：工具返回结果

注意 model_start 和 assistant_message 是分开的——模型开始想（调 API）和模型回复完，是两个独立的时间点。后面讲到 EventStream 时会明白为什么：模型可能需要几秒钟才返回，这期间 loop 要知道「模型正在想」。

● ● ●

PrologueTraceEvent：每一步的结构

// prologue.ts:10-16
export interface PrologueTraceEvent {
  step: number;
  owner: PrologueOwner;
  type: PrologueTraceType;
  detail: string;
  toolCallId?: string;
}
 

step 是序号，从 1 开始连续递增。toolCallId 是可选的——只有工具相关的步骤才带。课程管这个叫「因果锚」：同一个编号把请求、执行、结果锁成一条链。

● ● ●

七步轨迹：一条写死的 Demo

课程这节的核心就是这个 trace 数组——一条完全离线、不联网的七步轨迹：

// prologue.ts:18-54
const trace: PrologueTraceEvent[] = [
  { step: 1, owner: "user", type: "user_message", detail: "读取 README.md，并概括项目" },
  { step: 2, owner: "model", type: "model_start", detail: "turn=1" },
  { step: 3, owner: "model", type: "assistant_message", detail: "stopReason=toolUse name=read", toolCallId: "call_1" },
  { step: 4, owner: "loop", type: "tool_start", detail: "name=read", toolCallId: "call_1" },
  { step: 5, owner: "tool", type: "tool_result", detail: "README fixture", toolCallId: "call_1" },
  { step: 6, owner: "model", type: "model_start", detail: "turn=2" },
  { step: 7, owner: "model", type: "assistant_message", detail: "stopReason=stop" },
];
 

七步分两轮。

第一轮（step 1-5）：用户提问 → 模型想 → 模型说「调 read」→ loop 执行 read → 工具返回结果。

第二轮（step 6-7）：模型拿到结果 → 直接回答。

课程为什么写死这条轨迹？ 因为如果你接上真模型、真工具，每一步的输出都不一样，你没法看清「回路长什么样」。写死了，才能一步一步看清楚谁在干什么。

第 3、4、5 步都带 toolCallId: "call_1"。同一个编号把三步锁成因果链——模型要了（step 3），loop 派了（step 4），工具回了（step 5）。Pi 要支持并发——模型一次说「我要调 read、bash、write」，三个工具同时跑，结果混着回来，靠 callId 才能知道哪个结果对应哪次请求。

● ● ●

assertValidPrologueTrace：验证函数守红线

轨迹写好了，但怎么保证不出错？比如 step 4 写了 tool_start 但 step 5 忘了写 tool_result——悬空了。

课程给出的答案是写一个验证函数：

// prologue.ts:62-88
export function assertValidPrologueTrace(
  events: PrologueTraceEvent[],
): void {
  const calls = new Set<string>();
  const results = new Set<string>();
 
  events.forEach((event, index) => {
    if (event.step !== index + 1) {
      throw new Error(trace step 应为 ${index + 1});
    }
    if (event.type === "assistant_message" && event.toolCallId) {
      calls.add(event.toolCallId);
    }
    if (event.type === "tool_result") {
      if (!event.toolCallId || !calls.has(event.toolCallId)) {
        throw new Error("tool result 先于对应的 tool call");
      }
      results.add(event.toolCallId);
    }
  });
 
  for (const callId of calls) {
    if (!results.has(callId)) {
      throw new Error(tool call ${callId} 缺少配对结果);
    }
  }
}
 

两个 Set 做登记簿。遍历一遍：遇到带 toolCallId 的 assistant_message，记进 calls；遇到 tool_result，记进 results。最后比对——calls 里有但 results 里没有的，就是悬空。

这就是 call id 因果配对的完整实现。两道检查：

  1. 01结果先于请求：tool_result 出现时，calls 里必须已有对应的 callId（第 76 行）
  2. 02请求没有结果：遍历结束后，calls 里每个 callId 必须在 results 里也有（第 83 行）

少一步会怎样？把第 5 步（tool_result）删掉，验证函数遍历到结束时发现 calls 里有 call_1，results 里没有：

去掉 tool_result 后剩余 step: [ 1, 2, 3, 4, 5, 6 ]
报错信息: tool call call_1 缺少配对结果
 

轨迹断了，护栏立刻报警；轨迹完整，护栏一声不吭放行。

● ● ●

runPrologueDemo：深拷贝防篡改

// prologue.ts:56-60
export function runPrologueDemo(): PrologueTraceEvent[] {
  const result = structuredClone(trace);
  assertValidPrologueTrace(result);
  return result;
}
 

structuredClone(trace) 不是直接 return trace——深拷贝一份。因为返回值是可变的数组，调用方可能往里加东西或删东西。直接返回 trace，原始数据就脏了。

然后调 assertValidPrologueTrace 验证。先验证再返回——数据出门之前先过安检。

formatPrologueTrace：格式化输出

// prologue.ts:90-99
export function formatPrologueTrace(events: PrologueTraceEvent[]): string {
  return events
    .map((event) =>
      ${String(event.step).padStart(2, "0")} ${event.type.padEnd(17)} owner=${event.owner} ${event.detail},
    )
    .join("\n");
}
 

输出长这样：

01 user_message      owner=user  读取 README.md，并概括项目
02 model_start       owner=model turn=1
03 assistant_message owner=model stopReason=toolUse name=read
04 tool_start        owner=loop  name=read
05 tool_result       owner=tool  README fixture
06 model_start       owner=model turn=2
07 assistant_message owner=model stopReason=stop
 

四列：序号、事件类型、角色、详情。一眼看清整条回路。

这一节学了什么

课程 Checkpoint 00 教的三件事，在 Pi 源码里全找到了：

  1. 01四种角色：PrologueOwner 联合类型，编译期保证不会有第五种
  2. 02call id 因果配对：两个 Set 登记簿，悬空即报错
  3. 03回路形状：七步轨迹是后面所有章节的地基——EventStream 给它装上异步、Provider Adapter 接上真模型、Coding Tools 接上真工具、Session 给它加持久化

先让你看见一条完整的回路，再用一个验证函数告诉你回路不能断在哪。这就是 Checkpoint 00 的全部。
