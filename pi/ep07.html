大家好我是郑同学。前几篇我们拆完了 Agent Loop、Provider 适配器、文件工具——每次对话都是独立的一次。但你用 Pi 的时候会发现：关掉终端再打开，它还记得你上次说了什么。

这一篇拆 Pi 的状态管理，全在 session.ts（801 行）和 agent.ts（248 行）。两个文件管两件事：session.ts 负责持久化到磁盘，agent.ts 负责运行时的内存状态。

先搞清流程。你跟 Pi 说了一句话，这句话经过 Agent Loop 跑完后，需要存下来——不然关掉终端就忘了。下次打开 Pi，需要把之前的对话读回来。session.ts 就是干这两件事的。

● ● ●

核心设计决策：为什么选 append-only log

很多人会想：状态管理不就是把对话存到数据库吗？Pi 选了一个看似更简单的方案——每条消息追加写入一个文本文件，不修改、不删除、不建索引。

为什么不用 SQLite？为什么不用 update-in-place？

因为追加写入是崩溃安全的。不管是断电、进程被 kill、磁盘满，已经写入的数据不会丢。update-in-place 要先读旧数据、改、写回——中间任何一步崩了，数据就可能损坏。追加写入不需要读旧数据，直接在文件末尾加一行，操作系统保证 append 操作的原子性。

代价是：你想删一条消息？做不到。你想改一条消息？做不到。但 Pi 不需要——对话历史是不可变的，你可以开新分支，但不能改老内容。

这就是 Pi 选择的存储格式 JSONL（JSON Lines）——每行一个 JSON 对象，用换行符分隔。

● ● ●

Part 1：parentId 树——不是数组，是链表

存下来之后怎么读回来？最直觉的做法是按顺序存成一个数组——messages[0]、messages[1]...

Pi 没这么做。每条 entry 有 id 和 parentId，形成一条从根到叶的链：

// session.ts:26-30
interface EntryBase {
  id: string;
  parentId: string | null;
  timestamp: number;
}
 

为什么要用 parentId 链表而不是数组？

因为对话可以分叉。你可能在某条消息后面开一条新分支——「如果刚才换种问法呢？」同一个 parent 可以有多个子 entry，形成一棵树。数组只能表示线性顺序，树能表示探索。

读对话历史时，指定一个叶子节点（leafId），从叶子沿着 parentId 回溯到根，就是一条完整的对话路径。不需要读全部 entry，只需要这一条链。

三种 entry 类型：

// session.ts:61-64
type SessionEntry =
  | MessageSessionEntry
  | MetadataSessionEntry
  | CompactionSessionEntry;
 

MessageSessionEntry 包裹一条完整的消息（用户消息 / 助手回复 / 工具结果）。MetadataSessionEntry 存元数据（比如当前用的模型名）。CompactionSessionEntry 是上下文压缩的产物——当消息历史太长时，把旧消息合并成一条摘要 entry，释放 token 预算。

● ● ●

Part 2：崩溃恢复——换行符就是 commit marker

JSONL 靠换行符判断一条记录是否写完。这是整个持久化方案最精妙的地方。

// session.ts:580-618
export function recoverJsonl(value: string): SessionReadResult {
  const lines = value.split("\n");
  // 最后一段没有换行符 → 写到一半崩了
  const hasUnterminatedTail =
    !value.endsWith("\n") && lines.at(-1)?.trim().length !== 0;
  const committedLineCount =
    hasUnterminatedTail ? lines.length - 1 : lines.length;
 
  if (hasUnterminatedTail) {
    warnings.push({ code: "unterminated_tail", line: lines.length });
  }
 
  const entries: SessionEntry[] = [];
  for (let index = 0; index < committedLineCount; index += 1) {
    const line = lines[index] ?? "";
    if (line.trim().length === 0) continue;
    // 每行 JSON.parse 后做严格校验
    const parsed = JSON.parse(line);
    entries.push(parseSessionEntry(parsed));
  }
  return { entries, warnings };
}
 

换行符就是 commit marker。一行写完了换行符了，这条记录就生效。最后一行没有换行符，说明写入到一半被打断了（断电、进程崩溃），这行直接丢弃，只保留有换行符的完整行。

这和数据库的 WAL（Write-Ahead Log）是同一个思路——先写日志再操作，崩溃后靠日志恢复。Pi 没用数据库，但用了同样的原理：每个换行符都是一次隐式事务提交。

● ● ●

Part 3：tainted——坏了就不写了

写入失败（磁盘满、权限错误）时，Pi 做了一件反直觉的事——永久标记为 tainted，拒绝后续所有写入。

// session.ts:702-735（简化）
append(entry: SessionEntry): Promise<void> {
  // 文件已损坏 → 拒绝
  if (this.tainted) return rejected(this.taintCause);
  // 有未修复的尾部 → 拒绝
  if (this.repairWarning) {
    return rejected(new Error("修复前不能 append"));
  }
 
  const serialized = `${JSON.stringify(snapshot)}\n`;
  const operation = this.tail.then(async () => {
    validateNextEntry(snapshot, this.ids);
    try {
      await this.io.appendFile(this.file, serialized);
    } catch (error) {
      // 写入失败 → 标记 tainted，后续全部拒绝
      this.tainted = true;
      this.taintCause = error;
      throw error;
    }
    this.ids.add(snapshot.id);
  });
  this.tail = operation.catch(() => undefined);
  return operation;
}
 

为什么不重试？

因为不知道失败到什么程度。可能是磁盘满了（重试也没用），可能是文件系统损坏（重试会更糟），可能是权限被改了。在不确定的情况下继续写，可能把已有数据也搞坏。

Fail fast，不静默吞错——宁可停止接受新数据，也不在可能损坏的文件上继续操作。已写入的数据是安全的（append-only 保证），用户可以手动修复文件后重开。

写入操作本身通过 Promise 链串行化（this.tail），和 EP06 的 MutationQueue 一样的模式——同一个文件的写入操作排队执行，不会并发冲突。

Part 4：pathTo——从叶子回溯到根

读回所有 entry 后，怎么还原对话历史？从叶子节点沿着 parentId 回溯到根。

// session.ts:752-788（简化）
export function pathTo(
  entries: readonly SessionEntry[],
  leafId: string,
): SessionEntry[] {
  const byId = new Map<string, SessionEntry>();
  for (const entry of entries) byId.set(entry.id, entry);
 
  const reverse: SessionEntry[] = [];
  const visited = new Set<string>();
  let current = byId.get(leafId);
  // 从叶子往根走
  while (current) {
    // 环检测：A→B→A 直接报错
    if (visited.has(current.id)) throw new Error("形成环");
    visited.add(current.id);
    reverse.push(current);
    if (current.parentId === null) break;
    current = byId.get(current.parentId);
  }
  // 反转：从根到叶的顺序
  return reverse.reverse();
}
 

visited 集合做环检测——如果 parentId 链形成环（数据损坏导致 A→B→A），直接报错，不会无限循环。

拿到 path 后过滤出 message 类型的 entry，就是完整的对话历史：

// session.ts:794-801
export function messagesOnPath(
  entries: readonly SessionEntry[],
  leafId: string,
): AgentMessage[] {
  return pathTo(entries, leafId).flatMap((entry) =>
    entry.type === "message" ? [structuredClone(entry.message)] : []
  );
}
 

metadata 和 compaction entry 被过滤掉，不进入模型上下文。模型只看到消息序列，不知道存储格式。

Part 5：内存状态和持久化为什么分开

Agent 类（agent.ts）管运行时的内存状态。它持有当前消息历史、流式文本、工具调用状态。每次 prompt 调用都在内存里更新，关机就没了。

为什么要分两层？因为运行时状态和持久化状态的更新频率完全不同：

  •  运行时状态：模型每吐一个字就更新一次（streamingText 拼接），每秒可能几十次
  •  持久化状态：一条消息跑完后才追加一次

如果把两者合一，每吐一个字就要写磁盘——太慢了。分开后，内存状态高频更新不碰磁盘，持久化状态低频追加不阻塞 UI。

Agent 还支持两个运行时能力：

// agent.ts:193-206（简化）
async prompt(value: string): Promise<AgentRunResult> {
  const contextMessages = [...clone(this.state.messages), clone(message)];
  result = await runAgentLoop({
    context: { messages: contextMessages },
    takeSteeringMessages: () => run.steering.splice(0),
    takeFollowUpMessages: () => run.followUps.splice(0),
    onEvent: (event) => this.emit({ type: "loop", event }),
  });
  this.emit({ type: "run_end", result });
}
 

steering——趁 Agent Loop 还在跑，插入一条新指令。Agent Loop 每轮检查 takeSteeringMessages()，如果有新指令就加进当前上下文。这让用户能在模型思考时补充要求，不用等当前 run 结束。

followUp——排一条下一条要问的。当前 run 结束后自动接着跑。

Part 6：400 行校验——fail-closed 设计

session.ts 有将近 400 行在做反序列化校验。每行 JSONL 读回来时，不是直接 JSON.parse 就用，而是过一遍 parseSessionEntry + 一堆 xxxAt 函数。

为什么这么严格？因为文件可能被外部修改、版本升级后格式可能变、写入到一半可能截断。如果不校验直接用，模型收到的消息历史可能有缺失字段、类型错误，导致 API 调用失败或行为异常。

核心校验函数 exactKeys 检查字段集合完全匹配——多了未知字段报错（防止格式升级后静默忽略新字段），少了必需字段也报错。

// session.ts:347-403（简化）
function assistantMessageAt(record, label): AssistantMessage {
  // 必须恰好有这些字段
  exactKeys(record, ["role", "content", "provider", "model",
    "usage", "stopReason", "errorMessage", "timestamp"], label);
  // stopReason 必须是已知值
  if (!stopReasons.has(record.stopReason))
    throw new Error("不是已知终态");
}
 

宁可启动失败，不带病运行。这是 fail-closed 设计——出了问题立刻暴露，不往下走，不让坏数据污染后续逻辑。

对比真实 CC 的状态管理

CC 也用 JSONL 格式存储会话日志，文件在 ~/.claude/projects/ 目录下，每个项目一个子目录，每条对话一个 .jsonl 文件。这个设计思路和 Pi 一样——追加写入 + 换行符判断完整性。

但有几个关键差异：

① 分叉 vs 复制

Pi 的 parentId 链表原生支持分叉——同一个 parent 可以有多个子 entry，你可以在历史对话的某个节点开新分支，所有分支共享同一份日志文件。CC 创建子 Agent（subagent）时是复制整个上下文，子 Agent 有自己独立的日志。

② 压缩策略

Pi 有 CompactionSessionEntry——当消息历史太长时，把旧消息合并成一条摘要 entry，包含 goal、completed、decisions、next 等结构化字段。CC 也有上下文压缩（/compact 命令），CC 的压缩是自动触发的——当 token 数接近上下文窗口上限时自动压缩，不需要用户手动操作。Pi 的压缩是手动触发。

③ 工具结果缓存

CC 在状态里维护一份文件读取缓存（readFileState），同一个文件多次读取不重复 IO。Pi 的 read 工具每次都重新读文件，没有缓存。

④ 会话恢复粒度

Pi 恢复时从 JSONL 读回所有 entry，然后沿着 parentId 链回溯出一条路径。CC 恢复时读取整个 JSONL 文件，按顺序重建消息历史。Pi 支持选择任意分支恢复，CC 是线性恢复。

两边选了同样的存储格式（JSONL），但在上层抽象上走了不同方向。Pi 用 parentId 树支持分叉探索，CC 用线性历史 + 子 Agent 复制支持并行工作。

● ● ●

小结

设计决策选择为什么
存储格式JSONL append-only崩溃安全，已写入数据不丢
数据结构parentId 链表树支持分叉探索
崩溃恢复换行符 = commit marker半截行直接丢弃
写入失败tainted 永久拒绝不在损坏文件上继续写
校验策略exactKeys 严格匹配fail-closed，不带病运行
内存 vs 磁盘分两层运行时高频更新不碰磁盘

口诀：一行一消息，换行才算完，parentId 串成链，坏了直接扔。
