你第一次跟 Pi 说"帮我改登录页"，它改完了。你接着发"把标题也调大点"——它知道"标题"是哪个标题，不用你重新解释项目结构、不用重新贴代码、不用重新说"登录页在 src/pages/login.tsx"。

这个"记得"是怎么实现的？

前几节的 Agent 是个一次性函数：调一次 prompt()，函数一返回，里面所有的 messages、工具结果、中间状态全跟着局部变量一起被回收。你再发一句话过去，它像第一次认识你。说它是"金鱼脑"也不过分。

这一节（课程 Checkpoint 09）解决的就是这件事：把 Agent 从一次性函数升级成一个持续存活、可被外部观察的对象。核心全在 agent.ts 的 248 行里。下面逐块拆，解释尽量放进代码注释，正文只做引导。

● ● ●

AgentState：把 Agent 的脑子写成字段

先看状态长什么样。打开 agent.ts 第 24-32 行：

export interface AgentState {
  status: "idle" | "running";           // 是否在跑，一眼看出 Agent 忙不忙
  messages: AgentMessage[];             // 完整对话历史——"记忆"就靠这一条
  activeRunId?: number;                 // 当前运行编号，用来校验事件归属
  lastReason?: AgentRunResult["reason"];// 上次为什么结束：正常/上限/出错/取消
  streamingText: string;                // 模型正在生成的流式文本，边生成边累加
  pendingToolCallIds: string[];         // 还没返回的工具调用 id——非空就是在等工具
  diagnostics: string[];                // 诊断信息，比如哪个订阅者抛了异常
}
 

七个字段，一个完整快照。逐个对照使用场景就明白了：你想知道 Agent 现在是不是空闲，看 status；想知道它还记得什么，看 messages；想知道流式回答打到哪了，看 streamingText；想知道它是不是卡在等某个工具，看 pendingToolCallIds 还有没有没清空的 id。

任何时候调 getState 都能拿到当前全貌。这里有个认知要先立住：状态不是某个变量的当前值，而是一组字段的集合——你拿到的是整个脑子，不是某个念头。后面订阅、取消、插话都建立在这个基础上。

● ● ●

AgentEvent：状态变化的唯一来源

状态不会自己变。Pi 的选择是用事件作为状态变化的唯一驱动力。第 34-37 行定义了一个 tagged union：

export type AgentEvent =
  // 一次运行开始：带 runId 和触发它的用户消息
  | { type: "run_start"; runId: number; message: UserMessage }
  // 运行中间的每一步：text_delta / tool_start / tool_end 等全包在这层
  | { type: "loop"; runId: number; event: LoopEvent }
  // 运行结束：带最终 messages 和结束原因
  | { type: "run_end"; runId: number; result: AgentRunResult };
 

只有三层分支。注意课程概念里的 model_event、tool_start、tool_end、turn_end 这些，其实都藏在 loop 分支的 LoopEvent 里——Pi 做了两层设计：外层管运行生命周期，内层管单步细节。Agent 这个类只关心"运行开始、中间有动静、结束"这三件事，每步是模型回话还是调工具，交给 loop 层去处理。

每个事件都带 runId，这不是装饰。同一时刻队列里可能排着多条事件，runId 决定它们是否还属于当前运行，后面会看到它是过滤过期事件的关键。

● ● ●

reduceAgentState：一个纯函数管所有变化

这是本节最核心的部分。课程要求每次状态变化都经过同一个纯函数 reducer：给它当前状态和一个事件，返回新状态。第 43-46 行先看签名：

export function reduceAgentState(
  state: AgentState,   // 当前状态（只读，绝不改）
  event: AgentEvent,   // 要处理的事件
): AgentState {        // 返回全新状态对象
 

run_start 分支（47-57 行）：

if (event.type === "run_start") {
  return {
    ...state,                                                    // 复制所有旧字段
    status: "running",                                           // 翻到 running
    activeRunId: event.runId,                                    // 记下本次运行编号
    lastReason: undefined,                                       // 清掉上次结束原因
    messages: [...clone(state.messages), clone(event.message)],  // 把用户这条消息追加进历史
    streamingText: "",                                           // 流式缓冲归零
    pendingToolCallIds: [],                                      // 待处理工具清空
  };
}
 

每段都返回新对象，用 ...state 复制旧字段再覆盖个别字段。这是 reducer 的铁律：永远不改入参，永远返回新对象。好处是任何时候的状态都是不可变快照，可以随时回放、对比、调试。

接下来是一道校验门（59-64 行），除了 run_start，所有事件都要先过：

if (
  state.status !== "running" ||      // 已经不在 running 状态
  state.activeRunId !== event.runId  // 或事件的 runId 跟当前对不上
) {
  return state; // 过期事件，直接丢，不报错也不记录
}
 

这处理的是一种真实场景：运行 A 刚结束，队列里还残留 A 迟到的 loop 事件，此时运行 B 已经开始、runId 变了——A 的迟到事件被这段代码静默丢弃。比抛异常优雅得多，因为迟到事件本来就不是错误，是异步系统的常态。

过了校验进 loop 分支，按子类型分派。文本流式累加（68-76 行）：

if (
  loop.type === "model_event" &&
  loop.event.type === "text_delta"
) {
  return {
    ...state,
    streamingText: state.streamingText + loop.event.delta, // 每个 token 拼到尾巴
  };
}
 

模型每吐一个 token，streamingText 拼一段。这就是前端"逐字显示"的底层机制——每个 text_delta 都产生一个新状态，订阅者拿到新状态就刷新一次界面。你看到的打字机效果，背后是这条累加逻辑。

工具调用对称处理（77-93 行）：

if (loop.type === "tool_start") {
  return {
    ...state,
    pendingToolCallIds: [...state.pendingToolCallIds, loop.call.id], // 追加待处理 id
  };
}
if (loop.type === "tool_end" || loop.type === "tool_skipped") {
  return {
    ...state,
    pendingToolCallIds: state.pendingToolCallIds.filter(             // 把完成的 id 滤掉
      (id) => id !== loop.result.toolCallId,
    ),
  };
}
 

assistant_message 分支（94-96 行）把 streamingText 清空——这段文本已经正式写进 messages 数组，流式缓冲区可以归零，等下一段回答重新累加。

最后 run_end（100-108 行）把状态翻回 idle，写入最终 messages 和 lastReason，一次运行的状态机就此闭环。

整个 reducer 没有任何副作用：不读写文件、不发网络请求、不调回调。相同的状态加相同的事件，永远得到相同的新状态。这是后面所有机制——订阅、取消、插话、追问——能可靠运转的地基。

● ● ●

emit 消息泵：排队 + 重入保护

reducer 是纯函数，谁来调用它？答案是一个叫 emit 的消息泵。这部分课程讲得细，因为它要同时解决并发和容错两个难题。第 145-173 行：

private emit(event: AgentEvent): void {
  this.pendingEvents.push(event);     // 每个事件先进队列
  if (this.dispatchingEvents) return; // 已在分发中？直接走，别重复进循环（重入保护）
 
  this.dispatchingEvents = true;      // 拿到"分发权"
  try {
    while (this.pendingEvents.length > 0) {
      const next = this.pendingEvents.shift()!;        // 取出最早那条
      this.state = reduceAgentState(this.state, next); // 先用 reducer 更新状态
      for (const listener of [...this.subscribers]) {  // 再通知所有订阅者
        try {
          listener(clone(next));     // 给每个订阅者一份独立副本，谁也别想改原件
        } catch (error) {
          // 订阅者抛错不会炸掉分发循环，只记进 diagnostics
          this.state = { ...this.state,
            diagnostics: [...this.state.diagnostics,
              `subscriber: ${error instanceof Error ? error.message : String(error)}`] };
        }
      }
    }
  } finally {
    this.dispatchingEvents = false;  // 无论是否异常，复位标志
  }
}
 

读这段有几个细节值得记住。

第一，每个事件先 reduce 更新状态，再通知订阅者，保证订阅者拿到的状态总是最新的。

第二，开头那行 if (this.dispatchingEvents) return 就是重入保护。为什么要它？因为分发过程中，订阅者的回调可能又触发新的 emit（比如某个 subscriber 在回调里又调了 prompt）。没有这层保护就会无限递归，调用栈直接爆掉。有了它，递归触发的 emit 只会把事件 push 进队列然后返回，由外层那个 while 循环统一处理。

第三，也是最狠的一点：订阅者的回调被内层 try/catch 包住。一个订阅者抛异常，不会炸掉整个分发循环，只会被记进 diagnostics。想象一个 UI 订阅者因为渲染 bug 抛错，没有这层隔离，整个 Agent 就停摆了。finally 里复位标志位，保证异常之后还能继续分发后续事件。

● ● ●

对外接口：快照、订阅、单运行、取消

把几个对外方法放一起看，它们共同定义了 Agent 的"使用契约"。先看读取侧（136-143 行）：

getState(): AgentState {
  return clone(this.state); // 深拷贝，外部永远拿不到内部引用
}
 
subscribe(listener: (event: AgentEvent) => void): () => void {
  this.subscribers.add(listener);
  return () => this.subscribers.delete(listener); // 返回取消订阅的函数
}
 

getState 返回 clone(this.state)——外部改不到内部状态，哪怕外部把这个对象改得面目全非，内部 state 一个字都不会变。subscribe 返回一个取消订阅的函数，用完记得调，否则会内存泄漏（订阅者一直被 Set 持有）。

单运行语义写在 prompt 开头（193-196 行）：

async prompt(value: string): Promise<AgentRunResult> {
  if (this.activeRun) {
    throw new Error("Agent is busy"); // 已在跑？直接拒绝第二个
  }
 

同一时刻只允许一个 prompt 在跑。第二个调用直接抛 "Agent is busy"。这是有意的设计选择：多运行并发会让状态、订阅、取消全部失控，与其勉强支持不如直接拒绝。如果你真想排队，应该在外面自己写个队列，而不是让 Agent 内部承担并发复杂性。

取消用 AbortController（189-191 行）：

abort(): void {
  this.activeRun?.controller.abort(); // 打个信号，不是强杀线程
}
 

这是协作式取消，不是强杀——loop 内部在合适的检查点看到 signal 被 abort，就会优雅退出，把已经完成的部分整理好返回。?. 保证当前没运行时，空调用也安全。

● ● ●

steer 和 followUp：插话与追问

这两个名字像、语义完全不同的方法是 Checkpoint 09 最容易混淆的点。175-187 行：

steer(value: string): void {
  if (!this.activeRun?.acceptingInput) {
    throw new Error("steering 只在当前 run 尚未结束时有意义");
  }
  this.activeRun.steering.push(userMessage(value)); // 塞进插话队列
}
 
followUp(value: string): void {
  if (!this.activeRun?.acceptingInput) {
    throw new Error("follow-up 只在当前 run 尚未结束时排队");
  }
  this.activeRun.followUps.push(userMessage(value)); // 塞进追问队列
}
 

steer 是插话——运行还在中途，你临时塞一句话进去，loop 下一轮就会读到它，可能立刻改变后续走向。比如 Agent 正在批量改文件，你插一句"先别动测试目录"，它下一轮就看见了，不会再碰测试。

followUp 是追问——运行还在跑，但你已经想好下一句要问什么了，先排进队列，等这次运行结束后自动接上，省得你盯着屏幕等它跑完再发。

两个队列怎么被消费？看 prompt 传给 loop 的两个回调（222-223 行）：

takeSteeringMessages: () => run.steering.splice(0),  // splice(0) 清空数组并返回原内容
takeFollowUpMessages: () => run.followUps.splice(0), // loop 每轮调一次
 

splice(0) 是"取了即清"——loop 每轮把队列里的插话和追问全部取走，下一轮队列已空。这是个很干净的语义，避免同一条消息被重复消费。

边界在 acceptingInput 这个标志，它随 turn_end 关闭（224-227 行）：

onEvent: (event) => {
  if (event.type === "turn_end") run.acceptingInput = false; // 模型决定收尾，关闭输入
  this.emit({ type: "loop", runId: run.id, event });
},
 

turn_end 一到，acceptingInput 立刻关掉。之后 steer 和 followUp 都会被拒，因为模型已经决定结束这轮了，再插话也没意义。这个标志把"什么时候还能插话"划得很清楚。

● ● ●

一次完整 prompt 的时间线

把所有零件串起来，一次 prompt 调用的时间线长这样：

prompt("帮我改一下登录页")
  │
  ├─ 检查 activeRun，没有 → 放行
  ├─ 生成 runId，创建 ActiveRun + AbortController
  ├─ emit run_start → reducer 翻到 running，messages 追加用户消息
  │
  ├─ runAgentLoop 开始（每步通过 onEvent 回调）
  │   ├─ model_event(text_delta) → streamingText 累加
  │   ├─ tool_start → pendingToolCallIds 追加
  │   ├─ tool_end → pendingToolCallIds 移除
  │   ├─ (中途) steer("别动测试") → steering 队列
  │   ├─ assistant_message → streamingText 清空
  │   └─ turn_end → acceptingInput 关闭
  │
  ├─ runAgentLoop 返回 result
  ├─ emit run_end → reducer 翻回 idle，写入最终 messages
  └─ return clone(result)
 

每一个箭头都对应前面讲过的一段源码。整条链路里，状态只在 reducer 里被改，事件只经 emit 排队，外部只通过 subscribe 和 getState 观察。这套约束让 Agent 的行为可预测、可调试、可回放。

● ● ●

小结

读完这节三点最有感觉。

第一，把状态变化关进纯函数 reducer，是复杂系统能保持可控的关键。Agent 内部并发那么多——流式 token 一个接一个、工具调用有快有慢、用户随时插话——如果没有"事件→reducer→新状态"这条单一通道，状态早就乱成一锅粥。reducer 让所有变化都经过同一个关口，可审计、可回放。

第二，订阅者异常隔离看着是个小细节，却是生产级代码和玩具代码的分水岭。一个渲染 bug 就能让整个 Agent 停摆的系统，没人敢用。try/catch 包住 listener 那几行代码，价值远超它的篇幅。

第三，steer 和 followUp 的区分特别贴合真实使用直觉——插话和追问本来就是两种心智模型，硬合成一个 API 反而别扭。你跟同事讨论问题时，"等一下我插一句"和"你说完我再问"也是完全不同的两种动作。
