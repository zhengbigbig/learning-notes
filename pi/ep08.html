有一个瞬间会让人对 Pi 刮目相看：你聊了一下午，改了十几个文件，然后随手把终端关了。第二天重新打开，输入一句"接着昨天的继续"，它居然接上了——记得你问过什么、它改过哪些文件、哪些工具结果还没处理。

对话怎么没跟着进程一起蒸发？答案很简单：Pi 把对话写在了一个 JSONL 文件里，一行一条，关机重启都还在。

但"写进文件"这四个字背后藏着一堆魔鬼细节。进程写到一半被 kill 了怎么办？文件被截断了怎么办？磁盘满了怎么办？这些场景任何一种没处理好，"关掉重开还在"就会变成"关掉重开乱套"。

EP08 这一讲，我们看 Checkpoint 10，顺着使用者的真实疑问拆开三件事：对话是怎么变成文件的？写到一半崩溃了，重启会不会丢数据、会不会读到半行垃圾？恢复回来，又是怎么从一堆记录里拼出一条完整上下文喂给模型的？

源码全在 session.ts，八百行。我们逐段拆。

● ● ●

一、三种事实，挂在同一棵树上

先想清楚一件事：要存的不是一串聊天记录，是一棵会话树。

为什么是树？因为你在某一句话上可以 fork 出分支重试——"刚才那个方案不行，换一种思路重新来"，旧分支还留着当参考，新分支继续往下走。这种结构用一张线性表根本表达不了，必须用父指针把每条记录挂成一棵树。

Pi 把每一条落盘记录叫 SessionEntry，只有三种可能：

// session.ts:61-64 —— 一个会话文件里只有这三类条目
export type SessionEntry =
  | MessageSessionEntry     // 真正的对话内容：用户话、模型回复、工具结果
  | MetadataSessionEntry;   // 元信息：模型版本、token 用量，不进模型上下文
  | CompactionSessionEntry; // 上下文压缩点：把前面一段总结成一份摘要
 

一个会话里只有这三类条目，多一种都算污染。 三者共享一个底座：

// session.ts:26-30 —— 每条记录都带身份和父指针
interface EntryBase {
  id: string;               // 这条记录的唯一 id
  parentId: string | null;  // 指向上一条记录，根节点是 null
  timestamp: number;        // 落盘时间戳
}
 

这不是日志，是一棵树。 有 parentId 就意味着同一个会话里可以有多条"最新消息"——你在某个节点 fork 两条分支，两条都是合法的叶子，恢复时你得指明要走哪一条。

来看三种各自的形状。message 最直接：

// session.ts:32-35
export interface MessageSessionEntry extends EntryBase {
  type: "message";        // 标记这是一条对话消息
  message: AgentMessage;  // 实际的 user/assistant/toolResult 载荷
}
 

metadata 多两个字段：

// session.ts:37-41
export interface MetadataSessionEntry extends EntryBase {
  type: "metadata";
  key: string;            // 比如 "model" / "usage"，标识这是什么元信息
  value: JsonValue;       // 任意 JSON 值，但不进模型上下文
}
 

compaction 最重，它要承载被压缩掉的整段上下文：

// session.ts:53-59
export interface CompactionSessionEntry extends EntryBase {
  type: "compaction";
  parentId: string;            // 注意是 string 不是 null：压缩点必挂在一个真实节点下
  summary: CompactionSummary;  // 结构化摘要，七字段全是字符串数组
  firstKeptEntryId: string;    // 压缩后保留的第一条 entry 的 id
  tokensBefore: number;        // 压缩前的 token 数，留作事后审计
}
 

CompactionSummary 七个字段——goal、completed、unresolved、next 等等全是字符串数组。结构化摘要比一段自然语言有用得多，模型恢复时拿到的是能直接消费的字段，不是一坨散文。比如 unresolved 里写着"登录页的表单校验还没接后端"，模型下一轮就知道从哪儿接。

二、换行符就是落地的印章

类型定义是给编译器看的。真正从磁盘读回来的是 unknown，一坨未经审查的字节。Pi 要先决定一个更基本的问题：哪些字节算"一条完整的记录"。

文件写入不是原子的。进程可能写到一半被 kill，留下半截 {"id":"abc","parent。如果你把这半行当事实，下次解析直接炸。Pi 的做法很干脆：

// session.ts:580-586
export function recoverJsonl(value: string): SessionReadResult {
  const lines = value.split("\n");
  const warnings: UnterminatedTailWarning[] = [];
  // 关键判定：最后一行若没有换行符结尾，就按"未提交"处理
  const hasUnterminatedTail =
    !value.endsWith("\n") && lines.at(-1)?.trim().length !== 0;
  // 未提交的那一行不计入已提交行数，等于直接丢弃
  const committedLineCount =
    hasUnterminatedTail ? lines.length - 1 : lines.length;
 

只有以换行符结尾的行，才算"已提交"。 换行符就是 commit marker，没盖章的半行 JSON，无论多像合法数据，一律不算事实。

这是一个非常务实的选择。文件系统不给你原子写一行的保证，Pi 也不假装它有。它把"这条记录到底写完没"的判定权，下放给一个最朴素的事实：结尾有没有那个换行符。有，就算落地；没有，就当它从来没发生过。

丢弃不是静默，残行会被记成一条 warning，留给上层决定要不要修：

// session.ts:588-593
  if (hasUnterminatedTail) {
    warnings.push({
      code: "unterminated_tail",
      line: lines.length,   // 告诉你第几行是残行，方便定位修复
    });
  }
 

接下来循环解析每一行，空行跳过，非法 JSON 单独报错：

// session.ts:596-616
  const entries: SessionEntry[] = [];
  for (let index = 0; index < committedLineCount; index += 1) {
    const line = lines[index] ?? "";
    if (line.trim().length === 0) continue;       // 空行只是排版，不代表 entry
    let parsed: unknown;
    try {
      parsed = JSON.parse(line);                   // 第一层：JSON 合法性
    } catch (error) {
      throw new Error(
        `session JSONL 第 ${index + 1} 行不是合法 JSON：${describe(error)}`,
        { cause: error },
      );
    }
    try {
      entries.push(parseSessionEntry(parsed));     // 第二层：schema 校验
    } catch (error) {
      throw new Error(
        `session JSONL 第 ${index + 1} 行不是合法 session entry：${describe(error)}`,
        { cause: error },
      );
    }
  }
 

两层 try/catch，JSON 解析和 schema 校验分开报错，错误信息精确到第几行还带原始 cause。调试时一眼定位是哪一行炸的。

parseSessionEntry 本身是另一道关。它对从磁盘读回来的任何东西都先怀疑再相信。入口用 recordAt 检查是不是干净的 JSON object：

// session.ts:112-133（节选）
function recordAt(value: unknown, label: string): Record<string, unknown> {
  if (value === null || typeof value !== "object" || Array.isArray(value)) {
    throw new Error(`${label} 必须是 object`);        // 必须是对象，不是数组、不是 null
  }
  const prototype = Object.getPrototypeOf(value);
  if (prototype !== Object.prototype && prototype !== null) {
    throw new Error(`${label} 必须是普通 JSON object`); // 拒绝 prototype 污染
  }
  // 再逐字段检查：必须是普通 enumerable data property
  // 干掉 symbol 键、getter/setter、__proto__ 这类 JSON 不该有的 JavaScript 私货
  for (const key of Reflect.ownKeys(value)) { /* ...省略校验... */ }
  return value as Record<string, unknown>;
}
 

然后 exactKeys 检查字段集合是否精确匹配：

// session.ts:135-146
function exactKeys(record, allowed, label): void {
  const allowedKeys = new Set(allowed);
  for (const key of Object.keys(record)) {
    if (!allowedKeys.has(key)) {
      throw new Error(`${label} 包含未知字段 ${key}`); // 多一个字段就直接报错
    }
  }
}
 

未知字段不是警告，是错误。 旧版本读新格式会直接炸，而不是悄悄忽略新字段——这让 schema 演进变得可控。exactKeys 只防"多"，own 再防"少"：确认该有的字段确实存在。两层校验，一层防多一层防少。

三、写串起来，写坏就锁死

校验和恢复都有了，接下来是真正的存储类 JsonlSessionStore。它有三个关键设计：tail promise 串行化、taint 永久封印、repair warning。

构造和打开：

// session.ts:676-700
export class JsonlSessionStore implements SessionStore {
  private tail: Promise<void> = Promise.resolve();  // 串行化的尾巴 promise
  private tainted = false;                          // 一旦写坏就永久置 true
  private taintCause: unknown;                      // 记下当初那个错误，后面回传
 
  private constructor(
    private readonly file: string,
    private readonly io: SessionFileIO,
    private readonly ids: Set<string>,              // 所有已提交 entry 的 id，查重用
    private readonly repairWarning?: UnterminatedTailWarning, // 残行警告
  ) {}
 
  static async open(file, io = nodeSessionFileIO): Promise<JsonlSessionStore> {
    await io.ensureFile(file);
    const recovered = recoverJsonl(await io.readFile(file)); // 读全文走一遍恢复
    return new JsonlSessionStore(
      file, io,
      idsFromCommittedEntries(recovered.entries), // 把已提交 entry 的 id 收集成 Set
      recovered.warnings[0],                       // 残行警告存下来，没修就不让 append
    );
  }
 

这个 store 一出生就带着它过去的全部历史——所有已提交的 id 都在 this.ids 里，后续 append 时查重用。

append 是整个文件最精妙的一段：

// session.ts:702-735
  append(entry: SessionEntry): Promise<void> {
    // 第一道闸：已经 tainted，直接拒绝，返回当初那个错误（不是新错误）
    if (this.tainted) return rejected(this.taintCause);
    // 第二道闸：有残行未修复，也拒绝——先修再写，绝不带着脏数据继续加
    if (this.repairWarning) {
      return rejected(
        new Error(`session 文件第 ${this.repairWarning.line} 行有未提交尾部；修复前不能 append`),
      );
    }
 
    let snapshot: SessionEntry;
    let serialized: string;
    try {
      snapshot = parseSessionEntry(entry);           // 入参也要过一遍 schema
      serialized = `${JSON.stringify(snapshot)}\n`;  // 序列化，末尾必须带换行
    } catch (error) {
      return rejected(error);
    }
 
    // 关键：挂在 this.tail.then 上，保证写入串行
    const operation = this.tail.then(async () => {
      if (this.tainted) throw this.taintCause;
      validateNextEntry(snapshot, this.ids);         // 查 id 重复 + parent 是否已存在
      try {
        await this.io.appendFile(this.file, serialized);
      } catch (error) {
        this.tainted = true;                         // 写失败：永久封印整个 store
        this.taintCause = error;
        throw error;
      }
      this.ids.add(snapshot.id);                     // 注意顺序：写成功后才加 id
    });
    this.tail = operation.catch(() => undefined);    // 链不断，下次还能接上
    return operation;
  }
 

读这段有几个点要记住。

第一，一旦 tainted 为 true，后续所有 append 直接拒绝，返回当初那个错误。不是新错误，是原错误——调用方能看到失败原因。

第二，Node 的 fs.appendFile 本身不保证并发顺序。两个 append 同时进来，谁先写谁后写不一定。Pi 用 promise 链手动串起来，每次 append 等上一个完成再动手。

第三，先写成功，再加 id。写失败 id 不进集合，但 tainted 被置 true，store 从此只读。与其冒险继续写半截文件，不如彻底锁死等人工介入。这是"事实"这个词的代价：要么完整，要么不要。

你可以自己推一遍这个场景：磁盘满了，第一次 append 抛 ENOSPC，tainted 置 true。第二次 append 进来，第一道闸直接把它挡回去，返回的还是同一个 ENOSPC。整个 store 不会因为"再来一次"就莫名其妙恢复，它诚实地维持着"我坏了"这个状态，直到有人来修文件、重新 open 一个新 store。这才叫可信。

支撑落盘的接缝刻意做得很窄：

// session.ts:85-89
export interface SessionFileIO {
  ensureFile(file: string): Promise<void>;   // 建目录 + 建文件
  readFile(file: string): Promise<string>;   // 读全文
  appendFile(file: string, value: string): Promise<void>; // 追加一行
}
 

只有三个方法，默认实现就是包了一层 Node 的 fs。接缝窄的好处是测试可以注入假实现——精确模拟"写到一半失败""磁盘满""文件被截断"，而不需要真的去搞坏磁盘。

四、从叶子爬回根

会话是一棵树，但模型恢复上下文时需要的是一条路径——从根到某个叶子。这就是 pathTo 的工作：

// session.ts:752-788
export function pathTo(
  entries: readonly SessionEntry[],
  leafId: string,            // 你选的那条分支的叶子 id
): SessionEntry[] {
  // 第一步：建 id → entry 的索引，顺带查 id 重复
  const byId = new Map<string, SessionEntry>();
  for (const entry of entries) {
    if (byId.has(entry.id)) {
      throw new Error(`session entry id 重复：${entry.id}`); // parent 指针依赖 id 唯一
    }
    byId.set(entry.id, entry);
  }
 
  let current = byId.get(leafId);
  if (!current) {
    throw new Error(`未知 session leaf：${leafId}`); // 你给的叶子根本不存在
  }
 
  const reverse: SessionEntry[] = [];
  const visited = new Set<string>();   // 第二道防线：环检测
  while (current) {
    if (visited.has(current.id)) {
      throw new Error(`session parent 在 ${current.id} 形成环`); // 正常 parent 链无环
    }
    visited.add(current.id);
    reverse.push(current);              // 收集这条路径上的节点
    if (current.parentId === null) break; // 爬到根（parentId 为 null），停
    const parentId = current.parentId;
    const childId = current.id;
    current = byId.get(parentId);       // 顺着 parentId 往上爬一层
    if (!current) {
      // 第三道防线：parent 缺失
      throw new Error(`session entry ${childId} 的 parent ${parentId} 缺失`);
    }
  }
  // 反转成 根→叶 顺序，每个节点再过一遍 parseSessionEntry + 深拷贝
  return reverse.reverse().map((entry) => parseSessionEntry(entry));
}
 

算法不复杂：从叶子出发，顺着 parentId 往上爬，爬到 parentId 为 null 的根为止。但细节里藏了三道防线——id 重复检查、环检测、parent 缺失检查。

爬完之后还有个动作值得注意：

// session.ts:787
  return reverse.reverse().map((entry) => parseSessionEntry(entry));
 

每个节点再过一遍 parseSessionEntry。 哪怕它们是从 store 拿出来的、理论上已校验过，pathTo 还是重新校验并深拷贝一次。paranoia 到这种程度，是因为 pathTo 的输出要直接喂给模型，是最后一道关。

注释还点明一点：pathTo 只检查被选 leaf 的祖先链，其他分支可以暂时不完整。同一份会话文件可以并存多条分支，只要你恢复时选对叶子。这就是 parentId 带来的灵活性，线性日志做不到。

最后还有个辅助函数，把路径投影成模型能消费的消息序列：

// session.ts:794-801
export function messagesOnPath(
  entries: readonly SessionEntry[],
  leafId: string,
): AgentMessage[] {
  return pathTo(entries, leafId).flatMap((entry) =>
    entry.type === "message"               // 只保留 message
      ? [structuredClone(entry.message)]   // 深拷贝，防外部拿到引用改原件
      : []                                 // metadata / compaction 都被滤掉
  );
}
 

metadata 被过滤，compaction 没有 message 字段自然不进结果。走到这里的消息序列，就是模型这一轮要看到的全部上下文。

这里有个使用者最关心的点值得点破：恢复时你不用告诉 Pi 整条历史，只要指一个 leafId。Pi 自己顺着 parentId 爬上去，把该带的都带出来。你 fork 过的旧分支不会被混进来，因为它们不在你选的这条祖先链上。这就是会话树相对线性日志最大的好处：同一份文件里并存多条故事线，各取各的，互不干扰。

● ● ●

收尾：关掉再开，对话还在

回到开头的场景。你关掉终端再打开，Pi 干了这几件事：JsonlSessionStore.open 读回 JSONL → recoverJsonl 用换行符当印章、丢掉任何半行残 JSON → idsFromCommittedEntries 把已提交的 id 收集起来 → 你选一个叶子 → pathTo 爬父指针拼出完整路径 → messagesOnPath 投影成消息序列喂给模型。

这套设计的核心理念就一句：磁盘上的东西，要么是完整的事实，要么不算数。

没有"大概写了"，没有"应该是完整的"，没有"忽略错误继续跑"。每一行 JSONL 都是一条事实，事实不容含糊。写串起来，写坏就锁死，恢复时只信盖了章的行。这就是你关掉终端重开、对话还在的全部秘密。
