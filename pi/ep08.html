你有没有想过一个问题：一个 AI Agent 跑了半小时，改了七八个文件，然后进程崩了。它"记得"自己改过什么吗？

如果会话只活在内存里，答案是——什么都不记得。上一次的上下文、工具调用、用户指令，统统蒸发。

EP08 这一讲，我们解决的就是这件事：如何把一段对话变成磁盘上一份可恢复的事实记录。

不是日志，不是缓存，是事实。这个词很重，但 Pi 的源码对得起它。

● ● ●

一、为什么不是普通日志

很多人第一次写"对话持久化"，会本能地往数据库上想——建一张 messages 表，role、content、created_at 三列，完事。

这条路在 Agent 场景下有三个坑：

第一，对话不是线性的。用户可能 fork 出一条分支重试，旧分支留着当参考。线性表表达不了树。

第二，磁盘上的东西必须能信。一份被断电切掉一半的 JSON，不能假装它是完整的。

第三，写失败了就不能再写。一个已经损坏的文件，再 append 一行只会让损坏更深。

Pi 的 session.ts 把这三件事都解决了，而且只用了一个文件、八百行代码。我们逐段拆。

● ● ●

二、三种事实：message / metadata / compaction

先看会话里到底有什么。Pi 把每一条记录叫 SessionEntry，它是一个联合类型，只有三种可能：

// session.ts:61-64
export type SessionEntry =
  | MessageSessionEntry
  | MetadataSessionEntry
  | CompactionSessionEntry;
 

一个会话里只有这三类条目，多一种都算污染。

message 是真正的对话内容——用户说的话、模型的回复、工具的结果。metadata 是元信息，比如模型版本、token 用量，它们不会进模型上下文，但会随会话一起落盘。compaction 是压缩点：当上下文太长，系统把前面的对话总结成一份摘要，后续就从摘要继续。

三者共享一个底座 EntryBase：

// session.ts:26-30
interface EntryBase {
  id: string;
  parentId: string | null;
  timestamp: number;
}
 

注意 parentId。这不是日志，是一棵树。 每条记录都指向它的父节点，根节点的 parentId 是 null。

这意味着什么？意味着同一个会话里可以有多条"最新消息"。用户在某个节点 fork 出两条分支，两条分支都是合法的叶子，恢复时你得指明要走哪一条。

来看三种类型各自的形状。message 最直接：

// session.ts:32-35
export interface MessageSessionEntry extends EntryBase {
  type: "message";
  message: AgentMessage;
}
 

metadata 多两个字段，key 配 value：

// session.ts:37-41
export interface MetadataSessionEntry extends EntryBase {
  type: "metadata";
  key: string;
  value: JsonValue;
}
 

compaction 最重，因为它要承载一段被压缩的上下文：

// session.ts:53-59
export interface CompactionSessionEntry extends EntryBase {
  type: "compaction";
  parentId: string;
  summary: CompactionSummary;
  firstKeptEntryId: string;
  tokensBefore: number;
}
 

注意 compaction 的 parentId 是 string，不是 string | null。压缩点必须有父——它永远挂在一个真实节点下面，不会是根。 firstKeptEntryId 标记压缩后保留的第一条 entry，tokensBefore 记录压缩前的 token 数，方便事后审计。

CompactionSummary 本身有七个字段，全是字符串数组：

// session.ts:43-51
export interface CompactionSummary {
  goal: string;
  constraints: string[];
  completed: string[];
  decisions: string[];
  changedFiles: string[];
  unresolved: string[];
  next: string[];
}
 

这种结构化摘要，比一段自然语言总结有用得多。goal 是任务目标，completed 是已完成的步骤，unresolved 是悬而未决的问题，next 是建议的下一步。模型恢复时拿到的不是一坨散文，而是可以直接消费的字段。

● ● ●

三、parseSessionEntry：外部数据一律不可信

类型定义是给 TypeScript 编译器看的。真正从磁盘读回来的是 unknown，是一坨未经审查的 JSON。

Pi 的态度很硬：任何从外部进来的东西，都要过一遍 parseSessionEntry。这个函数不仅收窄类型，还顺带做深拷贝、剥掉原型链、拒绝未知字段。

入口在这里：

// session.ts:485-487
export function parseSessionEntry(value: unknown): SessionEntry {
  const record = recordAt(value, "session entry");
  const base = entryBaseAt(record);
 

第一关是 recordAt。它检查这个东西到底是不是一个干净的 JSON object：

// session.ts:112-133
function recordAt(
  value: unknown,
  label: string,
): Record<string, unknown> {
  if (value === null || typeof value !== "object" || Array.isArray(value)) {
    throw new Error(${label} 必须是 object);
  }
  const prototype = Object.getPrototypeOf(value);
  if (prototype !== Object.prototype && prototype !== null) {
    throw new Error(${label} 必须是普通 JSON object);
  }
  for (const key of Reflect.ownKeys(value)) {
    if (typeof key !== "string") {
      throw new Error(${label} 不能包含 symbol 字段);
    }
    const descriptor = Object.getOwnPropertyDescriptor(value, key);
    if (!descriptor?.enumerable || !("value" in descriptor)) {
      throw new Error(${label}.${key} 不是可序列化字段);
    }
  }
  return value as Record<string, unknown>;
}
 

这一段干掉三类攻击：prototype 污染、symbol 键、getter/setter。凡是从 JSON.parse 出来不该有的东西，统统拒之门外。

Reflect.ownKeys 比 Object.keys 严格，它会枚举 symbol 键；Object.getOwnPropertyDescriptor 进一步确认每个字段都是普通的 enumerable data property。一个被恶意构造的 __proto__ 在这里活不过三行。

第二关是 exactKeys，检查字段集合是否精确匹配：

// session.ts:135-146
function exactKeys(
  record: Record<string, unknown>,
  allowed: readonly string[],
  label: string,
): void {
  const allowedKeys = new Set(allowed);
  for (const key of Object.keys(record)) {
    if (!allowedKeys.has(key)) {
      throw new Error(${label} 包含未知字段 ${key});
    }
  }
}
 

未知字段不是警告，是错误。 这条规则让 schema 演进变得可控——旧版本读新格式会直接报错，而不是悄悄忽略新字段。

第三关是 jsonValueAt，递归校验任意深度的 JSON 值。它连数组都要检查键是否连续：

// session.ts:177-194
  if (Array.isArray(value)) {
    if (ancestors.has(value)) {
      throw new Error(${label} 不能形成循环引用);
    }
    if (
      Object.getOwnPropertySymbols(value).length > 0 ||
      Object.keys(value).some((key, index) => key !== String(index)) ||
      Object.keys(value).length !== value.length
    ) {
      throw new Error(${label} 必须是连续的 JSON array);
    }
 

一个被塞了额外属性的数组，比如 arr.foo = "bar"，在这里会被拦下。磁盘上的 JSON 必须是纯粹的 JSON，不能夹带 JavaScript 的私货。

parseSessionEntry 根据 type 字段分派到三种类型各自的校验逻辑，每条分支最后都调用 exactKeys 做收尾。比如 message 分支：

// session.ts:488-504
  if (record.type === "message") {
    exactKeys(
      record,
      ["id", "parentId", "timestamp", "type", "message"],
      session entry ${base.id},
    );
    if (!own(record, "message")) {
      throw new Error(session entry ${base.id} 缺少 message payload);
    }
    return {
      ...base,
      type: "message",
      message: agentMessageAt(
        record.message,
        session entry ${base.id}.message,
      ),
    };
  }
 

exactKeys 已经保证没有多余字段，但 own 再确认 message 字段确实存在——因为 exactKeys 只管"有没有多余的"，不管"该有的有没有"。两层校验，一层防多，一层防少。

● ● ●

四、recoverJsonl：换行符就是 commit marker

校验逻辑再严，也得先决定"哪些字节算是完整的记录"。这是 recoverJsonl 的工作。

JSONL 的每一行是一条记录，行与行之间用 \n 分隔。但 Pi 对"行"的定义比直觉更严：

// session.ts:580-586
export function recoverJsonl(value: string): SessionReadResult {
  const lines = value.split("\n");
  const warnings: UnterminatedTailWarning[] = [];
  const hasUnterminatedTail =
    !value.endsWith("\n") && lines.at(-1)?.trim().length !== 0;
  const committedLineCount =
    hasUnterminatedTail ? lines.length - 1 : lines.length;
 

关键这一句：只有以换行符结尾的行，才算"已提交"。最后一段如果没换行符，无论它看起来多像合法 JSON，都按"未提交尾部"丢弃。

为什么这么严？因为文件系统的写入不是原子的。进程可能写到一半被 kill，留下半截 {"id":"abc","parent。如果你把这半行当事实，下次解析就炸了。

Pi 的做法是：换行符是 commit marker，没有 marker 就不算落盘成功。

丢弃不等于静默。被丢弃的尾部会被记成一条 warning：

// session.ts:588-593
  if (hasUnterminatedTail) {
    warnings.push({
      code: "unterminated_tail",
      line: lines.length,
    });
  }
 

上层拿到 warning 可以选择修复——比如把残行补全，或者直接截断。但在修复之前，这个文件是"只读"的，不能再写。

recoverJsonl 循环解析每一行，空行跳过，非法 JSON 直接抛错：

// session.ts:596-616
  const entries: SessionEntry[] = [];
  for (let index = 0; index < committedLineCount; index += 1) {
    const line = lines[index] ?? "";
    if (line.trim().length === 0) continue;
    let parsed: unknown;
    try {
      parsed = JSON.parse(line);
    } catch (error) {
      throw new Error(
        session JSONL 第 ${index + 1} 行不是合法 JSON：${describe(error)},
        { cause: error },
      );
    }
    try {
      entries.push(parseSessionEntry(parsed));
    } catch (error) {
      throw new Error(
        session JSONL 第 ${index + 1} 行不是合法 session entry：${describe(error)},
        { cause: error },
      );
    }
  }
 

两层 try/catch，JSON 解析和 schema 校验分开报错。 错误信息精确到第几行，带上原始 cause，调试时一眼定位。

● ● ●

五、JsonlSessionStore：写失败就永久封印

校验和恢复都有了，接下来是真正的存储类 JsonlSessionStore。它有三个关键设计：tail promise 串行化、taint 机制、repair warning。

先看构造和打开：

// session.ts:676-700
export class JsonlSessionStore implements SessionStore {
  private tail: Promise<void> = Promise.resolve();
  private tainted = false;
  private taintCause: unknown;
 
  private constructor(
    private readonly file: string,
    private readonly io: SessionFileIO,
    private readonly ids: Set<string>,
    private readonly repairWarning?: UnterminatedTailWarning,
  ) {}
 
  static async open(
    file: string,
    io: SessionFileIO = nodeSessionFileIO,
  ): Promise<JsonlSessionStore> {
    await io.ensureFile(file);
    const recovered = recoverJsonl(await io.readFile(file));
    return new JsonlSessionStore(
      file,
      io,
      idsFromCommittedEntries(recovered.entries),
      recovered.warnings[0],
    );
  }
 

open 是个工厂方法。它先确保文件存在，读回内容，走一遍 recoverJsonl，把已提交的 entry id 收集成 Set。如果检测到未提交尾部，repairWarning 就存下来。

这个 store 一出生就带着它过去的全部历史——所有已提交的 id 都在 this.ids 里，后续 append 时用来查重。

接下来是 append。这是整个文件最精妙的一段：

// session.ts:702-735
  append(entry: SessionEntry): Promise<void> {
    if (this.tainted) return rejected(this.taintCause);
    if (this.repairWarning) {
      return rejected(
        new Error(
          session 文件第 ${this.repairWarning.line} 行有未提交尾部；修复前不能 append,
        ),
      );
    }
 
    let snapshot: SessionEntry;
    let serialized: string;
    try {
      snapshot = parseSessionEntry(entry);
      serialized = ${JSON.stringify(snapshot)}\n;
    } catch (error) {
      return rejected(error);
    }
 
    const operation = this.tail.then(async () => {
      if (this.tainted) throw this.taintCause;
      validateNextEntry(snapshot, this.ids);
      try {
        await this.io.appendFile(this.file, serialized);
      } catch (error) {
        this.tainted = true;
        this.taintCause = error;
        throw error;
      }
      this.ids.add(snapshot.id);
    });
    this.tail = operation.catch(() => undefined);
    return operation;
  }
 

第一道闸是 taint 检查。一旦 tainted 为 true，后续所有 append 直接拒绝，返回当初那个错误。 不是返回新错误，是返回原错误，这样调用方能看到失败原因。

第二道闸是 repairWarning。文件有未提交尾部时，append 也被拒——先修复，再写入，绝不带着脏数据继续加。

真正的写入逻辑挂在 this.tail.then(...) 上。这就是 tail promise 串行化：每次 append 都等上一个 append 完成，保证写入顺序。Node 的 fs.appendFile 本身不保证并发顺序，Pi 用 promise 链手动串起来。

写入失败的处理是精髓：

// session.ts:724-731
      try {
        await this.io.appendFile(this.file, serialized);
      } catch (error) {
        this.tainted = true;
        this.taintCause = error;
        throw error;
      }
      this.ids.add(snapshot.id);
 

注意顺序：先写成功，再加 id。如果写失败，id 不会进集合，但 tainted 会被置 true。整个 store 从此进入只读状态，任何 append 都被第一道闸拦下。

为什么要这么狠？因为 append 失败意味着磁盘状态不明——可能写了半行，可能一行没写。与其冒险继续写，不如彻底锁死，等人工介入。 这是"事实"这个词的代价：要么完整，要么不要。

● ● ●

六、InMemorySessionStore：同一套契约的内存版

不是所有场景都需要落盘。测试、临时会话、内存中的分支管理，都用 InMemorySessionStore。它实现同样的 SessionStore 接口，但数据只活在数组里：

// session.ts:649-674
export class InMemorySessionStore implements SessionStore {
  private readonly log: SessionEntry[] = [];
  private readonly ids = new Set<string>();
  private tail: Promise<void> = Promise.resolve();
 
  append(entry: SessionEntry): Promise<void> {
    let snapshot: SessionEntry;
    try {
      snapshot = parseSessionEntry(entry);
    } catch (error) {
      return rejected(error);
    }
    const operation = this.tail.then(() => {
      validateNextEntry(snapshot, this.ids);
      this.log.push(snapshot);
      this.ids.add(snapshot.id);
    });
    this.tail = operation.catch(() => undefined);
    return operation;
  }
 
  async entries(): Promise<SessionEntry[]> {
    await this.tail;
    return structuredClone(this.log);
  }
}
 

注意几点。第一，内存版也走 parseSessionEntry——哪怕数据从来没离开过进程，也要过一遍 schema。这保证了从内存 store 拿出来的 entry，和从磁盘 store 拿出来的，类型上完全等价。

第二，tail promise 串行化在内存版里也有。为什么？因为 JavaScript 是单线程，但 Promise 是异步的。两个 append 同时调用，如果不串行，validateNextEntry 检查时 id 还没加进去，第二个 append 可能漏过重复检查。

第三，entries() 返回 structuredClone(this.log)。深拷贝，防止调用方拿到引用后偷偷改内部状态。 这跟 parseSessionEntry 顺手做深拷贝是同一个思路：从 store 出来的东西，必须是不可变的快照。

支撑落盘的是 SessionFileIO 接口，刻意保持很窄：

// session.ts:85-89
export interface SessionFileIO {
  ensureFile(file: string): Promise<void>;
  readFile(file: string): Promise<string>;
  appendFile(file: string, value: string): Promise<void>;
}
 

只有三个方法。默认实现是 nodeSessionFileIO，直接包 Node 的 fs：

// session.ts:91-102
const nodeSessionFileIO: SessionFileIO = {
  async ensureFile(file) {
    await mkdir(path.dirname(file), { recursive: true });
    await appendNodeFile(file, "", "utf8");
  },
  readFile(file) {
    return readNodeFile(file, "utf8");
  },
  appendFile(file, value) {
    return appendNodeFile(file, value, "utf8");
  },
};
 

接缝窄的好处是：测试可以注入假实现，精确模拟"写到一半失败""磁盘满""文件被截断"这些场景，而不需要真的去搞坏磁盘。注释里说得明白——这个接口就是为可测试性设计的。

● ● ●

七、pathTo：从叶子爬回根

会话是一棵树，但模型恢复上下文时需要的是一条路径——从根到某个叶子。这就是 pathTo 的工作：

// session.ts:752-788
export function pathTo(
  entries: readonly SessionEntry[],
  leafId: string,
): SessionEntry[] {
  const byId = new Map<string, SessionEntry>();
  for (const entry of entries) {
    if (byId.has(entry.id)) {
      throw new Error(session entry id 重复：${entry.id});
    }
    byId.set(entry.id, entry);
  }
 
  let current = byId.get(leafId);
  if (!current) {
    throw new Error(未知 session leaf：${leafId});
  }
 
  const reverse: SessionEntry[] = [];
  const visited = new Set<string>();
  while (current) {
    if (visited.has(current.id)) {
      throw new Error(session parent 在 ${current.id} 形成环);
    }
    visited.add(current.id);
    reverse.push(current);
    if (current.parentId === null) break;
    const parentId = current.parentId;
    const childId = current.id;
    current = byId.get(parentId);
    if (!current) {
      throw new Error(
        session entry ${childId} 的 parent ${parentId} 缺失,
      );
    }
  }
  return reverse.reverse().map((entry) => parseSessionEntry(entry));
}
 

算法本身不复杂：从叶子出发，顺着 parentId 往上爬，爬到 parentId 为 null 的根为止。但细节里有三道防线。

第一道，id 重复检查。建 Map 时如果发现同一个 id 出现两次，直接抛错。parent 指针依赖 id 唯一，一旦重复，指针就失去意义。

第二道，环检测。用 visited Set 记录走过的节点，如果走到一个已经走过的 id，说明 parent 链成环了，立刻抛错。正常的 parentId 链是有向无环的，出现环只可能是数据损坏。

第三道，parent 缺失检查。如果某个 parentId 在 Map 里找不到，抛错并带上具体的 child id 和 parent id，方便定位。

爬完之后做了一件有意思的事：

// session.ts:787
  return reverse.reverse().map((entry) => parseSessionEntry(entry));
 

每个节点再过一遍 parseSessionEntry。 哪怕它们是从 store 里拿出来的、理论上已经校验过的，pathTo 还是重新校验一次，并顺带做深拷贝。 paranoia 到这种程度，是因为 pathTo 的输出会直接喂给模型，是最后一道关。

注释里点明了 pathTo 的语义：只检查被选 leaf 的祖先链，其他分支可以暂时不完整。这意味着同一份会话文件，可以并存多条分支，只要你恢复时选对叶子。 这就是 parentId 带来的灵活性——线性日志做不到。

最后还有一个辅助函数 messagesOnPath，把路径上的 entry 投影成模型能消费的消息序列：

// session.ts:794-801
export function messagesOnPath(
  entries: readonly SessionEntry[],
  leafId: string,
): AgentMessage[] {
  return pathTo(entries, leafId).flatMap((entry) =>
    entry.type === "message" ? [structuredClone(entry.message)] : []
  );
}
 

metadata 被过滤掉，compaction 节点也没有 message 字段，自然不进结果。走到这里的消息序列，就是模型这一轮要看到的全部上下文。

● ● ●

收尾

EP08 这一讲，Pi 用八百行 TypeScript 讲清了一件事：怎么把一段对话变成磁盘上可恢复的事实。

三种 entry 类型覆盖了对话、元信息、压缩点。parentId 把线性日志升级成会话树。parseSessionEntry 用 recordAt、exactKeys、jsonValueAt 三道关卡，把外部数据洗成可信的 canonical 形态。recoverJsonl 用换行符当 commit marker，拒绝半行 JSON。JsonlSessionStore 用 tail promise 串行写入，用 taint 机制让写失败的 store 永久封印。pathTo 从叶子爬父指针恢复路径，带环检测和重复 id 检查。

这套设计的核心理念就一句：磁盘上的东西，要么是完整的事实，要么不算数。

没有"大概写了"，没有"应该是完整的"，没有"忽略错误继续跑"。每一条 JSONL 都是一条事实，事实不容含糊。

下一讲我们会看到，这套持久化机制如何支撑更上层的会话管理——分支、回滚、跨会话引用。但那些都是建立在"每一行都是事实"这个地基上的。地基不牢，上面什么都立不住。
