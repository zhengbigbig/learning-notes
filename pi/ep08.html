大家好我是郑同学。上一篇拆了 session.ts 的状态管理——对话存进了 JSONL 文件。但存下来只是第一步，真正的问题是：模型的上限是有限的。

Claude 的上下文窗口 200K token，GPT-4o 是 128K。一个长对话跑几十轮，加上工具调用结果、文件内容，轻松超限。上下文管理要回答一个问题：超限时砍哪些消息、保留哪些？

这一篇拆 context.ts（419 行），Pi 的上下文管理模块。

● ● ●

第一步：分清什么不能拆

最直觉的做法是：超了就从最旧的消息开始删，一条一条删到不超为止。

Pi 没这么做。Pi 按 interaction（一次完整交互）分组，要么整组保留，要么整组丢弃。

什么是 interaction？一个用户消息开始，到下一个用户消息之前，中间所有内容是一组——包括助手的回复、工具调用、工具结果。一组就是一个完整的「问答回合」。

// context.ts:125-154

export function groupInteractions(

  entries: readonly MessageSessionEntry[],

): InteractionGroup[] {

  const groups: InteractionGroup[] = [];

  let current: InteractionGroup | undefined;

 

  for (const source of entries) {

    const entry = cloneMessageEntry(source);

    // 遇到 user message → 结束上一组，开始新组

    if (entry.message.role === "user") {

      if (current) {

        validateInteraction(current);

        groups.push(current);

      }

      current = { entries: [entry] };

      continue;

    }

    // 非 user message → 加到当前组

    current.entries.push(entry);

  }

  if (current) {

    validateInteraction(current);

    groups.push(current);

  }

  return structuredClone(groups);

}

 

为什么不按条砍？

因为一条消息可能依赖前面的消息。助手说「好的，我来修改刚才那个函数」，工具结果引用了前面的 toolCall。如果只删掉工具结果但保留助手的回复，对话就断了——模型会看到一条引用了不存在工具调用的消息。按 interaction 砍保证语义完整，每一组都是自包含的问答回合。

分组代码在每次结束一组时调了 validateInteraction 做完整性校验——下一节拆这个。

● ● ●

第二步：校验组的完整性

分组时每结束一组就调 validateInteraction，检查 toolCall 和 toolResult 是否一一配对：

// context.ts:79-119

function validateInteraction(group: InteractionGroup): void {

  const calls = new Map<string, string>();

  const results = new Map<string, string>();

 

  for (const entry of group.entries) {

    // 收集所有 toolCall

    for (const call of callsIn(entry)) {

      if (calls.has(call.id)) throw new Error(`重复 ${call.id}`);

      calls.set(call.id, entry.id);

    }

    // 收集所有 toolResult

    if (entry.message.role === "toolResult") {

      const callId = entry.message.toolCallId;

      if (results.has(callId)) throw new Error(`重复 ${callId}`);

      results.set(callId, entry.id);

    }

  }

 

  // 每个 result 必须有对应的 call

  for (const [callId] of results) {

    if (!calls.has(callId))

      throw new Error(`result 引用了不存在的 call`);

  }

  // 每个 call 必须有对应的 result

  for (const [callId] of calls) {

    if (!results.has(callId))

      throw new Error(`call ${callId} 缺少 result`);

  }

}

 

每个 toolCall 必须有对应的 toolResult，每个 toolResult 必须有对应的 toolCall。这是 API 的硬性要求——模型收到的消息序列里不能有悬空的工具调用。

组分好了，每组都验证过了。接下来算预算——这些组加起来超不超。

● ● ●

第三步：算预算——四笔账先扣

发给模型时，上下文窗口的 token 不是全给消息用的。要先扣掉四笔固定开销：

// context.ts:263-285

export function buildContext(

  activePath: readonly SessionEntry[],

  options: BuildContextOptions,

): BuildContextResult {

  // 固定开销：system prompt

  const system = options.systemPrompt === undefined

    ? 0

    : estimatedTokens(options, options.systemPrompt, "systemPrompt");

  // 消息可用 = 总预算 - system - 输出预留 - 安全余量

  const availableForMessages = Math.max(

    0,

    maxTokens - system - reservedOutput - safetyMargin,

  );

 

四笔账：

  •  maxTokens——模型上下文窗口大小（比如 200000）
  •  system——系统提示词占的 token
  •  reservedOutput——给模型回复预留的 token（模型也要空间输出）
  •  safetyMargin——安全余量（token 估算是近似的，留点缓冲）

消息预算 = 总窗口 - system - 输出预留 - 安全余量。剩下的才是消息历史能用的。

预算算好了，接下来决定哪些组放进预算，哪些砍掉。

● ● ●

第四步：从后往前选——保留最近的

预算有限，从最新的 interaction 开始往前加，加到预算用完为止。

// context.ts:328-348

let firstSelected = groups.length;

let selectedGroupCost = 0;

let reason: ContextBuildReason = "within_budget";

if (groups.length > 0) {

  const latestIndex = groups.length - 1;

  // 从最后一组开始

  firstSelected = latestIndex;

  selectedGroupCost = groupCosts[latestIndex] ?? 0;

  // 最新一组就超了 → 单组溢出

  if (selectedGroupCost > groupBudget) {

    reason = "single_group_overflow";

  } else {

    // 往前一组一组加

    for (let index = latestIndex - 1; index >= 0; index -= 1) {

      const candidateCost = groupCosts[index] ?? 0;

      if (selectedGroupCost + candidateCost > groupBudget) {

        reason = "trimmed";

        break;

      }

      selectedGroupCost += candidateCost;

      firstSelected = index;

    }

    if (firstSelected > 0) reason = "trimmed";

  }

}

 

为什么不从前往后选？

因为最近的对话最重要。用户正在讨论的问题、最近修改的文件、最新的工具结果——这些都在尾部。前面的旧对话可以被丢弃，但最近的不能丢。

三种结果：

  •  within_budget——全部都在预算内，不砍
  •  trimmed——砍了前面一些旧组，保留最近的
  •  single_group_overflow——最新一组单独就超了预算，这种情况不拆组，整组发出去（因为最近的信息最重要，宁可超也不能丢）

但砍掉旧组意味着模型忘了前面的内容。Pi 的方案是 compaction——不彻底丢失。

● ● ●

第五步：压缩摘要——不是删除，是替代

旧 interaction 被砍掉时，模型就忘了前面的内容。Pi 有一个更聪明的方案——compaction（压缩）：把旧消息合并成一条结构化摘要，作为新的起点。Pi 支持手动触发（/compact 命令）和自动触发（超过阈值或溢出时）。

// context.ts:190-211

function compactionSummaryText(summary: CompactionSummary): string {

  return [

    "【会话压缩摘要】",

    `目标：${summary.goal}`,

    ...summaryLines("约束", summary.constraints),

    ...summaryLines("已完成", summary.completed),

    ...summaryLines("决策", summary.decisions),

    ...summaryLines("变更文件", summary.changedFiles),

    ...summaryLines("未解决", summary.unresolved),

    ...summaryLines("下一步", summary.next),

  ].join("\n");

}

 

摘要不是随便写一段话，而是结构化的七个字段：目标、约束、已完成、决策、变更文件、未解决问题、下一步。这七个字段覆盖了一个任务的核心上下文——模型看完摘要就知道「我们在做什么、做完了什么、还差什么」。

压缩后，buildContext 会在消息列表最前面插入这条摘要：

// context.ts:300-303

const fixedMessages = compaction

  ? [summaryMessage(compaction.entry)]

  : [];

 

摘要 + 最近的 interaction = 审整上下文。摘要保留了旧对话的精华，最近的 interaction 保留了当前工作的细节。模型不需要回看每一条旧消息，只需要摘要 + 最近几轮。

但压缩也有一个约束——切口不能随便选。

● ● ●

第六步：压缩边界的严格检查

压缩不是随便选一个位置切——firstKeptEntryId 必须是一个完整 interaction 的起点。

// context.ts:379-419

export function createCompactionEntry(

  activePath: readonly SessionEntry[],

  input: CreateCompactionInput,

): CompactionSessionEntry {

  // firstKeptEntryId 必须是某个 interaction 的首条消息

  const firstKeptIsGroupStart = groups.some(

    (group) => group.entries[0]?.id === input.firstKeptEntryId,

  );

  if (!firstKeptIsGroupStart) {

    throw new Error(

      `firstKeptEntryId 必须是完整 interaction 的首条 message`,

    );

  }

 

为什么这么严格？

因为压缩边界落在一个 interaction 中间的话——比如助手的回复被保留了但工具结果被砍掉了——消息序列就断了。这和第一步说的一样：不能拆散一组完整的交互。firstKeptEntryId 必须是 user message（interaction 起点），保证压缩后的消息序列从完整的交互开始。

到这里，整条链路串起来了：分组 → 校验 → 算预算 → 从后往前选 → 砍不掉的压缩替代 → 压缩切口也得对齐 interaction 边界。每一步都在为「不破坏消息完整性」服务。

● ● ●

对比真实 CC 的上下文管理

CC 的上下文管理在 context-iterators.ts 和 messages.ts 里。

① 分组策略

两边都按 interaction 分组。CC 叫 turn boundaries——只在 user message 处可以切分。Pi 叫 InteractionGroup，逻辑一样。

② 压缩触发

Pi 支持手动和自动两种触发。手动用 /compact 命令。自动触发有两种：threshold——上下文超过配置阈值时自动压缩；overflow——模型返回上下文溢出错误时自动压缩并重试。设置面板里可以开关 auto-compact。CC 也有自动压缩，同样在 token 接近窗口上限时触发。

③ 压缩内容

Pi 用七字段结构化摘要（goal/completed/decisions 等）。CC 的压缩也是让模型生成摘要，不过 CC 的摘要格式是自由文本。

④ 单组溢出处理

Pi 遇到单组溢出时不拆组，整组发出去。CC 也有类似的「不拆 turn」策略，但 CC 还有一层微压缩（micro-compaction）——在一组内部压缩工具结果（比如截断超长的文件内容），尽量让组不超限。

两边核心思路一样：按 interaction 分组、从后往前保留、压缩替代删除。差别在自动化程度和压缩粒度。

● ● ●

小结

设计决策选择为什么
砍的粒度按 interaction 整组保证语义完整
砍的方向从后往前保留最近的最重要
预算计算四笔账先扣system + 输出预留 + 安全余量 + 消息
单组溢出不拆，整组发最近信息不能丢
旧消息处理compaction 摘要替代保留精华不丢上下文
压缩边界必须是 interaction 起点保证消息序列不断裂

口诀：按组砍不按条，从后往前留，摘要替旧文，切口找起点。
