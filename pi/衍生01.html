Q1：AGENTS.md 怎么写？要不要列技术栈？前后端放一块要不要分开？

先回忆 EP10 讲的：AGENTS.md 是叠加的——用户级 ~/.pi/AGENTS.md 和项目级从 cwd 逐级向上遍历，所有层级全部拼进 system prompt。不是覆盖。

所以最佳实践很清楚：

不要在 AGENTS.md 里写死技术栈版本。技术栈会升级，写死了维护不及时，反而误导模型。应该写约束和习惯，而不是具体版本：

# 好：写约束

- 用 TypeScript，strict 模式

- 测试用 vitest

- 提交前跑 npm run check

 

# 不好：写版本号

- React 18.2.0

- Next.js 14.1.0

- vitest 1.2.3

 

模型自己会读 package.json，知道你用什么版本。AGENTS.md 写版本号是重复且容易过时的信息。

前后端放一块的项目，用目录层级的 AGENTS.md 分开写。因为 Pi 从 cwd 逐级向上遍历，你可以在不同子目录放不同的 AGENTS.md：

my-project/

├── AGENTS.md              ← 全局约束（代码风格、提交规范）

├── frontend/

│   └── AGENTS.md          ← 前端规则（组件结构、样式约定）

├── backend/

│   └── AGENTS.md          ← 后端规则（API 设计、数据库约定）

 

在 frontend/ 目录下启动 Pi，它会同时加载根目录和 frontend 目录的 AGENTS.md。不是二选一，是叠加。这就是 loadProjectContextFiles 逐级向上遍历的设计意图。

Q2：Pi 和 CC 的 prompt cache 命中率差距是怎么来的？

先说事实。Pi 创始人 Mario Zechner 8月11日转发了一组数据：开发者 0xEvan 用 Pi 调 DeepSeek V4 Flash，处理近 10 亿输入 token，缓存命中率 99.93%，花了 $2.65（没缓存要 $132）。另一名开发者 Shantanu Goel 表示 DeepSeek V4 Flash 在其他 harness 里命中率通常 94-97%，在 Pi 里稳定 99%+。

Composio 做了一项横向测试：同一个 DeepSeek V4 Flash 模型，跑在 8 种不同 harness 里完成 30 项任务。Pi 通过 20 项（66.7%），CC 通过 16 项。Pi 完成单任务成本 $0.028，CC $0.195，接近 7 倍差距。

命中率差距的根源在 system prompt 的变化量。EP10 分析过缓存断点，这里讲实际原因。

DeepSeek 的 prompt cache 是自动前缀匹配——请求开头 token 序列和上次完全相同，服务端直接读缓存，计费远低于普通输入。前缀越早变化，后面被「连坐」的 token 越多。

Pi 的 system prompt 精简——AGENTS.md + skill 目录 + date + cwd。CC 的 system prompt 很大——内置几千字的工具使用指南、安全规则、CLAUDE.md、MCP 工具定义。CC 中间段更容易变（比如 MCP 工具列表增减），变了之后后面全失效。

社区开发者做了 pi-deepseek-cache 扩展，专门优化 DeepSeek 缓存。核心思路：

  •  P0 层：启动时冻结 date 和 cwd，杜绝动态内容导致的缓存失效——就是我们前面分析过的 Current date 问题
  •  P3 层：压缩摘要用 temperature=0 保证确定性，对结果做哈希缓存
  •  P2 层：SHA-256 哈希诊断前缀变化，及时发现缓存失效根因

效果：DeepSeek V4 Flash 输入 token 成本从每百万 $0.14 降到 $0.003，降幅 98%。

命中率接近 100% 确实有实际意义，但要看场景：

  1. 01省的是 input token 费用，不省 output。DeepSeek V4 Flash 本身便宜，省的绝对金额有限，但长对话场景累积可观
  2. 02真正的意义在于延迟——缓存命中意味着更快的首 token 响应（TTFT，Time To First Token，即从发出请求到模型吐出第一个字的时间）。前缀缓存的 token 不需要重新计算，直接从缓存读取，TTFT 大幅缩短。对交互式编码场景，用户体感的流畅度主要取决于 TTFT 而不是总输出速度
  3. 0399.93% 的前提是同一个 session 内、前缀稳定。跨 session 命中率取决于 provider 的缓存策略
  4. 04需要配合扩展才能达到。裸 Pi 默认 system prompt 里 date 每天变，不是天然 99%+

CC 命中率低不是因为分层设计不好。CC 有 SYSTEM.md（稳定段）和 APPEND_SYSTEM.md（追加段）的分离，追加段放尾部不破坏前缀缓存——这个分层设计是正确的。但 CC 的稳定段本身就比 Pi 大得多，再加上 MCP 工具定义是动态的，中间容易变。

总结：Pi 命中率高，一部分因为 system prompt 短且稳定，一部分因为社区扩展（pi-deepseek-cache）做了专门优化。Composio 测试里 Pi 默认安装就赢了，说明轻量 harness + 短路径 = 更少出错机会。

理性看，缓存命中率是 Pi 的一个实打实的优势，尤其配合 DeepSeek 这类按前缀缓存计费的模型时，长对话场景的成本差距很明显。但这只是 Pi 的优势之一，不是全部。选 Pi 还是 CC 要看综合场景，不能只盯一个指标。

DeepSeek V4 Flash 是 Flash 模型，定位速度和效率，做日常开发需求（改 bug、写函数、读文件、重构）完全够用。Pi 配合 Flash 的优势在于：system prompt 短、路径简洁、缓存命中率高，让一个中等能力的模型少绕路、少花钱、快响应。Composio 测试已经证明了这一点——同一个 Flash 模型，Pi 的任务通过率比 CC 高 20 个百分点。

但 CC 的优势同样明确：大段内置指南让强模型（Claude Sonnet/Opus）发挥更稳定，MCP 生态丰富、权限管理完善、企业功能齐全。如果你的场景依赖大量 MCP 工具、需要权限审批流程、团队协作审计，CC 更合适。

维度PiCC
system prompt 大小精简（AGENTS + skill 目录）大（几千字内置指南 + MCP 定义）
缓存命中率（DS Flash）99%+（配合扩展）94-97%
缓存失效原因date/cwd（可用扩展冻结）MCP 工具增减 + 大段指南变化

适合场景日常开发、长对话、成本敏感复杂推理、多 MCP、企业协作
模型适配中等模型也能跑好（路径短）需要强模型消化大段指南
MCP无内置，靠扩展原生支持
扩展能力TypeScript 扩展，洋葱模型可深度定制MCP + hooks，生态成熟

Q3：Pi 有 MCP 吗？扩展系统怎么用？

Pi 没有内置 MCP。源码里搜不到任何 MCP 相关代码。README 写得很明确：

No MCP. Build CLI tools with READMEs (see Skills), or build an extension that adds MCP support.

Pi 的哲学是不把功能塞进核心。MCP、子 Agent、权限弹窗、plan 模式——这些 CC 内置的功能，Pi 全部留给扩展系统。

Pi 的扩展系统是 TypeScript 模块。放在 ~/.pi/agent/extensions/（全局）或 .pi/extensions/（项目级），Pi 启动时自动发现并加载。EP10 讲的洋葱模型就是给扩展用的——beforeToolCall 可以拦截，afterToolResult 可以观察。

扩展能做什么：

// ~/.pi/agent/extensions/my-extension.ts

export default function (pi) {

  // 注册自定义工具（LLM 可以调用）

  pi.registerTool({ name: "deploy", ... });

  // 注册斜杠命令

  pi.registerCommand("stats", { ... });

  // 拦截工具调用（权限门控）

  pi.on("tool_call", async (event, ctx) => {

    if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {

      const ok = await ctx.ui.confirm("Dangerous!", "Allow rm -rf?");

      if (!ok) return { block: true, reason: "Blocked" };

    }

  });

}

 

对于前端，实际好用的扩展方向：

  •  路径保护：阻止写 .env、node_modules/、dist/
  •  Git checkpoint：每轮对话前自动 stash，方便回退
  •  自定义 lint：beforeToolCall 钩子里跑 eslint，不通过就 block

对于 Java：

  •  Maven/Gradle 集成：注册 build、test 自定义工具
  •  Spring Boot 热重载：edit 后自动触发重启
  •  MCP 桥接：如果你想用 MCP，可以写一个扩展把 MCP server 接进来——Pi 官方不做，但你可以自己做

想要 MCP 的，可以装社区包。Pi 支持 pi install 安装第三方扩展包。README 里提到有人已经做了 MCP 支持、SSH 沙箱执行等扩展。如何从零写一个扩展，我们在衍生02单独拆了一章。

Q4：沙箱和权限，Pi 和 CC 怎么选？

现在大部分人用 CC 的方式是直接放开沙箱内权限——--dangerously-skip-permissions，让模型在容器里自由跑。这样做的好处是不用反复点确认，效率高；代价是模型在沙箱里有全部权限，万一 prompt 注入或模型走偏，后果不可控。

CC 内置了 sandbox 执行模式，权限是三态弹窗（allow / deny / ask），让用户逐条确认。但实际使用中大多数人嫌烦，直接跳过。

Pi 的做法不同。Pi 没有内置沙箱，bash 工具直接在本机执行。也没有内置权限弹窗。但 Pi 把安全控制权完全交给你——通过扩展系统：

  •  权限门控：衍生02讲的 permission-gate.ts，35 行代码就能拦截 rm -rf、sudo 等危险命令，弹确认框
  •  路径保护：protected-paths.ts，阻止写 .env、.git/ 等敏感文件
  •  SSH 远程：ssh.ts 扩展把所有文件操作转发到远程机器，本机不碰文件系统

两者的安全哲学完全不同。CC 是内置一套规则，你接受就用，不接受就跳过（跳过等于裸奔）。Pi 是不内置规则，给你工具自己建，你可以精确控制哪些命令需要确认、哪些路径不能碰。

实际选择上，CC 适合不想折腾、用沙箱兜底的场景——进容器随便跑，出问题重头来。Pi 适合在本机工作、需要精细控制权限的场景——用扩展搭一套自己的安全网。

这个差异也是 EP10 讲的洋葱模型的实际价值——beforeToolCall 钩子让你在工具执行前拦截、检查、确认，安全逻辑完全由你定义。

Q5：从 CC 切换到 Pi 需要改什么？Codex 用户有必要切吗？

前面讲完了沙箱和权限的差异，接下来看实际迁移。从 CC 切换到 Pi，大部分东西能直接复用，少数需要改造。

能直接复用的：AGENTS.md（对应 CLAUDE.md，机制一样，逐级向上遍历叠加合并）、Skills 文件（Pi 遵循 Agent Skills 标准，和 CC 的 skill 格式一样）、Prompt Templates（对应 CC 的 custom commands，放在 ~/.pi/agent/prompts/，用 /name 触发）。

需要改造的：MCP 工具（Pi 不内置 MCP，需要装社区 MCP 扩展，或用 skill + bash 替代）、子 Agent（CC 的 sub-agent 在 Pi 里没有，用 tmux 启动多个 Pi 实例替代）、权限弹窗（CC 的 allow/deny/ask 在 Pi 里没有，用扩展写确认流程——就是前面 Q4 讲的 permission-gate）。

对于 Codex 用户，核心诉求是用 OpenAI 模型做编码。Pi 完全支持 OpenAI 模型——通过 ~/.pi/agent/models.json 配置自定义 provider：

{

  "my-openai": {

    "api": "openai",

    "baseUrl": "https://api.openai.com/v1",

    "apiKey": "YOUR_KEY",

    "models": [{ "id": "gpt-5.6", "name": "GPT-5.6" }]

  }

}

 

GPT-5.6 可以直接接入 Pi。Pi 的 provider adapter（EP04 讲的）支持 OpenAI-compatible API。任何兼容 OpenAI chat/completions 或 responses API 的模型都能接。配置好 baseUrl + apiKey + model id 就行。

但要不要切，取决于你的需求：

  •  只想用 GPT 模型写代码 → Codex 够用，Pi 不会给你额外能力
  •  想要更灵活的扩展系统、自定义工具链、跨 provider 切换 → Pi 更合适
  •  团队协作需要权限管理、审计日志 → CC 的企业功能更完善，Pi 是单人工具

Q6：Pi 用起来很弱，是少装了插件吗？图片输入要装插件吗？

Pi 用起来弱，99% 的原因是没有配 AGENTS.md 和 skill。

Pi 的 system prompt 极其精简——没有 CC 那种几千字的内置指南。Pi 的设计哲学是「你告诉它怎么干，而不是它自己知道怎么干」。如果你不写 AGENTS.md，Pi 对你的项目一无所知，表现自然弱。

三个快速提升：

  1. 01写一份 AGENTS.md——项目约束、代码风格、测试命令、目录结构
  2. 02放几个 skill——把重复的工作流写成 skill（代码审查、部署、重构等）
  3. 03装扩展——权限门控、Git checkpoint 等扩展能大幅提升安全性和体验

图片/多模态输入不需要装插件。

不需要。图片输入是 Pi 内置的，不是插件能力。源码确认：

// clipboard-image.ts：支持 PNG、JPEG、WebP、GIF 四种格式

const SUPPORTED_IMAGE_MIME_TYPES = ["image/png", "image/jpeg", "image/webp", "image/gif"];

 

// read.ts：read 工具直接读图片文件

description: `Read the contents of a file. 

Supports text files and images (jpg, png, gif, webp, bmp).`

 

两种方式用图片：

  1. 01剪贴板粘贴——Pi 编辑器里按快捷键（app.clipboard.pasteImage），从剪贴板读图，自动 resize 到 2000x2000
  2. 02read 工具读图片文件——模型用 read 读图片路径，图片作为 image content block 发给模型

唯一的限制：模型必须支持 vision（model.input 包含 "image"）。如果用不支持图片的模型，read 工具会返回文本提示 [Current model does not support images]，不会发送图片。
