上一篇那条七步轨迹是同步的——runPrologueDemo() 调一下，七步一次性返回。但你实际用 Pi 的时候，发一条消息后看到的是：文字一个字一个字冒出来，中间可能穿插工具调用的进度，最后才给你完整回复。

这个过程在源码里是怎么发生的？打开 event-stream.ts（82行），答案是 EventStream——一个对象同时管流式过程和最终结果。

类型相关的 survival/events.ts（tagged union + never 穷尽）是 Pi 写代码时的编译期安全网，不是 Agent 运行时的核心流程，这篇不展开。这篇讲 EventStream 怎么实现你看到的流式体验。

● ● ●

问题：过程和结果不在同一个时间

你发一条消息，Pi 调模型。模型返回有两种东西：

  •  过程：一连串 delta 事件——文字片段、工具调用片段，逐个送到 UI 渲染
  •  结果：一个完整的 AssistantMessage——等流结束才能拿到

这两件事来自同一个数据源，但发生在不同时间。如果你把它们拆成两个对象（一个事件流、一个结果 Promise），调用方就得自己协调「事件流到哪了」「结果什么时候 ready」——容易写出竞态。

Pi 的设计：一个对象同时提供两个视图。

// event-stream.ts:7-21
export class EventStream<T, R = T> implements AsyncIterable<T> {
  private readonly queue: T[] = [];
  private readonly waiting: Array<(value: IteratorResult<T>) => void> = [];
  private done = false;
  private readonly finalResult: Promise<R>;
  private resolveFinalResult!: (result: R) => void;
 
  constructor(
    private readonly isComplete: (event: T) => boolean,
    private readonly extractResult: (event: T) => R,
  ) {
    this.finalResult = new Promise<R>((resolve) => {
      this.resolveFinalResult = resolve;
    });
  }
 

implements AsyncIterable——可以 for await 逐个消费事件，UI 用这个渲染流式输出。

result(): Promise——等流结束后拿到完整的 AssistantMessage，Agent Loop 用这个判断下一步该干什么。

同一个对象，两个接口，内部保证状态一致。

两个泛型参数：T 是流里每个事件的类型，R 是最终结果类型，默认相等。构造函数收两个回调：isComplete 判断哪个事件是终态，extractResult 从终态事件里抠出最终结果。

● ● ●

模型吐 token 时：push 做了什么

模型那边每产出一个事件，Provider Adapter 就调一次 push。看它怎么分发：

// event-stream.ts:23-33
  push(event: T): void {
    if (this.done) return;
    if (this.isComplete(event)) {
      this.done = true;
      this.resolveFinalResult(this.extractResult(event));
    }
 
    const waiter = this.waiting.shift();
    if (waiter) waiter({ value: event, done: false });
    else this.queue.push(event);
  }
 

三步：

  1. 01终态闸门——done 已经翻过，丢弃后续事件。流结束后的 push 不会制造第二个事实。
  2. 02终态检测——如果这个事件是终态（done 或 error），翻 done 开关，同时 resolve finalResult。这时 result() 等待方立刻拿到完整消息。
  3. 03消费者调度——UI 如果在等（waiting 里有 resolve 函数），立刻唤醒它拿到这个事件；UI 如果还没来消费，事件先进 queue 排队。

第 2 步和第 3 步是独立的。终态事件触发 done + resolve 结果 Promise，但它本身仍然作为一个普通事件流给 UI。结果通道和过程通道分离——Agent Loop 通过 result() 拿到最终消息决定下一步，UI 通过 for await 拿到每个 delta 实时渲染，两条线互不干扰。

● ● ●

UI 渲染时：消费者怎么一个一个拿事件

// event-stream.ts:50-64
  async *[Symbol.asyncIterator](): AsyncIterator<T> {
    while (true) {
      if (this.queue.length > 0) {
        yield this.queue.shift() as T;
        continue;
      }
      if (this.done) return;
 
      const next = await new Promise<IteratorResult<T>>((resolve) => {
        this.waiting.push(resolve);
      });
      if (next.done) return;
      yield next.value;
    }
  }
 

三种情况循环处理：

  •  queue 里有积压——模型比 UI 快，事件先到了。直接 yield 出去，UI 拿到渲染。
  •  queue 空且 done——流结束了，退出迭代。
  •  queue 空且没 done——UI 比模型快，没事件可消费。消费者把 resolve 函数塞进 waiting 数组，然后 await 挂起。

模型下次 push 事件时，从 waiting 取出 resolve 调用，消费者唤醒拿到事件。生产者和消费者通过 resolve 函数握手，谁都不需要轮询。

queue 和 waiting 就是缓冲两边速度差的两个容器——事件先到进 queue，消费者先到进 waiting。谁先到谁排队等另一边。

● ● ●

流异常中断怎么办

模型可能网络超时、用户可能中途取消。这时没有正常的终态事件，result() 的 Promise 永远不会 resolve。end 方法处理这种情况：

// event-stream.ts:35-44
  end(result: R): void {
    if (!this.done) this.resolveFinalResult(result);
    this.done = true;
    while (this.waiting.length > 0) {
      this.waiting.shift()?.({
        value: undefined as T,
        done: true,
      });
    }
  }
 

做三件事：resolve 结果 Promise（保证 result() 一定能 resolve），翻 done 开关，把所有挂着的消费者全部唤醒并传 { done: true } 告诉它们流结束了。

● ● ●

真实用法：模型回复怎么流回 Agent

Pi 里最常用的子类——把模型的流式事件聚合成一条完整的 AssistantMessage：

// event-stream.ts:67-81
export class AssistantMessageEventStream
  extends EventStream<ModelEvent, AssistantMessage>
  implements ModelStream
{
  constructor() {
    super(
      (event) => event.type === "done" || event.type === "error",
      (event) => {
        if (event.type === "done") return event.message;
        if (event.type === "error") return event.error;
        throw new Error("非终态事件不能生成最终消息");
      },
    );
  }
}
 

T = ModelEvent——流里每个事件是一条 ModelEvent（start、text_delta、toolcall_delta、done 等）。R = AssistantMessage——最终结果是一条完整的 assistant 消息。

isComplete 回调：done 或 error 事件算终态。extractResult 回调：done 时返回 event.message，error 时返回 event.error。

子类只填两个回调，三态闸门的调度全由父类处理。这是好的分层——想接一个新的流式数据源，只需要告诉 EventStream「什么是终态、怎么抠结果」，queue/waiting/done 那一套不用重写。

● ● ●

在 Agent Loop 里的位置

EventStream 在整个 Agent 回路里扮演的角色：

runtime.prompt("帮我读README")
  → agent.prompt()
    → runAgentLoop()
      → model.stream(messages)          ← 返回 EventStream
        ← text_delta, text_delta, ...   ← UI 通过 for await 实时渲染
        ← done                          ← 终态事件
      ← await stream.result()           ← Agent Loop 拿到完整 AssistantMessage
      → toolCalls(assistant)            ← 检查有没有工具调用
      → executeToolCall(read)           ← 有就执行工具
      → 继续 for 循环...
 

模型返回的是 EventStream，Agent Loop 消费它的 result()，UI 消费它的 for await。同一个流式响应，两个消费方各取所需，EventStream 内部保证 done 状态一致。

小结

你看到的现象源码机制
文字一个字一个字冒出来for await 消费 EventStream 的 delta 事件
流结束后拿到完整回复result() 返回的 Promise 在终态事件时 resolve
模型快 UI 慢时不丢事件queue 缓冲积压事件
UI 快模型慢时不空转waiting 挂起消费者，等 push 唤醒
中途取消或网络断end() 兜底 resolve + 唤醒所有消费者
流结束后多余事件done 闸门丢弃
