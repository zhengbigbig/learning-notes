大家好，我是郑同学。

上篇我们跑完了一条写死的七步轨迹——user提问、model回复、tool执行、结果回填。但那条轨迹是同步的，调一下一次性返回。

你实际用 Pi 的时候完全不是这样。你发一句话，Pi 的回复是一个字一个字冒出来的——像有人在终端里实时打字。中间可能穿插「正在读取文件...」之类的工具进度。最后才给你完整回复。

这个体验在源码里是怎么实现的？打开 event-stream.ts，82 行，核心就一个类——EventStream。

● ● ●

先说问题在哪

你发一句话，Pi 调模型。模型返回的不只是一个答案，而是两种东西混在一起：

第一，过程——一连串 delta 事件。每一段文字片段、每一个工具调用片段，都是一个独立的事件。UI 收到一个渲染一个，所以你看到文字逐字出现。

第二，结果——一个完整的 AssistantMessage。要等所有 delta 事件流完，才能拼出这条完整消息。Agent Loop 需要它来判断「下一步该干什么」。

问题来了：过程和结果不在同一个时间。

过程是实时的，结果是滞后的。如果你把它们做成两个对象——一个事件流给 UI，一个 Promise 给 Agent Loop——调用方就得自己协调：事件流到哪了？结果什么时候 ready？两边的状态怎么同步？很容易写出竞态条件。

● ● ●

Pi 的解法：一个对象两顶帽子

Pi 没有拆成两个对象。它做了一个类叫 EventStream，同时戴两顶帽子：

  •  第一顶：AsyncIterable——UI 可以 for await 逐个消费事件，实时渲染
  •  第二顶：result(): Promise——Agent Loop 等 Promise resolve，拿到完整消息

看源码骨架：

// event-stream.ts:7-21
export class EventStream<T, R = T> implements AsyncIterable<T> {
  // 模型比 UI 快时，事件在这里排队等消费者
  private readonly queue: T[] = [];
  // UI 比模型快时，消费者的 resolve 函数在这里挂着等
  private readonly waiting: Array<(value: IteratorResult<T>) => void> = [];
  // 终态闸门：一旦翻过去，不再收新事件
  private done = false;
  // 结果通道：外置 Promise，内部随时可以 resolve
  private readonly finalResult: Promise<R>;
  private resolveFinalResult!: (result: R) => void;
 
  constructor(
    // 调用方告诉它：怎么判断一个事件是终态（比如 type === "done"）
    private readonly isComplete: (event: T) => boolean,
    // 调用方告诉它：怎么从终态事件里抠出最终结果（比如取 event.message）
    private readonly extractResult: (event: T) => R,
  ) {
    // 外置 Promise 模式：先 new 一个 Promise，把 resolve 函数存起来
    // 内部代码随时可以调 resolveFinalResult(...) 把结果塞进去
    this.finalResult = new Promise<R>((resolve) => {
      this.resolveFinalResult = resolve;
    });
  }
 

理解这段代码的关键，是看到 queue 和 waiting 这两个字段。它们不是随便写的——它们解决了流式系统最经典的问题：生产者和消费者速度不一致。

● ● ●

模型吐 token 时发生了什么

你发一句话之后，模型那边开始产出事件。每出一个事件，Provider Adapter 就调一次 push：

// event-stream.ts:23-33
  push(event: T): void {
    // ① 闸门检查：流已经结束了？丢弃，不制造第二个事实
    if (this.done) return;
 
    // ② 终态检测：这个事件是不是最后一个（done 或 error）？
    if (this.isComplete(event)) {
      this.done = true;              // 翻闸门
      this.resolveFinalResult(        // 把结果塞进 Promise
        this.extractResult(event)     // 从终态事件里抠出 AssistantMessage
      );
      // 这一刻，所有 await stream.result() 的地方立刻拿到完整消息
    }
 
    // ③ 消费者调度：把这个事件交给 UI
    const waiter = this.waiting.shift();
    if (waiter) waiter({ value: event, done: false });  // UI 在等？直接唤醒
    else this.queue.push(event);                         // UI 没来？排队
  }
 

注意一个设计细节：第②步和第③步是独立的。

终态事件触发了 done + resolve 结果 Promise——这是给 Agent Loop 的信号。但终态事件本身仍然作为一个普通事件流给 UI——UI 的 for await 会收到这最后一个事件，然后下一轮循环看到 done 就退出。

结果通道和过程通道是分离的。Agent Loop 通过 result() 拿到完整消息决定下一步，UI 通过 for await 拿到每个 delta 实时渲染，两条线互不干扰。

● ● ●

UI 怎么一个一个拿事件

换个角度，从 UI 那边看：

// event-stream.ts:50-64
  async *[Symbol.asyncIterator](): AsyncIterator<T> {
    while (true) {
      // 情况一：queue 里有积压——模型比 UI 快，事件先到了
      // 直接 yield 出去，UI 拿到渲染
      if (this.queue.length > 0) {
        yield this.queue.shift() as T;
        continue;
      }
 
      // 情况二：queue 空了，流也结束了——退出，没有更多事件
      if (this.done) return;
 
      // 情况三：queue 空了但流没结束——UI 比模型快，没东西可渲染
      // 把自己的 resolve 函数塞进 waiting 数组，然后 await 挂起
      // 等模型下次 push 时从 waiting 里取出 resolve 调用，这里才唤醒
      const next = await new Promise<IteratorResult<T>>((resolve) => {
        this.waiting.push(resolve);
      });
      if (next.done) return;
      yield next.value;
    }
  }
 

生产者和消费者通过 resolve 函数握手，谁都不需要轮询。

打个比方：queue 是收件箱，waiting 是等候室。模型有信就放收件箱，UI 来了从收件箱拿。如果收件箱空了，UI 去等候室坐着，模型下次有信了进来叫醒它。

● ● ●

中途出事了怎么办

模型可能网络超时，你可能中途按了取消。这时没有正常的终态事件，result() 的 Promise 永远不会 resolve——Agent Loop 会一直等。

end 方法处理这种兜底情况：

// event-stream.ts:35-44
  end(result: R): void {
    // 保证 result() 一定能 resolve——传一个错误结果进去
    if (!this.done) this.resolveFinalResult(result);
    // 翻闸门
    this.done = true;
    // 把等候室里所有挂着的 UI 全部叫醒
    // 告诉它们：done: true，没有下一个事件了，退出吧
    while (this.waiting.length > 0) {
      this.waiting.shift()?.({
        value: undefined as T,
        done: true,
      });
    }
  }
 

宁可报错也不卡死。这是 EventStream 的故障哲学。

● ● ●

真实使用：模型回复怎么流回 Agent

看完抽象层，看 Pi 里最常用的子类。Provider Adapter 调模型时返回的就是这个——把流式事件聚合成完整的 AssistantMessage：

// event-stream.ts:67-81
export class AssistantMessageEventStream
  extends EventStream<ModelEvent, AssistantMessage>
  implements ModelStream
{
  constructor() {
    super(
      // isComplete：done 或 error 都算终态
      // 正常结束和出错都意味着"流结束了"
      (event) => event.type === "done" || event.type === "error",
      // extractResult：done 时取 message，error 时取 error
      (event) => {
        if (event.type === "done") return event.message;
        if (event.type === "error") return event.error;
        throw new Error("非终态事件不能生成最终消息");
      },
    );
  }
}
 

子类只填两个回调，三态闸门的调度全由父类处理。

这意味着什么？如果你想接一个新的流式数据源——比如 WebSocket、Server-Sent Events、甚至一个本地文件流——你只需要告诉 EventStream 两件事：「什么是终态」和「怎么抠结果」。queue、waiting、done 那一套调度逻辑，一行都不用重写。

● ● ●

在整个 Agent 回路里的位置

把 EventStream 放回到你用 Pi 的完整流程里看：

你输入："帮我读README"
  → Pi 调 model.stream(messages)        ← 返回 EventStream
    ← text_delta "我"                    ← UI for await 收到，屏幕上出现"我"
    ← text_delta "来"                    ← 屏幕上出现"来"
    ← text_delta "读"                    ← 屏幕上出现"读"
    ← toolcall_delta (read工具)          ← UI 显示"正在读取..."
    ← done                               ← 终态事件
  → Agent Loop: await stream.result()    ← 拿到完整 AssistantMessage
  → 检查有没有工具调用 → 有，执行 read
  → 继续 for 循环，再调 model.stream()...
 

同一个 EventStream，UI 消费它的过程，Agent Loop 消费它的结果。你看到的逐字输出和 Pi 内部的循环判断，靠的就是这一个对象。

● ● ●

小结

你看到的现象源码里发生了什么
文字一个字一个字冒出来UI 在 for await 消费 delta 事件
流结束后拿到完整回复result() 的 Promise 在终态事件时 resolve
模型快 UI 慢时不丢字事件先进 queue 排队
UI 快模型慢时屏幕不动消费者在 waiting 挂起，等 push 唤醒
中途取消不卡死end() 兜底 resolve + 唤醒所有人
流结束后多余事件被忽略done 闸门直接 return

82 行代码，解决了流式系统里生产消费速度匹配、过程结果时序协调、异常兜底三个问题。这是后面所有流式场景的基础设施——Provider 返回它，Agent Loop 消费它，Session 持久化它吐出的事件。
