大家好，我是郑同学。

上篇我们跑完了一条写死的七步轨迹——调一下，七步一次性返回。但你实际用 Pi 的时候，回复是一个字一个字冒出来的。

做过 AI 应用开发的同学都知道，模型回复是流式的——一连串 delta 事件，逐个收、逐个渲染，最后拼出完整消息。标准套路。

但 Pi 没有直接用一个简单的流。它写了一个叫 EventStream 的类，82 行。

为什么要在标准流式上多包一层？因为真实 Agent 场景有三个问题是简单流解决不了的。

● ● ●

三个问题

一，过程和结果是两样东西。 你逐个渲染 delta 到屏幕上，但流结束后 Pi 内部还要一个完整的 AssistantMessage——判断有没有工具调用、要不要继续循环。两个东西来自同一个流，发生在不同时间。

二，生产消费速度不一致。 模型一口气吐 10 个 chunk，消费者还没跟上。或者反过来。

三，中途出错了怎么办。 网络断了、用户取消了，等最终结果的 Promise 永远不 resolve——卡死。

EventStream 用 queue、waiting、done 三个字段，加上 push、asyncIterator、end 三个方法，把这三件事全解决了。

● ● ●

先看骨架

// event-stream.ts:7-21
export class EventStream<T, R = T> implements AsyncIterable<T> {
  // 模型比消费者快时，事件在这里排队
  private readonly queue: T[] = [];
  // 消费者比模型快时，resolve 函数在这里挂着等
  private readonly waiting: Array<(value: IteratorResult<T>) => void> = [];
  // 终态闸门，翻过去不再收新事件
  private done = false;
  // 结果通道：外置 Promise，存了 resolve 函数随时可以塞结果
  private readonly finalResult: Promise<R>;
  private resolveFinalResult!: (result: R) => void;
 
  constructor(
    // 调用方告诉它：怎么判断终态事件（比如 type === "done"）
    private readonly isComplete: (event: T) => boolean,
    // 调用方告诉它：怎么从终态事件里抠出最终结果（比如取 event.message）
    private readonly extractResult: (event: T) => R,
  ) {
    this.finalResult = new Promise<R>((resolve) => {
      this.resolveFinalResult = resolve;
    });
  }
 

同一个对象，两个出口：for await 逐个拿事件渲染（过程），result() 等最终消息（结果）。

这里先提一句：Pi 内部有一个 Agent Loop（后面 EP05 专门讲），负责"调模型→执行工具→结果回填→继续调模型"。Agent Loop 不关心每个 delta，它只 await stream.result() 等最终消息。UI 拿过程实时渲染，Agent Loop 拿结果决定下一步。

● ● ●

push：模型每吐一个事件调一次

// event-stream.ts:23-33
  push(event: T): void {
    // ① done 翻了？丢弃
    if (this.done) return;
 
    // ② 是终态事件？翻闸门 + resolve 结果
    if (this.isComplete(event)) {
      this.done = true;
      this.resolveFinalResult(this.extractResult(event));
    }
 
    // ③ 交给消费者：在等就唤醒，没在等就进 queue
    const waiter = this.waiting.shift();
    if (waiter) waiter({ value: event, done: false });
    else this.queue.push(event);
  }
 

注意②和③是独立的。终态事件 resolve 了结果 Promise，但它本身仍作为一个普通事件交给消费者。结果和过程分开走。

● ● ●

消费者：for await 主动拉

// event-stream.ts:50-64
  async *[Symbol.asyncIterator](): AsyncIterator<T> {
    while (true) {
      // queue 有积压？直接 yield
      if (this.queue.length > 0) {
        yield this.queue.shift() as T;
        continue;
      }
      // 流结束了？退出
      if (this.done) return;
 
      // 都没有：消费者比模型快，把 resolve 塞进 waiting 挂起
      // 等 push 来唤醒
      const next = await new Promise<IteratorResult<T>>((resolve) => {
        this.waiting.push(resolve);
      });
      if (next.done) return;
      yield next.value;
    }
  }
 

queue 和 waiting 就是缓冲速度差的两个容器。事件先到进 queue，消费者先到进 waiting。谁都不需要轮询。

● ● ●

end：出错时谁调的

end() 不是 EventStream 自己检测超时调的——是 Provider Adapter 主动调的。正常完成和出错都调：

// provider-adapter.ts:738-757（简化）
try {
  stream.push({ type: "done", reason: stopReason, message });
  stream.end(message);  // 正常完成也调 end
} catch (error) {
  stream.push({ type: "error", reason: aborted ? "aborted" : "error", error: message });
  stream.end(message);  // 出错也调 end
}
 

为什么 push 了 done 还要调 end？因为 end 做了一件 push 做不了的事——把 waiting 里所有挂着的消费者全部唤醒，给每个传 { done: true }。否则消费者卡在 await 里永远出不来。

// event-stream.ts:35-44
  end(result: R): void {
    if (!this.done) this.resolveFinalResult(result);
    this.done = true;
    // 唤醒所有挂着的消费者
    while (this.waiting.length > 0) {
      this.waiting.shift()?.({ value: undefined as T, done: true });
    }
  }
 

宁可报错也不卡死。

● ● ●

真实用法

Provider Adapter 调模型时返回的就是这个子类，只填两个回调：

// event-stream.ts:67-81
export class AssistantMessageEventStream
  extends EventStream<ModelEvent, AssistantMessage>
  implements ModelStream
{
  constructor() {
    super(
      // done 或 error 都算终态
      (event) => event.type === "done" || event.type === "error",
      // done 时取 message，error 时取 error
      (event) => {
        if (event.type === "done") return event.message;
        if (event.type === "error") return event.error;
        throw new Error("非终态事件不能生成最终消息");
      },
    );
  }
}
 

子类只关心「什么是终态」「怎么抠结果」，queue/waiting/done 的调度全由父类处理。

● ● ●

小结

问题解法
过程和结果怎么同时拿一个对象：for await 拿过程，result() 拿结果
模型快消费者慢事件进 queue 排队
消费者快模型慢resolve 塞进 waiting 挂起
中途出错Provider 调 end() 唤醒消费者
流结束后的多余事件done 闸门丢弃

82 行，解决过程结果双通道、速度匹配、异常兜底三件事。这是后面所有流式场景的基础设施。
