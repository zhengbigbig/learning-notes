上一篇那条七步轨迹是同步的——调一下，七步一次性返回。但你实际用 Pi 的时候，发一条消息后看到的是：文字一个字一个字冒出来，中间可能穿插工具调用的进度，最后才给你完整回复。

这个过程在源码里是怎么发生的？打开 event-stream.ts（82行），答案是 EventStream——一个对象同时管流式过程和最终结果。

● ● ●

问题：过程和结果不在同一个时间

你发一条消息，Pi 调模型。模型返回有两种东西：

  •  过程：一连串 delta 事件——文字片段、工具调用片段，逐个送到 UI 渲染
  •  结果：一个完整的 AssistantMessage——等流结束才能拿到

这两件事来自同一个数据源，但发生在不同时间。拆成两个对象，调用方就得自己协调「事件流到哪了」「结果什么时候 ready」——容易写出竞态。

Pi 的设计：一个对象同时提供两个视图。

// event-stream.ts:7-21
export class EventStream<T, R = T> implements AsyncIterable<T> {
  // 模型比 UI 快时，事件在这里排队
  private readonly queue: T[] = [];
  // UI 比模型快时，消费者的 resolve 函数在这里挂着等
  private readonly waiting: Array<(value: IteratorResult<T>) => void> = [];
  // 终态闸门：翻过去就不再收新事件
  private done = false;
  // 结果通道的 Promise
  private readonly finalResult: Promise<R>;
  private resolveFinalResult!: (result: R) => void;
 
  constructor(
    // 调用方告诉 EventStream：怎么判断一个事件是终态
    private readonly isComplete: (event: T) => boolean,
    // 调用方告诉 EventStream：怎么从终态事件里抠出最终结果
    private readonly extractResult: (event: T) => R,
  ) {
    // 外置 Promise 模式：内部随时 resolve，外部通过 result() 拿
    this.finalResult = new Promise<R>((resolve) => {
      this.resolveFinalResult = resolve;
    });
  }
 

同一个对象，implements AsyncIterable 给 UI 渲染流式输出，result(): Promise 给 Agent Loop 拿完整消息判断下一步，内部保证状态一致。

● ● ●

模型吐 token 时：push 做了什么

模型每产出一个事件，Provider Adapter 调一次 push：

// event-stream.ts:23-33
  push(event: T): void {
    // 闸门：流已结束，丢弃后续事件，不制造第二个事实
    if (this.done) return;
 
    // 终态检测：是终态事件（done/error）就翻闸门 + resolve 结果
    if (this.isComplete(event)) {
      this.done = true;
      this.resolveFinalResult(this.extractResult(event));
      // 这时 result() 的等待方立刻拿到完整 AssistantMessage
    }
 
    // 消费者调度：UI 在等就直接唤醒，没在等就进 queue 排队
    // 注意：终态事件本身也会作为一个普通事件流给 UI
    const waiter = this.waiting.shift();
    if (waiter) waiter({ value: event, done: false });
    else this.queue.push(event);
  }
 

终态检测和消费者调度是独立的。终态事件触发了 done + resolve 结果 Promise，但它本身仍然作为一个普通事件流给 UI。结果通道和过程通道分离——Agent Loop 通过 result() 拿到最终消息决定下一步，UI 通过 for await 拿到每个 delta 实时渲染，两条线互不干扰。

● ● ●

UI 渲染时：消费者怎么一个一个拿事件

// event-stream.ts:50-64
  async *[Symbol.asyncIterator](): AsyncIterator<T> {
    while (true) {
      // 情况一：queue 里有积压——模型比 UI 快，事件先到了
      if (this.queue.length > 0) {
        yield this.queue.shift() as T;
        continue;
      }
 
      // 情况二：queue 空且流已结束——退出迭代
      if (this.done) return;
 
      // 情况三：queue 空且没 done——UI 比模型快，没事件可消费
      // 把自己的 resolve 函数塞进 waiting，然后 await 挂起
      // 模型下次 push 时从 waiting 取出 resolve 调用，这里才唤醒
      const next = await new Promise<IteratorResult<T>>((resolve) => {
        this.waiting.push(resolve);
      });
      if (next.done) return;
      yield next.value;
    }
  }
 

queue 和 waiting 就是缓冲两边速度差的两个容器——事件先到进 queue，消费者先到进 waiting。生产者和消费者通过 resolve 函数握手，谁都不需要轮询。

● ● ●

流异常中断怎么办

模型可能网络超时、用户可能中途取消。这时没有正常的终态事件，result() 的 Promise 永远不会 resolve。end 方法处理这种情况：

// event-stream.ts:35-44
  end(result: R): void {
    // 兜底 resolve：保证 result() 一定能拿到结果
    if (!this.done) this.resolveFinalResult(result);
    // 翻闸门
    this.done = true;
    // 把所有挂着的消费者全部唤醒
    // 传 done: true 告诉它们：没有下一个事件了，退出循环
    while (this.waiting.length > 0) {
      this.waiting.shift()?.({
        value: undefined as T,
        done: true,
      });
    }
  }
 

● ● ●

真实用法：模型回复怎么流回 Agent

Pi 里最常用的子类——把模型的流式事件聚合成一条完整的 AssistantMessage：

// event-stream.ts:67-81
export class AssistantMessageEventStream
  extends EventStream<ModelEvent, AssistantMessage>
  implements ModelStream
{
  constructor() {
    super(
      // isComplete：done 或 error 都算终态（正常结束和出错都意味着流结束）
      (event) => event.type === "done" || event.type === "error",
      // extractResult：done 时取 message，error 时取 error
      (event) => {
        if (event.type === "done") return event.message;
        if (event.type === "error") return event.error;
        throw new Error("非终态事件不能生成最终消息");
      },
    );
  }
}
 

子类只填两个回调，三态闸门的调度全由父类处理。想接一个新的流式数据源，只需要告诉 EventStream「什么是终态、怎么抠结果」，queue/waiting/done 那一套不用重写。

小结

你看到的现象源码机制
文字一个字一个字冒出来for await 消费 EventStream 的 delta 事件
流结束后拿到完整回复result() 返回的 Promise 在终态事件时 resolve
模型快 UI 慢时不丢事件queue 缓冲积压事件
UI 快模型慢时不空转waiting 挂起消费者，等 push 唤醒
中途取消或网络断end() 兜底 resolve + 唤醒所有消费者
流结束后多余事件done 闸门丢弃
