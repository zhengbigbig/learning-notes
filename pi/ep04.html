上篇拆了消息结构——你的话在 Pi 内部怎么存。但有个问题没回答：你配一个 API key，Pi 就能跟模型对话，中间发生了什么？

更关键的问题：为什么你把 provider 从 OpenAI 换成 Google、换成 Anthropic，Agent 核心代码一行都不用改？

这一篇拆 provider-adapter.ts——全仓库最大的单文件，776 行。它就是「API key 到模型回复」中间那层翻译器。

● ● ●

核心契约：Model 接口

Agent 核心只认一个接口：

// types.ts
export interface Model {
  // 完整对话历史 + 工具定义
  stream(
    context: AgentContext,
    // 用户点了停止就 abort
    options?: { signal?: AbortSignal },
  ): ModelStream;  // 返回异步事件流
}
 

整个 Agent 系统和具体模型之间唯一的契约就是这个接口。OpenAI、Anthropic、Google，不管外面字段叫什么，进到 Pi 内部全部变成 ModelStream，吐出上一篇定义的六种 ModelEvent。

先看一张全景图，后面的代码都在讲这张图里每一层做了什么：

数据从下往上走（入站）：Provider 吐 SSE 字节 → transport 切成三种 chunk → adapter 翻译成六种 ModelEvent → Agent 消费。数据从上往下走（出站）：Agent 的 canonical 消息 → adapter 翻译成 wire format → transport 发请求。

这层翻译器拆成两层：transport 切字节，adapter 翻语义。

● ● ●

transport 层：把 SSE 字节流切成 chunk

transport 只管网络——把 HTTP 响应体里的 SSE 字节流切成一条条离散的 chunk：

// provider-adapter.ts:62-67
export interface ProviderTransport {
  stream(
    request: ProviderRequest,
    options: { signal?: AbortSignal },
  ): AsyncIterable<ProviderChunk>;
}
 

它吐出来的 chunk 只有三种类型——provider 花样再多，收窄成三个 case：

// provider-adapter.ts:14-27
export type ProviderChunk =
  // 模型吐了文字
  | { type: "text"; delta: string }
  // 模型要调工具（参数片段是半截 JSON）
  | { type: "tool"; index: number; id?: string;
      name?: string; argumentsDelta?: string }
  // 流结束了
  | { type: "finish"; reason: "stop" | "length"
      | "tool_calls"; usage?: Partial<Usage> };
 

三种 chunk 对应模型能干的三件事：说话、调工具、说完了。

SSE 解析：逐行读 data 行

transport 最大的活儿是把字节流切成 JSON。核心是 readSSEData：

// provider-adapter.ts:342-368（简化）
async function* readSSEData(body, signal) {
  const reader = body.getReader();
  const decoder = new TextDecoder();
  const dataLines = [];
  let buffer = "";
 
  while (true) {
    // 读前后都查 abort
    throwIfAborted(signal);
    const { done, value } = await reader.read();
    buffer += decoder.decode(value, { stream: done ? false : true });
 
    let lineEnd = buffer.indexOf("\n");
    while (lineEnd >= 0) {
      // 切出完整一行，剩下的留 buffer
      let line = buffer.slice(0, lineEnd);
      buffer = buffer.slice(lineEnd + 1);
      const data = consumeSSELine(line, dataLines);
      // 一条完整消息 yield 出去
      if (data !== undefined) yield data;
      lineEnd = buffer.indexOf("\n");
    }
  }
}
 

consumeSSELine 按 SSE 协议规则挑 data: 行，空行表示一条消息结束：

// provider-adapter.ts:323-340（简化）
function consumeSSELine(line, dataLines) {
  // 空行 = 一条消息结束
  if (line === "") {
    // 多行 data 拼成一条
    const data = dataLines.join("\n");
    dataLines.length = 0;
    return data;
  }
  if (line.startsWith("data:")) {
    // 去掉 "data:" 前缀
    dataLines.push(line.slice(5));
  }
  return undefined;
}
 

buffer 是核心状态——把「不完整的字节流」变成可管理的内存状态。网络是流式的，但 SSE 协议的空行帮你切成一条条离散消息。

● ● ●

adapter 层：chunk 翻译成 ModelEvent

adapter 吃 transport 吐 chunk，翻译成 Pi 内部的 ModelEvent。入口是 createOpenAICompatibleModel：

// provider-adapter.ts:588-592
export function createOpenAICompatibleModel(options: {
  // 哪家 provider，写进 AssistantMessage
  provider: string;
  // 模型名
  model: string;
  // 网络层，可替换
  transport: ProviderTransport;
}): Model  // 返回 Agent 认识的 Model
 

换 provider 等于换 transport，adapter 几乎不用动。

按 index 累积工具参数

流式 tool call 的参数是分多次到达的，可能多个工具并发交错。adapter 用 Map 按 index 分桶：

// provider-adapter.ts:645-672（简化）
} else if (chunk.type === "tool") {
  // 按 index 取桶
  let buffer = toolBuffers.get(chunk.index);
  if (!buffer) {
    buffer = {
      id: chunk.id ?? `call-${chunk.index}`,
      name: chunk.name ?? "",
      // 参数片段往这儿拼
      argumentsText: "",
      contentIndex: content.length,
    };
    toolBuffers.set(chunk.index, buffer);
    content.push({ type: "toolCall", id: buffer.id, name: buffer.name, ... });
  }
  // 片段拼到末尾
  buffer.argumentsText += chunk.argumentsDelta ?? "";
}
 

每个工具调用占一个独立 buffer，互不串台。假设模型同时调两个工具，SSE 流可能是：先来 tool 0 的半个参数，再来 tool 1 的半个参数，再来 tool 0 的后半段。如果共用一个 buffer，参数就串了。

finish chunk 翻译停止原因

// provider-adapter.ts:691-699
// OpenAI 用下划线，Pi 内部用驼峰
const stopReason: "stop" | "length" | "toolUse" =
  finish.reason === "tool_calls" ? "toolUse"
  : finish.reason === "length" ? "length"
  : "stop";
 

然后对每个 tool buffer 做最后一次 JSON.parse——流式期间攒的是字符串，Pi 内部需要解析后的对象：

// provider-adapter.ts:701-713（简化）
for (const [index, buffer] of [...toolBuffers].sort(
  ([, left], [, right]) => left.contentIndex - right.contentIndex,
)) {
  // 只有真要调工具才 parse
  if (stopReason === "toolUse") {
    try {
      parsedArguments = JSON.parse(buffer.argumentsText || "{}");
    } catch {
      throw new Error(`Tool ${buffer.name} arguments 不是完整 JSON`);
    }
  }
}
 

停止原因决定怎么对待残片——如果是 stop 或 length，tool buffer 里的字符串可能是模型中途打断留下的半截，不强转 JSON，原样保留。sort 是因为 map 的 key 顺序和 content 数组顺序不一定一致，输出前要重排。

● ● ●

API key 安全：只进 Authorization header

key 的生命线被严格限制在 transport 的闭包内：

// provider-adapter.ts:415-428（简化）
const response = await fetchImplementation(endpoint, {
  method: "POST",
  headers: {
    Accept: "text/event-stream",
    // key 唯一出现的地方
    Authorization: `Bearer ${options.apiKey}`,
    "Content-Type": "application/json",
  },
  // request 里没有 key
  body: JSON.stringify({ ...request, stream: true }),
  signal: streamOptions.signal,
});
 

key 还可能通过错误信息泄漏——provider 返回 401 时 body 里可能回显 header。所以有个 sanitizedTransportError：

// provider-adapter.ts:316-321
function sanitizedTransportError(error: unknown, apiKey: string): Error {
  const message = error instanceof Error ? error.message : String(error);
  // 把 key 字面量替换成 [redacted]
  const sanitized = apiKey ? message.split(apiKey).join("[redacted]") : message;
  return new Error(sanitized || "OpenAI-compatible transport failed");
}
 

很便宜的防御，但能挡住常见泄漏路径。

● ● ●

出站翻译：canonical 消息变成 wire format

入站讲完了，还有出站。Agent 每轮调 model.stream(context)，context 里的消息是 Pi 自己的 canonical 格式（UserMessage / AssistantMessage / ToolResultMessage）。但 provider 不认这些，它只认 HTTP 请求 body 里的 JSON。

toProviderMessages 把 canonical 消息翻译成 provider 认的格式：

// provider-adapter.ts:513-541（简化）
for (const message of context.messages) {
  if (message.role === "user") {
    result.push({ role: "user", content: textValue(message.content) });
  } else if (message.role === "toolResult") {
    // Pi 的 toolResult 变成 OpenAI 的 tool role
    result.push({
      role: "tool",
      // 回指哪次调用
      tool_call_id: message.toolCallId,
      name: message.toolName,
      content: textValue(message.content),
    });
  } else {
    // assistant 带上 tool_calls
    const toolCalls = message.content
      .filter(block => block.type === "toolCall")
      .map(call => ({
        id: call.id, type: "function",
        function: { name: call.name, arguments: call.rawArguments ?? JSON.stringify(call.arguments) },
      }));
    result.push({
      role: "assistant",
      content: textContent || null,
      ...(toolCalls.length > 0 ? { tool_calls: toolCalls } : {}),
    });
  }
}
 

canonical 和 wire format 的差异全藏在这一层映射里。

● ● ●

支持多 provider 到底怎么做

这里有个关键设计决策：Pi 全仓库只有一套 transport——OpenAI-compatible。

你在源码里搜不到任何 anthropic 或 gemini 字样。Pi 不为每家 provider 写单独的 adapter。它的假设是：所有 provider 都暴露一个 OpenAI 兼容的 /chat/completions 端点。

这不是幻想——现在主流 provider 都提供兼容层：

  •  OpenAI：原生就是这格式
  •  DeepSeek / 通义千问 / Moonshot：API 直接兼容 OpenAI 格式
  •  Anthropic：通过 OpenAI 兼容代理接入
  •  本地模型（Ollama / vLLM）：都暴露 OpenAI 兼容端点

所以换 provider 只改配置里的 baseUrl 和 apiKey：

// 用 DeepSeek
createOpenAICompatibleModel({
  provider: "deepseek",
  model: "deepseek-chat",
  transport: createOpenAICompatibleTransport({
    baseUrl: "https://api.deepseek.com/v1",   // 只改这里
    apiKey: process.env.DEEPSEEK_API_KEY,
  }),
});
 
// 用通义千问
createOpenAICompatibleModel({
  provider: "qwen",
  model: "qwen-plus",
  transport: createOpenAICompatibleTransport({
    baseUrl: "https://dashscope.aliyuncs.com/compatible-mode/v1",
    apiKey: process.env.DASHSCOPE_API_KEY,
  }),
});
 

adapter 代码一个字都不用改。

那如果 provider 不兼容 OpenAI 格式怎么办

写一个新的 transport。transport 只是一个接口：

// provider-adapter.ts:62-67
export interface ProviderTransport {
  stream(
    request: ProviderRequest,
    options: { signal?: AbortSignal },
  ): AsyncIterable<ProviderChunk>;
}
 

你的新 transport 负责把 provider 的私有格式翻译成三种 ProviderChunk（text / tool / finish），adapter 不用动。Pi 自带两个 transport 实现：

  •  createOpenAICompatibleTransport：接 OpenAI 兼容 provider（生产用）
  •  fixedTransport：吐固定 chunk 序列（测试用，ScriptedModel 内部就是它）

transport 是可替换的零件，adapter 是固定的翻译器。这就是分层带来的扩展能力——上层（Model 接口）不关心你接了谁，中层（adapter）不关心你怎么切字节，下层（transport）只管把 provider 的格式收窄成三种 chunk。

● ● ●

延伸：CC Switch 也是同一套思路

读完这 776 行你可能觉得这种适配层很重。但如果你用过 CC Switch（farion1231/cc-switch，12 万 star），会发现它在做同一件事，只是层次不同。

CC Switch 的 ProviderService::switch(state, app_type, id) 核心逻辑是：从数据库读 provider 配置，写入对应 app 的 live 配置文件——Claude 写 ~/.claude/settings.json 里的 ANTHROPIC_BASE_URL + ANTHROPIC_API_KEY，Codex 写 config.toml，Gemini 写 auth 文件。

异曲同工的地方：

都靠中间格式隔离上下层。 Pi 用六种 ModelEvent 隔离运行时数据，CC Switch 用 Provider struct 隔离配置数据。Pi 的 toProviderMessages 把 canonical 消息翻译成 wire format，CC Switch 的 sync_current_provider_for_app_to_live 把 Provider struct 翻译成各家 app 的配置文件格式。

都挡住底层差异。 Pi 的 transport 挡住 SSE 半截 JSON 和网络边界，CC Switch 的 live.rs 挡住 Claude 用 JSON、Codex 用 TOML、Gemini 用 auth 文件的格式差异。

都支持零成本扩展。 Pi 接新 provider 只写 transport，CC Switch 加新 app 只加 AppType 枚举 + 对应配置写入逻辑。

根本区别：Pi 是翻译器，运行时实时翻译字节流；CC Switch 是开关，启动前写好配置文件。一个在代码运行时适配，一个在配置时切换。

层职责关键代码
