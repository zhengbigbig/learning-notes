这是《动手学 Pi》系列第 4 篇。

上一篇我们用 ScriptedModel 把模型变成了一个「按剧本逐字吐事件」的演员——你喂它一张表，它吐出六种 ModelEvent。但那是假的。真正用 Pi 的时候，你会在配置里填一个 OpenAI 的 API key，然后 Pi 去敲 api.openai.com 的门，把模型吐出来的 SSE 字节流翻译成那六种事件。

这中间发生了什么？为什么你把 provider 从 OpenAI 换成 Google、换成 Anthropic，Agent 的核心代码一行都不用改？这一篇拆 Checkpoint 05——Provider 适配器层，源码是全仓库最大的单文件 provider-adapter.ts，776 行。

● ● ●

你配一个 key，背后发生什么

先从使用者视角看。你打开 Pi 的配置，写下：

const model = createOpenAICompatibleModel({
  provider: "openai",
  model: "gpt-4o",
  transport: createOpenAICompatibleTransport({
    baseUrl: "https://api.openai.com/v1",
    apiKey: process.env.OPENAI_API_KEY,
  }),
});
 

然后这个 model 被塞进 Agent。你发一句话，Agent 就拿它去跟模型对话。整个过程中，Agent 核心代码——那个 while 循环、工具执行器、Session 存储——从头到尾没有出现一个 openai 字样。

这是怎么做到的？因为 Agent 核心只认一个接口：Model。任何 provider 只要伪装成这个接口，Agent 就拿它当模型用。我们从这个接口看起。

● ● ●

Model 接口：核心只认这一张脸

Checkpoint 05 的起点写得很清楚——上层只认识 canonical Model。接口定义在 types.ts：

// types.ts: Model 接口——所有 provider 都要实现它
export interface Model {
  stream(
    context: AgentContext,                    // 带着完整对话历史和工具定义
    options?: { signal?: AbortSignal },       // 用户点了停止就 abort
  ): ModelStream;                             // 返回一个异步事件流
}
 

就这么一个方法，叫 stream，吃进去一个 context，吐出来一个 ModelStream。整个 Agent 系统和具体模型之间唯一的契约就是这个接口。

上一篇讲过，ModelStream 是一个可迭代的异步流，一边吐 ModelEvent 一边能查最终结果。六种 ModelEvent——start、text_delta、toolcall_delta、toolcall_end、done、error——是 Pi 自己定义的内部格式，跟任何 provider 都没关系。OpenAI 返回的 choices[0].delta.content、Anthropic 返回的 content_block_delta，无论外面叫什么，进到 Pi 内部全部变成这六种之一。

中间层是长期事实，provider payload 只是临时噪音。这个判断决定了整个仓库的分层方式。

● ● ●

ProviderChunk：provider 花样再多，只剩三种 chunk

适配器的第一道抽象，是把 provider 那一堆字段名收窄成三种 chunk：

// provider-adapter.ts:14-27 不管哪家 provider，transport 吐出来就这三种
export type ProviderChunk =
  | { type: "text"; delta: string }                         // 模型吐了一段文字
  | {
      type: "tool";                                         // 模型要调工具
      index: number;                                        // 第几个工具调用（按到达顺序）
      id?: string;                                          // 调用 id，回指结果要用
      name?: string;                                        // 工具名，第一个 delta 带
      argumentsDelta?: string;                              // 参数片段，半截 JSON
    }
  | {
      type: "finish";                                       // 流结束了
      reason: "stop" | "length" | "tool_calls";            // 为什么停
      usage?: Partial<Usage>;                               // token 计数
    };
 

我看到这儿时停了一下。三种 chunk，对应的就是模型能干的三件事：说话、调工具、说完了。把 provider 的复杂性收窄到三个 case，后面所有的解析代码就有了明确目标。联合类型在这里等于一份穷举清单，编译器能强制 switch 覆盖所有分支。

这三种 chunk 由 ProviderTransport 接口产出：

// provider-adapter.ts:62-67 transport 只管网络和 SSE 解析
export interface ProviderTransport {
  stream(
    request: ProviderRequest,                 // OpenAI 兼容的请求格式
    options: { signal?: AbortSignal },
  ): AsyncIterable<ProviderChunk>;            // 吐出三种 chunk
}
 

这层只管把字节流切成离散的、经过验证的 chunk，不碰任何语义。它连「这段文字属于哪次回复」都不关心。

● ● ●

两层分工：transport 切字节，adapter 翻语义

Checkpoint 05 把适配器拆成两层。用一句话概括边界：transport 负责网络和 SSE 解析，adapter 负责把 chunk 翻译成 ModelEvent，Agent 核心不出现 provider 字段。

中间层是 createOpenAICompatibleModel，吃一个 transport 吐一个 Model：

// provider-adapter.ts:588-592 adapter 吃 transport 吐 Model
export function createOpenAICompatibleModel(options: {
  provider: string;               // 标记这是哪家 provider，写进 AssistantMessage
  model: string;                  // 标记模型名，写进 AssistantMessage
  transport: ProviderTransport;   // 网络层，可替换
}): Model {                        // 返回的是 Agent 认识的 Model
 

transport 和 adapter 是干净的分工：transport 解析 SSE 字节流产出 chunk，adapter 把 chunk 翻译成 ModelEvent。如果将来要接一个非 OpenAI 格式的 provider，比如 Anthropic 原生 SSE，只需要写一个新的 transport，adapter 几乎不用动。换 provider 等于换 transport，这是分层带来的直接红利。

● ● ●

SSE 流式解析：逐行读 data 行

网络层最大的活儿，是把 HTTP 响应体里的 SSE 字节流切成一条条 JSON。这是你用 Pi 时「文字一个字一个字冒出来」的物理基础。核心是 readSSEData 函数：

// provider-adapter.ts:342-358 把字节流切成一行行
async function* readSSEData(
  body: ReadableStream<Uint8Array>,           // fetch 返回的响应体
  signal: AbortSignal | undefined,
): AsyncIterable<string> {
  const reader = body.getReader();
  const decoder = new TextDecoder();           // 字节变字符串
  const dataLines: string[] = [];              // 累积 data: 行
  let buffer = "";                             // 半截内容的缓冲区
 
  try {
    while (true) {
      throwIfAborted(signal);                  // 用户点了停止，立刻抛
      const { done, value } = await reader.read();
      throwIfAborted(signal);                  // read 前后都查，防止卡在 await 里
      buffer += done
        ? decoder.decode()                     // 流结束，冲刷剩余字节
        : decoder.decode(value, { stream: true });  // 否则带 stream 标志解码
 

逻辑很直白：循环读字节，解码成字符串，往 buffer 里追加。buffer 是这块代码的核心状态，它把「不完整的字节流」这个物理事实变成了可管理的内存状态。然后按换行符切：

// provider-adapter.ts:360-368 遇到换行才算一行读完
      let lineEnd = buffer.indexOf("\n");
      while (lineEnd >= 0) {
        let line = buffer.slice(0, lineEnd);          // 切出完整一行
        buffer = buffer.slice(lineEnd + 1);           // 剩下的留在 buffer 里
        if (line.endsWith("\r")) line = line.slice(0, -1);  // 处理 CRLF
        const data = consumeSSELine(line, dataLines); // 按 SSE 规则挑 data 行
        if (data !== undefined) yield data;           // 一条完整消息 yield 出去
        lineEnd = buffer.indexOf("\n");
      }
 

consumeSSELine 按 SSE 协议的规则挑出 data: 开头的行：

// provider-adapter.ts:323-340 按 SSE 协议拼消息
function consumeSSELine(
  line: string,
  dataLines: string[],
): string | undefined {
  if (line === "") {                              // 空行 = 一条 SSE 消息结束
    if (dataLines.length === 0) return undefined;
    const data = dataLines.join("\n");            // 多行 data: 拼成一条
    dataLines.length = 0;                         // 清空，准备下一条
    return data;
  }
  if (line === "data") {                          // "data:" 后面没内容的边界情况
    dataLines.push("");
  } else if (line.startsWith("data:")) {
    const value = line.slice(5);                  // 去掉 "data:" 前缀
    dataLines.push(value.startsWith(" ") ? value.slice(1) : value);  // 可选空格
  }
  return undefined;
}
 

SSE 的规则是：data: 后面跟内容，空行表示一条消息结束。空行是 SSE 协议的消息边界标记。网络是流式的，但 SSE 协议帮你把它切成一条条离散的消息，这是流式 API 的底层基础设施。

● ● ●

半截 JSON 不是坏 JSON：它在等另一半

Checkpoint 05 留了一个预测题：{"path": 为什么不是坏 JSON？

答案藏在 readSSEData 的 buffer 逻辑里。网络流是分块到达的，TCP 包不保证一条 SSE 消息刚好在一个 chunk 里。{"path": 可能是某条 JSON 的前半段，后半段 "/tmp/foo"} 还在路上。

readSSEData 那个 while (lineEnd >= 0) 循环保证了：只有在遇到完整换行符时，一行才算读完。没有换行符的半截内容会留在 buffer 里，等下一次 reader.read() 再拼。还有更微妙的情况：一条 SSE 消息内部的 JSON 本身可能跨多个 data: 行，consumeSSELine 把它们累积进 dataLines，只在空行时 join 成完整字符串。

「半截」从来不是错误状态，它是流的常态。适配器要做的不是判断 JSON 完不完整，而是老老实实等空行，等到了再 parse。课程把这个细节单独拎出来做预测题，是因为很多人第一次写流式解析会想当然地在每次 reader.read() 后就 JSON.parse，然后被随机报错搞崩溃。

每读完一条 data，还有个关键检查：

// provider-adapter.ts:447-454 先验明正身再 parse
          if (data.trim() === "[DONE]") break;          // OpenAI 的结束标记
 
          let rawChunk: unknown;                        // 进来时先当 unknown
          try {
            rawChunk = JSON.parse(data) as unknown;
          } catch {
            throw invalidProviderChunk("data line is not valid JSON");
          }
 

[DONE] 是 OpenAI SSE 的结束标记，用一个特殊字符串而不是空流表示结束——这让代码能区分「结束了」和「网络卡了」。注意第 451 行：JSON.parse 的返回值被显式标注成 unknown。所有外部 JSON 进来时都是 unknown，必须经过形状验证才能成为 ProviderChunk。网络那头是不可信的，这是上一篇「unknown 收窄」原则的真实落地。

● ● ●

按 index 累积 delta：两个工具调用不能共用一个 buffer

第二个预测题：两个 tool call 的参数交错时，为什么不能共用一个 buffer？

看 adapter 处理 tool chunk 的逻辑：

// provider-adapter.ts:645-672 每个 index 一个独立 buffer
            } else if (chunk.type === "tool") {
              let buffer = toolBuffers.get(chunk.index);     // 按 index 取桶
              if (!buffer) {
                buffer = {                                    // 第一次见到这个 index
                  id: chunk.id ?? `call-${chunk.index}`,      // 没 id 就用 index 造一个
                  name: chunk.name ?? "",
                  argumentsText: "",                          // 参数片段往这儿累积
                  contentIndex: content.length,               // 记住它在 content 数组的位置
                };
                toolBuffers.set(chunk.index, buffer);
                content.push({
                  type: "toolCall",                           // 先占个位
                  id: buffer.id,
                  name: buffer.name,
                  arguments: "",
                  rawArguments: "",
                });
              }
              if (chunk.id) buffer.id = chunk.id;             // 后续 delta 可能补上 id
              if (chunk.name) buffer.name = chunk.name;
              buffer.argumentsText += chunk.argumentsDelta ?? "";  // 片段拼到末尾
 

关键是第 646 行：toolBuffers.get(chunk.index)。这里用了一个 Map，按 index 分桶。每个工具调用占一个桶，互不串台。

为什么必须按 index 分桶？因为流式 tool call 的参数是分多次到达的。假设模型同时调两个工具，SSE 流可能是这样：先来 tool index 0 的半个参数，再来 tool index 1 的半个参数，再来 tool index 0 的后半段。如果共用一个 buffer，第二个工具的参数会被拼进第一个工具。

ProviderChunk 里的 tool 类型带 index 字段，就是为了解决这个交错问题。每个 index 一个独立 buffer，参数各拼各的，互不干扰。流式世界的 bug 总是藏在低概率的时序组合里——大多数时候模型只调一个工具，一切正常，直到某天并发调两个，参数串了。

● ● ●

API key 安全：只进 Authorization header

Checkpoint 05 的安全检查写得很硬：transport 配置持有 API key，对外请求只允许它进入 Authorization header，body、context、日志和错误都不得包含密钥。

看 transport 发请求的代码：

// provider-adapter.ts:415-428 key 只出现在 header 里
        const response = await fetchImplementation(endpoint, {
          method: "POST",
          headers: {
            Accept: "text/event-stream",
            Authorization: `Bearer ${options.apiKey}`,     // key 唯一出现的地方
            "Content-Type": "application/json",
          },
          body: JSON.stringify({
            ...request,                                    // request 里没有 key
            stream: true,
            stream_options: { include_usage: true },
          }),
          signal: streamOptions.signal,
        });
 

options.apiKey 只在第 419 行的 header 里出现，body 里没有它，context 里没有它。key 的生命线被严格限制在 transport 的闭包内。闭包是这个安全模型的物理载体——key 不暴露成全局变量，不写进 context，不进 request body。

但 key 还是可能通过错误信息泄漏。如果 provider 返回 401 并在 body 里回显了你发出去的 header（包含 key），原始的 Error.message 里就带着 key。所以有个 sanitizedTransportError：

// provider-adapter.ts:316-321 错误信息里的 key 被替换成 [redacted]
function sanitizedTransportError(error: unknown, apiKey: string): Error {
  if (isAbortError(error)) return abortError();
  const message = error instanceof Error ? error.message : String(error);
  const sanitized = apiKey ? message.split(apiKey).join("[redacted]") : message;
  return new Error(sanitized || "OpenAI-compatible transport failed");
}
 

第 319 行把错误信息里所有出现的 key 字面量替换成 [redacted]。这是个很便宜的防御，但能挡住「错误信息回显 key」这类常见泄漏路径。catch 分支统一调用它，保证从 transport 抛出去的任何错误都已经脱敏。

● ● ●

出站翻译：canonical 消息变成 OpenAI wire format

入站讲完了，还有出站。Agent 内部的消息是 canonical 格式（UserMessage、AssistantMessage、ToolResultMessage），但 provider 只认 OpenAI 的 wire format。toProviderMessages 负责这个翻译：

// provider-adapter.ts:513-541 canonical 消息翻译成 wire format
  for (const message of context.messages) {
    if (message.role === "user") {                          // user 直接映射
      result.push({ role: "user", content: textValue(message.content) });
    } else if (message.role === "toolResult") {             // toolResult 变成 OpenAI 的 tool role
      result.push({
        role: "tool",
        tool_call_id: message.toolCallId,                   // 回指是哪次调用
        name: message.toolName,
        content: textValue(message.content),
      });
    } else {                                                // assistant 带上 tool_calls
      const textContent = textValue(message.content);
      const toolCalls = message.content
        .filter((block) => block.type === "toolCall")       // 从 content 数组抽出工具调用
        .map((call) => ({
          id: call.id,
          type: "function" as const,
          function: {
            name: call.name,
            arguments:
              call.rawArguments ?? JSON.stringify(call.arguments ?? {}),  // 优先用原始字符串
          },
        }));
      result.push({
        role: "assistant",
        content: textContent || null,                       // 没文字时 content 是 null
        ...(toolCalls.length > 0 ? { tool_calls: toolCalls } : {}),
      });
    }
  }
 

三种 canonical role 映射成三种 OpenAI role。canonical 和 wire format 的差异全藏在这一层映射里，Agent 核心永远不用知道 OpenAI 把 tool call 放在 tool_calls 数组而不是 content 里，也不用知道 OpenAI 要求 assistant 消息的 content 可以是 null。

● ● ●

收尾：finish chunk 和 JSON.parse 的最后一关

adapter 的最后一步是处理 finish chunk：

// provider-adapter.ts:691-699 finish_reason 翻译成 StopReason
          const stopReason: Extract<
            StopReason,
            "stop" | "length" | "toolUse"
          > =
            finish.reason === "tool_calls"
              ? "toolUse"                       // OpenAI 用下划线，Pi 内部用驼峰
              : finish.reason === "length"
                ? "length"
                : "stop";
 

注意 tool_calls 翻译成 toolUse——OpenAI 的命名带下划线，Pi 内部用驼峰，这种小差异在适配器里统一，核心层永远只看到干净的命名。

然后对所有 tool buffer 做最后一次 JSON.parse，因为流式期间攒的 argumentsText 只是字符串，Pi 内部需要的是解析后的对象：

// provider-adapter.ts:701-713 停止原因决定怎么对待残片
          for (const [index, buffer] of [...toolBuffers].sort(
            ([, left], [, right]) => left.contentIndex - right.contentIndex,
          )) {
            let parsedArguments: unknown = buffer.argumentsText;
            if (stopReason === "toolUse") {                 // 只有真要调工具才 parse
              try {
                parsedArguments = JSON.parse(buffer.argumentsText || "{}");
              } catch {
                throw new Error(
                  `Tool ${buffer.name || index} arguments 不是完整 JSON`,
                );
              }
            }
 

这里有个细节：只有 stopReason 是 toolUse 时才尝试 parse。停止原因决定了你怎么对待残片。如果是 stop 或 length，tool buffer 里的字符串可能是模型半途中断时留下的残片，强转 JSON 会报错，Pi 选择原样保留字符串，不抛异常。适配器对不完整状态的容忍，是它比简单 wrapper 高一档的地方。

还有那个 sort——按 contentIndex 排序后再处理。因为多个工具并发时，它们进入 toolBuffers map 的顺序（按 chunk.index）和它们出现在消息 content 数组里的顺序（按首次出现）不一定一致。map 的 key 顺序和数组顺序是两套东西。最终输出的 AssistantMessage.content 必须有序，所以收尾时重排一次。

● ● ●

小结

读完这 776 行，我自己最大的感悟是：适配器的本质不是「翻译」，而是「隔离不确定性」。

它隔离了三件事。第一，provider API 格式的不确定性——OpenAI 明天改字段名，只动 transport，不动 Agent。第二，网络的不确定性——半截 JSON、连接中断、SSE 边界，全在 transport 里处理掉，到 adapter 时已经是干净的 chunk。第三，安全的不确定性——key 在哪、错误信息会不会泄漏，都由 transport 的闭包和 sanitizedTransportError 兜底。

Pi 选择把这一层写成全仓库最大的文件，不是过度设计。每多支持一家 provider，省下的不是几行代码，而是一次全局重构。Agent 核心、工具系统、Session 存储，全都不用动，只要新写一个 transport。这就是抽象的复利：今天写的适配器，明天接 DeepSeek、接通义千问、接本地模型，都是零成本扩展。
