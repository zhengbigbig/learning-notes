这是《动手学 Pi》系列第 9 篇。

你跟一个 agent 聊了 30 轮：让它读了一堆文件、跑了几次测试、改了好几个函数。前 20 轮的 tool call 和 tool result 现在全量塞进上下文，token 早炸了，模型也开始前后矛盾——前面答应的事，后面忘得干干净净。

于是你冒出一个问题：对话越长，agent 到底越聪明还是越蠢？

直觉是「越聪明」——记得越多越好嘛。但现实是：长对话不压，模型会被自己的历史淹死；乱压一气，又把关键决策丢了，等于让 agent 失忆。

Pi 的答案在 src/context.ts，420 行。核心一句话：不动历史，只重建投影。这一篇一段段拆给你看。

● ● ●

先纠正一个直觉：压缩不是删除

最容易想到的压缩办法是「把旧的删了」。但你 EP08 刚学过——每条 entry 是一条事实，parentId 串成一棵树，每行一个 commit marker。删一条，后面整串 parentId 断掉，会话树塌了。

所以 Pi 不删。它的做法像你开会带笔记本：笔记本上记了 50 页，但你只带最近 5 页加一张摘要卡进会议室。笔记本一字不动，你手上拿什么另说。context.ts 干的就是「决定手上拿哪几页，以及怎么生成那张摘要卡」。

这句话贯穿整篇：压缩是追加一条新事实，让后续的投影从这条事实之后开始。不是修改，不是删除，是 append。

● ● ●

第一步：把对话切成 interaction 组

切历史的粒度不是「一条消息」，而是「一组 interaction」。

为什么？因为模型一次发言可能带多个 tool call，每个 call 必须有对应的 result。这叫一组 interaction。如果你从中间切，模型只看到 tool call A 却看不到 tool result A，它会以为工具没跑，要么重调一遍，要么直接报错。半组 interaction 是废数据，不能给模型看。

看源码怎么定义 interaction 边界。groupInteractions，第 125 行：

// context.ts:125-154
export function groupInteractions(
  entries: readonly MessageSessionEntry[],
): InteractionGroup[] {
  const groups: InteractionGroup[] = [];
  let current: InteractionGroup | undefined;
 
  // 收尾函数：校验当前组完整后入列，然后清空
  const finishCurrent = (): void => {
    if (!current) return;
    validateInteraction(current);  // 这组 call/result 必须配齐才放过
    groups.push(current);
    current = undefined;
  };
 
  for (const source of entries) {
    const entry = cloneMessageEntry(source);  // 深拷贝，避免改到原 entry
    // 规则一：遇到 user 消息，当前组收尾，开新组
    if (entry.message.role === "user") {
      finishCurrent();
      current = { entries: [entry] };
      continue;
    }
    // 规则二：第一条消息必须是 user，否则没有 interaction 起点
    if (!current) {
      throw new Error(
        `message entry ${entry.id} 在第一个 user interaction 之前`,
      );
    }
    // 其他角色（assistant / toolResult）追加进当前组
    current.entries.push(entry);
  }
  finishCurrent();  // 最后收尾
  return structuredClone(groups);  // 返回深拷贝，防外部篡改
}
 

规则只有一条：遇到 user 消息就开新组。因为新一轮用户输入开始，意味着上一轮的 tool call/result 必须全部收尾。user 消息是天然的组分界线。

structuredClone(groups) 出现了两次——入口处深拷贝入参，出口处深拷贝结果。这是为了让外面拿到的 group 改了不影响内部 session。投影函数必须纯函数，不能有副作用。

● ● ●

validateInteraction：用 Map 做 callId 集合相等

光切组不够，还得检查组内 call 和 result 是不是严格配对。validateInteraction，第 79 行：

// context.ts:79-119
function validateInteraction(group: InteractionGroup): void {
  const calls = new Map<string, string>();    // callId -> entryId
  const results = new Map<string, string>();  // callId -> entryId
 
  for (const entry of group.entries) {
    // assistant 消息里的 tool call：id 不能重复
    for (const call of callsIn(entry)) {
      const previous = calls.get(call.id);
      if (previous) {
        throw new Error(`tool call ${call.id} 重复：${previous} 与 ${entry.id}`);
      }
      calls.set(call.id, entry.id);
    }
    // toolResult 消息：callId 不能重复
    if (entry.message.role === "toolResult") {
      const callId = entry.message.toolCallId;
      const previous = results.get(callId);
      if (previous) {
        throw new Error(`tool result ${callId} 重复：${previous} 与 ${entry.id}`);
      }
      results.set(callId, entry.id);
    }
  }
  // 双向校验：result 必须有对应 call
  for (const [callId, resultEntryId] of results) {
    if (!calls.has(callId)) {
      throw new Error(`tool result ${resultEntryId} 引用了不存在的 call ${callId}`);
    }
  }
  // 双向校验：call 必须有对应 result
  for (const [callId, callEntryId] of calls) {
    if (!results.has(callId)) {
      throw new Error(`tool call ${callId}（entry ${callEntryId}）缺少 result`);
    }
  }
}
 

三个 Map 操作完成校验：重复检查、calls.has 查 result 的 call 在不在、results.has 查 call 的 result 在不在。本质就是两个集合相等——keys 一致且无重复。

为什么用 Map 不用双层 for？因为 Map 查找是 O(1)，双层 for 是 O(n²)。一组里塞 20 个并发 tool call，Map 版几乎瞬时，双层 for 要 400 次比较。

还有个细节：它不依赖 result 在数组里紧跟 call。两个并发调用可能是 call A、call B 发出去，result B 先回，result A 后回。按 callId 配对，不依赖相邻位置，这才能支持 EP05 讲过的 Promise.all 并发。

● ● ●

第二步：预算投影 buildContext

切完组，核心来了——预算投影。用一句话讲：在固定 token 预算内，从最新组往前挑，挑满为止，挑不下的整组丢掉。

先看返回结构，第 42 行：

// context.ts:42-48

  systemPrompt?: string;
  messages: AgentMessage[];     // 最终投给模型的消息序列
  keptEntryIds: string[];       // 保留了哪些 entry，可追溯
  reason: ContextBuildReason;   // 为什么是这么多：预算内/裁了/最新组溢出
  tokens: ContextTokenProjection; // 预算账本，每一项花多少 token
}
 

reason 三种取值，第 27 行：

// context.ts:27-30
export type ContextBuildReason =
  | "within_budget"          // 全放得下，没裁
  | "trimmed"                // 从前面裁了几组
  | "single_group_overflow"; // 最新一组单独就超预算——重点
 

第三种最反直觉，待会专门讲。先看 buildContext 主体，分四步走。

第一步：扣固定成本。 第 263 行：

// context.ts:263-285（节选）
export function buildContext(
  activePath: readonly SessionEntry[],
  options: BuildContextOptions,
): BuildContextResult {
  // 三个预算参数都得是非负 finite，否则直接抛错
  const maxTokens = nonNegativeFinite(options.maxTokens, "maxTokens");
  const reservedOutput = nonNegativeFinite(options.reservedOutput, "reservedOutput");
  const safetyMargin = nonNegativeFinite(options.safetyMargin, "safetyMargin");
  // system prompt 自己也有 token 成本
  const system = options.systemPrompt === undefined
    ? 0
    : estimatedTokens(options, options.systemPrompt, "systemPrompt");
  // 关键：固定成本先扣，剩下的才是消息预算
  const availableForMessages = Math.max(
    0,
    maxTokens - system - reservedOutput - safetyMargin,
  );
 

system prompt、输出预留（给模型回答留的额度）、安全余量（防估算误差），这三块先从总预算里减。固定成本先扣，剩下的才是消息预算。Math.max(0, ...) 兜底——system prompt 自己就超预算时，消息预算是 0 不是负数，避免下游算出负数崩掉。

第二步：取候选消息。 第 287 行：

  // 找最新一条压缩摘要（从末尾往前扫）
  const compaction = latestCompaction(activePath);
  // 从摘要的 firstKeptEntryId 之后开始切候选

    messageCandidates(activePath, compaction),
  );
 

摘要之后的消息才进候选池，摘要之前的不投给模型。所以历史没删，只是被摘要挡在了候选池外面。

第三步：摘要本身也占预算。 第 301 行：

  // 有摘要就把它当一条 user 消息，作为固定项
  const fixedMessages = compaction
    ? [summaryMessage(compaction.entry)]
    : [];
  // 摘要不是免费的，也要算 token 成本
  const fixedCost = fixedMessages.reduce(
    (total, message, index) =>
      total + estimatedTokens(options, message, `compaction summary ${index + 1}`),
    0,
  );
  // 组预算 = 消息总预算 - 摘要成本
  const groupBudget = Math.max(0, availableForMessages - fixedCost);
 

摘要不是免费的。摘要写得再精炼也有 token 成本。摘要越长，后面 interaction 能放进去的就越少。这是真实存在的约束，作者没假装它不存在。

第四步：从最新组往前累加。 第 315 行：

  // 先把每组成本预算好
  const groupCosts = groups.map((group, groupIndex) =>
    group.entries.reduce(
      (total, entry, entryIndex) =>
        total + estimatedTokens(options, entry.message,
          `interaction ${groupIndex + 1} message ${entryIndex + 1}`),
      0,
    )
  );
 
  let firstSelected = groups.length;  // 选中组的起始下标
  let selectedGroupCost = 0;
  let reason: ContextBuildReason = "within_budget";
 
  if (groups.length > 0) {
    const latestIndex = groups.length - 1;
    // 最新一组永远入选（最重要，必须留）
    firstSelected = latestIndex;
    selectedGroupCost = groupCosts[latestIndex] ?? 0;
    // 情况 A：最新一组单独就超预算
    if (selectedGroupCost > groupBudget) {
      reason = "single_group_overflow";
    } else {
      // 情况 B：从倒数第二组往前试，加得下就加
      for (let index = latestIndex - 1; index >= 0; index -= 1) {
        const candidateCost = groupCosts[index] ?? 0;
        if (selectedGroupCost + candidateCost > groupBudget) {
          reason = "trimmed";   // 加不下，裁掉它和前面所有
          break;
        }
        selectedGroupCost += candidateCost;
        firstSelected = index;
      }
      if (firstSelected > 0) reason = "trimmed";
    }
  }
 

逻辑很清楚：

  •  先放最新一组（最新对话最重要）
  •  往前逐组试，加得下就加，加不下就停
  •  全放得下 = within_budget，裁了前面 = trimmed
  •  最新一组单独超预算 = single_group_overflow，不拆，整组塞进去并标记

● ● ●

为什么 single_group_overflow 不拆

这是整个设计最反直觉的一步。最新一组超预算了，按常理应该拆开，放前面一半进去。作者偏不。

原因回到前面——一组 interaction 是一组工具契约，拆开就是半组废数据。模型看到 tool call 却看不到 result，等于让它基于「调用了工具但不知道结果」做决策，比没看到还糟。

所以作者的选择是：整组塞进去，并在 reason 里标 single_group_overflow。调用方拿到这个 reason，自己决定怎么办——报错、换大模型、还是让模型自己精简。context.ts 只如实报告，不替上层做决策。

这个态度很重要：投影函数只投影，不做策略决策。拆不拆、超了怎么办，是上层的事。单一职责，函数才好测、好维护。

● ● ●

第三步：createCompactionEntry 只追加不删除

前面都是「投影」——从现有历史里挑消息。现在讲「压缩」——怎么生成那条摘要事实。

这条事实叫 compaction entry，类型是 compaction，append 到会话树末尾。createCompactionEntry，第 379 行：

// context.ts:379-419
export function createCompactionEntry(
  activePath: readonly SessionEntry[],
  input: CreateCompactionInput,
): CompactionSessionEntry {
  // 父节点必须是 activePath 最后一条
  const parent = activePath.at(-1);
  if (!parent) {
    throw new Error("空 active path 不能创建 compaction");
  }
  // id 不能重复（append-only 的硬约束）
  if (activePath.some((entry) => entry.id === input.id)) {
    throw new Error(`session entry id 重复：${input.id}`);
  }
 
  // 重新切一遍组，确保 firstKeptEntryId 落在边界上
  const groups = groupInteractions(
    activePath.filter(
      (entry): entry is MessageSessionEntry => entry.type === "message",
    ),
  );
  // 关键约束：firstKeptEntryId 必须是某组的起点
  const firstKeptIsGroupStart = groups.some(
    (group) => group.entries[0]?.id === input.firstKeptEntryId,
  );
  if (!firstKeptIsGroupStart) {
    throw new Error(
      `firstKeptEntryId ${input.firstKeptEntryId} 必须是完整 interaction 的首条 message`,
    );
  }
 
  // 只构造对象并 parse 校验，不写 store
  const parsed = parseSessionEntry({
    id: input.id,
    parentId: parent.id,
    timestamp: input.timestamp,
    type: "compaction",
    summary: input.summary,
    firstKeptEntryId: input.firstKeptEntryId,
    tokensBefore: input.tokensBefore,
  });
  return parsed;
}
 

两个关键点：

第一，firstKeptEntryId 必须是某个 interaction 组的第一条 message。不能从一组中间开始保留——那又造出半组 interaction。这条约束和 groupInteractions 的边界规则严格对齐。

第二，看函数顶部注释（第 376 行）：「只创建一条可追加的 compaction 事实；不改历史，也不写 store」。createCompactionEntry 只返回一个对象，要不要 append、要不要落盘，由调用方决定。函数职责单一。

compaction 是追加一条新事实，不是修改旧事实。旧的那 20 条 tool call 还躺在 JSONL 里一条没少，只是多了一条说「从这里之后开始保留，之前的折叠成摘要」。

摘要长什么样？看 CompactionSummary 结构（session.ts 第 43 行）：

七个字段，结构化的项目状态快照。不是一段自由文本。compactionSummaryText 第 190 行把它格式化成中文：

● ● ●

第四步：恢复——只认最新摘要

最后一块拼图：进程重启后，怎么从 session 文件里恢复上下文？答案是只认最新摘要，从 firstKeptEntryId 投影后缀。

先找最新摘要。latestCompaction，第 213 行：

// context.ts:213-226
function latestCompaction(
  activePath: readonly SessionEntry[],
): { entry: CompactionSessionEntry; index: number } | undefined {
  // 从末尾往前扫，找到第一条 compaction 就停
  for (let index = activePath.length - 1; index >= 0; index -= 1) {
    const candidate = activePath[index];
    if (candidate?.type !== "compaction") continue;
    const parsed = parseSessionEntry(candidate);
    if (parsed.type !== "compaction") {
      throw new Error(`session entry ${candidate.id} 不是 compaction`);
    }
    return { entry: parsed, index };
  }
  return undefined;
}
 

为什么从后往前？因为可能压缩过多次。第一次压缩到第 10 轮，之后又聊到第 25 轮，再压一次到第 20 轮。恢复时只认最新那条（第 20 轮的），第 10 轮那条成了历史遗留，不参与投影。

找到摘要后切后缀。messageCandidates，第 228 行：

// context.ts:228-257
function messageCandidates(
  activePath: readonly SessionEntry[],
  compaction: { entry: CompactionSessionEntry; index: number } | undefined,
): MessageSessionEntry[] {
  let startIndex = 0;
  if (compaction) {
    // 找 firstKeptEntryId 在 activePath 里的位置
    startIndex = activePath.findIndex(
      (entry) => entry.id === compaction.entry.firstKeptEntryId,
    );
    // 校验一：必须能找到
    if (startIndex < 0 || startIndex >= compaction.index) {
      throw new Error(`compaction 的 firstKeptEntryId 不在它之前`);
    }
    // 校验二：必须是 user 消息（interaction 起点）
    const first = activePath[startIndex];
    if (first?.type !== "message" || first.message.role !== "user") {
      throw new Error(`compaction 的 firstKeptEntryId 不是 interaction 起点`);
    }
  }
  // 切后缀 + 只留 message 类型
  return activePath
    .slice(startIndex)
    .filter((entry): entry is MessageSessionEntry => entry.type === "message");
}
 

三道校验：必须能找到、必须在 compaction entry 之前、必须是 user 消息（interaction 起点）。

第三道校验又绕回来了——恢复的起点必须对齐 interaction 边界。createCompactionEntry 在写入时检查过一次，messageCandidates 在读取时再检查一次。写入和读取双向校验，防止任何路径漏掉。这是防御性编程的典型做法：哪怕有一条路径漏了，另一条还兜得住。

● ● ●

串起来：一次完整压缩的生命周期

把四步拼起来，一次压缩长这样：

1. buildContext 发现超预算（reason: trimmed）
   → 调用方决定压缩
 
2. 调用方生成 CompactionSummary（目标/已完成/决策/...）
   → 选一个 firstKeptEntryId（必须是某组起点）
 
3. createCompactionEntry 生成一条 compaction entry
   → 只造对象，不写 store
 
4. 调用方把这条 entry append 到 session
   → 旧 entry 一条没少，会话树多一个叶子
 
5. 下一次 buildContext：
   → latestCompaction 找到这条新 entry
   → messageCandidates 从 firstKeptEntryId 切后缀
   → 摘要当 fixed message + 后缀 groups 投给模型
 

全程没有删除，只有追加和投影。会话树越来越长，但模型每次拿到的上下文永远在预算内。

● ● ●

这一节学了什么

回到开头那个问题：对话越长越聪明还是越蠢。

Pi 的答案：取决于你压不压、怎么压。压得好，长对话变成结构化记忆，越聊越准；压不好，要么炸预算，要么失忆。

context.ts 420 行，四件事：

  •  interaction 配对：user 消息切组，callId 集合相等校验，一组不拆
  •  预算投影：扣固定成本 → 取候选 → 摘要当固定消息 → 从最新组往前累加
  •  compaction entry：追加一条结构化摘要事实，firstKeptEntryId 对齐 group 起点
  •  恢复策略：只认最新摘要，从 firstKeptEntryId 投影后缀，读写双向校验边界

旧 entry 一条不删，只是不再投给模型。会话树保持完整（EP08 的不变量不破），模型上下文窗口保持可控。投影是只读的、可重放的、无副作用的——同一个 activePath 配同一个预算，buildContext 永远返回同一个结果。

压缩是 append-only 的，和 git 一样。你永远不会因为压缩丢掉任何历史，最多只是暂时看不到。
