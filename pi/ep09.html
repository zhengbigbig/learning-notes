这是《动手学 Pi》系列第 9 篇。

EP08 把对话历史焊进了 JSONL 会话树——每条消息一行，换行就是 commit marker，进程重启也能接上。但有个问题一直没解决：会话越长，塞给模型的历史越胖。聊到第 30 轮，前面那堆 tool call 和 tool result 还全量喂进去，token 预算早早炸掉，模型也分不清主次。

Checkpoint 11 教的就是怎么解决这个问题——上下文压缩（context compaction）。但作者用的词不是「压缩」，是「投影」。一字之差，设计哲学全在里面：不动历史，只重建投影。

源码在 src/context.ts，420 行。这一篇一段段拆。

● ● ●

先看问题：历史该删还是该折叠

最朴素的压缩思路是「旧的删掉」。但 EP08 刚讲完——每条 entry 是一条事实，parentId 串成一棵树，换行就是 commit marker。删掉一条，后面所有 parentId 都断了，会话树塌了。

那作者的方案是什么？不删任何一条，只决定哪些投给模型。

打个比方：你的笔记本上记了 50 页会议纪要（完整历史），但开会时你只带最近 5 页 + 一张摘要卡（投影）。笔记本不动，你手上拿什么另说。context.ts 干的就是「决定手上拿哪几页 + 怎么生成摘要卡」。

这句话很关键，它会贯穿整篇：压缩不是删除，是追加一条新事实，让后续投影从这条事实之后开始。

● ● ●

第一步：把消息切成 interaction 组

课程第一个概念是「interaction 配对」。模型一次发言里可能带多个 tool call，每个 call 必须有对应的 tool result，这叫一组 interaction。切历史的粒度不是「一条消息」，是「一组 interaction」。

为什么？因为半组 interaction 是废数据。模型看到 tool call A 却看不到 tool result A，它会以为工具没执行，要么重调一遍，要么直接报错。所以切历史只能在 interaction 边界切，不能把一组劈成两半。

看源码怎么定义 interaction 边界。groupInteractions，context.ts 第 125 行：

// context.ts:125-154
export function groupInteractions(
  entries: readonly MessageSessionEntry[],
): InteractionGroup[] {
  const groups: InteractionGroup[] = [];
  let current: InteractionGroup | undefined;
 
  const finishCurrent = (): void => {
    if (!current) return;
    validateInteraction(current);
    groups.push(current);
    current = undefined;
  };
 
  for (const source of entries) {
    const entry = cloneMessageEntry(source);
    // user 消息开启一个新 group
    if (entry.message.role === "user") {
      finishCurrent();
      current = { entries: [entry] };
      continue;
    }
    if (!current) {
      throw new Error(
        message entry ${entry.id} 在第一个 user interaction 之前,
      );
    }
    current.entries.push(entry);
  }
  finishCurrent();
  return structuredClone(groups);
}
 

规则简单：遇到一条 user 消息，就结束当前 group，开一个新的。user 消息是天然的分界线——新一轮用户输入开始，意味着上一轮的 tool call/result 配对必须全部收尾。

注释里那句 在第一个 user interaction 之前 也要注意。如果第一条消息不是 user（比如文件损坏，开头是个孤立的 assistant），直接抛错。不允许没有起点的 interaction 存在。

● ● ●

validateInteraction：按 callId 集合相等校验

光切 group 还不够，还要检查每组 group 内部的 tool call 和 tool result 是不是严格配对。这是 validateInteraction，context.ts 第 79 行：

// context.ts:79-119
function validateInteraction(group: InteractionGroup): void {
  const calls = new Map<string, string>();
  const results = new Map<string, string>();
 
  for (const entry of group.entries) {
    // 收集所有 tool call 的 id
    for (const call of callsIn(entry)) {
      const previous = calls.get(call.id);
      if (previous) {
        throw new Error(
          interaction 中 tool call ${call.id} 重复：${previous} 与 ${entry.id},
        );
      }
      calls.set(call.id, entry.id);
    }
    // 收集所有 tool result 的 callId
    if (entry.message.role === "toolResult") {
      const callId = entry.message.toolCallId;
      const previous = results.get(callId);
      if (previous) {
        throw new Error(
          interaction 中 tool result ${callId} 重复：${previous} 与 ${entry.id},
        );
      }
      results.set(callId, entry.id);
    }
  }
  // result 必须有对应的 call
  for (const [callId, resultEntryId] of results) {
    if (!calls.has(callId)) {
      throw new Error(
        tool result ${resultEntryId} 引用了不存在的 call ${callId},
      );
    }
  }
  // call 必须有对应的 result
  for (const [callId, callEntryId] of calls) {
    if (!results.has(callId)) {
      throw new Error(
        tool call ${callId}（entry ${callEntryId}）缺少 result,
      );
    }
  }
}
 

两个 Map，一个记 call，一个记 result，最后做集合相等校验。三道检查：

  •  call 的 id 不能重复（同一个 callId 出现两次 → 抛错）
  •  result 引用的 callId 必须存在（result 找不到 call → 抛错）
  •  call 必须有对应的 result（call 找不到 result → 抛错）

注意它用的是 Map 不是数组遍历两两比对。Map 是 O(1) 查找，数组两两比是 O(n²)。当 interaction 里塞了 20 个并发 tool call 时，这个选择直接决定校验快不快。

还有个细节：它不依赖 result 在数组里紧跟在 call 后面。两个并发工具调用的完成顺序可能是反的——call A、call B 发出去，result B 先回，result A 后回。按 callId 配对，不依赖相邻位置。这是为了支持并发工具调用（EP05 讲过的 Promise.all 并发配对）。

第二步：预算投影 buildContext

切完 group，核心来了——预算投影。课程叫 buildContext，它要做的事用一句话讲：在固定的 token 预算内，从最新 group 往前挑，挑满为止，挑不下的整组丢掉。

看接口先，context.ts 第 42 行：

// context.ts:42-48
export interface BuildContextResult {
  systemPrompt?: string;
  messages: AgentMessage[];
  keptEntryIds: string[];
  reason: ContextBuildReason;
  tokens: ContextTokenProjection;
}
 

keptEntryIds 是保留的 entry id 列表，reason 是为什么保留这么多（三种：预算内 / 被裁剪 / 最新一组就超限）。tokens 是一份预算账本，每个字段多少 token 清清楚楚。

ContextBuildReason 三种值，context.ts 第 27 行：

// context.ts:27-30
export type ContextBuildReason =
  | "within_budget"     // 全放得下，没裁
  | "trimmed"           // 从前面裁了几组
  | "single_group_overflow"; // 最新一组单独就超限
 

第三种是重点。稍后讲。

看 buildContext 主体，分四步。第一步扣固定成本，context.ts 第 263 行：

// context.ts:263-285（节选）
export function buildContext(
  activePath: readonly SessionEntry[],
  options: BuildContextOptions,
): BuildContextResult {
  const maxTokens = nonNegativeFinite(options.maxTokens, "maxTokens");
  const reservedOutput = nonNegativeFinite(options.reservedOutput, "reservedOutput");
  const safetyMargin = nonNegativeFinite(options.safetyMargin, "safetyMargin");
  const system = options.systemPrompt === undefined
    ? 0
    : estimatedTokens(options, options.systemPrompt, "systemPrompt");
  // 先扣 system、输出预留、安全余量
  const availableForMessages = Math.max(
    0,
    maxTokens - system - reservedOutput - safetyMargin,
  );
 

固定成本先扣，剩下的才是消息预算。system prompt、输出预留（给模型回答留的额度）、安全余量（防估算误差），这三块先从总预算里减掉。Math.max(0, ...) 兜底——如果 system prompt 自己就超了总预算，消息预算就是 0，不会变成负数。

第二步，取候选消息。先看有没有压缩摘要，context.ts 第 287 行：

  const compaction = latestCompaction(activePath);
  const groups = groupInteractions(
    messageCandidates(activePath, compaction),
  );
 

latestCompaction 从 activePath 末尾往前扫，找最新一条 compaction entry。messageCandidates 从这条 compaction 的 firstKeptEntryId 开始往后切。摘要之后的消息才进候选池，摘要之前的不投给模型。这段稍后细讲。

第三步，如果有摘要，把摘要当成固定消息，context.ts 第 301 行：

  const fixedMessages = compaction
    ? [summaryMessage(compaction.entry)]
    : [];
  const fixedCost = fixedMessages.reduce(
    (total, message, index) =>
      total + estimatedTokens(options, message, compaction summary ${index + 1}),
    0,
  );
  const groupBudget = Math.max(0, availableForMessages - fixedCost);
 

摘要本身也占预算。摘要不是免费的，它有自己的 token 成本。所以 group 预算等于「消息总预算 减 摘要成本」。如果摘要自己就很长，group 能放的 interaction 就少。

第四步，从最新 group 往前累加，context.ts 第 315 行：

  const groupCosts = groups.map((group, groupIndex) =>
    group.entries.reduce(
      (total, entry, entryIndex) =>
        total + estimatedTokens(options, entry.message,
          interaction ${groupIndex + 1} message ${entryIndex + 1}),
      0,
    )
  );
 
  let firstSelected = groups.length;
  let selectedGroupCost = 0;
  let reason: ContextBuildReason = "within_budget";
  if (groups.length > 0) {
    const latestIndex = groups.length - 1;
    firstSelected = latestIndex;
    selectedGroupCost = groupCosts[latestIndex] ?? 0;
    // 最新一组单独就超限
    if (selectedGroupCost > groupBudget) {
      reason = "single_group_overflow";
    } else {
      // 从倒数第二组往前加，加不下就停
      for (let index = latestIndex - 1; index >= 0; index -= 1) {
        const candidateCost = groupCosts[index] ?? 0;
        if (selectedGroupCost + candidateCost > groupBudget) {
          reason = "trimmed";
          break;
        }
        selectedGroupCost += candidateCost;
        firstSelected = index;
      }
      if (firstSelected > 0) reason = "trimmed";
    }
  }
 

逻辑很清晰：

  •  先放最新一组（最新对话最重要，必须留）
  •  从倒数第二组往前试，加得下就加，加不下就停
  •  全放得下是 within_budget，裁了前面的是 trimmed
  •  reason 标成 single_group_overflow，表示最新一组单独超限，不拆，整组塞进去并报告溢出

● ● ●

为什么 single_group_overflow 不拆

这是整个设计最反直觉的一步。最新一组 interaction 超了预算，按常理应该把它拆开，放前面一半进去。但作者偏不。

原因回到前面讲的——一组 interaction 是一组工具契约，拆开就是半组废数据。模型看到 tool call 却看不到 result，等于让模型基于「工具调用了但不知道结果」做判断，比没有还糟。

所以作者的选择是：整组塞进去，并在 reason 里标 single_group_overflow。调用方拿到这个 reason，知道这次请求可能超预算，自己决定怎么办（报错 / 换大模型 / 让模型自己精简）。context.ts 不替调用方做决定，只如实报告。

这个设计态度很重要：投影函数只投影，不做策略决策。拆不拆、超了怎么办，是上层的事。

● ● ●

第三步：createCompactionEntry 只追加不删除

前面讲的都是「投影」——怎么从现有历史里挑消息。现在讲「压缩」——怎么生成那条摘要事实。

课程叫 compaction entry。它是一条新的 session entry，类型是 compaction，追加到会话树末尾。看 createCompactionEntry，context.ts 第 379 行：

// context.ts:379-419
export function createCompactionEntry(
  activePath: readonly SessionEntry[],
  input: CreateCompactionInput,
): CompactionSessionEntry {
  const parent = activePath.at(-1);
  if (!parent) {
    throw new Error("空 active path 不能创建 compaction");
  }
  if (activePath.some((entry) => entry.id === input.id)) {
    throw new Error(session entry id 重复：${input.id});
  }
 
  const groups = groupInteractions(
    activePath.filter(
      (entry): entry is MessageSessionEntry => entry.type === "message",
    ),
  );
  // firstKeptEntryId 必须是某个 group 的起点
  const firstKeptIsGroupStart = groups.some(
    (group) => group.entries[0]?.id === input.firstKeptEntryId,
  );
  if (!firstKeptIsGroupStart) {
    throw new Error(
      firstKeptEntryId ${input.firstKeptEntryId} 必须是完整 interaction 的首条 message,
    );
  }
 
  const parsed = parseSessionEntry({
    id: input.id,
    parentId: parent.id,
    timestamp: input.timestamp,
    type: "compaction",
    summary: input.summary,
    firstKeptEntryId: input.firstKeptEntryId,
    tokensBefore: input.tokensBefore,
  });
  return parsed;
}
 

两个关键检查：

第一，firstKeptEntryId 必须是某个 interaction group 的第一条 message。不能从一组的中间开始保留——那又会制造半组 interaction。这条约束和 groupInteractions 的边界规则是对齐的。

第二，这条函数只创建 entry，不写 store。看源码顶部那句注释（第 376 行）：只创建一条可追加的 compaction 事实；不改历史，也不写 store。createCompactionEntry 返回一个 CompactionSessionEntry 对象，至于要不要 append 到 session、要不要落盘，由调用方决定。

compaction 是追加一条新事实，不是修改旧事实。旧的那 20 条 tool call 还躺在 JSONL 里一条没少，只是多了一条 compaction entry 说「从这里之后开始保留，之前的折叠成摘要了」。

摘要长什么样？看 CompactionSummary 结构，session.ts 第 43 行：

// session.ts:43-51
export interface CompactionSummary {
  goal: string;          // 目标
  constraints: string[]; // 约束
  completed: string[];   // 已完成
  decisions: string[];   // 决策
  changedFiles: string[];// 改了哪些文件
  unresolved: string[];  // 没解决的
  next: string[];        // 下一步
}
 

七个字段，结构化的项目状态快照。context.ts 第 190 行的 compactionSummaryText 把它格式化成一段中文文本，塞进一条 user message 喂给模型：

// context.ts:190-201（节选）
function compactionSummaryText(summary: CompactionSummary): string {
  return [
    "【会话压缩摘要】",
    目标：${summary.goal},
    ...summaryLines("约束", summary.constraints),
    ...summaryLines("已完成", summary.completed),
    ...summaryLines("决策", summary.decisions),
    ...summaryLines("变更文件", summary.changedFiles),
    ...summaryLines("未解决", summary.unresolved),
    ...summaryLines("下一步", summary.next),
  ].join("\n");
}
 

摘要不是自由文本，是结构化字段的格式化拼接。这样模型拿到的不是「我们之前聊了好多东西」这种废话，而是「目标 X，已完成 A/B/C，改了文件 D，没解决 E」这种可操作的状态。

● ● ●

第四步：恢复——latestCompaction + messageCandidates

最后一块拼图：进程重启后，怎么从 session 里恢复上下文？答案是只认最新摘要，从 firstKeptEntryId 投影后缀。

先找最新摘要。latestCompaction，context.ts 第 213 行：

// context.ts:213-226
function latestCompaction(
  activePath: readonly SessionEntry[],
): { entry: CompactionSessionEntry; index: number } | undefined {
  // 从末尾往前扫，找到第一条 compaction
  for (let index = activePath.length - 1; index >= 0; index -= 1) {
    const candidate = activePath[index];
    if (candidate?.type !== "compaction") continue;
    const parsed = parseSessionEntry(candidate);
    if (parsed.type !== "compaction") {
      throw new Error(session entry ${candidate.id} 不是 compaction);
    }
    return { entry: parsed, index };
  }
  return undefined;
}
 

从后往前扫，找到第一条 compaction 就停。为什么从后往前？因为可能有多次压缩。第一次压缩到第 10 轮，之后又聊到第 25 轮，再压缩一次到第 20 轮。恢复时只认最新的那条（第 20 轮的），之前那条（第 10 轮的）就成了历史遗留，不参与投影。

找到摘要后，从 firstKeptEntryId 切后缀。messageCandidates，context.ts 第 228 行：

// context.ts:228-257
function messageCandidates(
  activePath: readonly SessionEntry[],
  compaction: { entry: CompactionSessionEntry; index: number } | undefined,
): MessageSessionEntry[] {
  let startIndex = 0;
  if (compaction) {
    startIndex = activePath.findIndex(
      (entry) => entry.id === compaction.entry.firstKeptEntryId,
    );
    if (startIndex < 0 || startIndex >= compaction.index) {
      throw new Error(
        compaction 的 firstKeptEntryId 不在它之前,
      );
    }
    // firstKeptEntryId 必须是 user 消息（interaction 起点）
    const first = activePath[startIndex];
    if (first?.type !== "message" || first.message.role !== "user") {
      throw new Error(
        compaction 的 firstKeptEntryId 不是 interaction 起点,
      );
    }
  }
  return activePath
    .slice(startIndex)
    .filter((entry): entry is MessageSessionEntry => entry.type === "message");
}
 

三道校验：

  •  firstKeptEntryId 必须能在 activePath 里找到（找不到 → 抛错）
  •  它必须在 compaction entry 之前（startIndex < compaction.index，否则逻辑矛盾 → 抛错）
  •  它必须是 user 消息（interaction 起点），不能是 assistant 或 toolResult

第三道校验又绕回来了——恢复的起点必须对齐 interaction 边界。从一组的中间开始恢复，照样会制造半组 interaction。createCompactionEntry 在写入时检查过一次，messageCandidates 在读取时再检查一次。写入和读取双向校验，防止任何路径漏掉。

● ● ●

串起来：一次完整压缩的生命周期

把四步拼起来，一次完整的上下文压缩长这样：

1. buildContext 发现 token 超预算（reason: trimmed）
   → 调用方决定压缩
 
2. 调用方生成 CompactionSummary（目标/已完成/决策/...）
   → 选一个 firstKeptEntryId（必须是某 group 起点）
 
3. createCompactionEntry 生成一条 compaction entry
   → 只创建对象，不写 store
 
4. 调用方把这条 entry append 到 session
   → 旧 entry 一条没少，会话树多了一个叶子
 
5. 下一次 buildContext：
   → latestCompaction 找到这条新 entry
   → messageCandidates 从 firstKeptEntryId 切后缀
   → 摘要作为 fixed message + 后缀 groups 投给模型
 

全程没有删除，只有追加和投影。会话树越来越长，但模型每次拿到的上下文永远在预算内。

● ● ●

这一节学了什么

课程 Checkpoint 11 的核心思想就一句话：不动历史，只重建投影。

context.ts 420 行，四件事：

  •  interaction 配对：user 消息切组，callId 集合相等校验，一组不拆
  •  预算投影：扣固定成本 → 取候选 → 摘要当固定消息 → 从最新 group 往前累加
  •  compaction entry：追加一条结构化摘要事实，firstKeptEntryId 对齐 group 起点
  •  恢复策略：只认最新摘要，从 firstKeptEntryId 投影后缀，双向校验边界

旧 entry 一条不删，只是不再投给模型。会话树保持完整（EP08 的不变量不破），模型的上下文窗口保持可控。投影是只读的、可重放的、无副作用的——同一个 activePath 配同一个预算，buildContext 永远返回同一个结果。

压缩是 append-only 的，和 git 一样。你永远不会因为压缩丢掉任何历史，最多只是暂时看不到。
