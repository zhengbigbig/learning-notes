上一篇我们把 Multica 的组织方案定了：队长分诊、spec 工程师澄清、领域矩阵执行、QA 收口。方案写得再好，没在真实项目上跑一遍都算数 。

所以这篇直接上真家伙：我自己的小程序项目（记账 + 物品管理，uni-app 前端 + Django 后端，在营产品），真实需求——「3D 空间功能继续完善：房间里物品多了，用户想知道每个房间值多少钱、哪些房间最值钱」。8 个 agent 组队接单，从需求进来到我验收，全程实录，包括一次真实事故。

8 人编制就位

● ● ●

需求进来了：队长的第一反应

我故意只给了一句话需求，不说分支、不说技术方案：「房间里物品多了，用户想知道每个房间值多少钱、哪些房间最值钱，在现有 3D 空间页上实现」。

队长的分诊：类型=需求；域=小程序前端 + 后端 space 域；复杂度=涉及后端接口 → 复杂需求，路由给 spec 工程师。然后它自己搭好了执行结构——四张卡、三个阶段：

QUAN-17（父）房间价值可视化
├── QUAN-18  Stage 1 [spec 工程师] 执行 spec
├── QUAN-19  Stage 2 [BE-小程序]  房间价值聚合接口
├── QUAN-20  Stage 2 [FE-小程序]  3D 页价值可视化
└── QUAN-21  Stage 3 [QA]         回归·联调·审查
 

分诊没有问过我一个问题：域靠代码结构定，复杂度靠「是否涉及后端」一条规则定，阶段靠依赖关系排。这符合我们的设计原则：能推断的自己定，打扰是有成本的。

● ● ●

spec 工程师：254 行零歧义施工图

spec 产出来第一眼就发现它真读了代码。三个细节：

一是目标页面定位准确。项目里有两个 3D 页（three.vue 和 three3d.vue），它确认了本轮改的是 three3d.vue——并把 three.vue 明确写进「非目标」。二是「零迁移」有论证：需要的字段（Item.amount、家具-房间-户型的外键链）全部现成，逐条列出模型行号，结论是聚合查询用 Django 的 Count/Sum 注解就能做，不动表结构。三是给出了并行开发的契约：新增 GET /floorplans/{id}/room-values/，响应 JSON 完整示例、错误码表、家庭隔离的鉴权口径，前后端各改哪些文件到文件级，还标了「urls.py 不用改，DefaultRouter 自动注册」。

到了我的人工节点。我的审查结论：目标页面定位正确、零迁移论证充分、接口方向对——批准放行，Stage 2/3 继续，合并前 diff 我终审。这就是「异议制人工节点」：不拦着流程，但审查留痕，出问题能追到我这次确认上。

人工节点：批准执行 spec

● ● ●

真实事故：它们直接推了主干

Stage 2 并行跑完，两笔提交出现的时候我愣了一下——提交直接落在了主仓库的 main 分支上，而且已经推送。

根因链很清楚：我在需求描述里只给了主仓库的路径，没有提为实现准备的 worktree 和分支；spec 工程师把所有锚点核实在主仓库上；实现 agent 顺着锚点在 main 上提交、推送。我们上一篇设计的分支规范（worktree、一卡一分支）一条都没触发——不是规范错了，是规范没有硬编码进队长的指令，它遇到「需求给了仓库路径」时，按最短路径走了。

处置我选了保留：两笔提交干净且严格限定在 spec 划定的范围内（前端 +364/-3，后端接口 + 单测），实现的就是要上的功能，产品未发版无用户影响。但流程修复立刻生效：队长指令补两条硬规则——派单前必须检查在途 worktree 与未合并分支，优先使用；没有「人类已确认」标记，禁止直接推送主干。

这次事故让我对「多 agent 团队」的理解落地了一层：你给 agent 的每一句模糊表述，它都会用自己的方式补全。人类团队里一句「仓库在那边」能靠默契消化，agent 团队里同样的句子就是一条直推主干的指令。

● ● ●

QA：换模型审出 29/29 和 27/27

QA 的验证报告是我见过最扎实的一份。独立克隆仓库（不碰原工作区），三件事：

独立复跑：manage.py check 零问题；makemigrations --check 确认零迁移；items 应用单测 10/10 通过；全仓 60 个测试有 30 个失败——它没有忽略，而是和父提交的基线失败集合逐一比对，确认全部既有、与本次交付无关。

接口回归 29/29：正常聚合、状态过滤、跨家庭 404、未认证 401、空户型不缺席、并列排名、金额边界降序、他人 family_id 防越权、方法限制 405，外加性能实测——10 次平均 1.7ms（门槛 100ms）。

前后端 E2E 27/27：真实起后端、真实浏览器驱动 3D 页，按 spec 用例逐条走。还主动声明了边界：原仓库工作区那 3 个未提交文件（我自己改到一半的代码）未触碰、未纳入审查，QA 全程没写生产库。QA 的边界感，来自它指令里写死的规则。

● ● ●

QA 升级：五道门验收 + 截图证据

第一轮验收通过后，我把 QA 的职责从「接口回归 + 联调」升级成了五道门验收流水线，写进它的指令：

门1 代码质量：换模型逐文件审 diff（边界/错误处理/安全/约定）
门2 需求匹配度：对照执行 spec 逐条核验覆盖率与越圈
门3 自动化测试：单测 + 接口回归 + 前后端联调真实跑通
门4 UI 自动化与样式还原：关键状态截图，四态齐全
门5 UI 逻辑：按交互流程逐条走查，含失败恢复
 

任一门不过即打回：报告分级列问题清单，@实现 agent 修复，修完重走全部门（不跳门）。截图是必须交付物，不是可选项——验收完自动以附件贴回任务卡，人验收时直接看图。

对这次价值可视化的交付实测跑了一遍：门 4 产出四态加关键状态共 9 张截图（正常态/旋转跟随/房间筛选/金额边界/全零引导/空态/错误恢复），UI 自动化断言 28/28 通过；门 5 把交互流程 U1-U10 全部走查（含标签层手势穿透实测）。

这次验证了什么

  1. 01分诊决策表可用：一句话需求进，队长自动定类型/域/复杂度并搭出三阶段结构，全程零提问
  2. 02执行 spec 是并行开发的胜负手：254 行 spec 让前后端并行零冲突，契约先行值回成本
  3. 03运行时矩阵成立：claude 与 dsh 两种 harness 在同一看板混编，领域 agent 绑定不同运行时
  4. 04分支纪律必须硬编码：规范写在文档里没用，写进队长指令才算数——这是本次事故最贵的教训，也是最有价值的产出
  5. 05QA 换模型审 + 基线比对，把「测试通过」从一句口号变成了可核验的结论

下一步有两件：一是把分诊路由接入真实需求入口（微信 bot / 定时巡检），让流水线从「我手动投喂」变成「需求自己进门」；二是给这条流水线配一个浏览器插件控制台——建任务、查进度、按需求聚合 PR 与分支，最后一步「人工核验」时点一下「切分支起服务调试」，agent 按项目配置（vite、umi 各自的启动方式）把服务拉起来，我直接在浏览器里点。
