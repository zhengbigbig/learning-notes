Multica 是什么

一个 Apache 2.0 开源项目（github.com/multica-ai/multica），定位是「人 + AI 编码 agent 混合团队的工作区」。核心模型一句话：工作区里有 agent 和人两类成员，任务就是 issue，指派给 agent 就会触发一次运行，agent 在你自己的电脑上干活，做完把任务挪到审核中，人验收。支持 26 种编码 CLI（Claude Code、Cursor、Codex、Kimi、OpenCode……），可完全自托管。

我把它的源码拆了一遍，又把自己的在营小程序投进去跑了一条真实流水线。这篇把两件事一次讲完：源码怎么实现，真机跑起来到底靠不靠谱——包括一次真实事故。

● ● ●

它给 agent 什么「员工待遇」

拆实现之前，先把功能盘清楚。Multica 里每个 agent 都是一等公民，有自己的档案和状态机，不是一句 prompt 就打发的玩具：

能力是什么源码位置
Agent 档案五态状态机 idle/working/blocked/error/offline，可设最大并行任务数migrations/001
Issue 看板七种状态 + 指派对象可以是人类、agent 或小队migrations/001、084
收件箱分三级：需要人拍板 / 需要关注 / 仅告知migrations/001
Squad 编队队长必须是 agent，队员人机混编migrations/084
Autopilotcron/webhook 定时触发 agent，可自动建 issue 或只执行migrations/042
Skills 技能包把经验沉淀成可复用技能，绑定给指定 agentmigrations/008
用量统计每个任务、每小时、每天的 token 消耗都能归因migrations/013、032

这套数据模型里最认可的是收件箱的三级分级——agent 的多数输出是「仅告知」，少数是「需要关注」，只有真正需要人拍板的才标「需要人拍板」。通知系统的最大痛点从来不是发不出，是不分轻重地全发。

● ● ●

最反直觉的设计：服务器上不跑一个 Agent

听到「Agent 平台」，多数人第一反应是：云端养了一堆容器，替用户跑着 agent。

Multica 正好反着来。它的服务器不执行任何 agent，所有 agent 都跑在用户自己的电脑上。

架构长这样：

你（浏览器）
   │ 建任务板 / 派 issue / 写评论
   ▼
Multica 服务端（只存状态和内容，不跑 agent）
   │ WebSocket 唤醒 + HTTP 认领
   ▼
你电脑上的 daemon（常驻后台进程）
   │ spawn 子进程
   ▼
Claude Code / Cursor / …… 26 种编码 CLI
   │ 用 multica CLI 回读写
   ▼
Multica 服务端（issue 状态、评论、PR 关联）
 

为什么这么设计？第一，代码不出境——项目源码永远在本机，服务器上只流过 issue 标题、评论和状态这些「协作元数据」。第二，不锁供应商——换模型等于在界面上换个下拉框。第三，agent 和人是对称的——这条最妙，下一节单独讲。

● ● ●

Agent 拿到的不是任务内容，是「自己去看任务的工具」

看它给 agent 组装的任务指令，来自 server/internal/daemon/prompt.go:215：

b.WriteString("You are running as a local coding agent for a Multica workspace.\n\n")
fmt.Fprintf(&b, "Your assigned issue ID is: %s\n\n", task.IssueID)
// 交付规则：活干完送待验收就行，done 永远留给人
fmt.Fprintf(&b, "Start by running `multica issue get %s --output json` to understand your task, then complete it.\n", task.IssueID)
 

注意一个细节：它没有把 issue 标题、描述、验收标准塞进 prompt，只给了一个 ID 和一句「你自己跑 multica issue get 去看」。

agent 干活用的 multica 命令行，和你浏览器里点鼠标，走的是同一套平台接口，凭证是任务作用域的 token（internal/daemon/daemon.go:163），这个 agent 只能读写自己这条 issue，想越权碰别人的任务，接口层直接挡住。

认领接口的响应也不是一个任务 ID，而是一整个任务的执行现场（internal/daemon/types.go:70）：工作区提示词、agent 人设、绑定仓库、技能包哈希、续接会话指针、预计算好的增量评论。daemon 拿到任务的那一刻，不需要再发第二次请求。多台机器抢同一个任务，服务端用一段 Redis Lua 脚本把「出队」和「标记运行中」焊死成原子操作。

● ● ●

26 个 CLI，收敛成一个接口

市面上的编码 CLI 每家一个性格：Claude Code 输出 stream-json，Cursor 类似，还有一批走 Zed 的 ACP 协议。Multica 的 pkg/agent 包用一个接口把它们全收了。工程细节里全是真实事故的痕迹：

  •  进程管理强制进程组所有权，取消时对整组 SIGKILL（pkg/agent/launch.go:112）——不这样，Windows 上一个被「取消」的 agent 实际又偷偷干了 40 分钟活
  •  协议关键 flag 有黑名单，用户自定义参数不能覆盖上报通道（launch.go:445）
  •  Claude Code 内置的交互提问工具被启动参数直接禁用（官方 issue #2588）——无人值守场景下，「问人」必须变成「留话」

● ● ●

平台的另外三道底座

Runtime Brief：agent 每次领任务，daemon 先在工作目录写一份 CLAUDE.md/AGENTS.md（工作区背景、命令手册、交付流程），用标记对包住——重写幂等、清除精确，且同会话多次任务间逐字节一致，因为差一个字节 prompt cache 全失效（源码标注 MUL-5377）。

交付比派活讲究：完成上报先做 NUL 消毒（真实 issue #7098：一个 \u0000 让任务永远卡 running）；幂等条件更新防重放；「假成功」（上下文耗尽没交付）重路由成失败；真失败先归因再自动生成子任务重试。

记忆是显式的：会话续接、工作区提示词、issue 评论增量下发、Skills 四层，全部用户可见。最意外的是它主动写配置关掉 Codex 的原生 auto-memory（codex_memory.go:11）——那套记忆是黑盒且会跨项目泄漏。

防跑飞靠显式规则：issue_trigger.go:97 的 WillEnqueueRun 是全项目唯一发车判定（backlog 不发车）；每个 run 强制解析责任人；小队队长的协议里有个 no_action——leader 评估后觉得不需要动就静默退出，防止 agent 互相 @ 刷屏。

● ● ●

真机实战：8 个 Agent 组队

源码拆完了，真机验证开始。我组建了一支 8 人编制的团队：队长（glm-5.3，分诊/排程/守闸门）、spec 工程师（glm-5.3，复杂需求澄清）、FE-小程序（glm-5.3）、FE-运维后台（flash）、BE-运维后台（flash）、BE-小程序（绑在 dsh 运行时上）、QA（flash，但代码审查保持与实现者不同模型）、运维（flash，发版硬规则：无「人类已确认」标记拒绝执行）。

通过 runtime profile create 把 dsh 注册成了第三套运行时——同一张看板，claude 和 dsh 两种 harness 混编。

8 人编制就位

然后把我自己的在营小程序投进去：真实需求——「3D 空间功能继续完善：房间里物品多了，用户想知道每个房间值多少钱、哪些房间最值钱」。

● ● ●

需求进来：队长分诊零提问

我故意只给了一句话需求，不说分支、不说技术方案。队长的分诊：类型=需求；域=小程序前端 + 后端 space 域；复杂度=涉及后端接口 → 复杂需求，路由给 spec 工程师。然后它自己搭好了执行结构——四张卡、三个阶段：

QUAN-17（父）房间价值可视化
├── QUAN-18  Stage 1 [spec 工程师] 执行 spec
├── QUAN-19  Stage 2 [BE-小程序]  房间价值聚合接口
├── QUAN-20  Stage 2 [FE-小程序]  3D 页价值可视化
└── QUAN-21  Stage 3 [QA]         回归·联调·审查
 

分诊没有问过我一个问题：域靠代码结构定，复杂度靠「是否涉及后端」一条规则定，阶段靠依赖关系排。

● ● ●

spec 工程师：254 行零歧义施工图

spec 产出来第一眼就发现它真读了代码。三个细节：目标页面定位准确（项目里有两个 3D 页，它确认了本轮改 three3d.vue，并把另一个明确写进「非目标」）；「零迁移」有论证（需要的字段全部现成，逐条列出模型行号）；给出了并行开发的契约（响应 JSON 完整示例、错误码表、前后端各改哪些文件到文件级）。

到了我的人工节点。我的审查结论：目标页面定位正确、零迁移论证充分、接口方向对——批准放行，Stage 2/3 继续，合并前 diff 我终审。这就是「异议制人工节点」：不拦着流程，但审查留痕。

人工节点：批准执行 spec

● ● ●

QA 五道门 + 截图证据

QA 的职责是五道门验收流水线：代码质量（换模型逐文件审 diff）→ 需求匹配度（对照 spec 逐条核验）→ 自动化测试（单测+回归+联调真实跑通）→ UI 自动化与样式还原（关键状态截图）→ UI 逻辑（交互流程走查）。任一门不过即打回，修完重走全部门。

对这次交付的实测：接口回归 29/29（含跨家庭 404、防越权、金额边界）、前后端 E2E 27/27、聚合接口平均 1.7ms。门 4 产出四态加关键状态共 9 张截图，UI 自动化断言 28/28。

● ● ●

真实事故：它们直接推了主干

Stage 2 并行跑完，两笔提交出现的时候我愣了一下——提交直接落在了主仓库的 main 分支上，而且已经推送。

根因链很清楚：我在需求描述里只给了主仓库的路径，没有提为实现准备的 worktree 和分支；spec 工程师把所有锚点核实在主仓库上；实现 agent 顺着锚点在 main 上提交、推送。分支规范（worktree、一卡一分支）一条都没触发——不是规范错了，是规范没有硬编码进队长的指令。

处置我选了保留：两笔提交干净且严格限定在 spec 划定范围内，实现的就是要上的功能，产品未发版无用户影响。但流程修复立刻生效：队长指令补两条硬规则——派单前必须检查在途 worktree 与未合并分支，优先使用；没有「人类已确认」标记，禁止直接推送主干。

这次事故让我对「多 agent 团队」的理解落地了一层：你给 agent 的每一句模糊表述，它都会用自己的方式补全。人类团队里一句「仓库在那边」能靠默契消化，agent 团队里同样的句子就是一条直推主干的指令。

● ● ●

打回之后：三轮修复回归

五道门跑通只是验收体系的一半，另一半是它真的敢打回。角标+搜索定位那条线的交付就被打回过：QA 报告列出 2 个阻断——后端搜索接口缺 floor_plan_id 过滤、前端搜索没传这个参数，导致「搜索→定位到房间」走不通。

修复分了三笔提交，每笔只做一件事：

33c72bc  后端：GET /items/ 支持 floor_plan_id 过滤（QUAN-23）
401108c  前端：搜索请求补传 floor_plan_id + 空值守卫（QUAN-24）
8e0d094  后端：keyword 过滤 + 序列化三字段 + limit 切片（QUAN-26）
 

每笔提交 QA 都独立复验：单测 15/15、curl 实测 13 例（含跨家庭防越权、空集、limit 边界）、与基线失败集合比对。三轮回归之后，验收标准 3 从「未达成」翻成「达成」——打回不是否定，是流水线的正常齿轮。

● ● ●

结论：验证了什么

  1. 01架构判断成立：服务器不跑 agent，代码不出境，模型供应商自由——真机实测连失败原因都是我本机的密钥问题
  2. 02执行 spec 是并行开发的胜负手：254 行 spec 让前后端并行零冲突，契约先行值回成本
  3. 03分支纪律必须硬编码：规范写在文档里没用，写进队长指令才算数——这是本次事故最贵的教训
  4. 04QA 换模型审 + 基线比对，把「测试通过」从一句口号变成了可核验的结论
  5. 05验收权永远在人：全流程只等人最后点头

下一步：把分诊路由接入真实需求入口（微信 bot / 定时巡检），让流水线从「我手动投喂」变成「需求自己进门」；再配一个浏览器插件控制台——建任务、查进度、按需求聚合 PR 与分支，人工核验时点一下「切分支起服务调试」。
