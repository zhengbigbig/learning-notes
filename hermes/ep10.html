大家好我是郑同学。桌面篇九集完结，接下来几篇衍生篇拆专题。第一篇拆 skill 自沉淀——这个系列里反复出现过「存成 skill」「patch skill」的动作，这次从源码看清它到底怎么运转，顺带回答一个实际问题：这套机制和 OpenClaw 的比，token 花得更多吗。

先说沉淀指什么：任务做完，把可复用的做法写成一份 SKILL.md 存进 ~/.hermes/skills/，下个会话自动出现在技能索引里，模型按需加载。经验从「聊过就忘」变成「写在盘上、随时可查」。

● ● ●

一、沉淀怎么触发：不是用户喊，是系统提示一直在喊

打开 agent/prompt_builder.py:175，有一段所有会话都会注入的固定指令：

SKILLS_GUIDANCE = (
    "After completing a complex task (5+ tool calls), fixing a tricky error, "
    "or discovering a non-trivial workflow, save the approach as a "
    "skill with skill_manage so you can reuse it next time.\n"
    "When using a skill and finding it outdated, incomplete, or wrong, "
    "patch it immediately with skill_manage(action='patch') — don't wait to be asked. "
    "Skills that aren't maintained become liabilities."
)
 

翻译过来三条：复杂任务做完（5 次以上工具调用）、修好一个难缠的 bug、发现一套非显然的工作流——就该沉淀。反向也有指令：用到某个 skill 发现它过时、残缺、写错，立刻 patch，不用等用户开口。

这段指令每轮请求都在系统提示里。也就是说沉淀不是用户想起来才喊一声，而是 harness 时刻在模型耳边念：做完值得记的事就写下来，发现旧账有问题就修。触发时机是模型自己判断的，判断标准（5+ 工具调用）写在指令里。

写盘的动作由 skill_manage 工具执行（tools/skill_manager_tool.py:1303）：create 全量写入、patch 精确替换、absorbed_into 记录合并去向。写入位置 ~/.hermes/skills/<分类>/<名字>/SKILL.md，frontmatter 里带 name/description，正文是方法步骤。

● ● ●

二、下个会话怎么想起来：索引进提示，全文按需载

沉淀的价值在复用。复用链路分两层。

第一层，索引。每次会话构建系统提示时，build_skills_system_prompt（agent/prompt_builder.py:1417）扫描全部 SKILL.md 的 frontmatter，把名字和描述压成一份清单注入：

  social-media:
    - claude-code-tutorial-series: 系列化技术内容创作与双平台发布…
    - wechat-publisher: 将本地 Markdown 文章发布到微信公众号草稿箱…
 

我本机现在有 92 个 skill，这份索引实测 11178 字符，约 2800 token，每轮请求都会带上。注意索引只放名字加描述，不放正文。还有两级缓存：进程内 LRU 字典加速重复构建，磁盘快照（.skills_prompt_snapshot.json）按 mtime/大小校验，重启进程也不用重扫。

第二层，加载。模型在索引里看到可能相关的技能，调 skill_view(name)（tools/skills_tool.py:864）拿全文，这才把方法步骤读进上下文。没用到就不读，92 个 skill 的正文不占一个字。skill_view 还带渐进披露：返回里有个 linked_files 字段，列出 references/templates/scripts 子文件，正文需要的才二次取。

所以「沉淀」的完整闭环是四步：系统提示触发写入 → skill_manage 写 SKILL.md 到盘 → 下次会话索引自动收录 → skill_view 按需载入全文。经验以文件形式存在磁盘上，不靠上下文硬记。

顺带一提防膨胀机制：系统提示的技能段还带 focus mode——写代码时非编码类目会被降级成「只留名字」的一行，描述全省，但任何技能都还能用 skill_view 加载。索引永远完整可见，只是描述可以省。

● ● ●

三、优势和代价

优势三条。第一，跨会话：经验写在盘上，换会话、换天、换任务都在，比 memory（存事实偏好）和 session_search（翻历史聊天）更结构化——skill 是「怎么做」，后两者是「知道什么」。第二，按需加载：不用不花 token，一个 skill 全文平均 14KB（我本机 92 个共 1.3MB，均值约 14KB），只在用到时进上下文。第三，可维护：patch 动作精确到字符串替换，坏一个坑修一处，不用整篇重写。

代价两条。第一，索引是固定开销：不管用不用技能，每轮都带那份清单（本机 2800 token）。skill 越攒越多，索引线性涨，92 个是 11K 字符，攒到 300 个就是 37K。第二，加载即膨胀：SKILL.md 没有截断，一个 186KB 的 skill（我本机真有，就是写公众号那个）全文进上下文就是 4 万多 token，用一次顶半轮压缩。写 skill 控制篇幅是自律问题，机制不设上限。

● ● ●

四、对比 OpenClaw：机制几乎同构，账算下来差不多

OpenClaw 的 skill 机制在官方文档里写得明明白白，两边对照着看：

维度HermesOpenClaw
存放~/.hermes/skills/workspace/skills/ 优先，另有 6 层加载序
触发沉淀系统提示每轮催（SKILLS_GUIDANCE）Skill Workshop 提案队列，用户审批后落盘
索引注入名字+描述，实测 92 个≈11K 字符名字+描述+路径+sha256 版本标记
按需加载skill_view 全文，无截断模型用 read 读 SKILL.md，sha 变化要重读
索引预算无硬上限（有 focus mode 降级）maxSkillsPromptChars 超了先砍描述再砍列表
token 开销每技能约「名字+描述」长度每技能约 97 字符+字段长度≈24 token 起

逐条对下来，核心链路两边完全同构：都是「索引进提示、全文按需读」，这是 2025 年后 agent harness 的共识设计，都源自 Anthropic 的 Agent Skills 提案。

差异在两点。一是沉淀的把关：Hermes 让模型直接写盘（写完可以人工审），OpenClaw 走 Skill Workshop 提案队列，先到待审区、用户批准才生效。把关紧的代价是沉淀慢、可能永远躺着没人审；把关松的代价是盘上会积攒模型自以为是的存货。二是预算控制：OpenClaw 给索引设了硬上限（超预算先砍描述），Hermes 靠 focus mode 软性降级，没有硬顶。

回到那个问题：token 消耗是不是比 OpenClaw 多。索引层面，OpenClaw 每技能多注入路径和 sha256（各约 30-60 字符），同样技能量下它的索引反而略大；Hermes 的索引没有硬上限但也就 11K 字符量级，focus mode 还能再压。加载层面，两边都是按需读全文，读多大的文件花多少 token，一视同仁。结论：机制成本基本打平，日常用不出差别。真拉开差距的是沉淀纪律——skill 写得短而准，两边都省；写得又长又水，两边都烧。

● ● ●

五、给使用者的三条实操

skill 数量控制住。索引每轮都花 token，攒过 100 个就该清理不用的（skill_manage action=delete，合并进主 skill 的用 absorbed_into 标记去向）。

写 skill 控制篇幅。正文压在 10K 字符内，长内容拆进 references/ 子文件靠 linked_files 渐进披露。一个 186KB 的 SKILL.md 等于每次使用都自费半轮压缩预算。

定期维护比沉淀更重要。SKILLS_GUIDANCE 那句「不受维护的技能会变成负债」是源码里的原话。命令变了、路径变了、坑修了，patch 一下，比新写十个都值。
