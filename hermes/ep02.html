大家好我是郑同学。EP01 拆了三层架构，这一篇顺着一条真实运行路径往下走：双击图标启动桌面端，到你在输入框敲下第一句话、模型开始吐字。

这条主线分两段：启动段（Electron 把 Python 后端带活）和会话段（你的消息怎么进 gateway、流式回复怎么回来）。先看全景图，后面每一节都是把图里某一段放大。

五个字先记住：找、拉、连、杀、更——找后端、拉起来、连接对话、杀干净、更新自己，就是桌面壳与后端的全部关系。

● ● ●

找：六级梯子选出真后端

为什么第一步是"找"？因为桌面 App 的安装包里根本不带 Python 后端——Electron 壳是壳，agent 是另外一套 Python 代码，装在用户磁盘的某个位置。"找"的全部产出是一个启动配方：用哪个 Python、跑什么命令、配什么环境变量，一个对象直接喂给 spawn。

找什么？先把目标说死：桌面端要启动的是 hermes serve——一个 HTTP+WebSocket 网关服务（EP01 讲过，三个前端连的就是它）。调用方在 main.ts 里把参数拼好再进梯子（真实源码）：

// main.ts（真实源码）
// --port 0: the OS assigns an ephemeral port;
// the child announces it on stdout.
const backendArgs = ['serve', '--host', '127.0.0.1', '--port', '0']
const backend = await ensureRuntime(resolveHermesBackend(backendArgs))
 

只绑本机回环、端口 0 让系统随机分配——参数本身就为下一节的"后端自己报告端口"埋了伏笔。老版本后端没有 serve 命令的，回退走 dashboard --no-open（不拉浏览器）。

怎么找？六级台阶按信任度从高到低，每一级的核心代码（真实源码节选）：

// main.ts resolveHermesBackend（真实源码）
function resolveHermesBackend(backendArgs) {
  // 1. 开发者显式指定：开发者在开车，直接信
  const overrideRoot = process.env.HERMES_DESKTOP_HERMES_ROOT
    && path.resolve(process.env.HERMES_DESKTOP_HERMES_ROOT)
  if (overrideRoot && isHermesSourceRoot(overrideRoot)) {
    const backend = createPythonBackend(overrideRoot, ...)
    if (backend) return backend
  }
 
  // 2. dev 模式：本地 Python 改动真正被测到
  if (!IS_PACKAGED && isHermesSourceRoot(SOURCE_REPO_ROOT)) {
    const backend = createPythonBackend(SOURCE_REPO_ROOT, ...)
    if (backend) return backend
  }
 
  // 3. 正式安装位：runtime 能跑就直接用，不重装
  const activeRuntime = activeRuntimeState()
  if (activeRuntime.shouldUseActiveRuntime && !bootstrapRepairRequested) {
    return createActiveBackend(backendArgs)
  }
 
  // 4. PATH 里的 hermes：用户自己装的，用但不接管
  //    verifyHermesCli = --version 冒烟
  //    looksLikeDesktopAppBinary = 防自己启动自己
  const hermesCommand = findOnPath('hermes')
  if (hermesCommand && !looksLikeDesktopAppBinary(hermesCommand)
      && verifyHermesCli(hermesCommand, { shell: ... })) {
    return { label: `existing Hermes CLI at ${hermesCommand}`,
             command: hermesCommand, args: backendArgs, ... }
  }
 
  // 5. 系统 Python + 模块：import 探测通过才信（见下文）
  const python = findSystemPython()
  if (python && canImportHermesCli(python)) {
    return { kind: 'python', command: python,
             args: ['-m', 'hermes_cli.main', ...backendArgs], ... }
  }
 
  // 6. 全部落空：返回"需要安装"哨兵，首启安装器接手
  //    刻意不 throw——老实现 throw 会把用户带进死胡同
  return { kind: 'bootstrap-needed' }
}
 

无论哪级命中，产出的都是同一个形状的对象。第 3 级的产出长这样（真实源码）：

// main.ts createActiveBackend（真实源码节选）
return {
  // venv 里的 python.exe，退化用系统 python
  kind: 'python',
  command,

  env: buildDesktopBackendEnv({...}),
  root: ACTIVE_HERMES_ROOT,

翻译成人话：最终执行的完整命令是 python -m hermes_cli.main serve --host 127.0.0.1 --port 0——用找到的那个 Python，以模块方式启动 CLI 入口，跑 serve 子命令。"找"就是回答"这条命令的 python 用哪个、在哪、靠不靠谱"。

六级里最值得展开的设计只有一个：存在 ≠ 可用。第 3 级安装目录里躺着两类信息——marker 文件是"出身证明"（谁装的），repo+venv 是"能不能跑"的事实。CLI 装的没有 marker、老版本装完可能忘写 marker，所以判断只认运行时状态：runtime 能跑才是决定性的，缺 marker 不能把健康安装逼进重装流程，runtime 坏了 marker 再漂亮也不 launch。

"真实验证"验到什么深度？第 5 级的探测代码：

● ● ●

拉：警报绳 + 三道闸

配方交给 spawn，子进程出现了——但"进程存在"和"后端可用"之间隔着一段灰区：Python 要导入依赖树、绑端口、初始化，这期间随时可能死。桌面端的核心机制画成一张图：

startFailed 不是失败，是一根等着被拉响的警报绳。看它怎么搭（真实源码，逐行注释）：

// main.ts（真实源码节选，逐行注释）
// 三道闸全过才置 true
let ready = false
// 先声明，下面才拿得到句柄
let rejectStart = null
 
const startFailed = new Promise((_resolve, reject) => {
  // 一个永不自己成功的 Promise，reject 句柄留给失败事件
  rejectStart = reject
// reject 句柄留给失败事件调用
})
 
// 失败路径一：根本没起来
child.once('error', error => {
  rejectStart?.(error)
})
// 失败路径二：起来又退出
child.once('exit', (code, signal) => {
  // ready 后退出是崩溃恢复的事，不算启动失败
  if (!ready) {
    rejectStart?.(new Error(`exited before it became ready`))
  }
})
 
// 赛跑：成功道（等宣告，最多90s）vs 警报绳（秒级）
const port = await Promise.race([
  waitForDashboardPortAnnouncement(child, { readyFile }),
  startFailed
])
 

这五行是整节的枢纽，逐行拆开看：

第 1 行（注释）先声明两条赛道的性质：成功道是"最多等 90 秒"——这个数是喂出来的，慢盘 + Windows 杀毒逐个扫描新写的 .pyc，冷启动实测 30-60 秒，早期 45 秒死线会杀掉健康后端再重开，孤儿进程越堆越多（issue #50209）；失败道是"秒级"——进程起来又崩，通常一两秒内 exit 事件就到了。

第 2 行const port = await：await 挂在 Promise.race 上，这行代码会停在这里不动，直到 race 内部某个 Promise 先出结果。拿到的值赋给 port——注意只有成功道才会产出端口，失败道是 reject（抛错），根本走不到赋值。

第 3-5 行race 的参数是两个 Promise，谁先 settle（无论成功还是失败）整个 race 就是那个结果：

  •  waitForDashboardPortAnnouncement(child, { readyFile })——成功道。它监听 child.stdout，逐行扫描等那行 HERMES_BACKEND_READY port=39871；匹配到就 resolve(端口号)。内部自带 90 秒超时：到点没等到也 reject（说明后端病了但没死透，同样按启动失败处理）。带 readyFile 时改走文件轮询——某些 Windows 终端管道会吞 stdout，后端就同时把宣告写进文件，桌面端轮询文件兜底。
  •  startFailed——警报绳。还记得上面它的构造吗？executor 里只执行了 rejectStart = reject，这个 Promise 永远不会自己 resolve，只会被 error/exit 事件从外部拉响。它参与 race 不贡献结果，只贡献"提前出局"。

三种结局推演：

结局A（健康启动，冷盘 ~40s）：
  stdout 在 40s 时打出 READY port=39871
  → 成功道 resolve(39871) 先到
  → race 结果 = 39871，port = 39871，继续走健康闸
 
结局B（import 崩溃，2s 死）：
  child 'exit' 在 2s 时触发 → rejectStart 拉响
  → startFailed reject 先到
  → await 这里直接 throw，启动函数失败退出
  → 90s 的成功道还在傻等？没关系，函数已经不在了
 
结局C（病了没死透，90s 无宣告）：
  成功道自己的超时到点 reject
  → 同样 throw，按启动失败处理
 

race 的本质：把最慢的正常路径和最快的失败路径绑在同一起跑线上，谁先发生响应谁。没有这层防备，结局 B 会退化成结局 C——进程 2 秒就死了，用户却要对着启动界面干等 88 秒才看到报错。

之后两道闸：健康探针轮询到应答才算 ready = true；最后用后端签发的正式 token 真实发起一次 WebSocket 升级验证——HTTP 健康 ≠ WS 能连。三道闸全过，启动段结束。

● ● ●

连：一条 WebSocket 两种帧

启动段结束，主角换成渲染进程——从这节开始，视角切到客户端：之前两节我们站在 Electron 主进程看它怎么伺候 Python 子进程，现在钻进渲染进程（React 那一侧），看它作为"客户端"怎么跟 gateway 服务器对话。你在输入框按回车，之后的一切都在一条 WebSocket 上跑：

先补协议背景。传输用 WebSocket（一条全双工长连接，连上后双向随时发消息，不用反复握手）；消息格式用 JSON-RPC 2.0——一个极简的远程调用协议，规范就几页纸，核心只有三种消息：

请求：  {"jsonrpc":"2.0", "id":1, "method":"prompt.submit", "params":{...}}
响应：  {"jsonrpc":"2.0", "id":1, "result":{...}}     ← id 原样带回
       {"jsonrpc":"2.0", "id":1, "error":{...}}      ← 或错误
通知：  {"jsonrpc":"2.0", "method":"xxx", "params":{...}}   ← 无 id，不等回执
 

精髓在 id：发起方给每个请求编号，响应方原样带回，一来一回凭编号配对——这就是"对号入座"的协议基础。Hermes 在 WS 上用一个变体：服务端主动推的消息走 method:"event" 的通知形态（无 id），恰好把 JSON-RPC 的第三种消息用活了——请求响应用 id 配对，推送用通知，一个协议规范覆盖两种通信模式。

客户端的实现在 apps/shared/src/json-rpc-gateway.ts（431 行的 JsonRpcGatewayClient，桌面端全部会话通信都走它）。发消息那一下的调用链（真实源码）：

// 再发送：编号就是回执凭证
socket.send(JSON.stringify({
  jsonrpc: '2.0', id,
  method, params

接收端 handleMessage 按帧形态分流（真实源码）：

// json-rpc-gateway.ts（真实源码节选）
// 有 id = 某次请求的响应，对号入座
if (frame.id !== undefined && frame.id !== null) {
  const call = this.pending.get(frame.id)
  this.clearPending(frame.id)
  // error 字段在就是失败，不在就是成功
  frame.error ? call.reject(...) : call.resolve(frame.result)
  return
}
// 无 id + method=event = 服务端推送，广播给订阅者
if (frame.method === 'event' && frame.params?.type) {
  this.dispatchEvent(frame.params)
}
 

每条请求都带超时定时器（默认 120 秒，prompt.submit 单独放宽）；断线时 pending 表整体清账（rejectAllPending），任何调用不会永远挂起——挂起表的完整生命周期：挂起→对号/超时/中止/断线清账，四条出路条条有交代。

杀·更：主线之外的收拢

先回答为什么要杀。Python 后端不是桌面 App 的孤儿子进程——它活着的时候自己也在 spawn 三类东西，先把名词说清：

  •  pty 终端会话：pty（pseudo-terminal，伪终端）是"软件模拟出来的终端"。桌面端里你点开终端面板跑 npm install 时，后端就 spawn 一个 pty 子进程——它模拟真实终端的输入输出行为（键盘、颜色、光标），让 bash/PowerShell 以为自己连着真终端，实际画面渲染在 App 里；
  •  hermes REPL：REPL（Read-Eval-Print Loop，读取-求值-打印-循环）= 交互式解释器——你敲一行代码它立刻执行并回显结果，Python 命令行里敲 python 进去的那个界面就是 REPL。Hermes 后端会起一个自己的 REPL 子进程用于交互评估；
  •  MCP 工具进程：Model Context Protocol 工具服务器，agent 的外挂手脚（文件系统、浏览器操作这些能力是独立进程提供的）。

所以进程树长这样：

Electron（桌面App）
└── python -m hermes_cli.main serve   ← spawn的直接子进程
    ├── pty 终端会话                   ← 孙进程（模拟终端，跑你的命令）
    ├── hermes REPL                    ← 孙进程（交互式求值）
    └── MCP 工具进程（文件/浏览器…）    ← 孙进程（agent的外挂手脚）
 

不杀就退出 App，这棵树会怎样？后端不会跟着死。POSIX 上父进程退出后子进程被 init 收养，继续在后台跑；Windows 上进程树照样活着，还锁着 venv 里的文件——下次启动安装器想更新，文件被占用直接失败。杀的时机也比想象多：正常退出、切换 profile（每个 profile 一个后端进程池）、卸载、更新前腾地——main.ts 里 stopBackendChild 有 9 个调用点。

杀的难点在"砍树别杀枝"。Node 的 child.kill() 只信号直接子进程：python 收到 SIGTERM 死了，它的孙进程一个没死，变成孤儿继续占资源。

那正确的杀法从谁开始？都不是——两种打法都不需要挨个点名，一次信号全家收到：

  •  Windows 的 taskkill /T /F：/T 的意思是 tree——你给它一个根 PID，它自己顺着父子关系枚举整棵树，先给每个成员标记，再统一强杀。桌面端只报 python 的 PID，终端/REPL/MCP 一个都不用认识。
  •  POSIX 的 killGroup(-pid)：信号根本不发给某个进程，而是发给进程组这个整体。spawn 时 start_new_session 已经把后端和它未来 spawn 的所有子孙划进同一组（pgid后端 pid），所以给负 PID 发 SIGTERM 时，内核把信号投递给组内所有成员，孙进程无论多深都在组里==。

换句话说：错误杀法是"从根开始一个一个杀"（杀完根，父子关系断了，孙进程再也找不齐）；正确杀法是按"集合"杀——Windows 按树这个集合，POSIX 按组这个集合，集合成员身份在进程活着的时候就已经登记好了。

真实源码：

// backend-child.ts stopBackendChild（真实源码节选）
// Windows：taskkill /T /F，T=整棵树，F=强制
if (isWindows && Number.isInteger(child.pid)) {
  deps.forceKillProcessTree(child.pid)
// POSIX：负 PID = 整个进程组
// spawn 时 start_new_session 已把后端打包进独立进程组

  } catch {

  }

现在回头看更新场景那个细节就懂了（stopBackendTreesForUpdate 的注释）：必须趁根进程 PID 还活着就调 taskkill /T——因为树的枚举依赖根进程活着，根先退了 Windows 再也数不出它的 MCP 孙进程，它们成了无名孤魂，带着锁死的 venv 活下来。

更随代码走：冻结的安装器无法自更新，修复要等发布滞后几个月。解法是把更新脚本放进代码仓库，每次 hermes update 连"驱动下一次更新的代码"一起刷新，冻结的只剩 PowerShell 本身。

● ● ●

小结

主线节点核心机制
找六级梯 + 存在≠可用：只认运行时状态，探测探到真实依赖
拉警报绳赛跑：成功道慢失败道快；三道闸全过才认活
连一条 WS 两种帧：编号帧对号入座，事件帧广播驱动 UI
杀/更砍树别杀枝 / 更新脚本随仓库走

口诀：找用梯子探真依赖，拉完双闸才认活，杀要砍树别杀枝，更随代码不冻结，连过两门再上屏——五个字对五个模块组，想起五个字就能顺出整条主线。
