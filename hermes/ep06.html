大家好我是郑同学。前几篇的 agent 都是"你问它答"——消息不来，它不动。这一篇讲另一面：agent 自己按时干活。每天早上 8 点发日报、每小时巡检日志、每周五汇总动态，你不在屏幕前，它照跑。机制上是三件事：一个 60 秒一跳的调度循环、一把跨进程文件锁、一个带渠道的投递地址。顺着这三件事，把 cron/ 目录 6699 行的 scheduler.py 从启动到投递走一遍。

● ● ●

心跳：gateway 每 60 秒叫醒一次调度器

cron 不是常驻进程。gateway 启动时拉起一个名叫 cron-scheduler 的后台线程，循环体只有两件事：调一次 tick()，睡 60 秒。

# cron/scheduler_provider.py:166（InProcessCronScheduler.start）
# 启动即先记一次心跳，让 hermes cron status 立刻能看到活着的 ticker
record_ticker_heartbeat()
while not stop_event.is_set():
    ok = False
    try:
        cron_tick(verbose=False, adapters=adapters, loop=loop, sync=False)
        ok = True
    except BaseException as e:
        # 连 SystemExit 都接住——ticker 线程死了所有定时任务全停（#32612）
        logger.error("Cron tick error: %s", e, exc_info=True)
    # 每轮都记心跳；成功标记只在干净的一轮里更新
    # status 就能区分"活着但每轮都失败"和"真在跑任务"（#32612, #32895）
    record_ticker_heartbeat(success=ok)
    stop_event.wait(interval)
 

几个值得注意的设计。异常接的是 BaseException 而不只 Exception——一个行为不端的 provider SDK 抛出 SystemExit，ticker 线程也不能静默死掉，否则所有定时任务无声停摆。心跳每轮都记，成功标记只在干净轮次更新，所以 hermes cron status 能告诉你 ticker 是"活着但一直失败"还是"真的在跑"。本机实测：

✓ Gateway is running — cron jobs will fire automatically
  PID: 97580
  Ticker heartbeat: 24s ago
 

调度器只负责"被叫醒时干活"，到点逻辑不在它手里。哪一分钟轮到哪个 job，由下一节的到期检查决定。

另一个细节：这个 60 秒循环被抽象成了 CronScheduler provider 接口（scheduler_provider.py）。内置实现就是这个线程循环，但接口留了后门——外部 provider（比如部署在 NAS 上的 Chronos）可以实现同一接口接管触发权，配置键 cron.provider 一行切换。什么时候跑归 provider 管，跑起来发生什么不归它管：执行和投递永远走共享的 run_job / _deliver_result，provider 不许自己重新实现一遍，防止两套执行逻辑分叉。

● ● ●

防重：一把文件锁挡住第二个 tick

tick() 开头第一件事是抢锁。

# cron/scheduler.py:3274（tick）
# 拿锁路径：~/.hermes/cron/.tick.lock
lock_dir, lock_file = _get_lock_paths()
lock_dir.mkdir(parents=True, exist_ok=True)
 
# 跨平台文件锁：Unix 用 fcntl，Windows 用 msvcrt
lock_fd = None
try:
    lock_fd = open(lock_file, "w", encoding="utf-8")
    if fcntl:
        fcntl.flock(lock_fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
    elif msvcrt:
        msvcrt.locking(lock_fd.fileno(), msvcrt.LK_NBLCK, 1)
except (OSError, IOError):
    logger.debug("Tick skipped — another instance holds the lock")
    if lock_fd is not None:
        lock_fd.close()
    return 0
 

为什么要锁：桌面端 gateway 在跑、你又手动敲了 hermes cron tick，两个 tick 可能在同一秒醒来。没有锁，同一个 job 会被跑两遍——日报发两份、巡检跑两次。有了锁，抢不到锁的那个 tick 直接返回 0，一个字不干。fcntl.flock 的 LOCK_NB 标志表示非阻塞——拿不到就立刻放弃，不排队等待。

锁住之后干的第一件事，藏着这个调度器最重要的语义。

# cron/scheduler.py:3320（tick 内，拿到锁之后）
# 先把所有到期 job 的 next_run_at 推进，再开始执行——保住 at-most-once
# 对于并行执行中的长任务，advance_next_run 会持续把 next_run_at 往前顶，
# 宽限窗口永远不过期；mark_job_run() 在完成时最终覆盖 next_run_at
for job in due_jobs:
    advance_next_run(job["id"])
 

先推进、再执行，顺序不能反。反过来会怎样：job 开始跑了，此时进程被杀——next_run_at 还停留在"过去"，下个 tick 发现它到期，再跑一遍。同一条日报在你重启之后又发了一次。先推进，job 即便中途死掉，也不会被下个 tick 重复拾起。at-most-once 语义靠的是"先记账再干活"这个顺序。

● ● ●

投递：一个地址决定结果去哪

job 跑完，结果发到哪。答案是一个字符串，platform:chat_id 形态。

# cron/scheduler.py:967（_resolve_single_delivery_target）
if ":" in deliver_value:
    platform_name, rest = deliver_value.split(":", 1)
    platform_key = platform_name.lower()
    ...
    return {
        "platform": platform_name,
        "chat_id": chat_id,
        "thread_id": thread_id,
    }
 

weixin:某chat_id 就是发到微信那个对话，api_server:某session 就是发到桌面端某个会话。除了显式地址，还有两个特殊值：origin 表示"发回创建这个 job 的渠道"（在飞书聊着聊着建的任务，结果回飞书），local 表示不外发。地址还支持人类可读的标签——"Alice (dm)" 这种别名会先经过 channel_directory 解析成真实 chat_id，解析不了就按原样发。

创建一个 job 的完整命令长这样：

hermes cron create "0 8 * * *" "汇总昨天未读邮件，发一份日报" \
  --name 早报 --deliver origin
 

CLI 能做的事在聊天里也能做——对话里敲 /cron 或让 agent 调 cronjob 工具，最终都汇到同一个 create_job 入口。

目录一瞥：调度器之外的一圈

cron/ 目录里 scheduler.py 之外还有几个文件，各自管一段：

最值得展开的是 lifecycle_guard，它防的事故值得整段引用源码注释。

# cron/lifecycle_guard.py（头注释，#30719）
# agent 在 gateway 里跑的时候，可以创建一个调 "hermes gateway restart"
# 的 cron job。job 到点触发：gateway 死、launchd/systemd 把它救活、
# auto-resume 接着跑那个会话、恢复的 turn 又执行同样的建 job 逻辑——
# 每 ~10 秒一个 SIGTERM-respawn 循环，直到有人手动打断
#
# 本模块在 cron.jobs.create_job 处拦截：prompt 或 script 里包含
# shell 层面的 gateway 生命周期命令就拒绝创建
 

一个 agent 无意间（或模型的执念）创建了一个重启 gateway 的定时任务，会造成每 10 秒一次的死亡循环——守护进程越尽责，循环越牢固。lifecycle_guard 在创建入口就拦掉，而且拦的是 CLI 和 agent 工具两条路（cronjob 工具直接调 create_job，绕过 CLI 层，所以必须在 create_job 拦）。前面 EP02 讲网关重启被 lifecycle_guard 拦截，就是这个模块的另一面。

● ● ●

动手：三种 job 形态

cron job 不止"到点让 agent 跑一遍 prompt"一种形态，hermes cron create 的参数暴露了三种：

默认形态：agent + prompt。到点拉起一个带 prompt 的 agent 跑完，结果投递。--skill 可以挂技能、--workdir 可以指定工作目录（注入那个目录的 AGENTS.md 并以此为根跑工具）。

脚本喂数据：script + agent。--script 指向 ~/.hermes/scripts/ 下的脚本，脚本的 stdout 注入 agent 的 prompt。适合"数据采集交给脚本，解读交给模型"的分工。

无 agent：script 即任务。--no-agent 跳过 LLM，脚本本身就是任务，stdout 原样投递，空输出则静默。这就是经典 watchdog 模式——磁盘告警、内存告警、CI ping，不需要模型参与，零 token 成本。

# 磁盘告警 watchdog：脚本自身即任务，无 LLM
hermes cron create "30m" --script disk_alert.sh --no-agent --deliver origin
# stdout 非空才投递，空输出不打扰
 

三种形态覆盖了"要智能"到"只要准时"的光谱。判定标准很直接：输出的每一行都需要模型生成，用默认形态；数据是死的、只是要不要发给人看，用 --no-agent。

● ● ●

小结

件机制
触发gateway 拉起 cron-scheduler 线程，60s 一轮 tick
心跳record_ticker_heartbeat 区分"活着但失败"和"真在跑"
防重.tick.lock 文件锁；拿不到锁直接返回
语义先推进 next_run_at 再执行，at-most-once
投递platform:chat_id / origin / local 三种地址
拦截lifecycle_guard 在 create_job 拦"重启 gateway"的 job
形态prompt / script+agent / --no-agent watchdog

cron 解决的是"你不在这它也要跑"。下一件事随之而来：跑完的结果发到手机上，你会想直接在手机上跟它对话——不用回电脑开桌面端。这就引出 EP07：手机浏览器怎么当桌面端用。
