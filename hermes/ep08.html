大家好我是郑同学。agent 能跑终端能写文件，安全问题不是附庸是地基。这一篇拆 Hermes 的双层防线：外层是你在桌面端看到的权限弹窗，决定"给不给权限、给多久"；内层是 agent 进程里的 tool_guardrails，盯着"同一个坑摔了五次还在摔"这种用户根本看不见的异常。两层各管一段，谁也不能替代谁。

● ● ●

外层：审批弹窗的四档刻度

EP04 讲过 ACP 适配层把 Hermes 审批翻译成客户端选项，这一节看选项本身。桌面端弹窗的四个按钮不是拍脑袋排的，每档都对应权限状态机里的一个真实迁移（acp_adapter/permissions.py:46）。

# acp_adapter/permissions.py:46（build_permission_options 节选）
# 每个弹窗选项 = 权限状态机的一次真实迁移
options.append(PermissionOption(
    option_id="allow_once", kind="allow_once", name="Allow once"))
 
options.append(PermissionOption(
    option_id="allow_session", kind="allow_always",
    name="Allow for session"))
 
options.append(PermissionOption(
    option_id="allow_always", kind="allow_always",
    name="Allow always"))
 
options.append(PermissionOption(
    option_id="deny", kind="reject_once", name="Deny"))
 

四个动作：仅此一次、本会话允许、永远允许、拒绝（deny_always 在客户端支持时追加第五档）。粒度本身就是安全设计：不是"允许/拒绝"的二极管，是"这次、这阵子、永远、不"的刻度。日常用 svn diff 这类只读命令，选 session 就够了——一小时后权限自动收回，不用你惦记。

细节见诚意：allow_session 在 ACP 协议里没有原生对应，适配层用 kind="allow_always" 加 option_id="allow_session" 的组合保住 Hermes 语义（permissions.py:50 注释原话：ACP has no session-scoped kind）。协议没给的语义，适配层自己补。

● ● ●

内层：guardrails 不弹窗，直接熔断

弹窗拦的是"用户看得见的危险"。guardrails 拦的是更阴的：agent 在一个工具调用上反复失败、反复重试、烧 token 不出活。这层的规则写在 ToolCallGuardrailConfig 的阈值里（agent/tool_guardrails.py:64）。

# agent/tool_guardrails.py:64（ToolCallGuardrailConfig 默认值）
warnings_enabled: bool = True
hard_stop_enabled: bool = False
exact_failure_warn_after: int = 2
exact_failure_block_after: int = 5
same_tool_failure_halt_after: int = 8
no_progress_warn_after: int = 2
no_progress_block_after: int = 5
 

三类规则，全是盯"重复"的：完全相同失败第 2 次警告、第 5 次拦截；同工具不同参数连续失败到第 8 次熔断整个 turn；幂等工具无进展（反复调用、参数不变、结果不变）第 2 次警告、第 5 次拦截。注意 hard_stop_enabled 默认 False——最重的"熔断"要显式打开，默认行为停在"拦截该次调用+警告"。

熔断发生时，Agent Loop 里工具执行后有一段专门的处理（agent/conversation_loop.py:4675）。

# agent/conversation_loop.py:4675（真实源码节选）
# 工具执行后检查 guardrail 的熔断决定
if agent._tool_guardrail_halt_decision is not None:
    decision = agent._tool_guardrail_halt_decision
    _turn_exit_reason = "guardrail_halt"
    final_response = agent._toolguard_controlled_halt_response(decision)
    agent._emit_status(
        f"⚠️ Tool guardrail halted {decision.tool_name}: {decision.code}"
    )
    messages.append({"role": "assistant", "content": final_response})
    # 把熔断解释发给客户端——不能和崩溃长得一样
    if final_response:
        agent._safe_print(f"\n{final_response}\n")
        if agent.stream_delta_callback:
            agent.stream_delta_callback(final_response)
            agent.stream_delta_callback(None)
 

两个设计点。其一，退出原因单独标记 guardrail_halt，不混进异常路径——用户和监控能区分"AI 拒绝继续"和"程序崩了"。其二，熔断解释文本主动推给客户端（注释原话：不能让熔断和崩溃长得一样）。静默拦截是这层的姿态，但熔断必须有解释。

这层在 agent 内核里，任何前端、任何渠道进来都躲不过：桌面端、网页端、微信消息触发，走的都是同一段 Agent Loop。

● ● ●

外层管看得见的，内层管看不见的

两层的分工一句话说清：弹窗是授权语义（用户决定给多少权限），guardrails 是底线语义（无论授权与否，异常循环就断）。

为什么必须两层。只有外层：弹窗拦不住"已授权工具的失败循环"——你允许过 shell，不代表允许它每秒空转烧 token。只有内层：guardrails 不懂"这个命令该不该跑"——它看的是行为模式，不是命令内容。双层让信任的粒度和异常的底线各归其位。

顺带一提 secret_scope（agent/secret_scope.py：get_secret 按作用域取凭据，credential_pool.py:19 引用）：API 凭据按作用域隔离存储，属于防线体系里更靠"资"的一环——凭据不给工具明文，工具再循环也偷不走钥匙。

● ● ●

小结

层管什么机制
外层弹窗授权语义once/session/always/deny 四档，状态机迁移
ACP 适配协议翻译session 档在 ACP 无原生对应，option_id 补语义
内层 guardrails行为底线失败 2 警告/5 拦截、同工具 8 熔断、无进展 5 拦截
熔断可见性可观测guardrail_halt 独立退出码 + 解释文本推送
凭据隔离资产安全secret_scope 作用域取凭据
