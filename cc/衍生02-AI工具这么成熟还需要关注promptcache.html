你的同事都搁那无脑 SDD——先写一份"完美"spec，然后让 AI 照着实现。他们用明白了吗？

spec 放哪里、读几次、被压缩了怎么办、迭代了谁维护——这些问题大部分人都没想过。他们只知道「写 spec 很高级」，然后看着 token 账单流泪。

看完这一篇，下次同事再吹 SDD 的时候，你也有话讲。

● ● ●

先搞清 prompt cache 在干什么

根据 Anthropic 官方文档，每轮 API 调用的 prompt 被分成两段：

系统提示词前缀（不变 → 缓存命中 0.1×，几乎免费）
  ├── 身份声明
  ├── 工具定义
  └── CLAUDE.md
─────────── 缓存断点 ───────────
消息历史 messages（每次变 → 全价 1×）
  ├── 用户消息
  ├── 工具结果（read 文件内容在这）
  ├── assistant 回复
  └── ... 越来越胖
 

大模型推理分两步：先把输入 token 全部转成 KV Cache（键值缓存），再基于缓存逐个生成输出。如果两次请求的前缀一模一样，算出的 KV Cache 也一样，服务商直接复用，跳过整个前置计算。

定价：

操作费用
正常输入1×
缓存写入1.25×（第一次贵 25%）
缓存读取0.1×（后续省 90%）
TTL5 分钟，每次命中自动续期

缓存命中时省掉的不只是钱——而是整个前缀的前向计算。 不命中时模型要先算完前缀才能吐第一个字，命中时直接跳过。20 轮对话累计下来，光等待前缀重算就能差几分钟。

prompt cache 的价值有两层：省钱是表层，省时间是底层。

● ● ●

SDD 的真正代价不是缓存失效

很多人说「SDD 把 spec 塞进 prompt 破坏缓存」——这个说法不准确。

分两种场景：

用 Claude Code / Cursor（工具用户）：spec 不是塞进系统提示词的，是通过 read 工具读取后进 messages。CLAUDE.md 里只放 spec 索引（200 token），不会反复改。工具定义也不变。系统提示词前缀的缓存一直稳定命中。

调 API 做 Agent：如果你把 spec 塞进 system prompt 且频繁改，确实会破坏缓存。但这是放错位置的问题，用 cache_control 多断点分层能解决。

那 SDD 真正的代价是什么？是 messages 膨胀。

● ● ●

场景一：用 Claude Code / Cursor

工具用户有个错觉：prompt cache 工具帮我管了，不用操心。

缓存确实帮你管了——但只管前缀。messages 的 token 一个都没省。

spec 怎么进 messages

每一次 read 的返回结果都是一条完整的 tool result，原封不动进 messages，全价计费。

你 round 1：读 docs/api-spec.md → messages +5000 token
你 round 5：改了点东西，模型又读了一次 → messages +5000 token
你 round 10：新需求，模型再读一次 → messages +5000 token
 
同一个 spec 文件被读 3 次，messages 里就有 3 份完整内容。
其中 10000 token 是纯重复。
 

重复读取是 SDD 烧 token 的头号原因。 模型不会"记住上次读过的文件"——它要确保拿到最新版本，每次都重新 read，每次都产生新的 tool result。

1M 窗口够不够

你可能会说：现在 GLM-5.2、Claude 都有 1M 窗口了，够用吧？

拿 GLM-5.2 1M 窗口算：

  •  系统提示词前缀约 20000 token（缓存命中）
  •  压缩触发线 ~83.5%：≈ 818000 token 可用于 messages
  •  一个 500 行代码文件 ≈ 6000 token
  •  每轮消耗（read spec + 回复 + write）≈ 10000 token
  •  理论能撑 ~80 轮

但 80 轮只是「每个文件只读一次」的理想值。 实际上同一文件会被重复读，10 轮下来 messages 已经 ~80000 token，其中 spec 重复内容就占了 ~15000。

压缩到底怎么工作

你以为 80 轮期间没有压缩？从第 1 轮就开始了。

Claude Code 的上下文管理是多级的：

级别触发条件做什么你能感知到吗
① 持续清理每轮调用前大工具输出落盘、超长结果裁剪头尾、去掉格式噪声基本感知不到
② 主动压缩上下文到 ~50-60%（官方推荐）摘要早期对话，腾出空间你可以手动 /compact 触发
③ 自动压缩上下文到 ~83.5%（CLAUDE_AUTOCOMPACT_PCT_OVERRIDE 可调）完整摘要整个对话历史明显——模型突然"忘了"之前的内容

83.5% 只是最后的安全网，在那之前轻量清理一直在跑。 但 ① 级只是截断大结果，不会帮你去重 spec 内容——同一文件读 3 次，3 份完整内容都在。

压缩触发后，之前读的文件内容全部被摘要替代：

压缩前（818000 token）：
  [tool result] payment.py 完整内容（6000 token）
  [assistant] 写了支付逻辑（4000 token）
  [tool result] payment.py 又读了一次（6000 token）
  [assistant] 改了退款逻辑（5000 token）
  ... 几十条消息
 
压缩后（~200000 token）：
  [摘要] 用户开发了一个支付模块，修改了退款逻辑，
         读取了 orders/payment.py。
  ... 几行摘要
 

文件的具体内容没了，只剩"用户读取了哪些文件"这种笼统摘要。 这时候如果你说"帮我改手续费计算"，模型发现上下文里没有 payment.py 的实际代码，必须重新 read——又烧一轮 token。

这就是 SDD 在长对话中的死循环：

spec 反复读取
  → messages 快速膨胀
  → 上下文窗口更快耗尽
  → 更早触发上下文压缩
  → 压缩后 spec 内容丢失
  → 下一轮又得重读 spec
  → messages 再次膨胀...（死循环）
 

SDD 的代价不是缓存失效，而是上下文窗口被 spec 内容快速吃满。 缓存一直在好好工作，但你的消息历史越来越胖，每轮全价计费的 token 越来越多。在流泪的不是缓存，是你的 token。

还有一个更隐蔽的问题：上下文越长，模型越容易「遗忘」。这在 AI 领域叫「lost in the middle」——长上下文里中间位置的信息容易被忽略。1M 窗口让这个问题更严重，因为你能塞进去的东西更多了。模型写错代码 → 你让它改 → 来回返工 → 每一轮都在烧 token。

工具层为什么不做去重

你可能觉得：工具加个缓存，同一文件读过了就跳过？没那么简单。

read 是无状态的——每次调用都独立返回完整文件内容。工具层不知道文件有没有被改过：

Round 1: 模型 read payment.py → 内容 A
Round 3: 模型 write payment.py → 代码改成 B 了
Round 5: 模型 read payment.py → 这时内容已经是 B
 
如果工具层做了去重（Round 1 读过就跳过）：
  → Round 5 直接复用 Round 1 的内容 A
  → 但实际文件已经是 B 了
  → 模型基于过时代码写逻辑 → 出 bug
 

文件可能在任意时刻被改：模型自己 write 改过、用户在编辑器里改过、git pull 更新了。工具层没法可靠判断"内容有没有变"，所以每次都老老实实读。

技术上能优化吗？能，但有代价：

方案原理问题
文件 hash 对比读之前先算 hash，跟上次一样就跳过要存储每次读取的 hash，多一轮 IO
mtime 检查文件修改时间没变就跳过外部编辑器可能不改 mtime，git 操作可能改
只去重同一轮同一轮对话内读同一文件只读一次跨轮还是重复

这些都是工具层优化，不是模型层。Claude Code 目前没做，Pi 也没做。设计取舍是：宁可重复读浪费 token，也不能用过时内容导致写错代码。

怎么减缓膨胀

既然重复读改不了，就在别处省：

CLAUDE.md 精简。 真实案例（来源）：1358 行精简到 807 行（减 41%），流程性规则移到 Skills。CLAUDE.md 是每轮缓存加载的，越小越省。

spec 拆分，按需读取。 不要写一个 5000 token 的大 spec，拆成模块文件，用到才读：

项目结构
├── CLAUDE.md          ← 全局架构 + spec 索引（精简，200 token）
├── docs/
│   ├── api-spec.md    ← API 设计（写接口时才读）
│   ├── data-model.md  ← 数据模型（改表时才读）
│   └── module-auth.md ← 认证模块（相关功能才读）
└── .claude/skills/
    ├── git-workflow   ← 提交规范（触发时才加载）
    └── deploy-check   ← 部署检查清单（触发时才加载）
 

三层载体各管不同的事：

载体放什么加载方式对上下文的影响
CLAUDE.md全局架构、技术栈、spec 索引每轮自动加载越大每轮越贵
docs/详细 spec 文档模型按需读取用到才进 messages
Skills流程规则触发时才加载不触发不占 token

判断标准：每轮都用 → CLAUDE.md；有明确触发时机 → Skill；是参考文档 → docs/。

spec 改了之后让模型重读。 在对话里明确说一句："我更新了 docs/api-spec.md，请重新读一下"。不要假设模型记得旧版本的内容。

启动只读 CLAUDE.md，需求来了靠猜

Claude Code 启动时只读四样东西：身份声明、工具定义、全局 ~/.claude/CLAUDE.md、项目级 ./CLAUDE.md。你的项目代码一个都不会读。

需求来了之后，模型猜，不是全盘读：

你说："帮我改支付逻辑"
 
模型：
  1. 先看项目级 CLAUDE.md 有没有索引
     → 有："支付逻辑在 services/payment.py" → 直接读（1 个文件）
     → 没有 → 进入猜测模式
 
  2. 猜测模式：
     → ls 看目录结构 → 猜 payment.py / pay.py / checkout.py
     → 逐个 read 确认 → 每猜错一次 = 浪费 5000-6000 token
 

注意：全局 CLAUDE.md 管的是个人偏好（类型标注、代码风格），不会写项目文件结构。文件索引得写在项目级 CLAUDE.md（项目根目录 ./CLAUDE.md）里。全局的照样加载，但它帮不了模型找文件。

项目级 CLAUDE.md 写了索引，模型精准读 1 个文件；没写，猜 5-6 个才找到。猜的每一步都在烧 token。

别上来就读全部代码

有些人启动后第一句话："读取项目所有代码，理解整体架构"。别这么干。

烧 token：50 个文件全读 = 25000 token 进 messages，每轮全价计费，90% 跟你的任务无关。

信息稀释：读了 50 个文件，等你问支付逻辑时，相关信息被夹在 30 个无关文件中间。读得越多，模型反而越容易漏掉关键细节。

读完也记不住：到第 5 轮，早期读的内容已经被压缩成摘要。你花了几万 token 让模型"理解架构"，到第 5 轮它什么都不记得。

正确做法：把架构写进 CLAUDE.md，200 token 比读 50 个文件有效得多。

CLAUDE.md：
 
项目架构：
  入口：app.py（Flask 应用）
  路由：routes/（每个文件一个模块）
  模型：models/（SQLAlchemy 定义）
  服务层：services/（业务逻辑在这）
  工具：utils/（分页、缓存等）
 
核心模块：
  - services/payment.py    支付（支付宝 + 微信）
  - services/order.py      订单状态机
  - routes/user.py         用户 CRUD
 

然后在对话里圈定范围："不需要读 legacy/、migrations/、tests/，只看 orders/payment.py"。

spec 改了：新开会话还是老会话

这直接影响 token 消耗，不是小事。

老会话 15 轮，messages 约 40000 token
  → 每轮全价计费这 40000 token
  → 改 spec 后还要再读一遍（+5000 token）
  → 加上压缩后的摘要（+3000 token）
  → 每轮实际计费 ~48000 token
 
新开会话
  → messages 从 0 开始
  → 读一次 spec（+5000 token）
  → CLAUDE.md 缓存命中（几乎免费）
  → 每轮实际计费 ~7000 token
 
spec 改动类型建议原因
小修（加字段、改约束）继续老会话改动小，重读一次 spec 就行
大改（重构模块、改架构）新开会话旧代码和讨论都失效了，留着只是 token 负担
纠正方向（模型理解错了）新开会话老会话的错误上下文会持续干扰

经验值：老会话 < 10 轮继续，10-20 轮看改动，> 20 轮新开。不要一直在老会话里改需求——messages 越胖每轮越贵。 老会话像一锅越煮越浓的汤，到一定浓度就该倒掉重来。

● ● ●

场景二：自己调 API 做 Agent

没有 CLAUDE.md 和 Skill 兜底，spec 放哪、缓存怎么管全靠自己。这时候有两个问题要处理。

问题一：spec 塞进 system prompt 还频繁改

❌ 常见错误做法
 
system = [
    "你是一个资深工程师...",
    spec_document,               ← 整个 spec 塞进 system prompt
]
 
第 1 轮 spec v1 → 缓存写入（贵 25%）
第 2 轮 spec v1 → 缓存命中（省 90%）✓
第 3 轮 改了 spec → v2 → 缓存失效！重新写入
第 5 轮 又改了 → 又失效...
 

SDD 的核心是「spec 先行」——意味着你会反复修改 spec。每次改 spec，整个 system prompt 前缀的缓存全部失效，之前省的全赔回去。

正确做法：用 cache_control 多断点分层：

system = [
    # 第一层：几乎永远不变（深度缓存）
    {"type": "text", "text": identity_and_tools,
     "cache_control": {"type": "ephemeral"}},
 
    # 第二层：版本迭代时才变（浅层缓存）
    {"type": "text", "text": architecture_rules,
     "cache_control": {"type": "ephemeral"}},
 
    # 第三层：每次开发会改（更浅缓存）
    {"type": "text", "text": current_sprint_spec,
     "cache_control": {"type": "ephemeral"}},
]
messages = [...]  # 不缓存
 

改 spec 时只有第三层之后的缓存失效，前两层仍然命中。

算一笔账（身份+架构 15000 token，spec 5000 token，每轮消息 3000 token，20 轮改 5 次 spec）：

不做分层：

项目计算费用
5 次写入20000 × 1.25 × 5125,000
15 次命中20000 × 0.1 × 1530,000
消息部分3000 × 2060,000
总计215,000 token

做了三层断点：

项目计算费用
第一层写入（1 次）15000 × 1.2518,750
第一层命中（19 次）15000 × 0.1 × 1928,500
spec 写入（5 次）5000 × 1.25 × 531,250
spec 命中（15 次）5000 × 0.1 × 157,500
消息部分3000 × 2060,000
总计146,000 token（省 32%）

spec 越大、改动越频繁，分层缓存的收益越高。

问题二：messages 一样会膨胀

即使是 API 用户，spec 通过工具返回进 messages 后一样膨胀。messages 没有缓存保护，每轮全价。场景一的 spec 拆分建议同样适用于 API 用户。

两个场景对比

工具用户API 开发者
prompt cache工具自动管你自己设 cache_control
spec 放哪docs/ 目录，模型按需读取system prompt 或 messages
SDD 破坏缓存吗不破坏，spec 进 messages 不进系统提示词看你放哪——放 system prompt 且频繁改才会
真正的代价上下文膨胀（messages 越来越胖）上下文膨胀 + 放错位置时缓存失效
怎么减缓CLAUDE.md 精简 + spec 拆分按需读多断点分层 + spec 拆分按需读

核心原则不变：不变的放前面缓存，会变的放后面不缓存，参考资料按需读取。

● ● ●

到底需不需要 SDD

到这里你应该理解了 SDD 的 token 代价。那到底要不要用？分三个维度判断。

维度一：既定项目 vs 从零搭建

既定项目有项目级 CLAUDE.md 索引：模型读索引就知道文件在哪，不需要额外写 spec。你要加功能只需要说："帮我加 XX 功能"，模型自己读相关文件。

既定项目没有 CLAUDE.md：模型到处猜文件，一次猜 5-6 个，token 白烧在搜索上。

没有 spec 的情况：
  你说："帮我加优惠券功能"
  模型：read package.json → read README → read src/ 结构
       → read orders/router.py → read orders/model.py
       → read users/service.py → read utils/payment.py
       → read config/settings.py → ...（到处翻）
  每个文件 500-2000 token，翻 10 个文件就是 5000-20000 token
 

先写一份精简 CLAUDE.md（200-500 token），省掉盲目翻文件：

CLAUDE.md（只需要这些）
 
技术栈：Flask + SQLAlchemy + PostgreSQL
核心目录：
  - orders/    订单模块（结算逻辑在这）
  - users/     用户模块
  - utils/     工具函数
开发约定：函数必须有类型标注，金额用分存储
 
不需要看的目录：
  - legacy/    废弃代码
  - scripts/   运维脚本
  - migrations/ 迁移文件
 

而且 spec 介绍了功能边界，你就能反向圈定不需要读的范围：

"帮我加优惠券功能，约束看 docs/feature-coupon.md。
 不需要读 legacy/、migrations/、tests/。
 只需要看 orders/router.py 和 users/service.py。"
 

一次少读 3-4 个文件，省几千 token。10 轮下来省的不是小数目。

项目状态spec 建议省 token 的方式
有 CLAUDE.md 索引不需要额外写在对话里圈定读取范围
没有 CLAUDE.md先写精简版避免模型盲目翻文件
有 spec 但模型还是乱翻在对话里明确说"只看 X 和 Y"反向排除不需要读的目录

从零搭建：两种策略。先写完整 spec（一致性有保障，但你得先想清楚）或不写 spec 边做边定（快速启动，但超 10 轮容易失控，失控就重来，重来就烧 token）。

维度二：单功能 vs 多模块

单功能：不需要 spec，但需要你在对话里把约束说清楚——说清楚本身就是一种轻量 spec，只不过不落盘。

❌ "优化一下这个接口"（模型猜你要什么 → 来回试 → 烧 token）
 
✅ "查三次数据库改成 Redis 缓存，TTL 5 分钟，参照 cache_helper.py"
 

单功能修改不需要 spec，但需要你在对话里把约束说清楚。

多模块：spec 的价值是把隐性约束显式化——优惠券和会员折扣能不能叠加？退单时券退不退？这些决策不写下来，模型只能猜，猜错就重来，重来就烧 token。

不写 spec 的后果：
- 模型改了结算逻辑，但不知道优惠券和会员折扣能不能叠加
- 上下文被压缩后，它忘了优惠券表有个"使用门槛"字段
- 结果：要么重复计算折扣，要么漏掉约束
- 你发现了，让模型改 → 又一轮 token
 

维度三：你能否确定 AI 一次做对

不确定时，与其在对话里反复试（每试一轮烧一轮 token），不如写一份功能级 spec 落盘：

docs/feature-coupon.md
 
- 优惠券和会员折扣不能叠加，取优惠更大的一个
- 退单时优惠券不退还
- 有效期 30 天
 
涉及改动：
- 新建 coupon 表：id, user_id, amount, threshold, status, expired_at
- orders/router.py 结算接口
- users/service.py 领取接口
 

不确定的时候，一份功能级 spec 比来回试错省得多。

高速迭代 / 日抛项目

需求每天变，写完整 spec 的维护成本比写代码还高。只写纠错 spec：

完整 spec（5000 token）：每天都在变 → 每天改 → 改 spec 比写代码还长
 
纠错 spec（500 token）：
- 金额一律用分（int），不用元（float）
- 时间一律 UTC
- user_id 是 varchar 不是 int
- 创建订单时要检查库存
→ 用痛苦换来的经验，几乎不会变，维护成本极低
 

什么时候从纠错 spec 升级到完整 spec？纠错 spec 积累到 20 条以上，或同一个坑踩了两次。

决策表

场景要不要 spec原因
既定项目，单功能，能说清楚不需要对话说清楚就行
既定项目，多模块改动功能级 spec隐性约束显式化，避免猜错重来
从零搭建，需求明确完整 spec一致性有保障
从零搭建，需求不确定先不要边做边定，超 10 轮停下来整理
高速迭代 / 日抛项目只写纠错 spec维护成本极低
探索性开发别用改 spec 比写代码还快

● ● ●

spec 写了不维护，比不写更烧 token

前面讲的都是「要不要写 spec」，还有个更隐蔽的问题：spec 写了不更新。

过时的 spec = 自信的错误文档

spec 写着："注册后分配 trial 角色，有效期 7 天"
产品改了：starter 角色，30 天
spec 没更新
 
模型读了 spec → 按 trial + 7 天写代码 → 你发现不对 → 让模型改
→ 模型又读了旧 spec → 又按旧约束改 → 死循环
 

过时的 spec 导致反复返工，每次返工都烧 token。 模型不会质疑 spec——对模型来说，docs/ 里写的比对话说的更"权威"。

防御方法：在每个 spec 文件顶部加一行最后更新时间和适用版本：

docs/api-spec.md
 
> 最后更新：2024-03-15 | 适用版本：v2.1
> 如果这个 spec 和代码冲突，以代码为准
 

在 CLAUDE.md 里加一条全局规则：

开发前先检查 docs/ 下 spec 的最后更新时间，
如果超过 2 周未更新，先 read 相关代码确认 spec 是否仍然有效。
 

什么时候不该写 spec

简单功能几次对话能搞定的，写 spec 的心智负担大于直接对话：

写 spec：打开文件 → 写需求 → 写约束 → 写涉及文件 → 保存 → 告诉模型读 → 10 分钟
不写 spec："给列表加搜索，参照 pagination.py" → 30 秒
 

spec 是给复杂决策用的，不是给简单功能用的仪式感。

大迭代用版本文件夹隔离

docs/
├── v1/                    ← 废弃，不要读
│   ├── api-spec.md
│   └── data-model.md
├── v2/                    ← 当前版本
│   ├── api-spec.md
│   └── module-payment.md
└── gotchas.md             ← 跨版本纠错，一直保留
 

CLAUDE.md 写"只读 docs/v2/"，模型不会误读 v1。

更进一步：大迭代的 spec 最好不要进 CLAUDE.md 索引。

CLAUDE.md 里写了 spec 索引：
  "API 设计：docs/v2/api-spec.md"
  → 模型每次启动都读这个文件（即使这次任务跟 API 无关）
 
CLAUDE.md 里不写索引，只在对话里按需指定：
  你："帮我改支付逻辑，读 docs/v2/module-payment.md"
  → 模型只在这一轮读这个文件
 

进索引 = 每轮自动加载；不进索引 = 用到才读。大迭代的 spec 变动频繁，不进索引更省 token。

维护成本总结

spec 类型维护成本过时后果建议
纠错 spec（gotchas.md）极低几乎不会过时强烈推荐
功能级 spec中误导模型，写错代码改功能时必须同步更新
完整项目 spec高严重误导，反复返工大迭代用版本文件夹隔离
不进索引的迭代 spec低只影响用到的会话推荐用于大版本迭代

● ● ●

廉价模型打草稿，强模型精修

如果 token 消耗实在大，可以用两个模型分工省 token：智谱 GLM-5.2 先写初版，GPT-5.6 精修。

强模型在已有代码上做优化，比从零写省得多——从零写需要理解全部上下文、做架构决策；优化只需要读现有代码做局部调整。

方案token 消耗效果
GPT-5.6 直接写100%最好
智谱打草稿 + GPT-5.6 优化~40% 贵 + ~60% 廉价接近最好，省 50%+
智谱全程30%够用但不完美

什么时候用：

任务类型建议原因
简单 CRUD直接廉价模型两步走的切换成本大于收益
复杂功能、多模块廉价打草稿 + 强模型精修强模型在初版上优化效率最高
Bug 修复直接强模型诊断比实现更重要
写测试、写文档直接廉价模型不需要创造力

注意：草稿和精修不要换会话，让强模型直接看到上下文。不要让弱模型做架构决策。

● ● ●

小结

问题答案
SDD 破坏缓存吗？工具用户不破坏（spec 进 messages）；API 用户放错位置才会
SDD 真正的代价？上下文膨胀——spec 重复读累积，messages 越来越胖，每轮全价计费
1M 窗口能救吗？不能——重复读 + 压缩丢信息 + 重读循环没变
怎么减缓？spec 拆分按需读，工具用 docs/，API 用多断点
上来读全部代码？别，把架构写进 CLAUDE.md
廉价 + 强模型可行吗？可行，省 50%+

SDD 的价值在于"先想清楚再写代码"。但想清楚的内容也要分层管理——不然你省下的思考时间全花在 token 费用上了。
