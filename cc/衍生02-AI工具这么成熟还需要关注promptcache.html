你的同事都搁那无脑 SDD——先写一份"完美"spec，然后让 AI 照着实现。他们用明白了吗？

spec 放哪里、读几次、和缓存什么关系、迭代了怎么办——这些问题大部分人都没想过。他们只知道「写 spec 很高级」，然后看着 token 账单流泪。

这一篇只回答一个问题：SDD 到底在哪里烧你的 token。

用工具的人（Claude Code / Cursor）和调 API 的人，烧的地方不一样。先讲原理，再分两个场景拆。

● ● ●

先搞清 token 在哪烧

根据 Anthropic 官方文档，每轮 API 调用的 prompt 被分成两段：

系统提示词前缀（不变 → 缓存命中 0.1×，几乎免费）
  ├── 身份声明
  ├── 工具定义
  └── CLAUDE.md
─────────── 缓存断点 ───────────
消息历史 messages（每次变 → 全价 1×）
  ├── 用户消息
  ├── 工具结果（read 文件内容在这）
  ├── assistant 回复
  └── ... 越来越胖
 

定价：

操作费用
正常输入1×
缓存写入1.25×（第一次贵 25%）
缓存读取0.1×（后续省 90%）

前缀缓存命中时省 90%，messages 每轮全价。 一条 5000 token 的 messages 历史，20 轮对话就是 100 万 token 的全价计费。

这就是 token 烧的地方：不是缓存断了，是 messages 越来越胖，每轮都在全价付账。

● ● ●

场景一：用 Claude Code / Cursor

工具用户有个错觉：prompt cache 工具帮我管了，不用操心。

缓存确实帮你管了——但只管前缀。messages 的 token 一个都没省。

spec 怎么烧 token

spec 不是塞进系统提示词的，是通过 read 工具读取后进 messages。每一次 read 的返回结果都是一条完整的 tool result，原封不动进 messages。

你 round 1：读 docs/api-spec.md → messages +5000 token
你 round 5：改了点东西，模型又读了一次 → messages +5000 token
你 round 10：新需求，模型再读一次 → messages +5000 token
 
同一个 spec 文件被读 3 次，messages 里就有 3 份完整内容。
其中 10000 token 是纯重复。
 

重复读取是 SDD 烧 token 的头号原因。 模型不会"记住上次读过的文件"——它要确保拿到最新版本，每次都重新 read，每次都产生新的 tool result。

1M 窗口也救不了你

你可能会说：现在 GLM-5.2、Claude 都有 1M 窗口了，spec 读几次才几万 token，够用吧？

拿 GLM-5.2 1M 窗口算：

  •  系统 提示词前缀约 20000 token（缓存命中）
  •  压缩触发线 ~83.5%：≈ 818000 token 可用于 messages
  •  每轮消耗（read spec + 回复 + write）≈ 10000 token
  •  理论能撑 ~80 轮

但 80 轮只是理论值。 实际上：

问题后果
同一文件重复读3 次 = 18000 token 纯重复
压缩触发后spec 内容被摘要替代，只剩"用户读取了某些文件"
压缩后模型要重读又一轮 read，又几千 token

1M 窗口推后了压缩时间，但没有消除"重复读 + 压缩丢信息 + 重读"的循环。

工具层为什么不做去重

你可能觉得：工具加个缓存，同一文件读过了就跳过？没那么简单。

文件可能在任意时刻被改：模型自己 write 改过、用户在编辑器里改过、git pull 更新了。如果工具层做了去重，上次读的内容可能已经过时——模型基于过时代码写逻辑，出 bug。

设计取舍是：宁可重复读浪费 token，也不能用过时内容写错代码。Claude Code 和 Pi 都没做去重。

怎么减缓 token 烧

既然重复读改不了，就在别处省：

CLAUDE.md 精简。 真实案例（来源）：1358 行精简到 807 行（减 41%），流程性规则移到 Skills。CLAUDE.md 是每轮缓存加载的，越小越省。

spec 拆分，按需读取。 不要写一个 5000 token 的大 spec，拆成模块文件，用到才读：

项目结构
├── CLAUDE.md          ← 全局架构 + spec 索引（精简，200 token）
├── docs/
│   ├── api-spec.md    ← API 设计（写接口时才读）
│   ├── data-model.md  ← 数据模型（改表时才读）
│   └── module-auth.md ← 认证模块（相关功能才读）
└── .claude/skills/
    ├── git-workflow   ← 提交规范（触发时才加载）
    └── deploy-check   ← 部署检查清单（触发时才加载）
 
载体放什么加载方式对 token 的影响
CLAUDE.md全局架构、spec 索引每轮自动加载越大每轮越贵
docs/详细 spec 文档模型按需读取用到才进 messages
Skills流程规则触发时才加载不触发不占 token

启动只读 CLAUDE.md，需求来了靠猜

Claude Code 启动时只读四样东西：身份声明、工具定义、全局 ~/.claude/CLAUDE.md、项目级 ./CLAUDE.md。你的项目代码一个都不会读。

需求来了之后，模型猜，不是全盘读：

你说："帮我改支付逻辑"
 
模型：
  1. 先看项目级 CLAUDE.md 有没有索引
     → 有："支付逻辑在 services/payment.py" → 直接读（1 个文件）
     → 没有 → 进入猜测模式
 
  2. 猜测模式：
     → ls 看目录结构 → 猜 payment.py / pay.py / checkout.py
     → 逐个 read 确认 → 每猜错一次 = 浪费 5000-6000 token
 

注意：全局 CLAUDE.md 管的是个人偏好（类型标注、代码风格），不会写项目文件结构。文件索引得写在项目级 CLAUDE.md（项目根目录 ./CLAUDE.md）里。

项目级 CLAUDE.md 写了索引，模型精准读 1 个文件；没写，猜 5-6 个才找到。猜的每一步都在烧 token。

别上来就读全部代码

有些人启动后第一句话："读取项目所有代码，理解整体架构"。别这么干。

烧 token：50 个文件全读 = 25000 token 进 messages，每轮全价计费，90% 跟你的任务无关。

信息稀释：读了 50 个文件，等你问支付逻辑时，相关信息被夹在 30 个无关文件中间。

读完也记不住：到第 5 轮，早期读的内容已经被压缩成摘要。

正确做法：把架构写进 CLAUDE.md，200 token 比读 50 个文件有效得多。然后在对话里圈定范围："不需要读 legacy/、migrations/、tests/，只看 orders/payment.py"。

spec 改了：新开会话还是老会话

这直接影响 token 消耗，不是小事。

老会话 15 轮，messages 约 40000 token
  → 每轮全价计费这 40000 token
  → 改 spec 后还要再读一遍（+5000 token）
  → 每轮实际计费 ~48000 token
 
新开会话
  → messages 从 0 开始
  → 读一次 spec（+5000 token）
  → CLAUDE.md 缓存命中（几乎免费）
  → 每轮实际计费 ~7000 token
 
spec 改动类型建议
小修（加字段、改约束）继续老会话
大改（重构模块、改架构）新开会话
纠正方向（模型理解错了）新开会话

经验值：老会话 < 10 轮继续，10-20 轮看改动，> 20 轮新开。不要一直在老会话里改需求——messages 越胖每轮越贵。

● ● ●

场景二：自己调 API 做 Agent

没有 CLAUDE.md 和 Skill 兜底，spec 放哪、缓存怎么管全靠自己。这时候 token 从两个地方流。

第一处：spec 塞进 system prompt 还频繁改

❌ 常见错误做法
 
system = [
    "你是一个资深工程师...",
    spec_document,               ← 整个 spec 塞进 system prompt
]
 
第 1 轮 spec v1 → 缓存写入（贵 25%）
第 2 轮 spec v1 → 缓存命中（省 90%）✓
第 3 轮 改了 spec → v2 → 缓存失效！重新写入
第 5 轮 又改了 → 又失效...
 

每次改 spec，整个 system prompt 前缀的缓存全部失效，之前省的全赔回去。

正确做法：用 cache_control 多断点分层：

system = [
    # 第一层：几乎永远不变（深度缓存）
    {"type": "text", "text": identity_and_tools,
     "cache_control": {"type": "ephemeral"}},
 
    # 第二层：版本迭代时才变（浅层缓存）
    {"type": "text", "text": architecture_rules,
     "cache_control": {"type": "ephemeral"}},
 
    # 第三层：每次开发会改（更浅缓存）
    {"type": "text", "text": current_sprint_spec,
     "cache_control": {"type": "ephemeral"}},
]
messages = [...]  # 不缓存
 

改 spec 时只有第三层之后的缓存失效，前两层仍然命中。20 轮对话省 32%。

第二处：messages 一样会膨胀

即使是 API 用户，spec 通过工具返回进 messages 后一样膨胀。messages 没有缓存保护，每轮全价。场景一的 spec 拆分建议同样适用于 API 用户。

两个场景对比

工具用户API 开发者
prompt cache工具自动管你自己设 cache_control
token 从哪烧messages 膨胀（spec 重复读）messages 膨胀 + 放错位置缓存失效
怎么省CLAUDE.md 精简 + spec 拆分多断点分层 + spec 拆分

核心原则不变：不变的放前面缓存，会变的放后面，参考资料按需读取。

● ● ●

到底需不需要 SDD

到这里你应该理解了 SDD 的 token 代价。那到底要不要用？分三个维度判断。

维度一：既定项目 vs 从零搭建

既定项目有项目级 CLAUDE.md 索引：模型读索引就知道文件在哪，不需要额外写 spec，token 花在精准读取上。

既定项目没有 CLAUDE.md：模型到处猜文件，一次猜 5-6 个，token 白烧在搜索上。先写一份精简 CLAUDE.md（200-500 token），省掉盲目翻文件。

而且 spec 介绍了功能边界，你就能反向圈定不需要读的范围：

"帮我加优惠券功能，约束看 docs/feature-coupon.md。
 不需要读 legacy/、migrations/、tests/。
 只需要看 orders/router.py 和 users/service.py。"
 

一次少读 3-4 个文件，省几千 token。

从零搭建：两种策略。先写完整 spec（一致性有保障，但你得先想清楚）或不写 spec 边做边定（快速启动，但超 10 轮容易失控）。

维度二：单功能 vs 多模块

单功能：不需要 spec，但需要你在对话里把约束说清楚——说清楚本身就是一种轻量 spec，只不过不落盘。

❌ "优化一下这个接口"（模型猜你要什么 → 来回试 → 烧 token）
 
✅ "查三次数据库改成 Redis 缓存，TTL 5 分钟，参照 cache_helper.py"
 

多模块：spec 的价值是把隐性约束显式化——优惠券和会员折扣能不能叠加？退单时券退不退？这些决策不写下来，模型只能猜，猜错就重来，重来就烧 token。

维度三：你能否确定 AI 一次做对

不确定时，与其在对话里反复试（每试一轮烧一轮 token），不如写一份功能级 spec 落盘：

docs/feature-coupon.md
 
- 优惠券和会员折扣不能叠加，取优惠更大的一个
- 退单时优惠券不退还
- 有效期 30 天
 
涉及改动：
- 新建 coupon 表
- orders/router.py 结算接口
- users/service.py 领取接口
 

不确定的时候，一份功能级 spec 比来回试错省得多。

高速迭代 / 日抛项目

需求每天变，写完整 spec 的维护成本比写代码还高。只写纠错 spec：

docs/gotchas.md
 
- 金额一律用分（int），不用元（float）
- 时间一律 UTC
- user_id 是 varchar 不是 int
- 创建订单时要检查库存
 

纠错 spec 是用痛苦换来的经验，几乎不会变，维护成本极低。

决策表

场景要不要 spec原因
既定项目，单功能，能说清楚不需要对话说清楚就行
既定项目，多模块改动功能级 spec隐性约束显式化，避免猜错重来
从零搭建，需求明确完整 spec一致性有保障
从零搭建，需求不确定先不要边做边定，超 10 轮停下来整理
高速迭代 / 日抛项目只写纠错 spec维护成本极低
探索性开发别用改 spec 比写代码还快

● ● ●

spec 写了不维护，比不写更烧 token

前面讲的都是「要不要写 spec」，还有个更隐蔽的 token 黑洞：spec 写了不更新。

过时的 spec = 自信的错误文档

spec 写着："注册后分配 trial 角色，有效期 7 天"
产品改了：starter 角色，30 天
spec 没更新
 
模型读了 spec → 按 trial + 7 天写代码 → 你发现不对 → 让模型改
→ 模型又读了旧 spec → 又按旧约束改 → 死循环
 

过时的 spec 导致反复返工，每次返工都烧 token。 模型不会质疑 spec——对模型来说，docs/ 里写的比对话说的更"权威"。

什么时候不该写 spec

简单功能几次对话能搞定的，写 spec 的心智负担大于直接对话：

写 spec：打开文件 → 写需求 → 写约束 → 写涉及文件 → 保存 → 告诉模型读 → 10 分钟
不写 spec："给列表加搜索，参照 pagination.py" → 30 秒
 

spec 是给复杂决策用的，不是给简单功能用的仪式感。

大迭代用版本文件夹隔离

docs/
├── v1/                    ← 废弃，不要读
│   ├── api-spec.md
│   └── data-model.md
├── v2/                    ← 当前版本
│   ├── api-spec.md
│   └── module-payment.md
└── gotchas.md             ← 跨版本纠错，一直保留
 

CLAUDE.md 写"只读 docs/v2/"，模型不会误读 v1。大迭代的 spec 最好不要进 CLAUDE.md 索引——用到才在对话里指定，不被动加载。

● ● ●

廉价模型打草稿，强模型精修

如果 token 消耗实在大，可以用两个模型分工省 token：智谱 GLM-5.2 先写初版，GPT-5.6 精修。

强模型在已有代码上优化，比从零写省得多。

方案token 消耗效果
GPT-5.6 直接写100%最好
智谱打草稿 + GPT-5.6 优化~40% 贵 + ~60% 廉价接近最好，省 50%+
智谱全程30%够用但不完美

注意：草稿和精修不要换会话，让强模型直接看到上下文。不要让弱模型做架构决策。

● ● ●

小结

问题答案
SDD 烧 token 在哪？messages 膨胀——spec 重复读，每轮全价计费
1M 窗口能救吗？不能——重复读 + 压缩丢信息 + 重读循环没变
工具用户怎么省？CLAUDE.md 精简 + spec 拆分按需读 + 圈定范围
API 用户怎么省？cache_control 多断点分层
spec 过时怎么办？过时 spec 比没 spec 更烧 token（反复返工）
上来读全部代码？别，把架构写进 CLAUDE.md
廉价 + 强模型可行吗？可行，省 50%+

SDD 的价值在于"先想清楚再写代码"。但想清楚的内容也要分层管理——不然你省下的思考时间全花在 token 费用上了。
