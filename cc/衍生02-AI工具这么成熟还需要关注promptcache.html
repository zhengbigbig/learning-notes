你的同事都搁那无脑 SDD——先写一份"完美"spec，然后让 AI 照着实现。他们用明白了吗？

spec 放哪里、读几次、和缓存什么关系、迭代了怎么办、多人协作谁维护——这些问题大部分人都没想过。他们只知道「写 spec 很高级」，然后看着 token 账单流泪。

看完这一篇，下次同事再吹 SDD 的时候，你也有话讲。

SDD（Spec-Driven Development，规范驱动开发）本身不是坏东西：先写需求文档，让 AI 按文档实现。但 SDD 的真正代价不在你想的地方。用工具的人和调 API 的人，踩的坑完全不同。

● ● ●

先搞清 prompt cache 在干什么

根据 Anthropic 官方文档，机制很简单：

API 服务商把你请求的前半段存下来，下次前半段没变就直接用缓存。

大模型推理分两步：先把输入的 token 全部转成 KV Cache（键值缓存），再基于这个缓存逐个生成输出。如果两次请求的前缀一模一样，算出来的 KV Cache 也一模一样，服务商直接复用，跳过整个前置计算。

请求 1：[系统提示词 + 工具列表 + CLAUDE.md] + 用户消息A
         ↑ 这部分算出的 KV Cache 存入缓存
 
请求 2：[系统提示词 + 工具列表 + CLAUDE.md] + 用户消息B
         ↑ 前缀没变 → 取缓存，不重算
         ↑ 只算新增部分
 

定价模型：

操作费用
正常输入1×
缓存写入1.25×（第一次贵 25%）
缓存读取0.1×（后续省 90%）
TTL5 分钟，每次命中自动续期

缓存命中省掉的不只是钱——而是整个前缀的前向计算。 不命中时模型要算完前缀才能吐第一个字，命中时直接跳过。20 轮对话累计下来，光等前缀重算就能差几分钟。

缓存边界把 prompt 一分为二：

静态前缀（可缓存）动态后缀（不缓存）
① 系统提示词④ 本轮用户消息
② 工具列表⑤ 工具结果
③ CLAUDE.md⑥ 对话历史
每次都一样 → 缓存命中每次都变 → 全价计费

理解了这个边界，后面两种场景的坑才能看清楚。

● ● ●

场景一：用 Claude Code / Cursor（工具用户）

大多数人不直接调 API，用的是 Claude Code 或 Cursor。这种场景下 prompt cache 工具帮你包了，你完全不用操心。

Claude Code 的实际工作流：

系统提示词前缀（不变 → 缓存命中）
  ├── 身份声明
  ├── 工具定义
  └── CLAUDE.md（全局 + 项目级）
─────────── 缓存断点 ───────────
消息历史 messages（每次变 → 全价计费）
  ├── 用户："读 docs/api-spec.md"
  ├── 工具结果：spec（5000 token）
  ├── assistant 回复
  ├── 用户："再读 data-model.md"
  ├── 工具结果：另一份 spec（5000 token）
  └── ... 越来越胖
 

spec 不是塞进系统提示词的，是通过 read 工具读取后进 messages。CLAUDE.md 里只放一个 spec 索引（200 token），不会反复改。工具定义也不变。系统提示词前缀的缓存一直稳定命中。

那 SDD 的真正代价是什么？是 messages 膨胀。

每次 read spec 的内容都进对话历史。一份 5000 token 的 spec，读 3 次就是 15000 token。再加上 assistant 回复和工具执行结果，几轮下来 messages 膨胀到几万 token：

spec 反复读取
  → messages 快速膨胀
  → 上下文窗口更快耗尽
  → 更早触发上下文压缩
  → 压缩后 spec 内容可能丢失
  → 下一轮又得重读 spec
  → messages 再次膨胀...（死循环）
 

SDD 的代价不是缓存失效，而是上下文窗口被 spec 内容快速吃满。缓存一直在好好工作，但你的消息历史越来越胖，每轮全价计费的 token 越来越多。这就是为什么你感觉 token 消耗飞快——在流泪的不是缓存，是你的 token。

等等，现在上下文已经有 1M 了

你可能会说：现在 Claude、GPT、智谱 GLM 都有 1M 上下文窗口了，spec 读几次才几万 token，离撑爆还远着吧？

那就拿 GLM-5.2 的 1M 窗口算一笔具体的账。

一个 500 行的文件，能读多少个？

一个 500 行的代码文件，大约 5000-6000 token（代码 token 密度比纯文本高）。

系统提示词前缀（身份 + 工具定义 + CLAUDE.md）大约占 20000 token，这部分缓存命中不膨胀。

剩余可用空间：1M - 20000 = ~980000 token。

压缩触发线 ~83.5%：980000 × 83.5% ≈ 818000 token。

每轮读取量能撑多少轮能读多少个文件
每轮读 1 个文件（6000 token）+ 回复 4000 token~80 轮~80 个
每轮读 2 个文件（12000 token）+ 回复 6000 token~45 轮~90 个
每轮读 3 个文件（18000 token）+ 回复 8000 token~30 轮~90 个

看起来很多？但实际情况没这么乐观。

没被压缩时，模型会重复读同一个文件吗？

会，而且每次都产生新的 tool result。

Round 1:  你："帮我改支付逻辑"
          模型: read orders/payment.py → 6000 token 进 messages
                写代码 → 4000 token 进 messages
 
Round 5:  你："再加个退款逻辑"
          模型: read orders/payment.py → 又 6000 token 进 messages
                （第一轮读的内容还在 messages 里，但模型选择再读一次确保最新）
                写代码 → 5000 token
 
Round 10: 你："改一下退款的手续费计算"
          模型: read orders/payment.py → 又 6000 token 进 messages
                （此时 messages 里已经有了 3 份 payment.py 的内容）
 

同一个文件被读 3 次，messages 里就有 3 份完整内容，18000 token 全是重复的。

模型为什么会重复读？因为它要确保拿到的是最新版本——你可能在 round 5 改了代码，round 1 读的内容已经过时了。模型没法判断"这个文件我上次读完之后有没有被修改过"，保险起见就再读一次。

这就是 token 浪费的重灾区：不是读了多少个文件，而是同一个文件被读了多少次。

被压缩了呢？

到了 ~83.5%，自动压缩触发。之前读的文件内容全部被摘要掉：

压缩前（818000 token）：
  [tool result] payment.py 完整内容（6000 token）
  [assistant] 写了支付逻辑代码（4000 token）
  [tool result] order.py 完整内容（6000 token）
  [tool result] payment.py 又读了一次（6000 token）
  [assistant] 改了退款逻辑（5000 token）
  ... 几十条消息
 
压缩后（~200000 token）：
  [摘要] 用户开发了一个支付模块，修改了退款逻辑，
         读取了 orders/payment.py 和 orders/order.py。
  ... 几行摘要
 

文件的具体内容没了，只剩"用户读取了哪些文件"这种笼统摘要。

这时候如果你说"帮我改手续费计算"，模型会发现上下文里没有 payment.py 的实际代码（被摘要掉了），必须重新 read。而且这次读回来的内容，跟摘要里的信息可能对不上——模型要花额外 token 理解"之前的摘要说做了退款逻辑，但现在的代码里退款逻辑长这样"。

需求来了：模型猜文件还是全盘读？

猜，不是全盘读。

Claude Code（或任何 Agent 工具）启动时只读了 CLAUDE.md，对你的项目结构一无所知。需求来了之后：

你说："帮我改支付逻辑"
 
模型做的决策：
  1. 看 CLAUDE.md 有没有提到支付相关文件
     → 有："支付逻辑在 services/payment.py" → 直接读
     → 没有 → 进入猜测模式
 
  2. 猜测模式（CLAUDE.md 没写）：
     → 先看目录结构（ls / glob）
     → 猜测可能是 payment.py / pay.py / checkout.py
     → 逐个 read 确认
     → 猜错了就换一个文件继续读
     → 每猜错一次 = 浪费 5000-6000 token
 
  3. 全盘读（极端情况）：
     → 只发生在 CLAUDE.md 没写 + 目录结构也猜不出
     → 模型可能尝试 read 多个文件
     → 但不会真的"读全部代码"，成本太高模型自己会收手
 

CLAUDE.md 写得好，模型精准读 1 个文件；写得烂，模型猜 5-6 个才找到。这就是为什么 CLAUDE.md 这么重要——它决定了模型从"猜"到"精准定位"的距离。

总结：1M 窗口下的实际情况

问题答案
500 行文件能读多少个？理论 ~80-90 个，但实际更少（重复读取）
同一文件会被重复读吗？会，每次 read 产生独立 tool result，不去重
没压缩时旧内容还在吗？在，但模型为确保最新会重读
压缩后文件内容还在吗？不在，被摘要替代，只剩"读取了哪些文件"
需求来了怎么找文件？猜——CLAUDE.md 有索引就精准读，没有就逐个试

1M 窗口不是免死金牌：重复读取会吃掉你以为充裕的空间，压缩后还得重读，猜文件会浪费大量 token。

工具用户怎么减缓膨胀

CLAUDE.md 保持精简。 真实案例（来源）：有用户把 1358 行规则精简到 807 行（减 41%），方法就是把流程性规则移到按需加载的 Skills。

项目结构
├── CLAUDE.md          ← 全局架构 + spec 索引（精简，200 token）
├── docs/
│   ├── api-spec.md    ← API 设计（模型只在写接口时读）
│   ├── data-model.md  ← 数据模型（模型只在改表时读）
│   └── module-auth.md ← 认证模块（相关功能才读）
└── .claude/skills/
    ├── git-workflow   ← 提交规范（触发时才加载）
    └── deploy-check   ← 部署检查清单（触发时才加载）
 

三层载体各管不同的事：

载体放什么加载方式对上下文的影响
CLAUDE.md全局架构、技术栈、spec 索引每轮自动加载越大每轮越贵
docs/详细 spec 文档模型按需读取用到才进 messages
Skills流程规则触发时才加载不触发不占 token

判断标准：每轮都用 → CLAUDE.md；有明确触发时机 → Skill；是参考文档 → docs/。

Claude Code 启动时到底读了什么

很多人以为 Claude Code 启动时会扫描整个项目目录、建立完整记忆。并没有。

实际启动过程：

启动时读的（进系统提示词前缀，缓存命中）：
  1. 身份声明（你是 Claude Code...）
  2. 工具定义（read/write/bash/...）
  3. 全局 ~/.claude/CLAUDE.md
  4. 项目级 ./CLAUDE.md
 
不读的（你的项目代码、docs/、其他文件）：
  → 全部等到用户消息进来之后
  → 模型根据用户消息"猜"要读哪些文件
  → 用 read 工具按需读取
 

启动时 Claude Code 对你的项目几乎一无所知。它只知道 CLAUDE.md 里写的那些内容。你的项目有 100 个文件还是 10000 个文件，启动时没区别——它一个都不会读。

这就是为什么 CLAUDE.md 这么重要：它是模型启动时唯一能拿到手的项目记忆。CLAUDE.md 写得好，模型第一次对话就能精准定位要读哪些文件；CLAUDE.md 没写或写得烂，模型只能靠猜——猜错了就读一堆没用的文件，浪费 token。

CLAUDE.md 写得好：
  你："帮我改支付逻辑"
  模型：CLAUDE.md 说了支付逻辑在 orders/payment.py
       → 直接读 orders/payment.py → 写代码
  总计：读 1 个文件
 
CLAUDE.md 没写或写得烂：
  你："帮我改支付逻辑"
  模型：不知道支付逻辑在哪
       → read package.json → read src/ 目录结构
       → read orders/ 目录结构 → read orders/payment.py
       → read orders/model.py → read config/settings.py → ...
       → 猜了 5-6 个文件才找到
  总计：读 5-6 个文件，多花几千 token
 

CLAUDE.md 本质上是一份「项目导航」——告诉模型什么东西在哪，省掉盲目搜索的成本。这跟前面讲的「spec 索引 + 反向圈定读取范围」是同一件事：你不告诉模型去哪找，它就得自己找，找的每一步都在烧 token。

"读取项目所有代码，理解整体架构"——别这么干

有些人启动 Claude Code 或类似工具后，第一句话就是："读取项目所有代码，理解一下整体架构"。

别这么干。原因有三层：

第一层：token 成本。 一个中等项目 50 个文件，平均每个 500 token，全读一遍就是 25000 token 进 messages。这些 token 每轮全价计费，而且大部分内容跟你这次要做的任务毫无关系。你只是想改一个支付 bug，模型却被迫背下了整个 README、所有测试文件、配置文件、迁移脚本。

第二层：信息稀释。 前面讲过「lost in the middle」——上下文越长，关键信息越容易被淹没。你让模型读了 50 个文件，等你真正问"帮我改支付逻辑"的时候，支付相关的信息已经被夹在 30 个无关文件的中间了。读得越多，模型反而越容易漏掉关键细节。

第三层：读完也记不住。 就算模型读了所有文件，到了第 5 轮对话，早期读的文件内容已经被压缩成摘要或直接丢弃了。你花了几万 token 让模型"理解架构"，到第 5 轮它什么都不记得。

正确做法：等具体需求来了再读。

❌ "读取项目所有代码，理解整体架构"
   → 读 50 个文件，25000 token 进 messages
   → 90% 的内容跟你的任务无关
   → 每轮全价计费这 25000 token
   → 关键信息被稀释
 
✅ "帮我改支付逻辑，支付相关代码在 orders/payment.py"
   → 读 1 个文件，500 token
   → 100% 相关
   → 后续每轮只付这 500 token
   → 信息集中，不稀释
 

如果你确实想让模型"理解架构"，把架构写进 CLAUDE.md 而不是让它读代码：

CLAUDE.md：
 
项目架构：
  入口：app.py（Flask 应用）
  路由：routes/（每个文件一个模块）
  模型：models/（SQLAlchemy 定义）
  服务层：services/（业务逻辑在这）
  工具：utils/（分页、缓存等）
 
核心模块：
  - services/payment.py    支付（支付宝 + 微信）
  - services/order.py      订单状态机
  - routes/user.py         用户 CRUD
 

这几行字 200 token，比读 50 个文件的 25000 token 有效得多。模型一读 CLAUDE.md 就知道架构了，不需要你额外花一轮对话去"建立记忆"。

spec 拆分，按需读取。 不要把整个项目的 spec 写成一个 5000 token 的大文件。拆成模块：读一个模块 1500 token，比读整个项目 5000 token 省得多。

spec 改了之后让模型重读。 在对话里明确说一句："我更新了 docs/api-spec.md，请重新读一下"。不要假设模型记得旧版本的内容。

spec 改了：新开会话还是继续老会话？

这是 SDD 实践中最常遇到的问题。改了 spec 之后，是在老会话里继续，还是开个新的？

先看两种选择各自发生了什么：

继续老会话：
  前缀（CLAUDE.md + 工具定义）→ 缓存命中 ✓
  老的 messages 历史 → 全价计费（带着旧 spec 内容、旧代码、旧讨论）
  新消息："spec 改了，重新读 docs/api-spec.md" → 模型读新版 spec
  但旧版 spec 的内容还在历史里 → 模型可能混淆新旧约束
 
新开会话：
  前缀 → 缓存命中 ✓（CLAUDE.md 没变）
  messages 从零开始 → 只有本轮的 spec 读取 + 对话
  模型不会被旧 spec 内容干扰
  但之前讨论的上下文（为什么这么设计、踩过什么坑）全部丢失
 

关键矛盾：老会话省了重新理解项目背景的成本，但拖着旧 messages 的 token 负担; 新会话消息干净，但模型要从零理解你的项目。

怎么选？看改的是哪类 spec：

spec 改动类型建议原因
小修（加一个字段、改一个约束）继续老会话改动小，老会话的上下文有价值，重读一次 spec 就行
大改（重构模块、改架构、加子系统）新开会话旧会话里的代码和讨论都失效了，留着只是 token 负担和混淆源
纠正方向（模型理解错了，要重来）新开会话老会话的错误上下文会持续干扰，越改越偏

还有一个隐藏因素：老会话的 messages 有多胖。

老会话已经 15 轮，messages 约 40000 token
  → 每轮这 40000 token 全价计费
  → 改 spec 后还要再读一遍 spec（+5000 token）
  → 加上压缩后的摘要（+3000 token）
  → 每轮实际计费 48000 token
 
新开会话
  → messages 从 0 开始
  → 读一次 spec（+5000 token）
  → 加上 CLAUDE.md（缓存命中，几乎免费）
  → 每轮实际计费 ~7000 token
 

当老会话的 messages 膨胀到一定体积，新开会话反而更省 token。粗略的经验值：

  •  老会话 < 10 轮 → 继续，上下文还有价值
  •  老会话 10-20 轮 → 看改动大小，小改继续，大改新开
  •  老会话 > 20 轮 → 新开。messages 太胖，每轮的全价 token 成本已经远超重新理解项目的成本

一句话：不要一直在老会话里改需求。老会话像一锅越煮越浓的汤，到一定浓度就该倒掉重来。你可以在 CLAUDE.md 或 docs/ 里留下关键决策（比如"支付模块用分存储"），新会话里模型一读就知道了——不需要靠会话历史来记忆。

● ● ●

场景二：自己调 API 做 Agent

如果你直接调 Anthropic API 做 Agent 产品，没有 CLAUDE.md 和 Skill 帮你兜底。这时候 spec 放哪、缓存怎么管，全靠你自己。

好消息是 Anthropic API 支持最多 4 个 cache_control 断点（文档），你可以精确控制哪部分缓存、哪部分不缓存。

坏消息是很多人把 spec 硬塞进 system prompt，然后频繁改 spec——这才是缓存真正的杀手：

❌ 常见错误做法
 
system = [
    "你是一个资深工程师...",
    spec_document,               ← 整个 spec 塞进 system prompt
]
 
第 1 轮 spec v1 → 缓存写入（贵 25%）
第 2 轮 spec v1 → 缓存命中（省 90%）✓
第 3 轮 改了 spec → v2 → 缓存失效！重新写入
第 4 轮 spec v2 → 缓存命中 ✓
第 5 轮 又改了 → 又失效...
 

SDD 的核心是「spec 先行」——意味着你会反复修改 spec。每次改 spec，整个 system prompt 前缀的缓存全部失效。

正确做法：用多断点分层

system = [
    # 第一层：几乎永远不变（深度缓存）
    {"type": "text", "text": identity_and_tools,
     "cache_control": {"type": "ephemeral"}},  # 断点 1
 
    # 第二层：版本迭代时才变（浅层缓存）
    {"type": "text", "text": architecture_rules,
     "cache_control": {"type": "ephemeral"}},  # 断点 2
 
    # 第三层：每次开发会改（更浅缓存）
    {"type": "text", "text": current_sprint_spec,
     "cache_control": {"type": "ephemeral"}},  # 断点 3
]
messages = [...]  # 不缓存
 

改 spec 时只有第三层之后的缓存失效，前两层仍然命中。

算一笔账

假设你的 SDD 项目：

  •  身份 + 工具 + 架构规范：15000 token（几乎不变）
  •  当前迭代的 spec：5000 token（每 2-3 天改一次）
  •  每轮用户消息 + 工具结果：平均 3000 token

不做缓存分层（整个 spec 一起缓存），20 轮对话改了 5 次：

项目计算费用
5 次写入20000 × 1.25 × 5125,000
15 次命中20000 × 0.1 × 1530,000
消息部分3000 × 2060,000
总计215,000 token

做了三层断点，改 spec 时只有第三层失效（5000 token），前两层命中：

项目计算费用
第一层写入（1次）15000 × 1.25 × 118,750
第一层命中（19次）15000 × 0.1 × 1928,500
spec 写入（5次）5000 × 1.25 × 531,250
spec 命中（15次）5000 × 0.1 × 157,500
消息部分3000 × 2060,000
总计146,000 token（省 32%）

spec 越大、改动越频繁，分层缓存的收益越高。

API 用户也要管上下文

即使是 API 用户，spec 通过工具返回进 messages 后，一样会膨胀。messages 部分没有缓存保护，每轮全价计费。所以场景一的 spec 拆分建议同样适用于 API 用户。

● ● ●

上下文压缩也和 SDD 有关

不管用工具还是调 API，Claude Code 在每轮调模型前会做上下文压缩。压缩只处理对话历史（messages），不会动 system prompt 前缀——所以缓存依然命中，只是 messages 部分更省。

压缩策略从轻到重分四步：

步骤做什么成本
① 大结果落盘工具输出超阈值就存到文件，上下文里只留预览0 API 调用
② 超长结果裁剪早期的大结果只保留头尾0 API 调用
③ 清理冗余去掉格式噪声和零碎内容0 API 调用
④ 历史摘要全部不够才压成摘要1 API 调用

前三步是纯文本操作，最后一步才花一次 API 调用。不是等报错后才救火，而是每次调用前都体检。

但压缩有个副作用：spec 内容被压缩后可能丢失关键约束。模型在第 1 轮读了 spec，到第 10 轮时这段内容可能已被压成一句话摘要。如果摘要丢了"所有金额字段用分存储"这条约束，模型就会写出用元存储的代码。

这就是 SDD 在长对话中的真正风险——不是缓存失效，而是 spec 内容在压缩中丢失。

● ● ●

两个场景的对比

工具用户（Claude Code）API 开发者
prompt cache工具自动管，不用操心你要自己设 cache_control 断点
spec 放哪docs/ 目录，模型按需读取system prompt 或 messages
SDD 破坏缓存吗不破坏，spec 进 messages 不进系统提示词看你放哪——放 system prompt 且频繁改才会
真正的代价上下文膨胀（messages 越来越胖）上下文膨胀 + 放错位置时缓存失效
怎么减缓CLAUDE.md 精简 + spec 拆分按需读多断点分层 + spec 拆分按需读

核心原则不变：不变的放前面缓存，会变的放后面不缓存，参考资料按需读取

● ● ●

到底需不需要 SDD

不是「看复杂度」一句话能概括的。要分三个维度判断：是既定项目还是从零搭建、是单功能还是多模块、你能不能确定 AI 能做对。

维度一：既定项目 vs 从零搭建

既定项目里加功能——项目已经有代码、有架构、有约定。但这里要分两种情况：

情况 A：项目有核心规则 spec（CLAUDE.md / docs/ 写好了约束）

模型进项目先读 CLAUDE.md，就知道技术栈、架构约定、spec 索引。你要加功能，只需要说："帮我加 XX 功能"，模型自己去读相关文件和 spec。

"帮我在 users/router.py 里加一个修改密码的接口，
需要验证旧密码，新密码用 bcrypt，
参照同文件 reset_password 的风格"
 

模型读 CLAUDE.md（知道全局约束）→ 读 users/router.py（知道代码风格）→ 直接写。你不需要额外写 spec。

而且有个省 token 的技巧：如果 spec 已经把功能边界和约束写清楚了，你可以在对话里明确告诉模型哪些文件不用读：

"帮我加优惠券功能，约束看 docs/feature-coupon.md。
 不需要读 orders/old_legacy/ 目录（废弃代码），
 不需要读 migrations/ 目录（数据库迁移脚本），
 不需要读 tests/ 目录（我后面单独写测试）。
 只需要看 orders/router.py 和 users/service.py。"
 

spec 介绍了功能边界，你就能反向圈定模型不需要看的范围。一次 read 少读 3-4 个文件，省几千 token。10 轮下来省的不是小数目。

情况 B：项目没有核心规则 spec（裸项目，只有代码没有文档）

模型进来只看到一堆文件，不知道架构约定、不知道哪些是核心代码哪些是废弃代码、不知道命名规范。这时候模型会大量 read 文件来摸索上下文——它不知道该看哪个，就会到处翻。

没有 spec 的情况：
  你说："帮我加优惠券功能"
  模型：read package.json → read README → read src/ 结构
       → read orders/router.py → read orders/model.py
       → read users/service.py → read utils/payment.py
       → read config/settings.py → ...（到处翻）
  每个文件 500-2000 token，翻 10 个文件就是 5000-20000 token
 

这种情况下，一份简短的 CLAUDE.md（200-500 token）就能省掉大量无意义的文件读取：

CLAUDE.md（只需要这些）
 
技术栈：Flask + SQLAlchemy + PostgreSQL
核心目录：
  - orders/    订单模块（结算逻辑在这）
  - users/     用户模块
  - utils/     工具函数
开发约定：函数必须有类型标注，金额用分存储
 
不需要看的目录：
  - legacy/    废弃代码
  - scripts/   运维脚本
  - migrations/ 迁移文件
 

CLAUDE.md 本质上是一份「文件索引 + 读取范围」指南。它告诉模型该看哪、不该看哪，省掉盲目翻文件浪费的 token。

所以既定项目的 spec 策略是：

项目状态spec 建议省 token 的方式
有核心规则 spec不需要额外写在对话里圈定读取范围
没有核心规则 spec先写一份精简 CLAUDE.md避免模型盲目翻文件
有 spec 但模型还是乱翻在对话里明确说"只看 X 和 Y"反向排除不需要读的目录

从零到一搭建新项目——空目录开始，模型没有任何上下文可以读。这时候有两种策略：

策略 A：先写完整 spec，再按模块实现。优点是一致性有保障，代价是你得先把整个项目想清楚。

策略 B：不写 spec，边做边定（"帮我搭个 Flask 骨架" → "加订单模块" → ...）。优点是快速启动，代价是超过 10 轮容易失控。

维度二：单功能 vs 多模块

这个维度决定了 spec 的粒度。

单功能修改：改一个接口、加一个字段、修一个 bug。模型 read 相关文件后，大概率能一次做对。不需要写 spec。

但有个前提：你能准确描述这个功能。如果你的描述本身就是模糊的——"帮我优化一下这个接口的性能"——模型只能猜你要什么。这种情况下，与其写 spec，不如先把你的需求在对话里说清楚：

❌ "优化一下这个接口"（模型不知道你要什么）
 
✅ "这个接口现在每次请求都查三次数据库，
    把用户信息和权限分开缓存到 Redis，
    TTL 设 5 分钟，参照 cache_helper.py 的写法"
 

单功能修改不需要 spec，但需要你在对话里把约束说清楚。 说清楚本身就是一种轻量 spec——只不过它不落盘，不独立成文件。

多模块改动：涉及多张表、多个接口、跨模块约束。比如给电商后台加优惠券——优惠券表（新建）、订单结算（改）、用户权益（改）、营销活动（改）。

不写 spec 的后果：
- 模型改了结算逻辑，但不知道优惠券和会员折扣能不能叠加
- 上下文被压缩后，它忘了优惠券表有个"使用门槛"字段
- 结果：要么重复计算折扣，要么漏掉约束
 

多模块改动的 spec 价值不是"指导 AI 写代码"，而是"把你自己脑子里的隐性约束显式化"。你写 spec 的过程就是在逼自己想清楚：优惠券和会员折扣能不能叠加？有效期怎么算？退单时券还退不退？这些决策不写下来，模型只能猜。

维度三：你能否确定 AI 能做对

这个维度最容易被忽略。

确定能做对：功能边界清晰、有参照代码、改动范围小。直接对话就行。

不确定能不能做对：需求模糊、涉及业务逻辑判断、没有现成参照。这时候有两种选择：

选择 A：在对话里反复试——让模型先写，你看了不对再让它改，来回几轮。代价是 token 和时间，以及来回改的过程中上下文越来越乱。

选择 B：写一份功能级 spec，只覆盖这次改动涉及的约束。

docs/feature-coupon.md（功能级 spec 示例）
 
## 优惠券功能
- 优惠券有面额（分）和使用门槛（满 N 分可用）
- 优惠券和会员折扣不能叠加，取优惠更大的一个
- 退单时优惠券不退还
- 有效期从领取日开始，30 天过期
 
## 涉及改动
- 新建 coupon 表：id, user_id, amount, threshold, status, expired_at
- orders/router.py 结算接口：计算最终金额时先比优惠券和会员折扣
- users/service.py：领取优惠券接口
 

功能级 spec 不是大而全的项目文档，只写这次改动涉及的决策。写完之后无论新开会话还是继续老会话，模型一读就知道边界在哪。不确定的时候，一份功能级 spec 比来回试错省得多。

特殊场景：高速迭代 / 日抛项目

有一种项目很特殊：需求每天都在变，代码今天写明天改。创业验证期、hackathon、快速试错的产品——这类项目的生命周期可能只有一两周。

很多人会想：既然项目变动这么快，要不要写一份完整的项目功能 spec，让模型每次都读？

答案是：不要写完整 spec，只写纠错 spec。

原因很直白：

完整的项目功能 spec（5000 token）：
- 介绍项目是做什么的
- 列出所有模块和接口
- 描述每个功能的具体逻辑
- 每天都在变 → 每天都要改 spec → 改 spec 的时间比写代码还长
 
纠错 spec（500 token）：
- 只记录 AI 出过错的约束
- "金额字段用分存储，不用元"
- "所有时间用 UTC，不用本地时区"
- "用户 ID 是字符串不是数字"
- 很少变 → 写一次管很久
 

完整 spec 描述的是"项目是什么"，纠错 spec 描述的是"AI 容易在哪犯错"。高速迭代的项目，前者每天都在变，维护成本极高；后者只在实际踩坑后才追加，它是用痛苦换来的经验，不会轻易变。

什么时候从纠错 spec 升级到完整 spec？当纠错 spec 积累到 20 条以上，或者同一个坑踩了两次的时候。这说明项目复杂度已经到了需要系统性文档的阶段，靠零散的纠错记录已经不够了。

实际操作：

docs/gotchas.md（纠错 spec 示例）
 
## AI 容易犯的错
- 金额一律用分（int），不用元（float）
- 时间一律 UTC，存数据库前转
- user_id 是 varchar 不是 int（历史遗留，别改）
- 创建订单时要检查库存，别只扣不减
- pay_callback 接口的签名验证在 middleware 里，别在路由里重复写
 

每次 AI 犯了错，你就在 gotchas.md 里加一条。 下次新开会话，模型一读就知道这些坑在哪。比起一份每天都在变的完整 spec，一份几百字的纠错清单反而更实用。

决策表

场景需要 spec 吗什么样的 spec
既定项目，单功能，能说清楚不需要对话里把约束说清楚就行
既定项目，单功能，说不清楚先把需求想清楚对话里描述清楚，或写几行要点
既定项目，多模块改动需要功能级 spec，只写跨模块约束和决策
既定项目，不确定 AI 能不能做对需要功能级 spec，把边界和约束显式化
从零搭建，需求明确需要完整 spec（架构 + 数据模型 + 接口）
从零搭建，需求不确定先不要快速搭骨架，超过 10 轮停下来整理
高速迭代 / 日抛项目只写纠错 specgotchas.md，只记 AI 犯过的错
探索性开发（就是来试的）别用你改 spec 的速度比模型写代码还快

核心判断标准：你对需求有多确定，以及你能否保证 AI 一次做对。需求确定、能做对 → 不需要 spec；需求不确定、怕做错 → 写功能级 spec 落盘；高速迭代 → 只写纠错 spec。

但不管哪种情况，一旦项目超过 10 轮，就必须把关键决策落到 docs/ 里。不是因为 SDD 高级，而是因为模型的上下文会丢——spec 文件是唯一不会丢的项目记忆。

● ● ●

spec 维护的隐性成本

前面一直在讲「要不要写 spec」，但有个更现实的问题：spec 写了之后谁来维护？

spec 过时比没有 spec 更危险

团队多人协作或长期迭代的项目里，最常见的情况是：有人写了一份功能 spec，然后功能改了，代码更新了，spec 忘了更新。

docs/api-spec.md 写着：
  "用户注册后自动分配 trial 角色，有效期 7 天"
 
但产品上周改了：
  注册后分配 starter 角色，有效期 30 天
  spec 没更新
 
新来的开发者（或 AI）读了 spec：
  → 写代码用了 trial 角色 + 7 天
  → 上线后用户投诉：怎么只有 7 天？
 

没有 spec 时，模型至少会去读代码确认；有过时的 spec 时，模型会信任 spec，反而被误导。过时的 spec 是一份自信的错误文档。

什么情况可以不写 spec

如果你的功能复杂度不高，几次对话就能搞定，写 spec 的心智负担反而大于直接对话：

情况：给用户列表加一个搜索功能
 
写 spec 的流程：
  1. 打开 docs/feature-search.md
  2. 写需求：支持按用户名和邮箱模糊搜索
  3. 写约束：分页用现有的 pagination.py
  4. 写涉及文件：users/router.py, users/service.py
  5. 保存，告诉模型去读
  6. 模型读 spec → 读相关文件 → 写代码
  总计：写 spec 10 分钟 + 模型读 spec + 读文件
 
不写 spec，直接对话：
  "给 users/router.py 的列表接口加搜索，
   支持用户名和邮箱模糊搜索，
   分页用现有的 pagination.py"
  模型直接读文件 → 写代码
  总计：说一句话 30 秒
 

对于 2-3 轮能搞定的事，写 spec 的心智负担（想清楚要写什么、打开文件、组织语言、维护文件）远大于直接在对话里说清楚。 spec 是给复杂决策用的，不是给简单功能用的仪式感。

持续维护的 spec 没及时更新会怎样

影响链条：
spec 过时
  → 模型读了旧 spec，按旧约束写代码
    → 代码和实际需求不一致
      → 你发现不对，让模型改
        → 模型又读了旧 spec，又按旧约束改
          → 死循环：只要 spec 还在误导，改多少次都不对
 

过时的 spec 不只是"没用"，它是主动的破坏源。模型不会质疑 spec 的正确性——对模型来说，docs/ 里写的比对话里说的更"权威"。

防御方法很简单：在每个 spec 文件顶部加一行最后更新时间和适用版本：

docs/api-spec.md
 
> 最后更新：2024-03-15 | 适用版本：v2.1
> 如果这个 spec 和代码冲突，以代码为准
 
## 接口规范
...
 

在 CLAUDE.md 里加一条全局规则：

CLAUDE.md 追加：
  开发前先检查 docs/ 下 spec 的最后更新时间，
  如果超过 2 周未更新，先 read 相关代码确认 spec 是否仍然有效。
 

大迭代用版本文件夹管理 spec

当项目经历一次大版本迭代——比如从 v1 到 v2，表结构改了、接口改了、业务逻辑改了——老 spec 全部失效，但还留在 docs/ 里污染模型读取。

解决方案：用版本文件夹隔离。

docs/
├── v1/                    ← 老版本 spec（不要读）
│   ├── api-spec.md
│   ├── data-model.md
│   └── module-auth.md
├── v2/                    ← 当前版本 spec
│   ├── api-spec.md
│   ├── data-model.md
│   └── module-payment.md  ← v2 新增
└── gotchas.md             ← 跨版本纠错（一直保留）
 

然后在 CLAUDE.md 里写清楚：

CLAUDE.md：
 
当前版本：v2
开发时只读 docs/v2/ 下的 spec。
docs/v1/ 是废弃版本，不要读取。
 

模型读 CLAUDE.md 就知道去 v2/ 找 spec，不会误读 v1/ 的旧内容。

更进一步：大迭代的 spec 最好不要进 CLAUDE.md 的索引。原因：

CLAUDE.md 里写了 spec 索引：
  "API 设计：docs/v2/api-spec.md"
  → 模型每次启动都读这个文件（即使这次任务跟 API 无关）
 
CLAUDE.md 里不写索引，只在对话里按需指定：
  你："帮我改支付逻辑，读 docs/v2/module-payment.md"
  → 模型只在这一轮读这个文件
  → 其他轮次不会被动加载
 

进索引 = 每轮自动加载；不进索引 = 用到才读。大迭代的 spec 变动频繁，进索引意味着每次都要维护，不进索引意味着用到才指定。对于频繁变动的 spec，不进索引更省心。

spec 维护成本总结

spec 类型维护成本过时后果建议
纠错 spec（gotchas.md）极低（只在踩坑后追加）几乎不会过时强烈推荐
功能级 spec中（改功能时同步改）误导模型，写错代码改功能时必须同步更新
完整项目 spec高（每次迭代都要维护）严重误导，污染所有后续会话大迭代用版本文件夹隔离
不进索引的迭代 spec低（用到才读）只影响用到的会话推荐用于大版本迭代

廉价模型打草稿，强模型精修

上面讲的都是单模型场景。但如果你的项目复杂、token 消耗大，可以用两个模型分工：

GPT-5.6 很强但很贵，智谱 GLM-5.2 便宜很多。策略是：先让廉价模型做一版，再用强模型优化。

第一步：廉价模型（智谱 GLM-5.2）打草稿
  "按 docs/api-spec.md 实现优惠券模块的初版"
  → 模型读 spec → 写出初版代码
  → 代码能跑，但可能不够优雅、边界处理不完善
 
第二步：强模型（GPT-5.6）精修
  "这是优惠券模块的初版代码，帮我优化：
   1. 检查边界情况是否处理完整
   2. 优化代码结构和命名
   3. 补充类型标注和错误处理"
  → 模型在初版基础上优化
  → 产出质量接近 GPT-5.6 直接写
 

为什么有效？强模型在已有代码上做优化，比从零写要省得多。从零写需要理解全部上下文、做架构决策、生成大量代码；优化只需要读现有代码做局部调整。

成本对比（粗略估算）：

方案模型token 消耗效果
GPT-5.6 直接写全程贵模型100%（全价）最好
智谱打草稿 + GPT-5.6 优化廉价 + 贵~40% GPT-5.6 + ~60% 智谱接近最好，省 50%+
智谱全程全程廉价30%够用但不完美

什么时候用这个策略

不是所有任务都值得两步走。

任务类型建议原因
简单 CRUD、单文件改动直接用廉价模型两步走的切换成本大于收益
复杂功能、多模块、需要架构决策廉价打草稿 + 强模型精修强模型在初版上优化效率最高
Bug 修复直接用强模型诊断比实现更重要，弱模型可能误判
代码审查、重构直接用强模型需要理解全局，弱模型容易漏问题
写测试、写文档直接用廉价模型不需要创造力，便宜就行

判断标准：任务需不需要创造力？需要 → 强模型；不需要 → 廉价模型；需要但预算有限 → 廉价打草稿 + 强模型精修。

实操注意事项

草稿和精修之间不要换会话。 在同一个会话里切换模型，让强模型直接看到廉价模型写的代码和对话上下文。如果新开会话，强模型还得重新读 spec + 读代码，省下的钱又花回去了。

精修时给明确指令。 不要只说"优化一下"。告诉强模型具体要优化什么：

✅ "检查这几个方面：
  1. 并发情况下的库存扣减有没有竞态问题
  2. 异常路径是否都处理了（数据库超时、支付失败回调）
  3. 是否符合 docs/gotchas.md 里的约束"
 

不要让弱模型做架构决策。 草稿阶段让弱模型写实现细节没问题，但模块怎么拆、接口怎么设计这类决策最好你自己定或者留给强模型。弱模型的架构决策往往是"能跑就行"，后续改起来更贵。

小结

问题答案
用工具时 SDD 破坏缓存吗？不破坏，工具管缓存，spec 进 messages
调 API 时呢？spec 放 system prompt 且频繁改才会，分层断点能解决
SDD 真正的代价？上下文膨胀——spec 读取累积，窗口更快耗尽
怎么减缓？spec 拆分按需读，工具用 docs/，API 用多断点
上来读全部代码有必要吗？没必要，烧 token + 信息稀释，把架构写进 CLAUDE.md
廉价模型 + 强模型可行吗？可行，廉价打草稿 + 强模型精修，省 50%+

SDD 的价值在于"先想清楚再写代码"。但想清楚的内容也要分层管理——不然你省下的思考时间全花在 token 费用上了。
