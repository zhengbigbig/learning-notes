大家好我是郑同学。EP05 讲了工具调用的三道关。这一篇看另一个方向的接缝（seam，系统中刻意留出的可替换边界）：模型请求从 agent loop 出发到真正的 HTTP 端点之间，隔着的一层——ctx.llm，一个适配器注册表加单一流式接口。dsh 官方接了两个适配器：llm-deepseek 直连 DeepSeek，llm-pi-ai 通用多提供方。这一篇的核心不是「怎么发请求」，而是「谁有权决定哪个 provider 在跑」——dsh 给出的答案是一句值得抄在笔记本上的话：哪些适配器存在是组装，哪些 provider 在跑是用户设置。

先说为什么这层要做成注册表。agent loop 只会一件事：拿着 provider/model 构造请求，调 ctx.llm.stream()。至于 deepseek-official 路由由谁服务、openai 路由存不存在，loop 一概不知。循环是插件，适配器也是插件，它们只在 ctx.llm 这个服务接口上握手。这一篇拆三块：注册的原子性、休眠路由双子、请求失败后的恢复瀑布。

● ● ●

registerAdapter：全成或全不生效

注册表的 API 语义，dsh-llm 的中文 README 写得非常清楚（README.zh.md:13）：

ctx.llm.registerAdapter(providers: string[], adapter: LlmAdapter) 为给定提供方路由注册一个适配器实例。注册要么全部成功，要么全部不生效，并且会随调用 fiber 一起 dispose。返回的句柄还提供 replace(providers)：候选路由集合会在注册状态发生任何变化前完成整体验证，因此与另一适配器发生冲突时，当前路由仍保持注册并继续提供服务。替换会在一次同步操作中完成，不会出现可观察的空档。

拆开读有三层。第一层，原子性：一个适配器声明服务多条路由，其中一条已被别人占有时，其余路由也不会注册进去——半截注册会让系统状态变得不可推理。第二层，replace 的无缝性：配置热更新时适配器先整体验证候选路由集合，验证不过就保持旧注册继续服务，线上请求感觉不到一次失败的换路由。第三层，注册随 fiber dispose：插件卸载时它的路由自动让出，不需要手工清理。

路由的排他性也有明确归属：README 第 31 行写「registerAdapter() 仍拥有提供方路由的排他性」——一个 provider 路由同一时刻只能有一个适配器实例服务。模型元数据（listModels）只是发现用，不构成白名单：适配器可以接受未列出的模型 id，消费方不得仅因模型没列出而拒绝请求。注册表管路由归属，不管模型清单的真伪。

每次拓扑变化（注册、dispose、目录条目增删）后都发一个无载荷的 llm/adapters-updated 事件，消费方据此重新读 listProviders，不轮询。

● ● ●

休眠双子：挂载即零路由，settings 一段就活

最有意思的设计在 llm-pi-ai 这个适配器上。它是「多提供方通用适配器」，基于 pi-ai 库动态解析已配置的 provider/model。dsh-base 组合文件里它的挂载注释值得整段贴（bundle/base/cordis.patch.yml:88-96）：

# The pi-ai multi-provider twin, mounted dormant: zero routes (and no extra
# models in the picker) until a `llm-pi-ai:` settings section supplies provider
# profiles — then those routes register live, keys resolving per request
# through their apiKeyEnv references, and drop again when the section empties.
# Supplying those profiles is exactly what the web Models page does. Which
# adapters exist is composition; which providers run is the user's settings
# document.
- id: llm-pi-ai
  name: '@deepseek-ai/dsh-llm-pi-ai'
 

翻译过来：pi-ai 双子以休眠（dormant）姿态挂载——零路由、模型选择器里不多一条；直到 settings.yaml 里出现 llm-pi-ai: 分节提供了 provider profiles，路由才即时注册存活；分节清空，路由再次归零。进程重启都不需要，因为 dsh-settings-file 是热重载的（patch 文件第 75-79 行的注释：settings 分节覆盖适配器条目 "without a restart"）。

llm-pi-ai 自己的 README 把这套姿态讲得更细（README.zh.md:74）：

providers 也可以为空或整体省略：适配器将以休眠姿态挂载——零路由、模型选择器不多一条——一旦 llm-pi-ai: settings 分节提供了 profile 就即时注册路由，分节清空时随之撤销。

这条注释的最后一句话就是本篇的题眼：哪些适配器存在归组合面，哪些提供方在运行可以完全交给用户的设置文档。组合（composition）决定能力面，设置（settings）决定运行面，两层正交，互不越界。想接一个 OpenAI 兼容网关，不用改任何代码、不用换 bundle，在 settings.yaml 写一个 profile 就行——README 里 acme-gateway 那个手工声明路由的例子就是干这个的。

配置变化时的注册替换同样是原子的：README 第 109 行——路由集合或重试策略任一变化时，插件原子地替换自己的注册，某条路由若已被另一适配器占有，先前的路由继续服务。凭据永远不进配置文件：apiKeyEnv 是按请求解析的引用，密钥本体躺在凭据存储里，配置文件里只有一个环境变量名。

● ● ●

目录与端点询问：配置界面的两块积木

注册表还提供两个面向配置界面的 API。registerConfigurableProviders 声明「可配置提供方目录」——无论路由已注册还是休眠都列出来，每个条目指明所属 settings namespace 和 profile 路径；界面把它和 listProviders() 合并，给每个条目标注存活或休眠。同样全成或全不生效，同样支持 replace——README 第 15 行特意强调：声明集合随配置变化的插件必须用 replace 而不是先 dispose 再注册，后者会在新集合被拒时让目录整个落空。

registerModelDiscovery 回答另一个问题：「这个提供方能服务哪些模型？」——这是配置期针对草稿的操作，以 settings namespace 为键（界面正在新增的提供方还不存在，没有路由可点名）。llm-pi-ai 注册了这样的发现能力，README 的端点询问一节（README.zh.md:121-131）写明了分寸：点名了已安装 catalog 路由的询问直接由 catalog 作答、完全不联网；只有 catalog 未描述的网关路由才真正发 HTTP 询问；回复是界面供用户采纳的候选，什么都不存储，settings.yaml 始终是唯一决定路由服务什么的东西。

● ● ●

llm-retry：恢复策略挂在请求错误的瀑布上

最后一块是失败恢复。先明确一个边界：dsh-llm 服务本身不执行重试。README 的已知限制一节（README.zh.md:96）写得直接：

本服务不执行重试、缓存或速率限制：提供方注册会存储重试策略，但 llm/stream 仍是单次尝试调用包装层。agent loop 会将已验证模型请求失败单独提供给 agent/request-error，其默认行为是保留原始失败；@deepseek-ai/dsh-llm-retry 是共享示例主干加载的可选执行器。

为什么不在 llm/stream 包装层里重试。README 扩展点一节（第 48 行）给了理由：包装层如果在已经发出分片后重试，就没有可持久记录的尝试边界——模型已经吐了一半的话不能当没说过。所以重试上移到 agent loop 的请求错误瀑布：失败发生在步骤边界上，重试边界也就落在那里。

链路是这样的。agent loop 的 step() 里，流式结束时若 finish 是 error 或 aborted，走 agent/request-error 瀑布（agent-loop/src/agent.ts:354-365）：

const finish = assembler.finish
if (finish.kind === 'error' || finish.kind === 'aborted') {
  const action = await this.dispatch.waterfall(
    'agent/request-error', {
      turn,
      step,
      provider: request.provider,
      failure: finish.failure,
      retryPolicy: preparedCall?.retryPolicy,
      signal,
    },
    () => Promise.resolve<RequestErrorAction>(undefined),
  )
 

载荷里带着 retryPolicy——它是 prepareCall 时随精确适配器注册捕获的不可变策略（提供方 profile 里配的 retryPolicy 字段）。监听器返回 { kind: 'retry' } 就重试，返回空就是终态。

llm-retry 插件就是那个默认执行器（llm-retry/src/index.ts）。它先判断失败 code 是否在策略的可重试集合里，然后算退避延迟：优先尊重服务端的 Retry-After，没有就指数退避加抖动（index.ts:58-63 的 localDelay）。最有 dsh 味的是这一段（index.ts:150-153）：

agent.session.append('llm/retry', eventData)
if (!await cancellableDelay(delayMs, fusedSignal)) return
agent.session.append('llm/retry-started', { retryId, turn, step, retry })
return { kind: 'retry' }
 

每一次排定的重试在等待之前就先写进会话日志——模块头注释说的 "Each scheduled retry is durable before its cancellable wait"。进程要是死在退避等待期间，恢复后的会话日志里躺着这次重试的记录，重试计数接着上次的算（previousRetry 从日志里 findLast 查出来，index.ts:182-189）。而且 llm/retry 是非 surface 事件，进日志但不进模型上下文——模型不需要知道自己被重试了几次，账本需要。

还有一个容易被忽略的细节：pi-ai 适配器强制把 SDK 内部的 maxRetries 设为零（llm-pi-ai README 第 119 行）——SDK 重试和 agent 级重试预算叠加会静默翻倍，dsh 选择把重试的全部可见性收拢到一层。

● ● ●

小结

机制语义
registerAdapter路由排他；全成或全不生效；随 fiber dispose
handle.replace候选先整体校验，冲突保旧注册，同步完成无空档
休眠双子挂载零路由；settings 分节激活；清空即撤销
configurable providers存活+休眠全列目录；变化必须用 replace
model discovery问端点只出候选不落盘；catalog 路由离线作答
agent/request-error失败在步骤边界进瀑布；retryPolicy 随注册捕获
llm-retry重试先入日志再等待；llm/retry 不进 surface
