大家好，我是郑同学。上一篇拆完组装线：四个文件叠出一棵 135 行的树。树站好了，谁在驱动它干活？这一篇讲 Agent Loop——dsh 的双层循环。

先看一个真实例子。本机一次 headless 对话（GLM-5.3）：你问「用一句话回答：你现在运行在什么框架里、是什么模型？」，模型答「我运行在 DeepSeek Harness 智能体框架中，底层模型是 GLM-5.3。」这一问一答在会话日志里留下 30 个事件，主干：

seq  事件                    内容
  3  agent/inbox/spliced    next-turn +1     ← 你的提问进收件箱
  4  turn/start             turn=1           ← 开圈：第 1 个 turn
  5  agent/inbox/spliced    next-turn +0     ← 领取：消息出队
  6  step/start             t=1 s=1          ← 开步：第 1 个 step
  7  user/message           （提问正式入库）
 10  request/header         reason=initial, model=GLM-5.3
 14  assistant/chunk        （流式块逐个记账，共 92 个）
106  assistant/message      （完整回复入库）
107  step/end               t=1 s=1          ← 收步
108  turn/end               reason=completed ← 收圈
 

双层循环的意思：外层 turn 是一件事的生命周期——从你发话到模型办完，中间可能调好几轮工具；内层 step 是其中一次「问一次模型 + 干一次活」。一圈至少一步，一步恰好一次模型请求。有活就转，没活就停，新活来了再转——这就是标题里的「心跳」。核心流程一句口诀，全文可对照：

turn 一圈，step 一问；发言领一条，配料整队端；先记账，后动手；执行乱序，入账有序

一、消息从哪进：三个入口，两条队列

你发消息，不是直接打给模型，而是先放进一个收件箱（Inbox）。三个入口对应你的三种动作（agent-loop lib:390）：

// 追加发言：排队开新圈，要唤醒
followup(input) → send(input, 'next-turn', true)
// 中途插话：当前循环的下一步捎上，要唤醒
steer(input)    → send(input, 'next-step', true)
// 静默注入：只放资料，不唤醒
inject(input)   → send(input, 'next-step', false)
 

循环来领活时，规则不对称（agent lib:56）：next-step 队整队端走（插话、工具结果这些配料，多多益善），next-turn 队只领一条——一条正式发言定义一个 turn，第二条排队等下一圈。开篇日志里 seq 3 是投递（+1），seq 5 是领取（纯删除）。

收件箱每个动作先写日志、再改内存。好处：进程崩了重启，重放日志就能把队列原样建回来；消息的来和走都有案可查。

本站输入 → 输出

输入   两个真实动作：
       追问「再详细一点」        → followup → next-turn 队
       干活中途插「别动配置文件」 → steer    → next-step 队
输出   两条队列各就各位；追问等开新圈，插话等下一步捎带

二、循环怎么转：kick 六行，turn 一圈

驱动器本体 kick 只有一段（agent-loop lib:477）。把 kick 和 turn 的主干合在一起看，双层循环就是这个嵌套结构：

private async kick(): Promise<void> {
  // 外层循环：一圈一圈（turn）
  while (await this.turn()) {}
}
 
private async turn(): Promise<boolean> {
  // …开圈记账（seq 4）…
  // 内层循环：一步一步（step）
  while (true) {
    const decision = await this.preStep(...)   // 领取 + 裁决
    const stepEnd = await this.step(...)       // 一次模型请求
    // 没有工具调用 → 本圈收工，跳出内层
    // 有工具调用 → 结果回注队列，继续下一步
  }
  // …收圈记账（seq 108）…
  // 队列还有活 → 返回 true，外层再转一圈
}
 

外层的每次 turn() 是一件事；内层的每圈循环是一次「问模型 + 干活」。驱动器没有任何业务逻辑，只负责判断「还有下一个圈要跑」。拿开篇日志对照：一圈一答的简单场景只转一圈；「帮我改个文件」会在内层转好几步（工具调用 → 结果回注 → 下一步），外层只转一圈。

  •  seq 4 turn/start：开圈记账，圈号 +1；
  •  seq 5-8：领取提问、入库、注入运行时上下文；
  •  seq 6-107：一步——一次完整的模型请求（下一节）；
  •  seq 108 turn/end reason=completed：收圈，终态带着「怎么结束的」（completed / max-tokens / blocked / aborted / error，是枚举不是布尔）。

两个规则知道即可。max-tokens 粘性：某步撞了输出上限，整圈终态锁死为 max-tokens，后面正常完成的步骤不能改写它。出口双检：收圈前先发一个 turn-stopping 事件，监听器还能最后一刻往队列塞活——塞了就继续转，没塞才真正收圈。

本站输入 → 输出

输入   收件箱里有活 + 循环处于 idle
输出   一圈：领取 → 若干步 → turn/end 带终态原因
       队列空 → kick 停转回 idle；又有活 → 再点火

三、一步里发生什么：领取 → 组装 → 流式记账 → 三岔出口

每步开头先过一道裁决（preStep）：领到的消息可以被监听器改写、甚至直接拒绝——权限插件拦敏感操作、压缩插件塞提示，都挂在这里。裁决通过后组装系统提示词、投影运行时上下文（seq 8 那条「Current runtime context」就是它）。

然后是一次模型请求。流式的处理顺序是全篇最值得记住的细节：

for await (const chunk of stream) {
  // 每个流式块：先写进会话日志
  seqs.push(session.append('assistant/chunk', chunk).seq)
  // 再喂给组装器
  assembler.push(chunk)
}
 

先记账，再消费——开篇日志 seq 14-105 的 92 个 chunk 就是这一行一笔笔记的；打字机效果来自日志回放，不是直连模型流。你按停止，已到的半截也会标 interrupted: true 入库，中断同样留下完整记录。

请求本身在发出前被冻结成档案（seq 10，真实日志）：

request/header  reason=initial
                provider=glm  model=GLM-5.3  maxTokens=128000
 

首次必记，之后只在变化时记——两次 change 之间所有请求用的都是同一份配置，查「当时用的什么模型」有据可查。

流结束看三岔出口：撞上限 → 整圈 max-tokens；没有工具调用 → completed，本圈收工（开篇即此路径：模型直接回答，没调工具）；有工具调用 → 执行工具，结果回注队列，本步返回 null 继续下一步。

本站输入 → 输出

输入   领到的提问 + 上下文注入
输出   开篇场景：92 个 chunk + 完整回复入库 → completed
       改文件场景：回复里带工具调用 → null，进入工具执行

四、工具怎么跑：栅栏与滚动池

「帮我改个文件」这类任务，模型的回复里会带工具调用。调度规则一句话：能并行的进池子一起跑，独占的（写文件这类）单独成组当栅栏——栅栏前的池子必须全部结束，栅栏才能跑。池子是有界的滚动池：同时最多 N 个在飞，完成一个补一个，既不一波全发也不串行等待。

真实场景的事件链长这样：

模型回复：改 a.ts、查 b.ts、查 c.ts（按模型给出的顺序）
  ↓ 查询类并行 → 滚动池：3 个同时跑
tool/call  a.ts（写，独占）→ 先等池子清空
tool/call  b.ts、c.ts（查，并行）→ 同时在飞
tool/result b.ts（先完成，先等着）
tool/result c.ts（凑齐后按模型顺序一起入库）
tool/result a.ts（栅栏开跑）
  ↓ 工具结果回注 next-step 队列头
下一步领取 → 模型看到三个结果 → 回复「改好了」→ completed
 

注意 执行可以乱序，入账必须有序：b.ts 先完成也先等着，结果严格按模型给出的顺序写日志——重放日志时调用与结果才对得上。工具结果作为额外上下文回注 next-step 队列头，下一轮领取第一批拿到，模型下一步就能看到结果。

你的动作内部路径日志里看什么

干活中途插话next-step 队 → 下一步捎带步间出现新的 inbox/spliced
模型一直调工具步返回 null → 结果回注 → 下一步tool/call ↔ tool/result 成对
断流/报错监听器表决 retry → 同一步重发同一 step 号下多批 chunk
按停止半截回复标 interruptedassistant/message interrupted:true

排错三项：卡住不回复——看是不是有后台任务没结束、唤醒被锁存；消息没反应——查 agent/inbox/spliced 有没有 +1、裁决有没有把它改空或拒绝；怀疑参数不对——看 request/header 的 change 记录。

收尾重复口诀：turn 一圈，step 一问；发言领一条，配料整队端；先记账，后动手；执行乱序，入账有序。贯穿全篇的一条线：循环是编排者，不是执行者——模型在 llm.stream、历史在会话日志、工具在注册表、消息在收件箱，循环本身只有节奏和裁决。而「先记账再动手」的地基是会话日志——下一篇就拆它：dsh 敢说「模型可见即已记录」，deriveMessages 怎么投影、日志怎么既能重放又能当上下文源。
