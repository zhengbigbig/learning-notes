大家好我是郑同学。EP07 讲完提示词组装，dsh 的「一切皆插件」还剩最后一块最极致的拼图：子 agent 本身。派活是所有 harness 的刚需，但 dsh 把「派活」拆成了一个纯粹的接口，接口后面站着八个提供方——有的在进程内复制自己，有的直接把活儿委派给别家产品。这一篇把这台千军万马拆开看。

先建立一个直觉。传统的 subagent 实现是「写死一种」：代码里 hardcode 子 agent 怎么创建、跑在哪、结果怎么回来。dsh 的做法是把这三个问题全部推给提供方，调用方只见 ctx.subagents 服务 API。提供方决定子 agent 在当前进程、其他进程，还是通过未来的传输方式运行（packages/subagent/subagent/README.zh.md）。这句话是整个家族的纲领。

● ● ●

注册表：一个服务 API 管住所有提供方

入口是 SubagentRuntime 服务，注册在 ctx.subagents 上。它的 API 面很窄（README.zh.md 原表）：

成员含义
registerProvider(provider)按名称注册可信的同进程实现；注册受 effect 作用域约束
getProvider(name)取提供方，不存在返回 undefined
list()按插入顺序列名称
start(name, request)校验请求，等待提供方发布一次性子 agent，返回 SubagentRun

三个细节值得停一下。注册是可逆的——移除注册只阻止新的启动，不撤销已发布给调用方的运行，这是 Cordis 可逆副作用语义在生命周期上的直接应用。start() 在提供方发布（publish）运行时才兑现：发布前的失败由提供方自己清理干净才拒绝，发布后的故障则通过 run 本身结算——责任的分界线画在「发布」这个瞬间。重复名称会明确报错，不做静默覆盖。

● ● ●

进程内三兄弟：spawn、fork、共享驱动器

进程内家族有两个面向用户的提供方，背后共用一个驱动器。

spawn 提供方（subagent-spawn-in-process）创建全新子 Agent：有自己的会话，看不到父 agent 的对话历史，复用宿主的 agent 工厂与 LLM/工具服务。子 agent 获得父 agent 的工作目录和会话谱系，默认继承父 agent 模型，但以空对话开始。

fork 提供方（subagent-fork-in-process）的行为差异只有一处：以父 agent 已完成的对话轮次作为初始内容。这个「已完成」的边界有讲究——父 agent 当前的工具调用轮次还没结束时，日志里有 assistant 工具调用但没有匹配的工具结果，直接复制会给子 agent 一个不平衡的无效会话。所以 fork 会计算截至最后一个 turn/end 的连续前缀：子 agent 能看到父 agent 所有已完成轮次，看不到进行中的轮次；父 agent 还没完成任何轮次时，fork 退化为全新的 spawn。初始内容只传对话历史，子 agent 拿到的是全新的扁平注册作用域，不继承父 agent 的工具限制或权限。

两个提供方都委托给共享的 startInProcessRun 驱动器（subagent-in-process-driver），由它负责取消、深度检查、persona、工具过滤、结果读取和完全停稳后的 dispose。spawn 声明 { outputSchema: true, depthLimit: true, toolFilter: true, persona: true } 四项能力——它控制子 agent 的创建窗口，所以四项全能强制执行。

● ● ●

跨产品四兄弟：把一轮委派给别家

进程外的四个提供方是「一切皆插件」最极致的体现：连子 agent 都可以是另一个产品。

subagent-claude-code：每次接受运行请求，在发起委派的会话工作区中调用官方 Claude Agent SDK，解析原生 claude 可执行文件，提交自包含文本任务，只返回最终答案。它对成功的判定非常严格：SDK 消息流里只有 subtype: "success"、is_error: false 且 result 非空白的消息才算数，且迭代器必须正常结束。

subagent-codex：启动真实的 Codex app-server 子 agent，走 app-server 协议。

subagent-acp：在全新子进程中运行 subagent，作为 ACP（Agent Client Protocol，代理客户端协议）客户端驱动它。子 agent 拥有自己的运行时、会话、模型配置和工具。启动序列是 spawn → ACP initialize → newSession 三步，全部成功才兑现。一个真实的多租户细节：工作目录绝不使用服务器进程自身的 cwd，因为同一个服务器进程会服务来自多个工作区的会话。

subagent-dsh-sdk：通过 TypeScript SDK 启动进程外的另一个 Harness 子 agent——dsh 把自己也注册成了自己的子 agent 提供方。

四个提供方语义各异，但调用方代码一行不改：换个名字，同一套 start(name, request)。

● ● ●

委派三件套：模型怎么用上这台机器

提供方是供给侧，模型侧的消费工具是三个包（家族 README）：

  •  tool-subagent：向模型公开委派操作，注册到 ctx.tools——模型发起「这事交给子 agent」的工具调用；
  •  tool-subagent-control：向模型公开子级消息发送和列举操作——对已发布的子 agent 追加指令、查看状态；
  •  tool-subagent-report：子级运行的汇报通道。

注意这三件套挂在 ctx.tools 上而不是私有通道，意味着它们和其他工具一样过 EP05 讲的三段瀑布：pre-execute 照样能拦、post-execute 照样能改结果。委派不是特权，是普通工具调用。

● ● ●

为什么要抽到这么狠

回头看这个设计解决了什么。如果 subagent 写死在核心里，「换一种子 agent」意味着改核心代码；抽成 seam 之后，加一个提供方就是挂一个插件（EP02 的 patch 行），禁用一个提供方就是摘一行。跨产品四兄弟证明了接口的抽象度——ACP、SDK、CLI 三种完全不同的传输方式装进了同一个 start() 契约。

家族目录本身就是架构图：subagent/（注册表）+ subagent-in-process-driver/（共享驱动器）+ spawn/fork/acp/codex/claude-code/dsh-sdk（六个提供方）+ tool 三件套（消费方），十二个包各管一段，没有一个是上帝模块。

● ● ●

小结

部件职责
subagent/提供方注册表、请求与结果约定、可继续编排
spawn / fork进程内全新子 agent / 继承已完成轮次的子 agent
in-process-driver共享驱动器：取消、深度、过滤、结果、dispose
acp / codex / claude-code / dsh-sdk跨产品委派：子 agent 是别家产品
tool 三件套委派/控制/汇报，走 ctx.tools 普通流水线

口诀：接口一契约，提供方千军；进程内外如换衣，委派原是寻常工具。
