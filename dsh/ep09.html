大家好我是郑同学。拆到最后一集。前九集讲的全部是 dsh-base 这层内核的能力——循环、日志、工具、模型、提示词、子 agent。这一篇看两个问题：同一套内核怎么长出浏览器版和一次性 CLI 两张脸；然后亲手写一个最小插件，把「一切皆插件」从论断变成手感。

先看表层为什么值得单独一集。EP02 讲过组装线：profile 叠 bundle。web 和 headless 就是叠在同一个 dsh-base 之上的两个 bundle，它们的全部差异都体现在各自的 cordis.patch.yml 里，一行内核代码都不用动。

● ● ●

web-app：把浏览器应用挂上去

dsh-web-app 在 base 之上叠加的东西（README.zh.md）：设置 coding persona，插入 Web 宿主行——webserver、API 网关、workspace、投影缓存、存储——加上浏览器插件名录和客户端热重载链，最后挂本包的 web-runtime 粘合插件。

一个安全细节值得单独讲：web-startup 提供方解析 --host 参数时，会拒绝 --host 0.0.0.0，因为 CLI 目前有意不支持绑定所有网络接口。这不是疏忽是设计——默认部署模型是本机使用，暴露到局域网需要用户显式配置受信主机（--trusted-host 可重复传）。

另一个工程细节：printUrl 打印 dsh web: URL 行的时机，要等自身的 Loader 配置树结算之后——兄弟插件失败时不公告一个已经失效的应用地址。启动顺序这种最容易被忽视的边角，写进了表层 bundle 的职责里。

● ● ●

headless：一个任务，一次人生

dsh-headless 是另一个极端：不挂载任何 Host、HTTP server、Web runtime 或浏览器插件，禁用 HMR，插入一个 headless-runner。它的生命周期是一条直线（README.zh.md）：

  1. 01Loader 结算后，runner 读取共享的 ctx.agentDefaultModel；
  2. 02通过 ctx.agents 创建一个全新的持久化 Agent；
  3. 03把任务作为普通用户消息提交，等待完全停稳；
  4. 04flush Session，汇总自己持有的持久化事件区间；
  5. 05最后一条非空 assistant 文本写 stdout；
  6. 06经 ctx.appExit 宿主钩子请求退出——最终 turn/end 完成则退出码 0，否则 1。

注意第 3 步：headless 没有为任务发明新入口，任务就是一条普通用户消息，走的是 EP03 拆过的完整 turn/step 循环。错误码写 stderr、成功时 stderr 保持空、进程不打开任何监听端口——这些约束让 headless 天然适合脚本管道和 CI。

两张脸的对照落在一点上：web 的价值是持续在场，headless 的价值是一次性把事做完。而它们 78 行 base 一字不改。

● ● ●

动手：写一个最小插件

收官动手篇。dsh 官方 cookbook（docs/cookbook/）给了扩展形状的参考模式，动手前先记住 EP01 的五概念里的三条：插件是 Service、注册要可逆、事件做拦截。

第一步：定义插件。 一个 Cordis 插件就是带 name/inject/apply 的对象（docs/cookbook/extension-cookbook.md）：

import { Context } from '@deepseek-ai/cordis'
 
export const name = 'my-first-dsh-plugin'
 
export function apply(ctx: Context) {
  // 第二步：贡献一段提示词（EP07 的段注册表）
  ctx.systemPrompt.section({
    name: 'my-plugin-note',
    order: 50,
    content: '回答前先确认工作目录。',
  })
 
  // 第三步：挂一个事件监听（EP05 的工具瀑布）
  ctx.on('tools/pre-execute', async (exec, next) => {
    // 只观察，委托下游（不调 next() 才是拦截）
    console.log(`[my-plugin] ${exec.name}`)
    return next()
  })
 
  // 可逆注册：apply 的返回值就是 disposer
  return () => {
    console.log('[my-plugin] 卸载，所有注册一并撤销')
  }
}
 

三个动作各对应前面一集：section() 是 EP07 的提示词段、on('tools/pre-execute') 是 EP05 的瀑布监听、返回的清理函数是 EP01 的可逆副作用。这段代码没有一行在改内核，全部挂在文档写明的扩展点上。

第二步：声明成组合包。 按 docs/cookbook/adding-a-package.md 的清单：package.json 用 dsh.bundle 字段指向你的 patch 文件，patch 里插入一行插件条目。

第三步：patch 进 profile。 在你 profile 的 cordis.patch.yml 里按 id 引用：

- insert:
    - id: my-first-plugin
      name: 'your-scope/my-first-dsh-plugin'
 

第四步：验证。 跑 dsh --profile <你的profile> --dump-config，在打印出的配置树里找到你的行；实际对话里触发一次工具调用，终端应出现 [my-plugin] 日志。卸载插件时 disposer 自动跑，提示词段和监听一起消失，像从没来过。

● ● ●

十集总结：一切皆插件的边界与代价

收尾把整个系列收拢。十集走过的路：EP00 插件树总览、EP01 Cordis 五概念、EP02 组装线、EP03 Agent Loop、EP04 会话日志、EP05 工具三瀑布、EP06 LLM seam、EP07 提示词组装、EP08 subagent 八提供方、EP09 双表层与动手。

这套架构的收益前面每集都在兑现：换模型不动内核（EP06）、换子 agent 不动内核（EP08）、加表层不动内核（EP09）。没有特权内核，就没有打不了补丁的死角。

代价也要说全（base README 的「已知限制」写得很诚实）：patch 是整行替换不是深度合并——profile 覆盖必须重述该行需要保留的每个字段；组合层数多了，调试要靠 --dump-config 看实际生效的树；78 行插件的加载顺序靠服务依赖隐式表达，出问题时排查链路比单体内的调用栈长。

一句话总结十集：dsh 用一棵可逆生长的插件树，把 agent 的每个器官都做成了可替换的零件，代价是你得学会读树。
