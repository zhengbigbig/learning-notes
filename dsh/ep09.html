大家好，我是郑同学。EP08 讲完提示词组装，「一切皆插件」还剩最后一块最极致的拼图：子 agent 本身。派活是所有 harness 的刚需，dsh 把「派活」拆成一个纯粹的接口，接口后面站着八个提供方——有的在进程内复制自己，有的直接把活儿委派给别家产品。口诀：

接口一契约，提供方千军；进程内外如换衣，委派原是寻常工具

先建立直觉：传统实现写死一种子 agent（怎么创建、跑在哪、结果怎么回来全在核心代码里）；dsh 把这三个问题全部推给提供方，调用方只见 ctx.subagents 这一个服务 API。

● ● ●

一、注册表：API 面窄到四行

成员含义
registerProvider(p)按名称注册，受 effect 作用域约束
getProvider(name)取提供方
list()按插入顺序列名
start(name, request)校验请求 → 等提供方发布子 agent → 返回 SubagentRun

两个细节：注册是可逆的——摘掉注册只阻止新的启动，不撤销已在跑的运行（EP02 可逆副作用的直接应用）；start() 在提供方发布运行那一刻为界——发布前的失败提供方自己清理，发布后的故障走 run 本身的错误通道。

● ● ●

二、进程内：spawn 与 fork，一个共享驱动器

spawn：全新子 agent——自己的会话、看不到父的对话历史、复用宿主的模型和工具服务，默认继承父的模型，空对话起步。fork：只差一处——以父 agent 已完成的轮次作为初始内容。「已完成」这个边界有讲究：父的工具调用轮次还没结束时，日志里有调用没结果，直接复制会给子 agent 一条残缺消息——所以要等轮次闭合。

两个提供方背后是同一个共享驱动器（in-process-driver），管取消、深度检查、persona、工具过滤、结果读取、完全停稳后的 dispose——共享的不确定性都收在一个地方。

● ● ●

三、跨产品：子 agent 可以是别家产品

「一切皆插件」最极致的四兄弟：

提供方委派给谁
subagent-claude-code官方 Claude Agent SDK，解析原生 claude 可执行文件，只返回最终答案
subagent-codex真实 Codex app-server，走 app-server 协议
subagent-acp全新子进程里的 ACP（Agent Client Protocol）客户端
subagent-dsh-sdk进程外的另一个 Harness——dsh 把自己也注册成自己的子 agent 提供方

四个语义各异，但调用方代码一行不改：换个名字，同一套 start(name, request)。

● ● ●

四、模型怎么用上它：委派三件套

消费侧是三个工具包：tool-subagent（模型发起「这事交给子 agent」）、tool-subagent-control（对已发布的子 agent 追加指令、看状态）、tool-subagent-report（汇报通道）。关键在它们挂在 ctx.tools 上——和其他工具一样过 EP06 的三段瀑布：pre-execute 照样能拦、post-execute 照样能改。委派不是特权，是普通工具调用。

● ● ●

为什么要抽到这么狠

如果 subagent 写死在核心里，「换一种子 agent」= 改核心代码；抽成接缝之后：加一个提供方就是挂一个插件（EP03 的 patch 行），禁用一个就是摘一行。跨产品四兄弟证明了接口的抽象度——ACP、SDK、app-server 协议差异巨大，接口不动。

家族目录本身就是架构图：注册表 + 共享驱动器 + 六个提供方 + tool 三件套，每个目录一个职责。

● ● ●

对照

部件职责
subagent/提供方注册表、请求与结果约定
spawn / fork全新子 agent / 继承已完成轮次
in-process-driver共享驱动器：取消、深度、过滤、dispose
acp / codex / claude-code / dsh-sdk跨产品委派
tool 三件套委派/控制/汇报，走普通工具流水线
