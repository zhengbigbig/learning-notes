大家好我是郑同学。EP01 说 dsh 连 Agent Loop 都是插件，这句话的承重墙是一个叫 Cordis 的插件框架——dsh 以 vendor（内置供应商代码）方式把它整个装进仓库。这一篇拆发动机本身：五个核心概念、四种事件分发模式，读完你就能看懂 dsh 里任何一行插件代码在干什么。

先说 Cordis 解决什么问题。五十多个插件包要协同，最要命的不是功能，是秩序：谁先启动、A 怎么找到 B、A 出事怎么不影响 C、插件卸载了注册的东西谁收走。Cordis 用五个概念把秩序全管了（docs/cordis-primer.zh.md）。

● ● ●

五个概念，一屏说完

一、插件是实现 Service 的对象。 它可以是一个带可选 inject 和 apply(ctx) 字段的函数，也可以是一个 Service 子类。生命周期由 Cordis 挂载到当前上下文中——apply 跑起来，插件就活了。

二、上下文是服务的容器。 一个服务占据一个稳定的 ctx.，比如 ctx.tools、ctx.llm、ctx.sessions。其他插件通过 key 查找服务，而非导入具体实现。这是 EP01 说过的「依赖位置不依赖身份」的机制落点：今天 ctx.llm 后面是 DeepSeek 官方适配器，明天换成多厂商适配器，调用方代码一个字不改。

三、通过 inject 声明服务依赖。 插件声明所需的服务后，会等这些服务就绪才启动。加载顺序通过服务依赖表达，而非手动编排启动序列——这是整个框架里我最喜欢的一句设计宣言，它把「启动顺序」从运维问题变成了类型系统里的声明。

四、类型化事件用于通信。 服务通过 TypeScript 声明合并注册事件名，然后以四种模式分发（下一节专讲）。事件是插件间通信的正式通道，不是调试用的旁路。

五、注册是可逆的副作用。 提示词片段、工具 schema、适配器、监听器通过 ctx.effect() 或 ctx.on() 安装，reload 和 teardown 时会按预期撤销。每个注册都应有对应的 disposer（清理函数）：要么从 ctx.effect() 返回一个，要么用 Cordis 的辅助方法自动处理。

五个概念合起来是一个完整的生命周期承诺：声明式依赖进、可逆注册住、干净卸载出。

● ● ●

调度是怎么发生的：加载器走读

上面第三条说「加载顺序通过服务依赖表达」。这句话在源码里由一台状态机执行，主角叫 Fiber——每个插件被应用一次，就有一个 Fiber 实例跟踪它的一生（vendor/cordis/src/fiber.ts:184）。状态定义原文：

export const enum FiberState {
  PENDING,
  LOADING,
  ACTIVE,
  FAILED,
  DISPOSED,
  UNLOADING,
}
 

逐个翻译：

  •  PENDING：插件已登记，但声明的依赖服务还没就绪——先挂着等
  •  LOADING：依赖齐了，插件的 apply(ctx) 正在跑
  •  ACTIVE：跑完了，插件提供的服务已上架，别的插件可以依赖它
  •  FAILED：apply 或配置校验抛了异常
  •  UNLOADING / DISPOSED：卸载中/已卸净，收尾动作逆序执行

整条链路的驱动者是 Loader（vendor/loader/src/index.ts:65）。它持有配置树，把每行清单 import 成插件模块，然后挂载；挂载时通过一个内部事件把插件和清单行绑在一起，并解析它的 inject 声明：

ctx.on('internal/plugin', (fiber) => {
  // 1. set `fiber.entry`
  if (fiber.parent[Entry.key] && !fiber.entry) {
    fiber.entry = fiber.parent[Entry.key]
    Inject.resolve(fiber.entry!.options.inject, fiber.inject)
  }
  ...
})
 

Inject.resolve 做的事：把清单行里写的依赖，登记到这个 Fiber 上。依赖没来，Fiber 停在 PENDING；任何一个被依赖的服务变 ACTIVE，等待者被唤醒、进入 LOADING。没有启动脚本，没有手动排序——顺序是状态机等出来的：谁依赖谁，谁就晚启动；依赖图有多深，启动波就有多少层。

这也解释了两个日常现象。一是配置写错（比如依赖了一个不存在的服务名），插件不会报错退出，而是一直停在 PENDING——它在等一个永远不会来的服务。二是热重载为什么干净：卸载走 UNLOADING，Fiber 把自己注册过的效果逆序收回，依赖它的 Fiber 掉回 PENDING，新版本挂上来后它们再被唤醒一轮。

● ● ●

四种分发模式：事件的公开契约

Cordis 里每个事件有且仅有一种分发模式，模式是事件公开约定的一部分，不是调用者随手选的。这张表是 primer 文档的原文浓缩：

模式是否 await分发顺序是否有返回值
emit否监听器按注册顺序观察否
waterfall否监听器按注册顺序观察是
parallel是所有监听器并行观察事件否
serial是监听器按注册顺序观察是

四种模式对应四种意图。emit 是广播——发生了件事，感兴趣的看看就走；parallel 是并发扇出——所有关心的人同时干活等全完；serial 是排队——按顺序一个个来，后面的能拿到前面的结果；waterfall 最特殊，它是环绕中间件，dsh 的三大拦截点（agent 请求、LLM 流、工具执行）全用它。

新的 harness 事件会通过 @mode 标签记录分发模式，生成的目录拿它跟声明和分发调用点做交叉校验——模式错了，文档就错了，CI 会说话。

● ● ●

waterfall：(...args, next) 的权力游戏

waterfall 值得单独展开，因为它是 dsh 一切「可拦截性」的基础。监听器收到的参数是事件参数加上一个 next()：调用 next() 会执行下游监听器，下游返回值经由 next() 回到当前层，可以包装后继续往外传；不调用 next() 直接返回，则短路——下游所有监听器不执行。

primer 文档特别强调：对于单决策事件，短路是设计意图。策略监听器在拥有决策权时可以不委托直接拍板，只做观察的监听器则必须委托。这不是漏洞是分工——EP06 会看到工具执行的三段瀑布全靠这个语义实现权限拦截、超时包装、结果改写。

一个工程细节：仅当监听器必须在普通注册之前运行时才用 prepend: true。顺序是注册顺序，先来后到，想插队得显式声明。

● ● ●

为什么这套东西值得单独一集

因为 dsh 的所有「魔法」到最后都是这五个概念的组合。工具的权限闸门是 waterfall；模型适配器的热插拔是 ctx 容器加可逆注册；「哪些插件先启动」没有启动脚本，全是 inject 依赖图的自然结果；配置树的热重载靠注册可逆——旧插件卸干净、新插件挂上来，中间不留垃圾。

框架的最高境界是让「换零件」变成日常操作而不是手术。Cordis 把这个境界做成了 API 面就十几个方法的朴素样子，这是它值得拆的原因。

● ● ●

小结

概念一句话
插件=Service带 inject/apply 的对象，挂载即活
ctx=容器服务按 key 查找，不 import 实现
inject=依赖等服务就绪才启动，无手动排序
事件=通道四种模式是公开契约
可逆=纪律每个注册有 disposer，卸载无痕

口诀：键上认服务，事前先声明；挂载有次序，卸载不留名。
