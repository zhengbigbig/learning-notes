一句口诀贯穿：树长万物，行替千钧——树（插件树）长出万物，一行清单替换千钧之力。

先从最反直觉的地方进门。一般拆一个 agent 项目，第一件事是找主循环——模型调完工具、工具结果回给模型，那个 while 循环在哪。dsh 仓库近 40 个能力域、两百多个 package.json，你从入口文件一路追下去，追不到一个写死的主循环。它不在内核里，因为它根本不是内核：Agent Loop 是一个插件，和计时器插件、沙箱插件并排挂在一棵插件树上。

证据就在每个 profile 的第一层 dsh-base 里。base 的 cordis.patch.yml 是一份 78 行的插件清单，Agent Loop 在里面就是普通的一行（packages/bundle/base/cordis.patch.yml）：

# Agents created at startup. The base stays empty; raw overlays may
# create agents, while Web creates sessions on client request.
- id: agent-loop
  name: '@deepseek-ai/dsh-agent-loop'
  config:
    agents: []
 

注释说得直白：base 里不预建任何 agent，启动时这行插件的配置是空列表。循环、模型适配器、工具注册表、会话日志，全是这棵树上的普通插件，架构文档（docs/architecture.zh.md）开篇的原话是：产品的每一部分都是插件，因此每一部分都可以从配置替换。

自上而下四层：apps/（cli 和 web 两个启动器）→ packages/bundle/（base、web-app、headless 三个组合包）→ packages/ 其余近 40 个能力域（llm 四个包、session、subagent、sandbox、mcp、lsp、skill、compaction……）→ vendor/（Cordis 底座）。能力域的包自己不带入口，全靠 bundle 的清单挂上树——这就是 78 行清单装得下一个 agent 的原因。

配上一次数据流总览：你在网页发一句话，apps/web 起的服务把会话交给 base 挂起来的 agent-loop 插件，它调 ctx.llm 问模型、ctx.tools 跑工具、ctx.sessions 记日志——这条链的每一段，就是这个系列接下来的每一集。

● ● ●

「一切皆插件」到底指什么

这句口号容易说飘，落到 dsh 里有三个可检验的断言。

第一，没有需要打补丁的特权内核。扩展 dsh 的方式是把你的插件挂到别的插件旁边，而不是 fork 内核改源码。官方文档原话：「不存在需要打补丁的特权内核」。

第二，每个插件的注册都是可逆的副作用。提示词片段、工具 schema、适配器、监听器，装上去的时候就在契约里写好了怎么卸下来——插件卸载时所有注册一并撤销，进程里不留残骸。

第三，连「产品形态」都是插件组合出来的。浏览器版的 Web 界面是一个 bundle（组合包），一次性跑任务的 headless 模式是另一个 bundle，两者叠在同一个 base 上，一行内核代码不用动。

这套东西的底座是一个叫 Cordis 的插件框架（dsh 以 vendor 方式内置）。EP01 会专门拆它，这里只需要知道：插件向共享上下文贡献服务，服务占据稳定的 ctx.（比如 ctx.tools、ctx.llm），其他插件按 key 查找服务而不是 import 具体实现——依赖的是位置，不是身份。

● ● ●

和「垂直整合」路线的分野

做个对照帮定位，只对照架构不评价优劣。这个系列之前拆过的 Hermes 桌面版走的是垂直整合：CLI、TUI、桌面、消息网关多个前端，背后一个自家的 Python agent 内核，产品边界清晰。dsh 走的是另一条极端路线：没有内核，只有插件树，连 Agent Loop 这个「内核中的内核」都以普通插件身份挂载。

垂直整合的好处是每一层都能为整体体验专门优化；一切皆插件的好处是没有哪个决定是改不动的。换模型适配器、换文件系统提供方、把子 agent 换成别家产品、把整个 Web 界面换成自己的——在 dsh 里都是「替换一个插件行」，不是「动一次手术」。代价也真实存在：组合层数多了，调试要靠工具看实际生效的配置树（dsh --profile web --dump-config），这个系列后面会反复用到它。

● ● ●

一个循环的自白：我为什么敢把自己做成插件

Agent Loop 敢做成插件，是因为它依赖的东西全部以服务形式存在于 ctx 里：模型请求走 ctx.llm 的流式接口，工具执行走 ctx.tools 的带把关流水线，上下文来自 ctx.sessions 的会话日志，提示词来自 ctx.systemPrompt 的组装。循环自己只做编排——它是最重要的插件，但不是最特殊的插件。

这带来一个很实际的推论：如果你不喜欢 dsh 的默认循环行为，理论上可以写一个自己的 agent-loop 插件，patch 替换那一行，模型和工具原封不动。生态里已经有人这么玩了——官方 README 自己也说，这个仓库是「一个想法、一个官方展示、一个灵感来源，而不是对我们的命令」。
