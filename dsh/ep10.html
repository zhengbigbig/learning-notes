一、两张脸：一个 bundle 的差异

EP03 讲过：web 和 headless 就是叠在同一个 dsh-base 之上的两个 bundle，全部差异都在各自的 cordis.patch.yml 里，一行内核代码不用动。

web-app 叠的是：coding persona、webserver、API 网关、workspace、投影缓存、存储、浏览器插件名录、web-runtime 粘合插件。两个工程细节：--host 0.0.0.0 会被拒绝——默认部署模型是本机使用，暴露局域网要显式配受信主机；打印 URL 要等配置树结算之后——兄弟插件失败时不公告一个已失效的地址。

headless 是另一个极端：不挂任何 Host 和端口，生命周期一条直线——创建全新持久化 Agent → 把任务作为普通用户消息提交 → 等完全停稳 → flush 会话 → 最后一条非空回复写 stdout → 退出（完成则退出码 0）。任务没有专门入口，走的就是 EP04 拆过的完整 turn/step 循环，天然适合脚本和 CI。

对照一句话：web 的价值是持续在场，headless 的价值是一次性把事做完——而它们脚下的 base 一字不改。

二、动手：一个最小插件

第一步，定义插件——带 name/apply 的对象（docs/cookbook/extension-cookbook.md），三个动作各对应前面一集：

import { Context } from '@deepseek-ai/cordis'
 
export const name = 'my-first-dsh-plugin'
 
export function apply(ctx: Context) {
  // 贡献一段提示词(EP08 的段注册表)
  ctx.systemPrompt.section({
    name: 'my-plugin-note', order: 50,
    text: '回答前先确认工作目录。',
  })
 
  // 挂一个工具瀑布监听(EP06)
  ctx.on('tools/pre-execute', async (exec, next) => {
    // 只观察,委托下游;不调 next() 才是拦截
    console.log(`[my-plugin] ${exec.name}`)
    return next()
  })
 
  // 可逆注册:apply 的返回值就是 disposer(EP02)
  return () => console.log('[my-plugin] 卸载,注册一并撤销')
}
 

这段代码没有一行在改内核，全部挂在文档写明的扩展点上。

第二步，patch 进 profile——在你 profile 的 cordis.patch.yml 里插一行（EP03 的语法）：

- insert:
    - id: my-first-plugin
      name: 'your-scope/my-first-dsh-plugin'
 

第三步，验证：跑 dsh --profile <你的> --dump-config，在打印的树里找到你的行；对话里触发一次工具调用，终端出现 [my-plugin] 日志。卸载时 disposer 自动跑，提示词段和监听一起消失，像从没来过。

收益每集都在兑现：换模型不动内核、换子 agent 不动内核、加表层不动内核——没有特权内核，就没有打不开补丁的死角。代价也说全（base README 已知限制）：patch 是整行替换不是深合并，覆盖必须重述保留字段；层数多了调试靠 --dump-config；加载顺序靠服务依赖隐式表达。
