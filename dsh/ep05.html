大家好我是郑同学。EP04 讲了会话日志怎么把一切记录在案。这一篇跟着一次工具调用的旅程走：模型发出 tool-call 之后、结果写回日志之前，中间发生了什么。dsh 的答案是一条三段瀑布（waterfall，环绕式事件：监听器拿到参数和 next，调 next 放行、不调或短路即拦截）：权限在 pre-execute 把关，执行包装在 execute，结果裁决在 post-execute。三段都是插件接口，沙箱、审批、超时、指标、压缩修剪，全部挂在这三道关口上，核心注册表一行策略都不写。

先说为什么拆三段。如果把「检查权限、跑函数、改写结果」做成一个钩子，每个插件都得自己调用工具本体，权限插件和超时插件就互相看不见对方的包装，顺序也无法约束。拆成 pre（裁决要不要跑）、around（环绕怎么跑）、post（裁决结果算不算），每一道关口只回答一个问题，插件之间的组合才是可预测的。dsh-agent-loop 的 README 把整条链列为插件职责清单的第一条：tools/pre-execute → tools/execute → tools/post-execute → 定义拥有的 finalizeContent → tools/result。

● ● ●

第一关 pre-execute：allow、deny、ask

先看事件声明自带的 JSDoc 原文（tools/src/index.ts:143-152）：

/**
 * Allow, deny, or ask before dispatch. `next()` delegates to allow; missing
 * approval support turns `ask` into denial. Async gates must observe
 * `exec.signal`; the registry rechecks cancellation after they settle but
 * never abandons their promise.
 * Scope-filtered dispatch (`@deepseek-ai/dsh-scope`): agent-scoped listeners receive only that agent's calls.
 * @param exec - the pending call (name, parsed arguments, caller agent).
 * @mode waterfall
 */
'tools/pre-execute'(this: Scoped<ToolRuntime>, exec: ToolExecution, next: () => Promise<PreToolDecision>): Promise<PreToolDecision>
 

三种裁决对应 PreToolDecision 类型（index.ts:588-591）：

export type PreToolDecision =
  | { kind: 'allow' }
  | { kind: 'deny'; reason: string }
  | { kind: 'ask'; reason?: string }
 

关键设计有两个。第一个是ask 的降级语义：注释写明 "missing approval support turns ask into denial"——部署里没挂审批服务时，ask 不是放行、不是挂死，而是变成拒绝。实现里给出了区分度的拒绝理由（index.ts:1693-1698）：

const approval = this.ctx.get('approval')
if (approval === undefined) {
  return {
    decision: { kind: 'deny', reason: ask.reason ?? `tool "${exec.name}" requires approval (not yet supported)` },
    approvalCancelled: false,
  }
}
 

审批服务的四种结局一一映射：allowed-once 放行，rejected、cancelled、unavailable 各自给出不同的拒绝文案——模型能分清「用户拒绝了」和「没有审批通道」这两种「不」。fail closed，但失败得可解释。

第二个是瀑布之后的 monotonic guard（单调守卫）：瀑布是可扩展的，监听器顺序决定裁决；但注册表在瀑布之后还有一道自己管理的 guard 层，只有拒绝结果、没有放行结果（index.ts:703-711）：

/**
 * A monotonic execution guard evaluated after every `tools/pre-execute`
 * listener and before the tool body. Returning a reason denies the call;
 * returning `undefined` leaves it unchanged. Because guards have no allow
 * result, listener ordering cannot turn a denial back into permission.
 */
export type ToolGuard = (execution: Readonly<ToolExecution>) => string | undefined
 

注释就是设计文档：guard 没有 allow 结果，监听器顺序不可能把一道拒绝翻回成允许。沙箱策略（dsh-sandbox-policy）走的就是 tools.guard()。权限的「软裁决」交给插件瀑布，安全底线交给单调 guard——两层职责分得清清楚楚。

还有个前置短路值得注意：code 模式折叠（模型只能直接调 run_code）的调用在进入策略管线之前就被拒绝（index.ts:1373-1381 的注释："pre-execute listeners, approval ask, and guards must never observe — or worse, approve — a call that can only fail"）。一个注定失败的调用，不该让审批插件有机会放行它。

● ● ●

第二关 execute：wrapper 只许换 signal，注册表再保险

tools/execute 是 around-dispatch（环绕分发）瀑布，超时、重试、指标包装都挂这里。JSDoc 原文（index.ts:153-163）：

/**
 * Around-dispatch waterfall for timeout, retry, or metrics. `next()` returns
 * a normalized result; wrappers may change only `exec.signal`, while call
 * identity remains immutable. The registry re-fuses the original caller
 * signal before the body, so replacement cannot detach caller cancellation;
 * wrappers must still restore their signal and reach quiescence.
 * ...
 * @mode waterfall
 */
'tools/execute'(this: Scoped<ToolRuntime>, exec: ToolDispatchExecution, next: () => Promise<ToolExecutionResult>): Promise<ToolExecutionResult>
 

wrapper（包装层）可以替换 exec.signal（取消信号）——超时插件就是靠这个把一个带 deadline 的信号塞给工具本体。但这里有个容易忽略的漏洞：如果 wrapper 换上的信号和调用方的原始信号断了链，调用方取消就传不到工具本体了。dsh 的对策写在注释里：注册表在工具本体执行前把原始调用方信号重新熔合（re-fuse）进 wrapper 的替换信号。实现就在 dispatchToolBody（index.ts:1532-1544）：

private async dispatchToolBody(exec: MutableToolRunContext): Promise<ToolExecutionResult> {
  const state = this.cancellationStates.get(exec)
  // ...
  const wrapperSignal = exec.signal
  const fused = fuseToolSignals(state.callerSignal, wrapperSignal)
  const signal = fused.signal
 
  if (isAborted(signal)) {
    fused.dispose()
    return toolAbortedBeforeDispatchResult()
  }
  exec.signal = signal
 

fuseToolSignals（index.ts:1889-1916）把两个信号的 abort 事件接到一个新控制器上——任一来源取消，熔合信号就取消。wrapper 想加超时可以，想甩掉调用方的取消权不行。这是典型的「扩展点自由度 + 注册表兜底不变量」组合。

另一条硬规则：取消从不遗弃在途工作。类文档写明 "Cancellation never abandons the body: a started promise reaches quiescence before its outcome becomes ABORTED"（index.ts:1527-1531）。已经启动的工具承诺会跑到静止点，结果再按「本体是否已启动」归一成两种错误码：ABORTED_BEFORE_DISPATCH（没启动）和 ABORTED（启动了但被取消）。工具自己声明的 timeoutMs 也强调是协作式的：声明它就是承诺自己的实现会响应 signal 达到静止，注册表不做硬杀（index.ts:249-255）。dsh-tool-call-timeout-policy 就是挂在 execute 瀑布上的一个 wrapper 插件。

● ● ●

第三关 post-execute：接受、替换、丰富、拦截

工具跑完了不等于结果直接进日志。tools/post-execute 拿到归一化结果做最终裁决，四种动作用 PostToolDecision 表达（index.ts:593-601）：

export type PostToolDecision =
  | { kind: 'accept'; content?: ContentBlock[]; value?: never; additionalContexts?: UserMessage[] }
  | { kind: 'accept'; value: JsonValue; content?: never; additionalContexts?: UserMessage[] }
  | { kind: 'block'; feedback: ContentBlock[]; additionalContexts?: UserMessage[] }
 

读法：accept 不带字段是原样接受；accept 带 content 或 value 是替换投影（二选一，都带会抛 TypeError）；block 是把结果拦成错误，feedback 就是给模型的纠正性反馈文本；任何一种都能附 additionalContexts——在下一次请求里追加上下文消息，比如重复调用提醒插件（dsh-repeat-tool-reminder）在检测到模型连续三次发同一个调用后补一段提醒。JSDoc 里还有一条：抛了异常的工具也会到达这道瀑布（"thrown tools still reach this waterfall as errors"），失败结果同样可以被监听器改写。

瀑布之后的落点也讲究。归一化结果先过工具定义自己的 finalizeContent（定义拥有的最后一英里内容变换，注册表在调用开始时就快照了这个回调），然后物化（快照+验证+冻结），最后 tools/result 以 emit 模式广播最终冻结结果供观测。整条管线结束时对象被冻结，观察者拿到的是只读视图（index.ts:1657-1660）。

一个真实挂件的例子：dsh-compaction-tool-result-pruner 在 post-execute 上把超长工具结果修剪到预算内；dsh-spill-policy 处理 tools/code-dispatch-log 瀑布，把巨型文本结果替换成「预览 + 定位符」。核心注册表对此一无所知，它只知道有人在三道关口上做了裁决。

● ● ●

作用域：agent 只看见自己的调用

三段瀑布的事件签名里都有一句相同的话：Scope-filtered dispatch: agent-scoped listeners receive only that agent's calls。这是 dsh-scope 包提供的作用域过滤分发：通过 agent.ctx 注册的监听器，只收到该 agent 名下的工具调用事件。多 agent 同进程时，A agent 的权限插件不会被 B agent 的调用打扰；监听器注册在哪个上下文，就天然属于那个作用域，不需要写任何 if。

和它对照的是 tools/change（工具集变更通知），JSDoc 特意声明它是 UNFILTERED 的：工具集变了关系到每个 agent 的下一次提示词组装，全局事件就该全局广播。哪类事件过滤、哪类不过滤，JSDoc 逐个写明——事件契约不靠猜。

● ● ●
