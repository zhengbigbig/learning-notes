大家好，我是郑同学。EP04 结尾留了个尾巴：循环「先记账再动手」，地基是会话日志。这一篇就拆它。

先看真实例子。EP04 那次问答——你的提问、92 个流式块、模型的回答、冻结的请求配置——全部躺在盘上一个 14KB 的压缩文件里：~/.dsh/sessions/<会话id>/session.jsonl.zstd。重开这个会话，界面能逐字复现当时的打字过程，模型能看到一模一样的历史。原因只有一个：从头到尾只有一本账。追加进日志的瞬间事件就被深度冻结——核心流程一句口诀，全文可对照：

只追加，不修改；派生不出错；双轨各管各；前缀即分叉

● ● ●

一、一本账：append 是唯一写入

Session 类的注释开门见山：an append-only log of SessionEvents（一个只追加的事件日志）。内部就一个数组，写入路径只有一个 append 方法（session/src/index.ts:604），核心就三步：

append(type, data) {
  // 1. 快照：一趟遍历同时完成「校验可 JSON 序列化 + 复制」
  const dataSnapshot = snapshotJsonValue(data)
  // 2. 冻结：事件连同嵌套 data 递归只读
  const event = deepFreeze({ type, seq: this.log.length, time: Date.now(), data })
  // 3. 入列：seq 永远等于日志长度
  this.log.push(event)
}
 

真实事件长这样（seq 3，一个字未改）：

{ "type": "agent/inbox/spliced", "seq": 3, "time": 1787371217441,
  "data": { "target": "next-turn",
    "inserted": [{ "text": "用一句话回答：你现在运行在什么框架里…" }] } }
 

seq = log.length 这个连续性契约贯穿全系统：EP04 日志里每条事件带着的 seq，就是它在这本账里的行号。追加不等 I/O——持久化是插件订阅事件异步落盘的事，append 本身只管记账。

● ● ●

二、模型看到什么：只投影三种事件

日志是全量的，但模型不需要全量——turn/start、assistant/chunk 这些对模型没有意义，模型只要消息序列。所以日志之上有一层 surface（表层投影），只有三种事件能进：

const SURFACE_EVENT_TYPES = new Set([
  'user/message',       // 你说的话
  'assistant/message',  // 模型说完的话
  'tool/result',        // 工具执行结果
])
 

模型每步请求前拿历史，走的就是 EP04 见过的 deriveMessages()：

deriveMessages(): Message[] {
  // 增量缓存：只处理上次之后新增的 surface 节点
  for (const seq of surface.nodes.slice(this.derivedNodes)) {
    const msg = this.deriveEventMessage(this.log[seq])
    if (msg) this.derived.push(msg)
  }
  this.derivedNodes = nodes.length
  return [...this.derived]
}
 

拿真实会话数一遍：这本账 110 个事件，模型视角只有 3 条消息——提问（seq 7）、运行时上下文（seq 8）、回答（seq 106）。日志是全量，surface 是模型视角的视图。上下文压缩也不改日志：它追加一个带 replace 标记的新事件，把被遮蔽的节点从 surface 里换掉——原始账面原封不动，随时可以还原。

● ● ●

三、双轨：一条给眼睛，一条给模型

EP04 那段「先记账再消费」的流式代码，落在日志里是同一个回复的两条记录：92 个 assistant/chunk（token 级增量，给界面回放和遥测）+ 1 条 assistant/message（完整消息，进 surface 给模型）。它们的关联字段是真实可查的：

assistant/message  seq=106
  sourceEventSeqs: [14, 15, 16, …, 105]   ← 92 个，一个不少
 

sourceEventSeqs 列出构建这条消息的全部分片 seq——chunk 保真回放，message 面向模型，账是同一本。断流重放时能精确到 token：重放到 seq 60 就是当时屏幕上的样子。

● ● ●

四、可信与分叉：账对不上就当场报错

这本账还有一道可选的校验器（dsh-session/invariant），每个事件追加前过三条规则：seq 严格递增、turn/step 必须配对闭合（turn 没收就来了新 turn/start，报错）、tool/result 必须对应同一步的 tool/call（有果无因，报错）。守的就是标题那句话：凡模型看到的，必能从日志重建。

分叉（fork）在这套设计里是自然推论：取源会话的前缀当种子，建一个新会话。例子：一次改文件任务做到一半想换个思路——把前 50 个事件作为前缀分叉出新会话，带着前半段重新来。唯一的硬约束：分叉点不能落在未闭合的 turn 里（OPEN_TURN 报错）——账可以从前半段重来，但不能从半笔账开始。恢复同理：整个日志作为种子重放，建出一模一样的 surface，轮次编号接着算。

● ● ●

对照：机制与一句话

机制一句话
append-only 日志唯一写入路径；快照+冻结+入列，seq = log.length
surface 层三种消息事件的有序投影；replace 只换视图不动日志
deriveMessages增量投影缓存，只处理新增节点
双轨记录chunk 给眼睛（92 条），message 给模型（1 条），seq 互链
invariantseq 递增/turn 闭合/调用配对，错就当场报
fork/恢复前缀即种子，走同一套校验

收尾重复口诀：只追加，不修改；派生不出错；双轨各管各；前缀即分叉。EP04 的循环+这一篇的日志，合起来就是 dsh 的发动机和账本。下一篇 EP06 讲工具执行的三段瀑布：一个工具调用要闯 pre-execute、execute、post-execute 三道关——权限、超时、结果拦截各归各的关口。
