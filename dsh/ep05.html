大家好我是郑同学。EP03 讲完了 turn/step 双层循环，模型一步接一步地跑。这一篇往下挖一层：每一步循环产生的所有东西，都去了哪里。答案只有一个地方——会话日志（SessionEvent 日志），一个只追加、不修改的事件流。dsh 里模型的上下文、UI 的渲染、会话的分叉恢复、遥测上报，全部是从这一条日志派生出来的，没有任何一个是平行写入的第二份账。

先说为什么这样设计。一个 agent harness 最怕的不是模型笨，而是账对不上：界面显示的回复和重开会话后看到的不一样、恢复会话时上下文少了一段、分叉出去的会话和源会话对不齐。只要所有消费方都从同一个事件流投影，这些不一致就没有产生的土壤。dsh 把这条原则推到了最严格的形式：追加进日志的瞬间就深度冻结，模型可见即已记录，已记录即不可篡改。

● ● ●

一条 append 撑起全部写入

先看日志本身长什么样。Session 类的注释开门见山（packages/core/session/src/index.ts:417-424）：

/**
 * An event-sourced session: an append-only log of {@link SessionEvent}s.
 *
 * Plain class (not a Service) — create live instances via
 * `ctx.sessions.create()` and detached instances via {@link create}.
 * Seeding with an existing event log replays/forks a session.
 */
 

事件溯源（event sourcing，一种把状态变更记录为不可变事件、状态由回放得到的架构）在这个包里不是口号，是字面实现：Session 类内部就一个私有数组和几个缓存字段，写入路径只有一个 append 方法。append 的热路径绝不等待 I/O——持久化是插件的事，订阅 session/event 事件异步落盘；append 本身只做三件事：快照、冻结、入列（index.ts:604-655）：

append<T extends SessionEventType>(
  type: T,
  data: SessionEventMap[T],
  ...opts: T extends SurfaceEventType ? [opts: SurfaceIntent] : []
): SessionEvent<T> {
  const surfaceOpts: SurfaceIntent | undefined = opts[0]
  // ...组装 surface 元数据...
  const dataSnapshot = snapshotJsonValue(data)
  if (dataSnapshot === undefined) {
    throw new Error(`session event "${type}" carries non-JSON-serializable data`)
  }
  // ...
  const event = deepFreeze({
    type,
    seq: this.log.length,
    time: Date.now(),
    data: dataSnapshot,
    // ...
  } as unknown as SessionEvent<T>)
  this.surfaceManager.validateNext(event as SessionEvent)
 

snapshotJsonValue 是一趟遍历里同时完成「校验可无损 JSON 序列化 + 复制」的函数——getter 想在校验时给一个值、存储时给另一个值，在这里就会被拦下。deepFreeze 把整个事件连同嵌套的 data 递归冻结。也就是说，事件从进入日志那一刻起就是只读的，session.events 返回的是按追加失效的冻结快照（index.ts:559-562）：

get events(): readonly SessionEvent[] {
  this.eventsSnapshot ??= Object.freeze([...this.log])
  return this.eventsSnapshot
}
 

seq 永远等于日志长度——seq = log.length 这个连续性契约贯穿整个系统，fork、恢复、重放全部依赖它（index.ts:564-567）。

日志里都记什么。核心事件类型在 types.ts 里逐条声明：turn/start、step/start、user/message、assistant/chunk、assistant/message、tool/call、tool/result、step/end、turn/end，还有 log-only 的 todo/write、request/header 等。有意思的是 SessionEventMap 是合并可扩展的：插件用 TypeScript 的 declaration merging 往里加自己的事件类型（压缩插件的 compaction/*、重试插件的 llm/retry），同一条日志就能装下所有插件的状态。

● ● ●

surface：模型视角的有序投影

事件日志是全量的，但模型不需要全量。turn/start、assistant/chunk 这些事件对模型没有意义，模型只需要消息序列。dsh 在日志之上维护一个 surface 层（表层，产生消息事件的有序投影），只有三种事件能进 surface：user/message、assistant/message、tool/result（surface.ts:15-19）：

const SURFACE_EVENT_TYPES = new Set<string>([
  'user/message',
  'assistant/message',
  'tool/result',
])
 

这三种事件追加时必须带 surfaceOp 标记，取值两种：'append' 尾部追加，或者 { op: 'replace', start, end } 替换一段已有节点——后者是压缩（compaction）用的。surface.ts 的模块注释说得直白（surface.ts:1-9）：

/**
 * Surface layer on top of the session event log: an ordered view of events
 * that produce LLM messages. The append-only log remains the source of truth.
 */
 

日志是唯一真源，surface 是模型视角的视图。压缩不修改日志——它追加一个带 replace 标记的新事件，把被遮蔽的节点从 surface 里换掉，原始日志原封不动。这套替换有完整的校验：replace 范围必须是当前 surface 上真实存在的节点，sourceEventSeqs 必须引用每一个被遮蔽的节点，tool/result 的替换只允许改 content 一个字段（surface.ts:286-317 的 assertToolResultRewrite 连「除 content 外逐字段深比较」都做了）。

● ● ●

deriveMessages：一次投影，处处复用

模型每步请求前要拿消息历史，deriveMessages() 就是那个入口。它的完整实现值得贴一遍（index.ts:726-747）：

deriveMessages(): Message[] {
  const surface = this.surface
  const nodes = surface.nodes
  const generation = surface.replaceGeneration
  if (generation !== this.derivedGeneration) {
    this.derived = []
    this.derivedNodes = 0
    this.derivedGeneration = generation
  }
  for (const seq of nodes.slice(this.derivedNodes)) {
    // Surface sequences are built from this.log — seq is always a valid
    // index by construction.
    const msg = this.deriveEventMessage(this.log[seq]!)
    // A surface node is one of the five message-producing types, but an
    // empty-content assistant/message (a max-tokens step that hosts only
    // usage) derives to null and must not enter the transcript.
    if (msg) this.derived.push(msg)
  }
  this.derivedNodes = nodes.length
  return [...this.derived]
}
 

三个细节。第一，增量缓存：derivedNodes 记录投影到 surface 的第几个节点，每次调用只处理新增节点，复杂度 O(new nodes)；一旦发生 replace（replaceGeneration 变了），缓存整体作废重建。第二，返回的是新数组，但数组里的 Message 对象是共享的、且已经深度冻结的——它们直接复用事件里那份冻结的 data，不需要二次深拷贝，消费者也改不动。第三，空 content 的 assistant/message（max-tokens 截断那步只带 usage）投影为 null 被跳过——不会往请求里塞一条没有内容的 assistant 消息。

逐节点的投影规则 deriveEventMessage 是一个刻意不穷举的 switch（surface.ts:83-114）：

export function deriveEventMessage(event: SessionEvent): Message | null {
  switch (event.type) {
    case 'user/message': {
      return event.data
    }
    case 'assistant/message': {
      if (event.data.message.content.length === 0) return null
      return event.data.message
    }
    case 'tool/result': {
      return event.data.message
    }
    default:
      return null
  }
}
 

注意 user/message 分支上的注释：不要在这里加 之类的包装——框架层保持逐字透传，包装是生产方的事。同一个函数既是实时派生的规则，也是外部重建者回放日志时的规则，一份逻辑两处使用。

● ● ●

双轨：chunk 保真，message 面向模型

同一个模型回复在日志里有两条记录。流式输出期间，每个原始分片（chunk，token 级增量）逐条追加为 assistant/chunk；流结束后，组装完成的整条消息追加为一条 assistant/message，并在 sourceEventSeqs 里列出构建它的全部分片 seq。agent-loop 的 step() 是这么写的（agent-loop/src/agent.ts:347-350、381-390）：

for await (const chunk of stream) {
  signal.throwIfAborted()
  chunkSeqs.push(this.session.append('assistant/chunk', { turn, step, chunk }).seq)
  assembler.push(chunk)
}
// ...
this.session.append(
  'assistant/message',
  {
    turn,
    step,
    message,
    // ...
  },
  { surfaceOp: 'append', sourceEventSeqs: chunkSeqs },
)
 

为什么要双份。assistant/chunk 不进 surface、不派生消息，它的价值是回放保真：UI 重放会话时能逐 token 复现当时的样子，遥测也能拿到 token 级的原始流。assistant/message 才是模型视角，进 surface 参与派生。一条给眼睛，一条给模型，账是同一本。

sourceEventSeqs 这个字段还有个精细语义（types.ts:422-430）：assistant/message 允许携带空数组，表示「已知提供方流为空」；字段缺席则表示旧版或外部事件没有记录来源。空与非空在 dsh 里是两种不同的意思。

● ● ●

运行时不变量：断言模型看到的一切有出处

dsh 还有更狠的一层：可选的 invariant 配套入口。加载 @deepseek-ai/dsh-session/invariant 后，每一个事件的追加都会先过一遍关系校验（invariant.ts:55-166 的 validateEvent）：

function validateEvent(
  trace: SessionTrace,
  event: SessionEvent,
  fail: InvariantFailure,
): SessionTraceTransition {
  if (event.seq <= trace.lastSeq) {
    fail(`seq must strictly increase: saw ${event.seq} after ${trace.lastSeq}`)
  }
  // ...
  switch (event.type) {
    case 'turn/start': {
      if (trace.openTurn !== null) {
        fail(`turn/start ${event.data.turn} while turn ${trace.openTurn} is still open`)
      }
      // ...
    }
    // ...
    case 'tool/result': {
      // ...
      requireOpenStep(trace, 'tool/result', event.data.turn, event.data.step, fail)
      const callId = event.data.message.source.callId
      if (!trace.pendingCalls.has(callId) && !syntheticNotStarted) {
        fail(`tool/result for ${callId} with no prior tool/call in this step`)
      }
      // ...
    }
 

校验的内容包括：seq 严格递增、turn/step 必须配对闭合、tool/result 必须能对应上同一步之内的 tool/call、todo/write 和 request/header 必须落在开放的 turn 里。校验是纯函数——先算出转移、提交成功后再应用（invariant.ts:223-241），一个事件被后续监听器否决也不会污染轨迹状态。

这套断言守的就是本篇标题那句话：凡模型看到的，必能从日志重建。seq 断了、工具结果找不到调用、step 没闭合就来了新消息——任何一条都会当场 fail，而不是等到某天恢复会话时发现历史对不上。

● ● ●

fork 与恢复：前缀即新会话

有了统一日志，fork（分叉）和恢复就是自然推论。SessionStore.fork 的实现核心就一句：取源会话事件的前缀当种子，建一个带谱系元数据的新会话（index.ts:1081-1095）：

fork(source: SessionForkSource, boundary?: number, childSessionId?: SessionId): Session {
  // ...
  const liveSource = this._resolveForkSource(source)
  const seed = this._forkSeed(liveSource, boundary)
  return this.create(childSessionId, {
    seed,
    meta: {
      ...liveSource.header.cwd !== undefined ? { cwd: liveSource.header.cwd } : {},
      parentSession: liveSource.id,
      seedLength: seed.length,
    },
  })
}
 

种子走的是和实时追加完全相同的校验路径：构造函数里逐条验证 envelope、seq 从 0 连续、surface 转移合法（index.ts:508-537），所以一个 fork 出来的会话不可能构造出持久化后端存不下来的状态。fork 有一个硬约束——边界不能落在未闭合的 turn 里，否则抛 OPEN_TURN 错误：一个 turn 做到一半的会话没法分叉，因为分叉的语义就是「带着完整的前半段重新来」。

恢复（resume）同理：从磁盘读出的整个日志作为构造种子，重放建出一样的 surface，轮次编号和派生历史接着算。构造时还会追加一个 session/end-seed 事件标记种子的边界——之后重开一个没动过的会话不会重复加标记，日志不会因为反复打开而悄悄变长。

● ● ●

小结

机制一句话
append-only 日志唯一写入路径；快照+深冻结+入列，seq = log.length
surface 层三种消息事件的有序投影；replace 只换视图不动日志
deriveMessages增量投影缓存；冻结消息共享复用，O(new nodes)
双轨记录chunk 保 token 级回放，message 供模型派生
invariant 配套seq 递增/turn 闭合/调用配对，纯函数校验事后可关
fork/恢复前缀即种子，走同一套校验；OPEN_TURN 拒绝半截轮次

口诀：只追加，不修改；派生不出错；双轨各管各；前缀即分叉。下一篇 EP05 讲工具执行的三段瀑布：一个工具调用要闯 pre-execute、execute、post-execute 三道关，权限、超时、结果拦截各归各的关口——dsh 连「工具怎么被执行」都拆成了三层插件接口。
