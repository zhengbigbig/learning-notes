大家好，我是郑同学。EP06 讲完工具的三道关，这一篇看另一个方向的接缝：模型的请求从循环出发，到真正的 HTTP 端点之间，隔着的一层——ctx.llm。一句话口诀，全文可对照：

注册全成或全不生效；组合定能力，settings 定运行；重试在步骤边界

先看真实状态。本机这份 web 组合挂着两个官方适配器：llm-deepseek（直连 DeepSeek）和 llm-pi-ai（多提供方通用）。循环对它们的了解是零——循环只管拿着 provider/model 调 ctx.llm.stream()，路由由谁服务它一概不知。

● ● ●

一、registerAdapter：全成或全不生效

注册表的语义就一条（dsh-llm README.zh.md:13）：

ctx.llm.registerAdapter(providers, adapter)
  要么全部成功，要么全部不生效
 

拆开是三层。原子性：一个适配器声明服务多条路由，其中一条已被别人占有，其余路由也不注册——半截注册会让系统状态不可推理。替换无缝：配置热更新时先整体验证候选路由集合，验证不过就保持旧注册继续服务，线上请求感觉不到一次失败的换路由。排他性：一个 provider 路由同一时刻只有一个适配器服务。拓扑每次变化发一个 llm/adapters-updated 事件，消费方据此重读列表，不轮询。

● ● ●

二、休眠双子：挂载即零路由，settings 一段就活

最有意思的设计在 llm-pi-ai 上。组合文件里的挂载注释（bundle/base/cordis.patch.yml:88）说得很清楚：

# 挂载即休眠:零路由,模型选择器里不多一条
# 直到 settings.yaml 出现 llm-pi-ai: 分节提供 profiles
#   → 路由即时注册存活
# 分节清空 → 路由再次归零
- id: llm-pi-ai
  name: '@deepseek-ai/dsh-llm-pi-ai'
 

真实用法：想接一个 OpenAI 兼容网关，不改代码、不换 bundle——在 settings.yaml 里写一段 llm-pi-ai: 分节给出地址和模型名，路由立刻活了；删掉这段，路由归零。哪些适配器存在归组合面，哪些提供方在运行归用户的设置文档——两层正交，互不越界。

凭据的边界同样清楚：apiKeyEnv 是按请求解析的引用，密钥本体躺在凭据存储里，配置文件里只有一个环境变量名。

● ● ●

三、llm-retry：重试为什么挂在步骤边界

先划边界：dsh-llm 服务本身不执行重试——README 已知限制写得直接：llm/stream 是单次尝试调用包装层。理由（README 扩展点一节）：包装层如果在已经发出分片后重试，就没有可持久记录的尝试边界——模型吐了一半的话不能当没说过（EP04 讲过：每个 chunk 都已逐条入账）。

所以重试上移到 agent loop 的请求错误瀑布：

step() 流式结束
  ↓ finish 是 error / aborted
agent/request-error 瀑布
  ↓ dsh-llm-retry 挂在这里:按重试策略表决
  ↓ 表决 retry → 同一 step 重新发起请求
  ↓ 默认 → 保留原始失败
 

失败发生在步骤边界上，重试边界也就落在那里——日志里表现为同一 step 号下多批 chunk（EP04 的对照表里就有这条）。

● ● ●

对照：这层接缝的四个积木

积木职责关键语义
registerAdapter注册路由全成或全不生效；路由排他
休眠适配器能力占位组合挂载零路由，settings 分节激活
目录/发现 API配置界面已注册和休眠的都列出；发现是草稿期操作
llm-retry失败恢复挂 agent/request-error，步骤边界重试

收尾重复口诀：注册全成或全不生效；组合定能力，settings 定运行；重试在步骤边界。至此，请求这条线从循环（EP04）、账本（EP05）、工具（EP06）到模型端点（EP07）全部接通。下一篇 EP08 讲 system-prompt：每一步组装一次的段注册表——提示词不是一份写死的文档，而是一堆插件各注册一段、每次请求现拼的清单。
