大家好我是郑同学。EP06 讲了模型请求的出站接缝。这一篇看请求的头部：系统提示词在 dsh 里不是一段写死的文本，而是一个每一步组装一次的段注册表。工具引导、部署 persona、harness 身份、计划模式规则，各自是注册表里的一个段（section），每次模型调用前按顺序拼起来。谁都能贡献一段，agent 还能遮蔽全局段——连「你是谁」这句话都是插件化的。

先说为什么每步组装而不是一会话组装一次。因为段的文本可以是函数：工具目录会变（工具热装卸）、变量会变（当前模型、cwd）、agent 作用域会遮蔽。组装的时机跟着请求走，请求看到什么由组装那一刻的注册表决定。dsh 的 README 第一句就写明：「循环在每个步骤组装一次，并将结果渲染为完整的模型提示词」。

● ● ●

段注册表：order 排序，同名遮蔽

核心 API 是 ctx.systemPrompt.section()，一个段的形状（system-prompt/src/index.ts:53-75）：

export interface PromptSection {
  /**
   * Unique name — a duplicate registration throws (see {@link SystemPrompt.section}).
   */
  readonly name: string
  /**
   * Sections are concatenated in ascending order. Convention: `-100` is the
   * harness identity, `0` the deployment persona, tool guidance uses 100–199;
   * other negative orders also render before the persona.
   */
  readonly order: number
  /**
   * Static text or a provider evaluated at each assembly with that assembly's
   * {@link AssembleContext}. The text may reference `{{variable}}`s — they are
   * interpolated later, by {@link renderPrompt}.
   */
  readonly text: string | ((context: AssembleContext) => string)
 

约定一条数轴：-100 是 harness 身份，0 是部署 persona，100-199 是各工具的引导段，其他负数段排在 persona 之前。段的顺序规范化了「插件加载时序」这个偶然产物——README 的已知限制里明说：共享同一 order 的段按注册顺序打破平局，确定性依赖约定，不依赖加载顺序。

遮蔽规则和 EP05 的工具作用域一脉相承：通过 agent.ctx 注册的段只属于那个 agent，同名时遮蔽全局段。README 第 20 行写明 agent.ctx 只为该 agent 贡献并在该处遮蔽同名全局段。这个机制最典型的用法就是 persona 替换：PERSONA_SECTION 常量和它的注释（index.ts:122-131）：

/**
 * The deployment persona's section name and order. Exported because a
 * composition can replace this slot — an agent preset shadows the
 * deployment's persona with its own — and both sides naming the same section
 * is what makes the replacement work rather than duplicate.
 */
export const PERSONA_SECTION = 'deployment:persona'
 
/** Prompt order of the persona slot; the first section a model reads. */
export const PERSONA_ORDER = 0
 

两边叫同一个名字，替换才不会变成重复。这个常量导出来不是为了好看，是让 agent preset 的作者能精确对准这个槽位。

● ● ●

-100 的开场白与 0 号 persona

服务构造函数里注册了两个自带段（index.ts:353-370）：

constructor(ctx: Context, config: Config) {
  super(ctx, 'systemPrompt')
  this.toolOrder = validateToolOrder(config.toolOrder)
  // Keep harness-owned openers independent of the selected loop plugin.
  if (config.includeHarnessIdentity ?? true) {
    this.section({
      name: 'harness:identity',
      order: -100,
      text: 'You are an AI agent powered by DeepSeek Harness.',
    })
  }
  this.section({
    name: PERSONA_SECTION,
    order: PERSONA_ORDER,
    // The fallback narrows the optional input type; the schema already defaults it.
    text: config.persona ?? '',
  })
 

-100 的开场白就一句固定的话，由 includeHarnessIdentity 开关（默认 true，README：「仅当兼容性部署拥有完整系统提示词时设为 false」）。注释里的理由值得注意：harness 拥有的开场白要独立于所选的循环插件——哪怕 agent-loop 被别的实现替换，这句身份声明还在。

0 号 persona 是唯一由配置直接提供的提示词片段，模板语法用 {{variable}}。变量从哪来。注册表有 ctx.systemPrompt.variable(name, provider) 接口，agent loop 在服务构造时注册了三个（agent-loop/src/index.ts:351-353）：

ctx.systemPrompt.variable('provider', context => context.agent?.options.provider)
ctx.systemPrompt.variable('model', context => context.agent?.options.model)
ctx.systemPrompt.variable('cwd', context => context.agent?.session.header.cwd)
 

所以部署可以在 persona 里写「你在 {{cwd}} 下工作，当前模型 {{model}}」，每个 agent 每次组装各自求值。插值是严格模式（index.ts:258-295 的 interpolate）：未知变量名抛异常、已注册但本次无值抛异常、格式错误的完整组抛异常，孤立无匹配的 {{ 才按字面量放行。README 的说法是「明确失败胜过交付格式错误的提示词」。还有一个安全细节：变量查找用 Object.hasOwn，原型链名称按未知处理，不会被 Object.prototype 的继承成员劫持。

● ● ●

toolOrder：显式声明工具顺序

组装结果里的工具 schema 顺序也是注册表管的。toolOrder 配置是一个名字列表，必须恰好包含一个 标记（index.ts:139-157）：

/** Reserved {@link Config.toolOrder} marker for unlisted tools. */
export const TOOL_ORDER_REST = '<unlisted-tools>'
 
function validateToolOrder(toolOrder: string[] | undefined): string[] | undefined {
  if (toolOrder === undefined) return undefined
  const seen = new Set<string>()
  for (const name of toolOrder) {
    if (seen.has(name)) throw new Error(`toolOrder lists "${name}" more than once`)
    seen.add(name)
  }
  if (!seen.has(TOOL_ORDER_REST)) {
    throw new Error(`toolOrder must contain the "${TOOL_ORDER_REST}" rest entry (where unlisted tools are inserted)`)
  }
  return toolOrder
}
 

已列工具按列表位置排，未列工具按字典序插进标记所在的位置；不配置就整体字典序（compareToolNames 的注释特意说明这是 code-unit 比较，在任何机器上顺序都一样）。错误处理分层：形状问题（重复、缺标记）加载时就抛；点名了不存在工具则是每次组装时抛——README 已知限制里如实承认这个时序差。为什么用中心列表而不是每插件权重。README 指向了设计笔记《显式面向模型工具顺序》，顺序是模型体验的一部分，该由一个地方统一声明。

还有个 complete: true 的段类型：声明自己是完整提示词。组装照常跑完瀑布（工具、上下文、变量都正常解析），然后这个段被恢复为唯一的提示词段。两个 effective complete 段同时存在，组装直接拒绝——「谁是完整提示词」这个问题只能有一个答案。

● ● ●

组装与最后的瀑布

assemble() 的流程（index.ts:467-542）：合并全局层与 scope 链的段、上下文、变量（近处作用域胜出） → 逐提供方收集工具 schema 并做防御性 detach → 应用 toolOrder 排序 → 交给 system-prompt/assemble 瀑布 → 最后落实施 complete 段约束和 runtime-context 抑制。

system-prompt/assemble 是最后一次改写机会。它的 JSDoc（index.ts:19-31）写明：返回值是权威的，但已注册的 complete 段会在瀑布之后被恢复，complete 场景下监听器无法增删该 scope 的提示词段。事件签名带作用域过滤：scoped 监听器只收自己 scope 的组装。注意它和段的 text 函数的区别——text 是声明式的注册期贡献，瀑布是命令式的组装期改写，先规范化再扩展，扩展不破坏规范。

● ● ●

每步组装与 KV Cache 的张力

每步重新组装，最直接的质疑就是缓存：系统提示词是请求前缀，前缀变了，服务端的 KV Cache（键值缓存，推理引擎复用已计算 token 注意力的机制）就得从第一个变化的 token 起重算。dsh 没有回避这个问题——它的每个包 README 里都有一节「KV Cache 影响」，system-prompt 的这节写得最直白（README.zh.md:71）：

只要身份、persona、变量、段文本与顺序的渲染完全相同，前缀就保持稳定。任何变更都可能从第一个变化的系统提示词 token 起使复用失效。

这就是 dsh 自己管理这股张力的方式：不缓存组装结果，而是把「什么会导致前缀变化」写成每个组件的公开契约。工具 schema 一节同样声明「只要可见 schema 集合、渲染与顺序不变，前缀就保持稳定」；会话日志一节声明追加条目保留可复用前缀、replace 操作从首条被遮蔽消息起失效。变量插值是严格抛错而不是静默跳过，也是同一个逻辑——一个悄悄变成 undefined 的变量会无声地改变前缀，明确的失败反而保护了缓存。

实际运行中这套是自洽的：-100 身份是常量；persona 是配置，不随步变；工具目录除非装卸否则稳定；模型变量变了意味着路由变了，缓存本来就该失效。每步组装的成本是确定性的检查，收益是任何注册表变化下一次请求立刻生效——热装卸工具、切 persona、agent 遮蔽，全都不用重启。

● ● ●

小结

机制语义
section()有序段贡献；-100 身份 / 0 persona / 100-199 工具引导
同名遮蔽agent.ctx 的段遮蔽全局；persona 槽靠同名替换
persona 变量{{model}}/{{cwd}}/{{provider}}，严格插值，失败抛错
toolOrder显式列表加标记；缺省字典序
complete 段瀑布后恢复为唯一段；两个 complete 即拒绝
assemble 瀑布最后的权威改写点；作用域过滤分发
KV Cache 契约每包 README 公开「什么会打碎前缀」
