这篇把 9 月 7 日到 9 月 10 日的四个版本打包拆一遍。还是老规矩：所有"新增"论断都对着新旧 npm 包 diff 过，不是复述发布说明——上回把旧源码里就有的闸门当成新变化的教训，还热乎着。

注意版本号从 0.1.3-alpha.2 直接跳到了 0.1.5-alpha.1。我专门翻了 npm 的完整发布列表：0.1.4 从来没发布过，不是漏看。monorepo 里跳号通常意味着内部重号或者整个候选序列被放弃，外部用户无感，但查问题的时候别去找 0.1.4 的 changelog，它不存在。

顺带解释一下这套版本节奏：alpha 是日常迭代线，rc 才是候选冻结。四天里 0.1.5 走完 alpha.1 → alpha.2 → rc.1，说明 alpha 阶段没有出现需要回炉的问题，团队对这批变更的信心不低。

主线一：system prompt 可以热更新，而且不炸缓存

0.1.5-alpha.1 的第一条新增：支持动态修改系统提示词且不破坏 KV Cache，模型需显式声明支持。

这句话信息密度有点高，拆开看。先说为什么这是个难题。KV Cache 的命中条件是前缀一字不差：这一轮请求的开头部分和上一轮完全相同，模型服务方才能复用之前算好的缓存。

而 system prompt 恰恰坐在整个请求的最前缀上，改它一个字，后面所有缓存全部作废，整轮按全价重算。所以在大多数模型上，"动态修改系统提示词"约等于"每轮都放弃缓存"，听起来美好，用起来烧钱。

没机制的时候和有机制的时候，差别长这样：

没有插入行机制：
  轮次1: [system prompt A][对话...] → 缓存命中 ✓
  轮次2: [system prompt A'][对话...] → 前缀变了，全量重算 ✗
 
dsh 的插入行机制：
  [系统段落(包A插入)][工具说明(包B插入)][身份段(包C插入)]
  改包A的段落 → 只有包A那一段负责缓存代价，B、C 的贡献不受牵连
 

第一层是架构。dsh 的 system prompt 不是一整块写死的字符串，而是由各个插件包以"插入行"的方式拼出来的组合。dsh-base 的 README 里有一节专门讲这件事，原文很短但信息量很大：

## KV Cache 影响
 
组合包本身不添加任何请求前缀；
每条插入行所属的包负责各自的缓存影响。
 

缓存责任下放到了每个插入行所属的包：谁往 system prompt 里插内容，谁就负责自己的插入方式对缓存友好。组合层只负责拼装，不碰前缀。这样改其中某一段提示词时，其余段落的贡献者不受牵连，缓存作废的范围被限制在真正变化的那一段。

这套机制打开了什么场景？会话进行到一半换人格、换工具说明，不用再重开会话。以前改 system prompt 等于换一个新会话，上下文全丢；现在可以原地改，缓存还留着大头。

第二层是声明机制：模型必须显式声明"我支持 system prompt 更新"，dsh 才会对它启用这套能力。不声明的模型照旧走老路——提示词在会话开始时定死。这是把兼容性风险关在了适配器层，而不是赌每个模型都能正确处理中途变化的指令。

插入行这个模型其实早就藏在日常使用里了：你装的每个插件、挂的每个 MCP 工具，它们的说明都是 system prompt 里的一段插入行。以前这些内容一变，整个前缀缓存陪葬；现在变更的代价被拆到了每一行头上。

主线二：deepseek-flash 上位，成为新会话默认模型

0.1.5-rc.1 新增了 DeepSeek-V41-Flash（模型名 deepseek-flash），发布说明里写了三个能力点：文本、图片，以及会话历史中的系统提示词更新。

重点不在"多了个模型"，在于新会话的默认模型已经悄悄换成它了。证据在 dsh-base 的 cordis.patch.yml 里，agent-default-model 的挂载配置就三行：

name: '@deepseek-ai/dsh-agent-default-model'
config:
  provider: deepseek-official
  model: deepseek-flash
 

我对照了 0.1.2-rc.1 的同位置文件：整个包里搜不到 deepseek-flash 字样，这个默认值是 rc.1 新写的。

这件事分两种情况看待：如果你在配置文件里显式指定了模型，升级后完全不受影响；如果你一直用默认值跑，新会话会直接切到 V41-Flash。升级前先想清楚你要的是哪个行为。

图片输入这个能力点值得单独说一句。V41-Flash 支持图片，意味着 dsh 的读图能力第一次接入官方默认模型——之前想让它看截图或设计稿，得自己配一个支持视觉的第三方模型，现在默认配置开箱就有。

至于为什么 V41-Flash 能第一个支持 system prompt 动态更新？官方自家模型，适配器声明支持是自己家说了算。第三方模型想跟上，得等各自的适配器显式声明，这是第二层机制决定的节奏。

主线三：Sidebar 三级跳，Detail 面板退役

Web 界面这七天动了一次大手术，节奏是三级跳：

  •  0.1.5-alpha.1：实验性 Sidebar 上线，支持多标签、分栏、全屏，原 Detail 面板还在
  •  0.1.5-alpha.2：加文档预览，Markdown、代码高亮、HTML、PDF、图片都能直接看；模型可以显式"交付文件"
  •  0.1.5-rc.1：Sidebar 转正，原 Detail 面板移除

对使用者的实际意义：以前模型产出一个文件，你得自己去工作区目录里翻。现在会话右侧直接预览，可以用默认应用打开，也可以在文件管理器里定位。

从实验特性到转正只用了两天，连中间那个专门展示详情的 Detail 面板都为新架构让了路，这个迭代速度在严肃工具里不多见。

模型显式"交付文件"这个动作也值得单独记一笔：它把"模型说它做了"和"文件真的在会话里可查"绑在了一起。以前模型回一句"已保存到 xx.ts"，那个路径只是文本；现在交付的文件是会话资产，预览、打开、定位都从 Sidebar 一键完成。

主线四：容易被忽略的工程细节

几个不上头条但实际影响使用的：

  •  所有出站请求现在遵循 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY、NO_PROXY。我在启动器的依赖清单里确认了对应的独立包 @deepseek-ai/dsh-http-proxy 是这版新加的——一个代理环境变量做成一个 Cordis 插件，这很 dsh。公司内网用代理的同学升级后不用再自己想办法了。
  •  子代理支持消息排队、编辑、删除、单条或全部 Steer 与停止。注意 这套能力最早出现在 0.1.3-alpha.2，rc.1 发布说明里的列举是汇总性质，别当成新东西。Steer 的价值在于子代理跑偏时不用整个杀掉重来，插一句话就能纠。
  •  子代理的内置运行时升级：Codex 0.153.4、Claude Code 2.1.263（0.1.5-alpha.1）。显式配置过模型的保持不变，没配置的跟上游默认走。
  •  /feedback 支持独立提交明细反馈，不用接着对话才能提，提交时会附带相关会话内容。
  •  模型探测支持自定义提供商的 models 对象和 Anthropic 原生模型列表，能自动回填模型名、上下文窗口和最大输出 token（0.1.3-alpha.1）。接第三方 provider 时少手写一堆配置。

要不要升级

  •  还在 0.1.2-rc.1 及之前：升。命令一行：
npx @deepseek-ai/dsh@latest
 

升级理由：prompt 热更新、默认模型换新、Sidebar 文件预览，都是日常使用能感知的改进，npx 拉一下新版就行。

  •  配置里显式指定了模型：放心升，默认值变化与你无关，行为完全可预期。
  •  拿它当生产依赖：可以再等一等，rc.1 毕竟还是候选版，等 0.1.5 正式发布更稳。升级前记得看一眼自己的 settings 有没有被默认模型切换影响。

小结

  1. 01七天四版，0.1.4 被跳过没发布，0.1.5-rc.1 是自 0.1.2-rc.1 以来的官方汇总，适合当升级决策点。
  2. 02system prompt 热更新走的是"插件插入行 + 缓存责任下放"的架构，模型需显式声明支持，兼容性风险关在适配器层。
  3. 03deepseek-flash 成为新会话默认模型，还带图片输入；显式配置的用户不受影响，用默认值的升级前想清楚。
  4. 04Sidebar 从实验到转正用了两天，Detail 面板退役；子代理 Steer 那套能力是 0.1.3-alpha.2 就有的，别被汇总说明骗了。

再啰嗦一句 Steer 的使用手感：子代理改代码改到一半方向不对，插一句"只改测试文件，别动源码"就能纠，成本比推倒重来低一个量级。这次把它和排队、编辑、删除打包在一起，子代理才算真正能当同事用。

读完这四版，我自己最大的感受是：dsh 的更新已经不是"加功能"，而是在给插件架构的每个缝隙补上治理机制——缓存责任、声明机制、代理策略都各自有了明确的归属包。架构先行，功能只是顺便。

感兴趣可以拉源码自己 diff 两个版本。

下一篇前瞻，等下一个版本发布再说——按这个节奏，应该用不了太久。
